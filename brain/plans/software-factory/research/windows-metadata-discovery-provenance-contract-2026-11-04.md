## SDK provenance alternatives and stop gates

* **Catalog membership:** Windows documents [WinVerifyTrust catalog member verification](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/ns-wintrust-wintrust_catalog_info) and [catalog hash lookup functions](https://learn.microsoft.com/en-us/windows/win32/seccrypto/cryptography-functions). A future design could verify a trusted catalog signer and actual held member's membership, with an independently selected publisher/trust policy and bounded stable inputs. Documentation does not prove any catalog exists for these particular files or that all SDK closure members are covered. A valid signed neighboring file, catalog signature without member association, publisher text, or directory hash does not bind them. This path would require a separately designed and selected verification implementation, not invocation of an untrusted SDK tool.
* **Authenticated package equivalence:** Microsoft lists [official SDK releases and NuGet feed](https://learn.microsoft.com/en-us/windows/apps/windows-sdk/downloads). A future separately authorized investigation may establish exact package version and authenticated distribution/signature chain and deterministic member mapping, then compare each held installed byte to its corresponding independently authenticated package member with collision-resistant digest and size. Need explicit package identity, integrity authority, transforms/servicing/version correspondence, complete member mapping and stable bounded extraction; available documentation does not establish those facts for these seven bytes. No installer execution or global installation is required by the proposed equivalence principle, but neither acquisition nor equivalence was performed here. Unsupported/unmapped/transformed members remain blocked.
* **Explicit independent SDK-image trust:** root could separately decide to trust a precisely identified image/build and SDK installation scope, provenance, maintainer, update/custody and immutable input selection, including protection through use and exact consumed closure. This is a changed external prerequisite and a versioned source/record contract requiring explicit root decision, separate from the selected OS/WinPS premise. It assumes that the trusted party supplied and protected the selected SDK files; it does not cryptographically authenticate Microsoft origin or prove package membership. A flag, observed path, raw hash or image label alone cannot create this trust. No such SDK trust has been selected here.

Whichever future route root chooses must bind every actual SDK header and library consumed by the build, not extrapolate from seven samples. The accepted builder contract requires actual dependency and resolved-library evidence, stable before/after identities and existing 256-record/512 MiB limits; incomplete closure, absent provenance, ambiguity, drift, inability to fit the cap, or a receipt schema mismatch stops build eligibility for explicit resolution. A change to the current strict signature contract cannot be smuggled in as a successful metadata result. No actual tool tuple, build-only source execution, native/ABI/storage/helper or Windows C1 acceptance is released by this packet.
