# Runtime and SQLite packaging fit

Research date: 2026-10-15. This is a source-based comparison for the accepted local, foreground TypeScript factory. The runtime and database choice remain a product decision. No runtime was installed or exercised, no native platform was qualified, and no performance comparison was performed.

## Finding

Recommend Node.js LTS with built-in `node:sqlite` as the leading path for the initial design. It keeps one ordinary Node runtime, avoids a native addon, and documents the required SQLite capabilities: synchronous prepared statements, incremental row iteration, transactions through SQLite SQL, WAL through a pragma, and a Promise-based SQLite backup API. The main cost is real: Node marks `node:sqlite` as a release candidate, not stable. Keep the use to its documented core surface and treat that status as a risk to qualify and track. This recommendation informs the lifecycle decision; it does not select a runtime or create a version pin.

As of the research date, Node 24.22.0 was the latest LTS and was released on 2026-10-14. Its official release files include native macOS Intel/Apple Silicon, Linux x64/ARM64, and Windows x64/ARM64 binaries. The Node.js 24 SQLite docs say `node:sqlite` became a release candidate in 24.15.0, has no experimental flag requirement, and exposes `DatabaseSync` and `StatementSync` methods that execute synchronously. `statement.iterate()` yields rows incrementally; `sqlite.backup()` returns a Promise and transfers the database in page batches. The SQLite connection can use ordinary transaction SQL through `database.exec()` and enable WAL with `PRAGMA journal_mode=WAL`. The accepted operating model shares one repository store among foreground invocations from separate worktrees and the dashboard. WAL permits readers alongside a writer, but SQLite still serializes writers. Therefore, separate-worktree invocations can contend even if the dashboard read is concurrent; keep write transactions short and handle lock/busy outcomes. [Node.js releases](https://nodejs.org/en/about/previous-releases), [Node.js 24.22.0 release](https://nodejs.org/en/blog/release/v24.22.0), [Node.js 24 SQLite API](https://nodejs.org/download/release/latest-krypton/docs/api/sqlite.html), [SQLite WAL](https://sqlite.org/wal.html).

Node's built-in TypeScript stripping is stable as of Node 24.12.0. It executes erasable TypeScript syntax without a separate runtime transpiler, but does not type-check, ignores `tsconfig.json`, and does not transform TypeScript constructs that require generated JavaScript. A normal TypeScript check/build remains a separate development step. [Node.js TypeScript support](https://nodejs.org/api/typescript.html).

Transactions use ordinary SQLite commands rather than a wrapper. It has a built-in Promise-based online backup. Node's erasable TypeScript execution is stable, but type checking remains separate. | Official Node archives cover the target desktop OS families and common x64/ARM64 architectures, so a local managed runtime can be extracted and invoked by path; the no-global-runtime arrangement is an installation inference from those archives and the accepted operating model. Bun runs TypeScript directly and now includes `bun check`; its SQLite API is synchronous, has transaction helpers and row iterators, supports WAL, and can serialize/deserialize database bytes. The reviewed SQLite API page has no module-specific stability label and documents no dedicated file-to-file online backup operation. Serialization is an in-memory byte representation, so using it as a backup would add explicit file writing and whole-image memory handling. The idle-only migration policy means online backup is not a requirement. Inference: a checkpointed, closed-file backup may suffice, but that path remains unqualified and must account for Bun's macOS WAL sidecar behavior. | Bun ships as a single dependency-free executable with direct downloads for macOS x64/ARM64, Linux x64/ARM64 and musl, and Windows x64/ARM64. Docs state macOS 13+, Windows 10 version 1809+, and Linux glibc 2.17+ or musl requirements. A per-repository binary is feasible by downloading the official target asset, an inference from the documented direct downloads. A WAL edge matters for this history store: Bun uses Apple's system SQLite on macOS, where WAL and SHM sidecars persist after close; it statically links SQLite on Linux and Windows, where they normally disappear after the last connection closes. Its docs prescribe disabling persistent WAL and checkpointing on close for uniform cleanup. All three database choices expose synchronous query calls. The implication that they block the JavaScript thread follows from their documented synchronous APIs. Their row iterators avoid collecting every result in an array, but they are synchronous iterators, not asynchronous database streams. Because accepted policy retains history without a fixed upper bound and permits invocations from separate worktrees to share the database, no source evidence establishes that a full-history scan or the expected write load will remain responsive. This is a qualification gap, not evidence for or against an option. Keep queries bounded and write transactions short, then measure growth and contention before deciding whether to offload database work. `better-sqlite3` documents worker-thread support for large or slow queries, but no evidence here justifies adding that execution path now. The Node and better-sqlite3 online backup APIs are available; under the accepted idle-only migration policy they are convenience capabilities, not a reason on their own to select either driver. [Node.js 24 SQLite API](https://nodejs.org/download/release/latest-krypton/docs/api/sqlite.html), [better-sqlite3 README](https://github.com/WiseLibs/better-sqlite3/blob/v13.0.3/README.md), [Bun SQLite API](https://bun.sh/docs/runtime/sqlite), [SQLite WAL](https://sqlite.org/wal.html), [accepted history retention policy](../../tickets/operating-and-installation-model.md#resolution), [accepted separate-worktree concurrency](../../tickets/task-scheduling-and-integration.md#exclusive-invocation-ownership).

## Limits and recommendation boundary

The official files establish that distribution artifacts exist; they do not qualify installation, SQLite locking, WAL behavior, SSE responsiveness, or process behavior on the factory's target OS builds. No performance recommendation is drawn from vendor benchmark claims. The exact runtime patch pin should be chosen during implementation from the then-current supported LTS line, with native qualification before claiming platform support.

**UNVERIFIED:** whether Node promotes `node:sqlite` from release candidate before implementation; whether Bun later assigns `bun:sqlite` an explicit stability contract or documents a dedicated online backup; and installation, locking, WAL cleanup, and latency on target OS builds.
