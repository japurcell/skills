## Assessment

SSSF is a strong reference for the requested control boundary: deterministic Python owns workflow ordering, retry limits, validation, persistence, and final acceptance; coding agents work inside named phases and return typed envelopes. This keeps model judgment inside bounded steps while ordinary commands and state transitions remain inspectable code. The repository README calls this “agent proposes, code disposes”; the workflow and agent modules implement that split in the pinned snapshot. See the [README](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/README.md), [agent execution module](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/agents.py), and [workflow runner](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/runner.py).

Its best transferable work is the observability path and package shape. Pi emits JSONL while running; Python forwards normalized events into SQLite; a small Vue interface polls the same event history that it uses for a completed run. The skill itself carries the installer, cookbooks, references, workflow templates, prompts, and visualizer. There are important limits for a broader factory: Pi is the only implemented coding-agent harness, traces do not become an automatic learning loop, and the visualizer does not expose every raw model turn or a first-class skills timeline.

## Stack and package

- The factory runner is Python, invoked with `uv run`. Workflow scripts declare inline dependencies such as Pydantic, python-dotenv, PyYAML, and Rich. The inspected tree did not expose a pinned Python or `uv` version.
- The coding-agent interface invokes Pi's non-interactive JSON mode and reads its JSONL output. Pi can select provider/model pairs from its model catalog, so model diversity is broader than harness diversity.
- Tracing uses Python's SQLite support with WAL. The visualizer is a Bun-served TypeScript and Vue app built with Vite. Its package metadata says visualizer version 0.1.0, Vue `^3.5.13`, TypeScript `^5.7.2`, and Vite `^7`; Bun itself is not pinned in the inspected metadata. See the [visualizer package manifest](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/apps/visualizer/package.json).
- The reusable package is a Claude Code skill rooted at `.claude/skills/sssf/`. It contains `SKILL.md`, lazily loaded cookbooks, references, scripts, visualizer sources, and templates. The installer stamps selected templates into the target repository.

## Lifecycle and reasoning boundary

A run starts in a thin `adw_*.py` entry point. The script loads configuration, validates required agent names and prompts, pins or creates an `adw_id`, then enters one or more named phase context managers. Each phase is either human input, an agent call, or deterministic code. The [simple SDLC workflow](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_simple_sdlc.py) demonstrates plan, build, test, review, documentation, and separate commit phases.

Inside an agent phase, Python renders and saves the compiled system and user prompts, invokes the configured harness, parses the final response against a Pydantic envelope type, runs gates, persists the envelope, and passes that structured result to the next phase. A deterministic phase runs known commands or repository operations directly. The [data types](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/data_types.py) define the envelopes and phase parameters; [gates.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/gates.py) holds mechanical checks.

That gives the reasoning boundary a concrete form:

- Agents read, interpret, plan, implement, or review within one named phase. Their identity, prompt, model, thinking level, tools, and allowed repo writes are configured by agent.
- Python owns the phase order, agent selection, typed output contract, gate evaluation, retry bounds, event writes, and final status. A model's prose does not decide that a run is accepted.
- Known commands belong in code phases. Their failure output can be handed back to a builder through the same envelope-and-correction path as an agent gate failure.
- `run.finish(accepted=...)` separates “all phases executed” from “the requested outcome passed acceptance,” then settles the process exit status and recorded session status together.

The same-session correction loop is a useful mechanism. Malformed output gets an initial parse plus two correction attempts by default. Gate violations get a bounded number of phase-configured correction attempts. Both continue the same Pi session, preserving context; the usage total accumulates across sends. A later ADW can reuse the run ID and agent session map to continue the existing context. See [agents.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/agents.py), [agent_pi.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/agent_pi.py), and [session.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/session.py).

The envelope is also the seam between phases: files can be placed in the runtime handoff area, while the final JSON envelope is parsed, saved, and injected into the next agent's prompt. A type, its prompt's JSON example, and the call site's declared output type are intended to stay synchronized.

## Workflow customization and skill installation

The README lists twelve starter ADWs, from a one-agent prompt or read-only scout to plan/build/test/review/document chains. The workflow contract is ordinary Python rather than a new DSL. New chains can be copied from a nearby script and their phase sequence changed. Agent configuration lives separately in YAML, while prompts are copied into the target repo so teams can edit them there. This separation is a good fit for a reusable skill that bootstraps local, project-owned behavior.

The documented install contract is two steps: copy `.claude/skills/sssf/` into the target repository, then run `/sssf install` in Claude Code or invoke the included installer manually. The [installer](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/scripts/install.py) writes workflow modules, the roster, prompt and harness folders, environment sample, just recipes, and gitignore entries from templates. Existing files are skipped by default. `--force` overwrites them, including user-edited prompts and configuration, so upgrades need an explicit review/backup step. Runtime sessions and the SQLite database are gitignored; prompts and stamped workflow code are tracked.

The install flow is reusable but Claude-specific at the skill front door. The callable Python workflows remain usable from a shell, while other agents do not receive a native skill definition or install command in this repository snapshot.

## Observability: live runs and historical runs

The trace path is one of the repository's strongest ideas. Pi stdout is read line by line; raw JSONL is flushed to disk as it arrives; tool events are normalized and written directly to SQLite. The [tracer](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/tracer.py) records sessions, phases, events, envelopes, gate results, agent sessions, and processes. Events carry run and phase IDs, with a parent ID for nesting. WAL allows UI reads while the workflow writes.

The [observability reference](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/references/observability.md) says SQLite is the queryable mirror and session files are the raw record. It also claims the database can be rebuilt from those files. I did not find a replay or reindex command in the inspected files, so the claimed reconstruction path remains unverified.

The UI uses a rowid cursor query for events, pages through history, then polls for newer rows every 500 ms. The same session and phase detail components render both states; there is no separate replay transport. See the [SQLite event query](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/apps/visualizer/server/db.ts), [API routes](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/apps/visualizer/server/index.ts), and [SessionTrace.vue](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/apps/visualizer/src/components/SessionTrace.vue).

The phase drilldown includes the incoming request, compiled system/user prompts, agent configuration, phase errors, gate results and checks, typed output envelopes, event payloads, tool-call arguments/results, and token/cost detail. Tool-call events are normalized into one row per call. Args and result text are clipped at 20,000 characters by the Pi adapter. The visualizer displays the parsed envelope for valid model responses; invalid parse attempts retain only a bounded raw snippet in the envelope record. The raw Pi JSONL is on disk, but the inspected visualizer API exposes prompts, events, envelopes, and gates rather than a raw transcript endpoint. See [PhaseDetail.vue](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/apps/visualizer/src/components/PhaseDetail.vue), [agent_pi.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/agent_pi.py), and the [visualizer API](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/apps/visualizer/server/index.ts).

There is no first-class `skill` event or skills panel in the inspected trace schema. Agent configuration records Pi harness extensions, tools, model, and prompt paths; it does not record skill activation/use as a normalized event. This is a direct gap against a cross-harness prompt/response/tool/skills/error drilldown.

## Retries, failure handling, and limits

The main reliability mechanisms are bounded correction, explicit gates, evented process tracking, and fail-closed phase status. Phases default to failure and become successful only when their context exits cleanly. Session startup records the parent process before opening phases. SIGTERM and SIGINT handlers close the run as failed so a killed process does not remain falsely marked running. Permission enforcement snapshots the repo before each agent phase, checks changes after agent sends, and rejects/rolls back unauthorized writes. See [runner.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/runner.py), [session.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/session.py), and [permissions.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/permissions.py).

This is still a local synchronous runner, not a durable queue. Process IDs are recorded so an operator can find a hung child; the README's recovery guidance is to inspect the process table and kill it. I found no worker lease, automatic timeout, scheduler, retry-on-process-crash, or checkpoint that resumes the workflow at the failed phase. Reusing an ADW ID preserves artifacts and agent context, but it is not equivalent to durable graph recovery.

The README explicitly calls out further deployment limits: workflows run on the current branch, without a sandbox, branch-per-run, merge step, or human approval phase. It also warns that starter test commands are placeholders that can exit successfully until replaced in quality.py. These are adoption risks, not merely future enhancements.

The `tools` list is not treated as a filesystem permission boundary. `writes` and protected paths are checked after the call because an unrestricted shell could mutate arbitrary paths. The code rolls back unauthorized changes introduced by the agent, but it cannot reconstruct the engineer's pre-existing uncommitted contents if an agent reverts them. Post-call rollback is also not a security sandbox: a shell command may have outside-repository side effects that a Git diff cannot undo. **Inference:** a production design should pair tool allowlists and change checks with a process/container boundary for agents that can execute arbitrary shell commands. See the implementation in [permissions.py](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/permissions.py).

## Adapter and learning support

The pinned configuration defaults every agent to Pi. The `claude_code` coding-agent option is schema-valid but its adapter raises `NotImplementedError`; the agent validator rejects non-Pi harnesses. This means Gemini and OpenAI models can be selected through Pi when present in Pi's provider catalog, but Codex, Copilot, Gemini CLI, OpenCode, and other harnesses are not implemented as interchangeable adapters here. See the [agent validator](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/agents.py), [Claude Code stub](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/adws/adw_modules/agent_cc.py), and [roster template](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/templates/sssf.config.yaml).

SSSF supports human improvement by making prompts, roster, workflows, gates, and trace data visible and editable. It does not implement automatic learning from past runs: I found no evaluator that compares outcomes across runs, no prompt-version experiment loop, and no automatic policy/config update. Same-session correction is short-term recovery, not cross-run self-improvement. The trace UI includes an archive field for review triage, but that is manual organization rather than a learning mechanism.

There is a documentation mismatch in this snapshot. The README and source tree include the visualizer, but the skill's v1 scope says the visualizer ships later and recommends SQLite queries only. That stale instruction can route an orchestrating agent away from a capability that is present. Compare the [README](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/README.md) with [SKILL.md](https://github.com/disler/super-simple-software-factory/blob/de31374882e7a4e3e5b7bb9bd09e69dc2f779356/.claude/skills/sssf/SKILL.md).

## Evidence for the three architecture alternatives

| Alternative | What this source supports | Main gap to close |
|---|---|---|
| Repo runner | SSSF is direct evidence that repo-local Python entry points, YAML agent rosters, editable prompts, and typed phase scripts can form a low-ceremony factory. This is the closest match to the upstream implementation. | Same-branch execution, one implemented harness, manual process recovery, and current install overwrite behavior. |
| Durable graph | Keep the phase/envelope/gate semantics and explicit agent-vs-code split, while persisting step state and attempts as a resumable graph. | Add queue/worker lifecycle, idempotent side effects, checkpointed resume, cancellation/timeouts, and isolated workspaces. |
| Event factory | Treat normalized events, raw artifacts, query APIs, and the trace UI as a boundary independent of workflow execution. Adapter-specific streams can normalize into one live/history schema. | Add events for skills and adapter metadata; preserve full prompt/response/tool/error records with explicit redaction and retention rules. |

These are comparison inputs, not a choice of architecture. A later design can combine a repo runner or durable graph with an event factory.

## Architectural sketch inferred from the evidence

Human request -> workflow definition and agent roster -> deterministic run controller -> named human, agent, and code phases. Agent phases call a harness adapter, parse a typed envelope, run gates, and either hand off or continue the same session with bounded corrections. Code phases run known commands directly. Each transition writes normalized events and durable artifacts. An event store backs one query/API contract; the same cursor-based UI renders live tails and historical runs.

For the broader requirement, the adapter port would normalize Codex, Copilot, Gemini, OpenCode, Pi, and later harnesses into the same event and result contract. The trace schema should include prompt version, response content or artifact reference, tool calls, skill use, errors, model/harness metadata, and token/cost accounting. A separate improvement stage could compare accepted outcomes, gate failures, reviewer findings, and costs across runs, then propose versioned prompt/workflow changes for human approval. Those are design inferences; SSSF does not implement them.
