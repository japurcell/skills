## Fixture code-root and image custody protocol

The interface is one fixed qualification invocation with a root-owned immutable selection, not a public loader API. It accepts no arbitrary executable, DLL, helper script, token, SID, raw HANDLE, addon path or extra load option from a product caller. Root chooses the fresh fixture parent and a fixed test-case enum; all staged child names are constants.

1. Obtain the normal non-impersonating process identity independently with the documented token/SID calls from the accepted storage packet. Construct the private descriptor in trusted Python from that binary identity. Current TokenUser must be owner; protected non-NULL/nonempty DACL grants only that user, plus optional trusted SYSTEM/Administrators, ordinary full-control ACEs with the required directory inheritance. There is no account lookup or requested new privilege. Verify the returned descriptor/profile independently through the held object, not the candidate canary.
2. `CreateDirectoryW` creates one new random final directory below the preselected trusted parent using explicit `SECURITY_ATTRIBUTES`. ERROR_ALREADY_EXISTS is refusal; no adoption or ACL repair. Create nested code/stage directories individually and exclusively. Never pass a recursive create operation that silently accepts an existing object. Windows applies supplied security at creation on a filesystem supporting persistent ACLs. [CreateDirectoryW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw)
3. Create each fixed output using `CreateFileW(CREATE_NEW)` with explicit private security and noninheritable handles. Copy authenticated bytes, enforce size/count caps, and close owned write handles. Before execution, open final image and JS handles for `FILE_GENERIC_READ` with **FILE_SHARE_READ only**, `OPEN_EXISTING`, `FILE_FLAG_OPEN_REPARSE_POINT`; directories additionally use `FILE_FLAG_BACKUP_SEMANTICS`. Retain directory/ancestor handles with the same read-only sharing. No FILE_SHARE_WRITE or FILE_SHARE_DELETE on code custody. A sharing conflict refuses; never close a pin temporarily to make loading succeed. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
4. Hold the canonical trusted-parent chain, fixture/code directory, exact `node.exe`, fixed JS loader, receipt and `.node` handles before process creation. There must be no acquisition gap across actual load. The exclusive write-to-read transition is allowed only inside the newly private namespace under the cooperative same-user/trusted-host assumption. It is not a defense against an already-open privileged/same-user writer. Parent directory share denial does not alone prevent creation of new children, and share flags do not lock WRITE_DAC/WRITE_OWNER. The private DACL, exact inventory and trusted principals are essential, independent parts of custody.
5. Check disk type, attributes/tag, standard information and FileIdInfo on those exact handles. Reject reparses on every walked component, non-directory parents, non-regular images, delete-pending files, image link count other than one and unusable IDs. Retain volume serial + 128-bit FileId internally. Verify owner/DACL through `GetSecurityInfo` on the same handles, including trusted mutation policy on the external anchor. Its returned descriptor is released once with LocalFree; it cannot atomically exclude concurrent descriptor updates. [handle information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex), [GetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo)
6. Derive normalized volume-GUID final paths from held handles and verify fixed parent/name relationships; reject ADS, UNC/device aliases as external input, ambiguous segments, trailing-dot/space names and all intermediate reparses. The internal canonical representation is volume-GUID + object IDs. The Node-visible absolute DOS path is a single fixed spelling proven to resolve to those held identities under the trusted host DOS namespace. Reopen and compare immediately before process creation, at the pre-load handshake and after the load result. Path or digest equality alone is insufficient. No CWD/DOS-device remapping is performed by a candidate. [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew)
7. Hash the `.node` and executable by reading their held handles, compare with independently selected digests, and validate the exact staged inventory. The actual load still uses a pathname: the pin plus private mutation namespace bridges that pathname to the admitted object under the stated adversary. `LoadLibraryExW` has no supported passed-file-handle image-load route; its `hFile` is reserved/NULL. Do not claim atomic loading from an inspected handle or universal namespace immunity. The selected share mode's coexistence with **actual Node loading** remains a real positive proof gate. No relaxed share mode may be introduced to make that proof green.

Proposed fixture refusal caps: no more than 64 path segments / 4096 UTF-8 path bytes, 16 staged files, 256 MiB staged aggregate, 128 MiB selected Node executable, 4 MiB canary, 1 MiB loader/controller metadata per file; descriptor at most 256 KiB / ACL 64 KiB / 256 ACEs with the tighter accepted trustee policy. These are accepted-input/operation caps, not hard OS-call completion promises, and do not increase any existing product/placement/test bound. No unbounded scan or retry loop is added.

The trusted Python provisioner uses `CreateProcessW` with an explicit full application name for the held pinned `node.exe`, fixed safely quoted arguments, fixed Unicode environment/CWD and private process/thread security. The fixture code spawns no descendants. The two handshakes let the outer controller test retained sharing at real load phases and inspect the module observations while the process remains live. A Node result is provisional until independent outer checks and closure finish.

Use two anonymous output pipes plus fixed stdin control pipe, explicit ownership of every end, immediate parent close of its redundant child ends, and byte caps. A single owner polls bounded available data using PeekNamedPipe and reads only a known available bounded chunk. No concurrent read of the same pipe, user-configurable waiter, blocking read of an empty pipe or worker-reader thread is needed. If the selected controller cannot preserve this single-reader model, resolve that implementation issue before execution instead of silently adding a threading/lifetime strategy.
