# Service-engine operating fit

Checked 2026-10-12 against first-party releases, documentation, package metadata, and CI configuration. The accepted target is a per-repository install with isolated and pinned runtime dependencies, one foreground runner per invocation, automatic recovery of a specifically selected interrupted run on the next invocation, native Windows/macOS/Linux, offline local control, ordinary TypeScript workflow functions with managed operations, durable parallel review and human checkpoints, external agent CLIs, and no stale approvals or duplicate publication. No engine is selected by this report.

## Restate TypeScript

**First-party support.** Restate Server is distributed as one self-contained binary with no external dependencies. The official installation page offers Homebrew, downloadable prebuilt archives, npm packages, and Docker. The stable `1.7.13` release archives list Apple Silicon and Intel macOS plus ARM64 and x64 Linux builds. There is no Windows archive in the release asset table or Windows option on the installation page. Restate's Server CI workflow has no Windows runner. These sources establish no documented native Windows distribution or native Windows CI; they do not establish that a source build or future distribution is impossible. ([Installation](https://docs.restate.dev/installation), [v1.7.13 release assets](https://github.com/restatedev/restate/releases/tag/v1.7.13), [Server CI](https://github.com/restatedev/restate/blob/main/.github/workflows/ci.yml))

Restate's workflow service guarantees a `run` handler once per workflow ID; durable promises can suspend it until a signal or external event arrives. `ctx.run` records managed operations, and the SDK documentation shows external work being triggered through `ctx.run` before awaiting a durable promise. Restate also documents durable fan-out/fan-in where parallel tasks retry, recover, and gather their results. These primitives can represent human checkpoints and parallel review branches. Each branch still needs a stable run/branch key and durable result before repair begins. ([Services and workflow handlers](https://docs.restate.dev/concepts/services/), [TypeScript external events](https://docs.restate.dev/develop/ts/external-events), [parallel work guide](https://docs.restate.dev/guides/parallelizing-work))

**Fit inference and gaps.** The Server, not the foreground TypeScript runner, owns durable invocation state. Once a service endpoint is available, Restate can dispatch/replay pending invocations. The docs establish workflow IDs and replay semantics, but not a foreground mode that resumes only one user-selected run while leaving all other unfinished runs parked. The factory would need to prove that it can route or expose only the selected workflow and that concurrent invocations cannot claim the same run. Restate's documented immutable deployments route new requests to the latest deployment while existing requests continue on their original deployment until completion. That is a useful code-version boundary, but it means the exact old endpoint and workflow code must remain available for interrupted work after a later invocation starts. ([Services and deployment versions](https://docs.restate.dev/concepts/services/))

Restate's Server release notes state that `x.y` to `x.(y+1)` upgrades migrate state automatically without manual data migration. This reduces normal minor-upgrade work, but I found no downgrade guarantee. Pin the Server and SDK per repository, preserve the state directory, and treat rollback as a restore/recovery operation until the selected version pair's downgrade behavior is proven. ([Server README](https://github.com/restatedev/restate), [releases](https://github.com/restatedev/restate/releases))

The SDK's managed operation avoids repeating already-journaled work. It does not make an arbitrary external CLI or publication transaction atomic with Restate's journal: a crash after the external effect but before its result is durably recorded can leave an uncertain effect and a retry. That is the standard external-effect boundary, inferred from the journal/retry model and the documented use of `ctx.run` for external work. Agent CLI calls and publication therefore need stable idempotency keys, process reconciliation, and read-after-write checks. ([TypeScript external event pattern](https://docs.restate.dev/develop/ts/external-events), [Restate design notes on side effects](https://restate.dev/blog/why-we-built-restate))

## DBOS TypeScript

**First-party support.** DBOS TypeScript is a library launched in the application process, but the documented system database is Postgres. Its local guide says to connect to an existing Postgres or start Postgres in Docker with `npx dbos postgres start`; the TypeScript configuration accepts a Postgres URL and does not document SQLite. The latter distinction is important: the SQLite option belongs to DBOS Python, not this SDK. A local Postgres installation can be operated offline after setup, but it remains a persistent service outside the invocation process. ([TypeScript programming guide](https://docs.dbos.dev/typescript/programming-guide), [TypeScript configuration](https://docs.dbos.dev/typescript/reference/configuration), [TypeScript integration requirements](https://docs.dbos.dev/typescript/integrating-dbos))

DBOS recovers a workflow from its last completed step when an executor restarts. Steps may run at least once until their result is checkpointed; transactions through DBOS datasources have separate exactly-once guarantees. Durable messages and `recv` support external events and human checkpoints. Parallel steps may be started in deterministic order and awaited with `Promise.allSettled`; for parallel sequences, DBOS recommends child workflows. These semantics fit parallel reviews if each review is its own persisted branch and the aggregate waits for all branch outcomes. ([Workflow guarantees and parallel steps](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial), [workflow communication](https://docs.dbos.dev/typescript/tutorials/workflow-communication))

Recovery is broader than the accepted per-run policy by default. On one server without Conductor, each application restart recovers **all** workflows that were pending before restart. With `executorID`, a process recovers only pending workflows assigned to that ID and owned by that application. This is useful ownership machinery, but a stable ID can resume multiple old runs, while a fresh per-invocation ID will not match the prior run. DBOS documents workflow IDs as idempotency keys, but not an out-of-the-box policy that starts one runner and recovers exactly one selected unfinished run. A Continue action could select the ID at the UI layer, but the launcher still needs a supported selected-run recovery mechanism and duplicate-dispatch protection. ([Workflow recovery](https://docs.dbos.dev/production/workflow-recovery), [workflow IDs](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial), [concurrent executions](https://docs.dbos.dev/explanations/concurrent-executions))

DBOS's default application version hashes workflow source. Recovery only runs when the application version matches. The documented upgrade procedure is blue-green: retain old code processes until their workflows drain, or use patches while old and new code coexist. Rolling back the latest application version controls new work; it does not make a changed workflow's old code available by itself. A foreground-only model therefore needs versioned code/dependency retention for each unfinished run. The DBOS system schema migrates at launch by default; migrations can be run out of band, and launch fails if the schema is behind. The docs describe forward migration, not schema downgrade. ([Upgrading workflow code](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows), [system database configuration](https://docs.dbos.dev/typescript/reference/configuration), [DBOS schema CLI](https://docs.dbos.dev/typescript/reference/cli))

The integration guide explicitly forbids bundling DBOS and workflow code with Webpack, Vite, Rollup, esbuild, Parcel, and similar bundlers because the workflow registry depends on its runtime structure. That constrains packaging if the factory intends to distribute a bundled Node executable or bundle user-authored workflow files. The official TypeScript CI workflow currently runs on Ubuntu only. The evidence does not certify native Windows behavior, and it does not prove a Windows blocker. ([Integration and bundling restriction](https://docs.dbos.dev/typescript/integrating-dbos), [TypeScript CI](https://github.com/dbos-inc/dbos-transact-ts/blob/main/.github/workflows/test.yml))

As with Restate, wrapping an external agent CLI or publication call in a step gives durable retry/checkpoint behavior, not exactly-once side effects. A crash inside the step after the external action but before the checkpoint can cause the step to be attempted again. The engine cannot decide whether an interrupted CLI is still running, whether it committed, or whether a review approval still applies to the current proposal. Those require factory-level effect keys, process discovery/reconciliation, and approval binding to an immutable proposal or plan digest. ([Workflow guarantees](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial), [concurrent execution behavior](https://docs.dbos.dev/explanations/concurrent-executions))

## DBOS Python with SQLite

**First-party support.** DBOS Python supports SQLite or Postgres as its system database and uses a file-backed SQLite database by default. Its official database guide calls SQLite excellent for prototyping and testing, says it cannot serve a distributed application running on multiple servers, and recommends Postgres for production. That does not rule out the accepted one-machine local case, but the checked sources do not guarantee concurrent foreground processes safely coordinating recovery against one SQLite file. The Python CI matrix tests both SQLite and Postgres on Ubuntu, not Windows. PyPI metadata calls the wheel OS independent and supports Python 3.10+, which is packaging evidence, not native Windows runtime validation. ([DBOS Python database connections](https://docs.dbos.dev/python/tutorials/database-connection), [Python configuration](https://docs.dbos.dev/python/reference/configuration), [Python CI](https://github.com/dbos-inc/dbos-transact-py/blob/main/.github/workflows/unit-test.yml), [PyPI metadata](https://pypi.org/project/dbos/3.2.0/), [Python package source metadata](https://github.com/dbos-inc/dbos-transact-py/blob/main/pyproject.toml))

SQLite mode changes operational shape from a helper database process to a repository-pinned Python environment plus a durable local file. Its documented workflow/recovery semantics are DBOS semantics, but exact single-file crash recovery, same-machine multi-process ownership, locking, and downgrade behavior remain acceptance questions for this workload. Python DBOS 3.0 changed stored workflow input/output schema: its guide says 3.0 can process workflows created by 2.x, while 2.x cannot process workflows created by 3.0. That is a concrete one-way rollback constraint across that major upgrade; pin versions and keep a recoverable database backup before upgrades. ([Python upgrade guide](https://docs.dbos.dev/python/upgrading))

This is not a storage-only change to the accepted TypeScript contract. DBOS Python workflows are Python functions marked with DBOS decorators. A TypeScript factory could invoke a Python workflow process through an explicit JSON/IPC contract, but that adds a Python interpreter and dependency environment, serialization and error boundary, process lifecycle, and another place to implement run ownership and version retention. The language used internally by an engine is not itself a blocker; the public workflow authoring and invocation contract is what matters. ([Python workflow tutorial](https://docs.dbos.dev/python/tutorials/workflow-tutorial), [Python integration](https://docs.dbos.dev/python/integrating-dbos))

## Installation and offline operation

**Operational inference.** Restate can be pinned as a per-repository npm server package or installed as a versioned binary. It avoids a separate database server, but the factory still has to start or connect to a Restate Server and preserve its data directory across invocations and upgrades. The official local installation supports offline use after artifacts are installed; a first-time npm/Homebrew/download install itself needs access to the package or binary source. The Server's state migration is automated for documented minor upgrades, but old server/SDK binaries and state backups still need a retention and rollback policy. ([Installation](https://docs.restate.dev/installation), [Server version guidance](https://github.com/restatedev/restate#versions))

DBOS TypeScript dependencies can be isolated and pinned per repository, but an isolated local Postgres instance adds OS-specific service installation, startup, persistent data, migration, backup, and shutdown ownership. The official `npx dbos postgres start` path uses Docker; it is a convenience, not a Postgres requirement. An already installed local Postgres can work offline and avoids Docker, while sharing a Postgres service across repositories reduces duplicated services at the cost of service-wide ownership and isolation decisions. DBOS Python with SQLite avoids that database service, leaving a Python environment and managed SQLite file per repository; upgrades still need a compatible code pin and an explicit file-backup/rollback procedure. ([TypeScript programming guide](https://docs.dbos.dev/typescript/programming-guide), [DBOS TypeScript migration CLI](https://docs.dbos.dev/typescript/reference/cli), [Python database connections](https://docs.dbos.dev/python/tutorials/database-connection))

## Continue versus automatic recovery

A UI **Continue** action is a different trigger policy from automatic recovery on the next invocation. If accepted, it could remove the need to recover work merely because the command was launched, and it could let the user explicitly choose the run. It does not remove the need for durable checkpoints, partially completed parallel branch results, one-owner-per-run dispatch, old workflow code, or reconciliation of agent processes and uncertain external effects. It also does not remove Restate Server or DBOS TypeScript's Postgres prerequisite. For either DBOS SDK, default startup still recovers all pending application workflows; a Continue button is only sufficient if the launcher can safely target the selected workflow while leaving other unfinished runs parked. This policy is proposed here for evaluation, not treated as an accepted contract change.

## Conditional fit and acceptance gaps

Restate is the strongest TypeScript durable-execution baseline if a local helper process and its persistent state are acceptable. Its standalone Server avoids a database-server dependency, and its workflow service, durable promises, and immutable deployments map well to long-running review and human checkpoints. The blocking evidence gap is native Windows distribution and validation. Its second major gap is proving selected-run dispatch and versioned endpoint retention under one foreground process per invocation.

DBOS TypeScript is the strongest same-language in-process library baseline. It has explicit workflow IDs, step checkpoints, durable messages, recovery, and version-aware code rollout, but Postgres remains a persistent service and a bundled single-executable workflow package is unsupported by its integration guide. The default all-pending recovery behavior is also a mismatch for selecting one run on Continue or next invocation.

DBOS Python SQLite is the only relevant checked DBOS alternative that removes a separate database server. It is conditional on changing or explicitly bridging the TypeScript workflow contract; its docs recommend Postgres for production, and the required Windows plus multi-process SQLite behavior is not proven by official CI or documentation. Do not cite it as an embedded DBOS TypeScript capability.

Before any engine selection, acceptance evidence should cover:

1. Native Windows install and crash/restart behavior, plus the required macOS and Linux targets. Missing prebuilt binaries or CI jobs are evidence gaps, not proof of impossibility.
2. Two or more simultaneous foreground invocations, with recovery of only the selected run and no claim duplication, even if an old process is merely slow rather than dead.
3. Recovery after killing the runner during parallel reviews, a human wait, and immediately before or after an external CLI/publication effect.
4. Binding each human approval to the exact proposal/plan digest and invalidating it when that input changes.
5. Runtime and workflow version retention for unfinished runs, plus documented system-state backup, forward migration, and rollback policy.
6. Per-repository install, update, and offline operation without modifying application dependencies; for DBOS TypeScript, packaging must retain the DBOS workflow registry unbundled.

No engine was installed, executed, or selected during this research. The closed [local runtime prerequisites findings](../local-runtime-prerequisites/findings.md) remain the baseline for engine/server requirements.
