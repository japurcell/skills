# Copilot and Gemini native permission feasibility

Research date: 2026-10-14. Research only: no installation, credentials inspection, authenticated model request, or product implementation. This updates the uncertainty in [the historical adapter survey](../../harness-adapters.md), without changing that survey.

## Decision

Both harnesses can support dashboard approvals through a live protocol bridge. Prefer **Copilot SDK controlling the local Copilot CLI** and **Gemini CLI ACP over stdio**. A common ACP adapter for both is a credible alternative, but Copilot ACP is explicitly public preview and its product-specific permission behavior still needs conformance tests. Ordinary prompt/headless streaming does not provide a sufficient bidirectional approval interface. A universal handoff to a native terminal cannot be inferred from these protocols.

**Permission equivalence is a dispatch gate.** Switching from CLI UI to SDK/ACP must not silently discard existing deny rules, managed restrictions, sandbox requirements, or approval scope. If the selected interface cannot faithfully retain or enforce a required profile, reject that profile before launch. An SDK allow handler is not evidence that native CLI policy has also approved the operation.

These are feasibility conclusions, not validated adapters. The foreground factory runner can own two independent child processes, persist their events and approval records to repository SQLite, publish dashboard SSE, and route HTTP decisions back to the live child. That is a proposed factory bridge, not a native SSE/HTTP capability. Factory checkpoints survive exit; a native permission callback or JSON-RPC request is not established as durable across process death.

## Copilot control and policy details

**D/S: SDK remains the native harness.** Local SDK setup explicitly launches a chosen Copilot CLI binary and communicates over stdio. This is not GitHub cloud coding agent or `workflow run`, and not a direct model SDK. Pin CLI and SDK together; inspect negotiated protocol version. Current compatibility documentation lists support for protocol v2-v3, with v2 adapters. The SDK also offers other runtime setups, so explicitly choose the local CLI subprocess route. [Local setup](https://github.com/github/copilot-sdk/blob/f9a6c731432bec99b0a63a24cda1e77a29697634/docs/setup/local-cli.md), [SDK client process launch](https://github.com/github/copilot-sdk/blob/f9a6c731432bec99b0a63a24cda1e77a29697634/nodejs/src/client.ts#L3066).

**D/S: structured approval is feasible.** Without a handler, SDK permission events are left pending for manual resolution. Requests carry a `requestId`, kind-specific fields, and optional tool-call identity. Distinguish requested decision scope from reported outcome. Pinned event documentation mentions `session.respondToPermission()`, but the inspected pinned `session.ts` does not define that convenience method; its actual response path is `session.rpc.permissions.handlePendingPermissionRequest({requestId, result})`. Do not implement the documentation shorthand without checking the shipped generated types. Requests already resolved by a permission hook are skipped by handler dispatch. Handler failure attempts a `user-not-available` response; disconnected handlers do not send late responses. [SDK permission guide](https://github.com/github/copilot-sdk/blob/f9a6c731432bec99b0a63a24cda1e77a29697634/nodejs/README.md#permission-handling), [event contract](https://github.com/github/copilot-sdk/blob/f9a6c731432bec99b0a63a24cda1e77a29697634/docs/features/streaming-events.md#permission-and-user-input-events), [dispatch and response source](https://github.com/github/copilot-sdk/blob/f9a6c731432bec99b0a63a24cda1e77a29697634/nodejs/src/session.ts#L1451).

**S/unknown: disconnect is not a demonstrated deny.** Source shows client-side suppression after disconnection and a best-effort unavailable-user response after handler errors. It does not establish what the closed-source runtime does with every pending request on connection loss, abort, or process restart. Do not claim disconnect automatically declines, persists, expires, or later reissues the request. Those outcomes require a runtime fixture. Factory state should record the interruption and uncertainty rather than synthesizing a native denial.

**Documentation conflict found during parent review:** the same pinned compatibility guide says requests are denied without a handler, whereas the Node README explicitly describes pending manual resolution and `session.ts` emits no default reply in that event path. Prefer an explicit tested permission handler/response path; do not rely on either shorthand as a verified runtime default. This conflict does not remove the documented structured response interface. [Compatibility wording](https://github.com/github/copilot-sdk/blob/f9a6c731432bec99b0a63a24cda1e77a29697634/docs/troubleshooting/compatibility.md), [Node permission handling](https://github.com/github/copilot-sdk/blob/f9a6c731432bec99b0a63a24cda1e77a29697634/nodejs/README.md#permission-handling).

**D/S: native scopes differ by surface.** Ordinary CLI `--allow-tool`/`--deny-tool` are invocation-scoped. Tool filtering is separate from authorization. Location consent persists in `permissions-config.json`; permanent URL domains in `settings.json`. SDK compatibility lists those CLI permission switches as CLI-only, with hooks/handlers as alternatives. The SDK must make its own explicit decisions. `approveAll`, `skipPermission`, and bypass options are not acceptable implicit adapter defaults. [CLI configuration storage](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference).

**S: enterprise settings require deliberate preservation.** `enableManagedSettings` is an opt-in SDK bootstrap field, not evidence of equivalent defaults to interactive CLI. Source requires a session token for runtime self-fetch. Host-injected `managedSettings` is startup-only, not persisted, and must be re-supplied on resume; older runtimes may ignore the additive field. A source comment specifies restrictive composition of managed deny/ask and allow lists. Treat missing version support as unavailable, not permission to proceed. This research did not inspect credentials or test policy loading. [SDK settings types](https://github.com/github/copilot-sdk/blob/f9a6c731432bec99b0a63a24cda1e77a29697634/nodejs/src/types.ts#L3082).

**D: hooks are a secondary route.** `permissionRequest` can allow/deny before native rules, with a bounded command-hook timeout (default 30 seconds). It therefore can weaken native checks if misused. Hooks do not preapprove sandbox escape: interactive confirmation remains required for `requestSandboxBypass`. An HTTP hook granting permission requires HTTPS even though some other localhost HTTP hooks are allowed. A notification hook reports a prompt but does not answer it. These constraints make a localhost dashboard hook bridge less straightforward than an SDK/ACP client. [Hook reference](https://docs.github.com/en/copilot/reference/hooks-reference).

## Gemini control and policy details

**S: exact ACP request/response.** v0.64.0 sends `sessionId`, `toolCall` (ID/title/status/kind/content/locations), and native `options` to `connection.requestPermission`. It parses `{outcome:{outcome:"selected",optionId:<native option>}}` or `{outcome:{outcome:"cancelled"}}`, calls the confirmation handler, and updates policy. Select an advertised option; do not invent option strings. Native options include once/reject, session allow, MCP tool/server session allow, and optional future-session approval when enabled. Edit requests can carry old/new text. [Session implementation](https://github.com/google-gemini/gemini-cli/blob/4a0749aceac5643e6f85a36d7420314d85e13b52/packages/cli/src/acp/acpSession.ts#L707), [option construction and response schema](https://github.com/google-gemini/gemini-cli/blob/4a0749aceac5643e6f85a36d7420314d85e13b52/packages/cli/src/acp/acpUtils.ts#L85), [flag deprecation](https://github.com/google-gemini/gemini-cli/blob/4a0749aceac5643e6f85a36d7420314d85e13b52/packages/cli/src/config/config.ts#L363).

**D/S: policy is more than a global allow/deny toggle.** TOML rules can match tool/MCP identity, argument patterns, command prefixes/regex, approval modes, and interactive state. Highest priority wins across tiers; deny is not universally dominant as in Copilot CLI. `default` retains prompts; `auto_edit` approves some edits; `yolo` broadly approves. Pinned docs say workspace `.gemini/policies` is disabled; do not assume repository-local policy files work. The parser supports invocation `--policy` inputs, but scope/precedence and interactions with user/admin rules need a fixture. Preserve existing admin restrictions. Permanent consent has mode scope and is not a pending request. [Pinned policy reference](https://github.com/google-gemini/gemini-cli/blob/4a0749aceac5643e6f85a36d7420314d85e13b52/docs/reference/policy-engine.md), [policy input flags](https://github.com/google-gemini/gemini-cli/blob/4a0749aceac5643e6f85a36d7420314d85e13b52/packages/cli/src/config/config.ts#L346).

**S: cancellation while approval waits requires client participation.** `cancelPendingPrompt` aborts the prompt controller, but the shown permission exchange separately awaits its JSON-RPC response. The ACP standard requires the client to answer outstanding permission requests with cancelled when the prompt is cancelled. Send `session/cancel`, settle each pending request as cancelled, retire its dashboard controls, then observe completion; do not merely hide the dialog. No request timeout or crash-safe replay guarantee was established. [Gemini cancellation source](https://github.com/google-gemini/gemini-cli/blob/4a0749aceac5643e6f85a36d7420314d85e13b52/packages/cli/src/acp/acpSession.ts#L206), [ACP v1 permission contract](https://agentclientprotocol.com/protocol/v1/tool-calls#requesting-permission), [ACP cancellation](https://agentclientprotocol.com/protocol/v1/prompt-turn).

## Concurrency, output, restart, and platform fit

| Concern | Copilot | Gemini | Factory implication |
| --- | --- | --- | --- |
| Two concurrent agents | D: ACP TCP supports multiple clients; SDK exposes sessions and per-session events. | S: ACP manager holds multiple session objects in a map. | Use two independently owned stdio children first. Concurrency feasibility is not a promise that two agents safely edit the same files. |
| Output capture | SDK events include model deltas, tool output/results, completion and usage; protocol stdout must remain separate from stderr. | ACP updates include messages/tools/diffs; headless stream separately has aggregated usage. | Persist original events with provenance. ACP usage completeness is unverified; do not manufacture missing token counts. |
| Stop pending work | SDK `abort()` sends `session.abort`; waiting timeout alone does not abort runtime work. | `session/cancel` plus cancelled replies to outstanding approvals. | Keep runner alive while waiting; terminal approval cancellation is not identical to killing a child process. |
| Resume | D: named SDK sessions and `resumeSession`; hooks/handlers and applicable startup policies need restoration. | D/S: `loadSession` reconstructs chat from stored conversation and creates a new Session/config. | Resume history is not replay of a suspended OS process or guarantee of a live old approval ID. |
| Stale approval | SDK permission events are listed as persisted; a historical event is not proof its pending RPC is live. Closed connection suppresses handler responses. | Source shows live pending request; load reconstructs conversation rather than restoring its Promise. | On runner exit mark approvals stale. After explicit Continue, bind fresh attempt/process epoch and native request ID. Reject old/duplicate HTTP decisions; revalidate current operation before consent. |
| Native Windows | D: CLI supports PowerShell, with PowerShell 6+ prerequisite; WSL is another option, not required for all use. Public engine internals unavailable. | D/S: native Windows documented; shell source prefers `pwsh.exe`, falls back to `powershell.exe`; PTY code explicitly uses ConPTY. | A stdio bridge needs no Unix terminal assumptions. Process-tree cancellation and child-tool I/O must be tested on native Windows. |
| Native macOS/Linux | Both documented. Copilot local sandbox backend/prerequisites differ by OS. | Both documented; shell/PTY paths differ by OS. | Approval policy is not an OS sandbox. Advertise isolation separately and fail if a required backend is unavailable. |

The SDK route changes who renders and answers approvals: the dashboard/runner becomes the client UI. It does not produce a native interactive Copilot terminal. Likewise Gemini ACP is a separate mode from its TUI. A terminal tab may display runner progress or tool output, but should not be described as the native approval UI unless the factory deliberately launches and retains the native interactive CLI in a separately supported mode.

## Validation gaps and next experiment

1. Pin actual binaries and SDK dependency versions; negotiate protocol/capabilities before dispatch. The Copilot safe probe needs an already-extracted permitted installation for future validation. No cache permissions were widened here.
2. In disposable authenticated workspaces, prove once/reject/session approvals for write, shell, URL, MCP, path expansion and sandbox escape, including requests that native policy preapproves or denies. Verify SDK managed-policy parity rather than assuming it.
3. Record two concurrent sessions with independent approval identities and output; compare the normalized trace with native events. Test user-input elicitation separately from tool permission.
4. Cancel during a pending approval; prove no tool starts, late/duplicate choices fail safely, and process-tree shutdown completes on Windows/macOS/Linux. Test SDK timeout separately from abort.
5. Crash the runner while awaiting approval, exit voluntarily, and restart after manual Continue. Prove factory checkpoint persistence, inspect resumed native history, and require a fresh live permission request before any resumed action. Test crash after approval but before observed execution result as an uncertain outcome, not a safe replay.
6. Verify policy precedence, ambient saved consent, workspace-policy limitations, optional permanent grants, stderr separation, sensitive-output redaction, and missing usage fields. Pin fixtures to the tested harness release.

No native authenticated approval, cancellation, crash recovery, or platform E2E behavior is validated by this note. Approval request durability and native terminal attachment remain explicit gaps, not capability promises.
