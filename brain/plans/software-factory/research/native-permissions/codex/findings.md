# Native Codex permissions for the local factory

Research date: 2026-10-14. Recommendation: use a runner-owned `codex app-server --listen stdio://` process and bridge its server requests to the dashboard's separate HTTP controls. Keep the process alive while a native approval is pending. Persist factory checkpoints in the repository's SQLite database, but do not treat saved native request IDs as durable approvals that can be answered after process death. This is a feasibility recommendation, not an adopted human policy or a tested factory adapter.

## Permission protocol contract at 0.162.1

The following names and shapes are verified in locally generated schema; [probe evidence](probe-evidence.json) records schema hashes and selected exact definitions. JSON-RPC request identity, not `itemId` alone, routes the response. `approvalId` can further distinguish several command callbacks for one item. Preserve native payloads and provenance instead of flattening them into one Boolean.

| Server request | Response and scope | UI meaning |
| --- | --- | --- |
| `item/commandExecution/requestApproval` | `{decision:"accept"}`, `acceptForSession`, `decline`, `cancel`, `acceptWithExecpolicyAmendment`, or `applyNetworkPolicyAmendment`. The schema describes session acceptance as reuse in the same approval cache; amendments change future matching command/network policy. | Show command/cwd/reason where present. `kind` distinguishes command versus stdin review; `networkApprovalContext` requires network-specific presentation. `decline` lets the agent continue; `cancel` interrupts the turn. |
| `item/fileChange/requestApproval` | `accept`, `acceptForSession`, `decline`, `cancel`. | Show proposed file change from its associated item. `grantRoot` is explicitly unstable with uncertain enforcement in the schema; do not promise a functioning directory-wide grant from it. |
| `item/permissions/requestApproval` | `{permissions: <granted subset>, scope:"turn"|"session"}`; default scope is turn. Empty permissions grant nothing. | Review requested filesystem/network access, including environment and cwd. No `decision:"decline"` variant exists here. |
| `item/tool/requestUserInput` | `{answers:{<question-id>:{answers:[<string>]}}}`. Required `isBlocking` determines blocking behavior; `autoResolutionMs` is deprecated locally. | User questions are not automatically tool authorizations. Connector approvals can use question-shaped prompts, so preserve tool context and offered options. |
| `mcpServer/elicitation/request` | `{action:"accept"|"decline"|"cancel",content:...}` with form or URL variants. | External server elicitation is distinct from sandbox expansion and ordinary planning input. |

Stable generation omits `availableDecisions` and `additionalPermissions` from command approvals; they appear with `--experimental`, requiring client experimental opt-in. Present only supported choices from the selected protocol/profile. A persistent policy amendment is a materially broader human choice than allowing one action. Do not automatically synthesize or save one.

These are protocol documentation examples, not factory implementation:

```json
{"id":71,"method":"item/commandExecution/requestApproval","params":{"threadId":"thr_A","turnId":"turn_A","itemId":"item_A","startedAtMs":1791972000000,"command":"git status","cwd":"/repo","kind":"command"}}
{"id":71,"result":{"decision":"decline"}}
{"id":72,"result":{"permissions":{},"scope":"turn"}}
{"id":73,"method":"turn/interrupt","params":{"threadId":"thr_A","turnId":"turn_A"}}
```

Line three presumes a separate additional-permissions request with ID 72. A response must use the actual live server request ID; a response message has no `method`. The protocol omits the JSON-RPC `jsonrpc` member. Perform the `initialize`/`initialized` handshake first. `turn/completed` distinguishes completed, failed, and interrupted work. The `serverRequest/resolved` notification clears corresponding UI state. [App-server lifecycle](https://learn.chatgpt.com/docs/app-server).

Sandbox configuration defines what tools can technically access; approval policy determines when review is required; `approvalsReviewer` chooses human `user` versus `auto_review`. `never` does not remove a sandbox, and a workspace sandbox does not require approval for every routine action. Choose explicit effective settings for both concurrently active threads, and respect managed constraints. For this feasibility route, retain human review rather than assuming automatic review or bypass flags. [Sandbox distinction](https://learn.chatgpt.com/docs/sandboxing), [approval configuration](https://learn.chatgpt.com/docs/agent-approvals-security).

## Runner exit, cancellation, and stale requests

**A native permission wait holds a live request callback and turn.** Pinned app-server source stores pending requests in a process-local `HashMap` with one-shot response senders. It supports replay from this live map. The command/file replay tests call `thread/resume` while the original server and in-progress turn still exist, then answer the replayed ID. They do not kill and restart the server. [Callback/replay implementation](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/src/outgoing_message.rs#L446), [command replay test](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/tests/suite/v2/thread_resume.rs#L5467), [file replay test](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/tests/suite/v2/thread_resume.rs#L5604).

**Factory checkpoint durability is separate.** Inferred factory behavior: save the native request, exact action preview, process incarnation, thread/turn/item/request identifiers, and permission profile before showing it through SSE. A dashboard may disconnect while the runner keeps working or waiting. HTTP controls reach the runner through the selected local control mechanism; they are translated to RPC replies, not sent through SSE. SQLite records outlive the runner, but cannot recreate a callback.

On a deliberate stop, send `turn/interrupt`, keep reading terminal/resolution notifications, invalidate outstanding controls, then shut down the child. On a crash or lost child, retain history as evidence and mark requests stale; do not replay approvals into a replacement process. On human Continue, start a fresh server connection, resume persisted history, reconcile workspace effects, and obtain any newly issued permission request before answering. Treat reused numeric RPC IDs in another process incarnation as different requests. These are proposed factory rules, not guarantees supplied by Codex.

If product policy says runners exit whenever humans must act, apply that rule to durable **factory checkpoints**. For native permissions, either retain the live foreground runner while waiting or interrupt and reconstruct work on Continue. Exiting and later answering the old native prompt has no established support. Avoid keeping a shared daemon solely to make an ephemeral prompt look durable. Local help now exposes shared-daemon/remote TUI features, but they are not required by the recommended stdio route.

Cancellation differs from denial: a command `decline` returns the denial to the agent; command `cancel` also interrupts its turn. Additional-permission denial uses an empty grant, while interruption is a separate RPC. Source cleanup drains pending callbacks; raced or duplicate responses must not trigger a second effect. Native test evidence confirms permission `serverRequest/resolved` ordering before completion, but does not replace a factory race test. [Permission test](https://github.com/openai/codex/blob/092d3acd6bec3e3a14bdc7e7a2810ab628ab759d/codex-rs/app-server/tests/suite/v2/request_permissions.rs#L875).

## Native platform limits

| Platform | Native feasibility and limits | Evidence |
| --- | --- | --- |
| macOS | Stdio app-server protocol is locally available. Native sandbox uses Seatbelt. Human approval transport itself needs no terminal. Filesystem/network enforcement and child cleanup were not exercised. | P for help/schema; D for sandbox. [Sandbox](https://learn.chatgpt.com/docs/sandboxing). |
| Linux | Same client protocol is documented; native sandbox uses bubblewrap. A missing system `bwrap` falls back to bundled helper subject to user namespace support. AppArmor restrictions can prevent sandbox startup. | D only; no native Linux probe. [Sandbox prerequisites](https://learn.chatgpt.com/docs/sandboxing). |
| Native Windows | Supported native path, not inherently WSL-only. Current documentation recommends MXC on compatible Windows 11 devices, with elevated/unelevated legacy fallback; elevated setup needs administrator approval, unelevated has weaker network isolation and lacks denied-read paths. MXC ends remaining child processes when its foreground command exits. | D only; no Windows probe. [Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox). |

Windows OS/UAC setup approval is distinct from a model tool permission request and may require native UI outside the dashboard. Current guidance recommends Windows 11, treats recent Windows 10 as best effort, and does not prove MXC availability on a particular machine. The pinned pending-approval replay fixtures include cross-host Wine exclusions; their coverage cannot establish Windows parity. Transport portability therefore does not establish sandbox or lifecycle equivalence.

## Required validation before advertising support

1. Pin the exact executable and schema bundle. Capture real command/file/additional-permission and MCP/user-input request fixtures, including experimental opt-in behavior and managed restrictions.
2. With two active agents, hold one approval open while the other streams and finishes. Confirm event draining, IDs, correct scope, partial grant, decline-versus-cancel, and no implicit approvals. Test one and session grants independently; determine whether any grant survives fresh-process resume rather than assuming it does.
3. Cancel while permission is pending; race a late HTTP answer against interruption, duplicate submissions and child exit. Verify terminal request state, turn outcome, background process cleanup and Windows descendants.
4. Close/reopen the dashboard while the runner waits. Separately kill/restart runner and app-server, then use human Continue. Verify durable factory history, stale controls, native history recovery and newly issued prompts. Surviving-server replay and process-death recovery are separate cases.
5. Repeat sandbox enforcement and lifecycle checks on native macOS, supported Linux distributions and native Windows configurations. Include Windows UAC/setup and unsupported sandbox environments; no route may silently fall back to unrestricted execution.

Research closes the interface question: human permission handling is feasible through native app-server RPC. Production readiness, request durability after process death, per-platform cleanup and permission-grant persistence remain validation gaps.
