# OpenCode and Pi native permission feasibility

Research date: 2026-10-14. Research only: no installation, authenticated model job, credential inspection, or product implementation occurred. Neither `opencode` nor `pi` was on this host's PATH. Documentation and pinned source establish feasibility; the acceptance tests below remain unexecuted.

## Conclusion

OpenCode is feasible for native permission mediation through a managed headless server and its matching SDK. The coherent first experiment is **OpenCode V1 `opencode-ai` 1.19.0 plus `@opencode-ai/sdk` 1.19.0**, using V1 HTTP endpoints through that SDK's `/v2` export. The export name identifies a generated SDK interface and does not mean the OpenCode V2 product. `run --format json` cannot serve as the approval bridge: pinned source automatically rejects asks unless auto-approval is enabled. Pi 1.2.0 has useful RPC control and streaming, but its native tool-permission capability is **unavailable**. A separately configured and tested extension can supply partial enforcement; generic extension confirmations alone do not establish that capability. [OpenCode package](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/sdk/js/package.json), [run source](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/cli/cmd/run.ts), [Pi security](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/security.md).

These recommendations concern transport and enforcement feasibility. They do not choose which factory actions humans must approve, and native permission checks do not establish an OS sandbox.

## Enforcement and scope

OpenCode V1 supports allow/ask/deny per tool or input pattern, global config and agent overrides. Defaults are permissive for most tools. `once` approves one request; `reject` also rejects other pending requests in that session. The docs describe `always` as lasting for the current session, but the pinned implementation stores `approved` rules in `InstanceState`, whose key is the **directory**, with no session ID on those rules. Future asks in another session sharing that directory instance can therefore reuse them. Immediate draining after `always` filters to the replying session. State is in memory and clears on disposal/restart. Do not label this as a durable or strictly session-isolated grant. Use `once` initially and separate managed servers per agent attempt if approval isolation is required. [V1 permissions docs](https://opencode.ai/docs/permissions/), [pinned permission service](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/permission/index.ts), [directory-keyed state](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/effect/instance-state.ts).

V2 is different: ordered `permissions` rules use `shell`/`subagent` instead of V1 `permission` rules using `bash`/`task`. Current V2 docs make `always` durable and project-scoped, subordinate to configured denies. Pending requests remain in a live map, whereas saved patterns use a storage service. Shell runs with host authority and directory inference is best effort. This is not permission or restart parity with V1. [V2 permissions](https://opencode.ai/v2/docs/permissions/), [tagged V2 core source, distinct from the V1 route](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/core/src/permission.ts).

Pi explicitly says tools use the process account's authority and do not ask before every call. Its project trust concerns loading executable resources; it does not restrict tool access. `--approve` is a project-resource trust override, not tool auto-approval. JSON/RPC/print cannot display the built-in trust prompt and may skip protected project resources, so a project-local permission extension can silently be absent unless launch/resource configuration proves it loaded. [Pinned security](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/security.md).

Pi's extension `tool_call` hook can block execution and `ctx.ui.confirm()` can ask. Nested `ctx.executeTool()` calls also traverse hooks, and parallel sibling tool calls may occur. Tool annotations are unverified hints. Extensions execute arbitrary code with Pi's authority, and user shell calls have their own `user_bash` interception contract. A permission extension therefore needs documented coverage, absence/failure behavior, cancellation and tests for built-in/custom/MCP/nested tools and direct shell commands before the adapter may claim partial tool permission support. [Pinned extension contracts](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/extensions.md).

## Pending prompts, cancellation and crash recovery

OpenCode V1 pending requests are in-memory Deferred values. Interruption removes an awaited request in its finalizer; instance disposal rejects all pending values. A stale reply raises request-not-found. `session.abort` cancels that session's runner and associated background jobs; verify child sessions and OS descendants separately. Durable session history is not a surviving pending Deferred. On a live transport reconnect, re-list pending requests and match native IDs before offering a response. On process restart, invalidate old IDs and require a fresh request if work is restarted. [Pinned permission service](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/permission/index.ts), [run cancellation](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/session/run-state.ts).

Pinned V1 ACP cancel/close delegates to backing `session.abort`; its permission responses are still request-lifetime values. Current V2 ACP docs explicitly reject pending permissions on cancel, support many sessions per process with one prompt per session, and distinguish history-replaying load from resume. Do not borrow those V2 guarantees for the V1 binary without fixtures. [Pinned V1 service](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/acp/service.ts), [V2 ACP](https://opencode.ai/v2/docs/cli/acp/).

Pi RPC UI requests live in a process-local map. Unknown response IDs are silently ignored. Supported select/confirm/input dialogs resolve defaults on a supplied signal or timeout; signal propagation is optional. Consequently `abort` must not be assumed to dismiss an extension confirmation that did not pass the operation signal. Cancel outstanding UI requests explicitly before aborting and verify idle; forced termination is a separate outcome. Restarting a saved session does not reconstruct that map. [Pinned RPC implementation](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/modes/rpc/rpc-mode.ts).

Pi `abort` waits for idle, but queued input can continue; `clear_queue` before `abort` implements the documented Esc behavior. Prompt acceptance is not completion, and `agent_end` can precede retries or compaction: use `agent_settled` for settled work. [Pinned commands](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/rpc-commands.md), [RPC lifecycle](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/rpc.md).

V2 HTTP native events are volatile: slow consumers can fail and disconnected events are missed. Its separate experimental session log supports a sequence cursor, but is not proof that pending permissions survive a restart. The matching client does not automatically reconnect or replay. [V2 API](https://opencode.ai/v2/docs/api), [client stream contract](https://opencode.ai/v2/docs/build/client/).

## Factory integration recommendation

The foreground workflow runner should own two managed agent children by default, each with a separate native session/attempt identity and workspace. For the pinned OpenCode experiment, each child runs V1 `serve` on a unique loopback port and the runner uses the matching SDK/V1 routes. For Pi, use one RPC child per active agent. Keep the independent dashboard connected only to factory SSE and HTTP. It sends a human response to the factory; the current foreground owner reconciles it and forwards it through the selected native channel.

Persist native event provenance, session/request IDs, run/step/attempt IDs, binary/SDK version and a process-generation token in per-repo SQLite. Validate all these identities plus live pending state before forwarding approval. Treat a stale, timed-out, externally answered or cancelled request as terminal. Persisting a human decision is an audit/checkpoint record; it does not recreate the native continuation. Dashboard disconnect need not kill the runner, but runner crash changes ownership. Human Continue after crash creates a new attempt or explicitly restores history, inspects partial filesystem effects and obtains new native requests. Never replay a recorded approval as tool execution.

Native V1 SSE gives live delivery; the factory's persisted sequence must provide dashboard replay. Do not make the dashboard the sole consumer of native pipes/events: stalled native readers can stall agents. Permission and ordinary question/form/extension-input records need distinct types in the factory contract. Pi dialogs can be rendered as extension input while native tool approvals remain unavailable. These are architectural inferences from the cited contracts, not implemented behavior.

## Native platforms and unexecuted acceptance tests

OpenCode documents macOS/Linux installation and direct Windows operation, while recommending WSL for its terminal/tool compatibility. WSL is a Linux environment and does not demonstrate native Windows conformance. Pi documents macOS/Linux/Windows installers, Node.js 22.19+, native Windows Git Bash discovery and an optional PowerShell tool. TTY presentation constraints apply to interactive modes; server/RPC approval transports use HTTP or pipes. Process tree interruption and shell path semantics need separate macOS, Linux and native Windows fixtures. [OpenCode install](https://opencode.ai/docs/), [Windows guidance](https://opencode.ai/docs/windows-wsl), [Pi README](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/README.md), [Pi Windows](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/docs/windows.md).

Before adoption, execute these tests in disposable workspaces with a pinned local/mock provider where supported, avoiding credentials and real external side effects:

1. OpenCode: configured ask/deny for edit, shell, external directory, custom/MCP tool and subagent; assert no side effect before approval. Capture once/reject/feedback and duplicate/late/wrong-session replies.
2. Prove the V1 directory-instance `always` scope across two sessions and across separate servers, disposal and restart. Verify whether remembered rules can alter configured-deny precedence in V1; prefer once until resolved. Separately prove V2 durable project scope if that route is later adopted.
3. Disconnect/reconnect SSE while approval is pending; re-list live requests. Crash foreground runner or native process while pending and after response but before result persistence. Validate stale-ID handling and human Continue without duplicate tools.
4. Cancel a pending ask and a running shell tree; verify idle, child/subagent cancellation and surviving descendants on every native platform. Test concurrent asks and independent streaming for two agents, slow consumers and port conflicts.
5. Pi: show default tools execute without universal confirmation; project trust/approve flags affect loading only. For any proposed permission extension, prove loaded identity, fail-closed behavior, all tool paths, parallel/nested calls, user_bash and cancellation both with and without propagated signal. Check false/undefined timeout defaults and unknown response IDs.
6. Verify exact installed help/version and SDK package pin before adapter startup. Record fixtures for settled completion, retry/compaction, process exit and session history restoration. No conformance claim is made until these pass.
