## User surface and explicit selection

Extend the existing external versioned `skills/default/software-factory/scripts/install.py` launcher. Do not run the installed CLI to remove its own files. Supply authenticated local controller release and exact pinned Node archive through the existing `--bundle-root`, `--manifest-sha256`, `--node-archive` mechanism; no download, npm install, provider construction/call, notification, or global runtime lookup is part of uninstall.

- `inspect-uninstall --repository R [controller source arguments] [--operation UUID]`: read-only, bounded JSON. Return `ready`, `incomplete`, `absent`, or `blocked`, repository/active receipt identity, exact proposed `install/` and `toolchain/` paths/count/bytes/inventory digest, retained categories, native artifact list, owners/limitations, confirmation digest, and recorded progress if an operation exists. Never print a claim token. Inspection creates no repository operation/stage; the launcher's disposable authentication stage may be created and cleaned normally.

- `resume-uninstall --repository R [same controller source arguments] --operation UUID --selection-sha256 DIGEST --operator-confirmed --note NOTE`: continue only the recorded operation and controller selection, with bounded nonempty note and exact claim reclamation. It never changes selection, restores files, or starts a new uninstall over partial removal. Missing/changed recorded stage or inventory refuses; explicit installation repair is a separate future path.
- Success JSON is `{state:'absent',operationId,repositoryId,...bounded counts/retained-stage status}`. No fresh uninstall is admitted when already absent. Repeat inspection or resume of the same terminal operation returns its validated terminal receipt without new claims or deletions. A different/unknown operation refuses.

## Admission, lifetime, backup and durable ordering

1. Authenticated selected controller inspects genuine active ownership without executing the old installed runtime. `beginUninstall` atomically rechecks ready current-schema repository, exact latest completion, and zero owner claims, inserts the typed sole maintenance claim and `maintenance.started`. This is the same gate as runner/dashboard admission. Closing a browser tab is insufficient; do not stop dashboard/jobs automatically. Preserve known-live, uncertain or unrelated claims and refuse.
2. While `preparing`, revalidate active receipt/full inventories and prepare an independently executable private payload under `<factory>/controller-staging/OP/payload`, outside both deletion roots. Copy authenticated controller code and pinned Node, self-check closure, measure stage digest/identity, and bind source/selection/inventory/stage facts atomically. Selected external Python must be canonical, hash/identity/version-bound and outside the install/factory/private temporary stage just as `validateSelectedPython` and existing handoff require. Do not run npm or providers.
3. Preserve the ExecPlan's conservative existing-store backup boundary: adapt the existing verified SQLite backup helper, private absent target, integrity/count/source-identity proof and bound receipt from `maintenance.ts:331-493` for current-schema uninstall, without pretending it is a forward-schema operation. The new backup has a distinct operation-bound ID under `maintenance-backups/OP/ID`; never overwrite/reuse a partial target. Retain it after success and protect it during incomplete uninstall. No migrations, restoration, downgrade or salvage occurs. Do not copy a live main DB file. Failure/low space refuses modification and preserves evidence.
4. Reuse `prepareMaintenanceHandoff` (line 698), external Python `bounded_child`/`publish_candidate` wait discipline (`install.py:571,1026`), and one-use exit receipt. Preparer must exit, both streams close and its original POSIX group be absent before Python writes/flushed post-wait receipt. Staged controller consumes it atomically (`store.ts:1135`), rotates live ownership through the existing handoff, persists `modifying` and repository `incomplete` before any deletion. Bind/recheck the live parent launcher. No admitted factory-managed installed process or image being deleted may still execute; the uninstall chain runs only authenticated external/staging images. This proof covers recorded managed lifetimes, not arbitrary unclaimed processes launched by another same-user program; do not add a global process scan or claim universal absence. Known-live original preparer/controller/launcher blocks recovery. Unknown identity requires accepted explicit operator-confirmed clearance and retains its uncertainty basis. Never signal stored PIDs or create a daemon.
5. At admission, resume and mutation entry, validate sole exact claim/token/phase/owner as applicable, repository/common/factory and stage identities, source receipt digest, bound inventory and backup. Run one full residual-inventory/extra-entry validation at each such boundary: require all untouched entries present/exact, all committed-deleted entries absent, and no extra entries under either deletion root. Do not repeat the full remaining-tree scan or rehash after each deletion; step 6 performs per-entry ancestor/object checks, and directory removal performs exact empty-directory checks, preserving bounded linear inventory work. Fixed order: files deepest-first with bytewise path tie-break; then now-empty directories deepest-first, finally the two roots. A root is removed only by `rmdir` after its recorded children are absent and its exact emptiness is checked; an added foreign entry therefore survives and blocks completion. No recursive `rm`, `rmSync`, `rmtree`, wildcard, dependency uninstall hook or dynamic discovery expands selection.
6. For each single next entry: recheck all relevant ancestors and entry identity/type/mode/hash/nlink; transactionally commit `uninstall.delete_intent` plus the sole pending sequence under exact claim CAS; recheck entry immediately before mutation; unlink only a regular file or `rmdir` only the exact empty directory; fsync the containing directory; verify absence and parent identity; transactionally append `uninstall.deleted` carrying the immutable deletion receipt and advance progress/clear pending. Never begin a second deletion until this receipt commits. DB transaction plus SQLite durability is the deletion receipt; no redundant per-file filesystem receipt directory is needed.
7. Crash reconciliation allows exactly one filesystem-ahead gap: the persisted pending entry may be present/exact (delete it), or absent (fsync parent and commit `reconciled-absent`, truthfully distinguishing recovery observation). With no matching committed pending intent, a missing untouched path refuses. A receipted path that reappears, changed pending/suffix entry, foreign extra entry, unexpected/missing receipt, sequence gap, changed parent, or unavailable/ambiguous filesystem result leaves incomplete with claim/evidence retained. Do not delete the replacement, infer a longer absent prefix, repeat an uncertain external action, or auto-release a claim.
8. After both target roots are absent and every sequence has a receipt, persist `validating` with `recordMaintenanceStage` semantics. Validate current schema/integrity, retained repository identity/source completion/receipt/backup/journal and target absence. No installed manifest/runtime/toolchain command can run now; their pre-removal authenticated facts are retained in the bound inventory. Write and flush a small terminal receipt binding selection, inventory, source receipt/completion, deletion receipt digest/count, stage/controller/launcher identity and retained categories.
9. In one exact validating-claim transaction: recheck source active completion and incomplete repository, append `uninstall.completed` with terminal receipt hash, set `repository.state='absent'` retaining repository ID/release/history, and delete only matching claim/token. A crash before this commit remains incomplete even if paths are absent. Teach read-only inspection to project state `absent` (current `inspectMaintenance:576` maps all non-ready states to incomplete), and expose a clear installation-required startup diagnostic rather than initializing an empty store. No bootstrap over retained factory state.
10. Return through Python only after staged controller exit, both EOFs and original group closure. Reuse exact `snapshot_completed_stage`/`cleanup_completed_stage` (`install.py:1071-1138`) for this operation's stage only after closure and unchanged inventory. If stage/image cleanup is unsupported or uncertain, retain its recorded path for later explicit idle cleanup; terminal installed state remains absent, but public result must disclose retained/uncertain staging and must not claim complete cleanup. No background self-delete. Operation metadata, source receipts and backups remain retained regardless of stage cleanup.

Preparation may be explicitly abandoned only before modifying, after proving no pending/deletion events, unchanged complete original installation and quiescent/reclaimed owners; record the failure and exact claim release atomically. Reuse the narrow unchanged-preparation pattern at `store.ts:1204` rather than inventing rollback. After modifying, the only path here is exact uninstall completion; explicit installation repair remains separately selected and implemented.

## Native safety limit and proof boundary

Use canonical private 0700 directories, no-follow regular descriptor reads, held ancestor identities, full inventory preflight and immediate per-entry validation on Darwin/Linux. Qualify unlink/rmdir and parent-directory fsync on the actual supported local filesystem profiles. POSIX pathname deletion is not atomically conditional on `dev:ino`; `atomicPublicationMove` explicitly documents the same source-lookup limit (`atomic-publication.ts:45`). Do not advertise immunity to an arbitrary same-user writer replacing names between the last check and unlink. Native canaries must cover detectable swaps before each mutation and refusal afterward. If the required security model demands an absolute identity-conditional destructive operation against an actively hostile same-user writer, this is a real additional mechanism/decision gate, not something held read descriptors, a rename helper, a successful canary or postchecks establish. No such stronger native primitive was established by this read-only task.
