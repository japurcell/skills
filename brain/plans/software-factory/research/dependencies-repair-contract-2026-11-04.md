## Decision and delivery boundary

Current implementation sequencing supersedes the original two-deliverable grouping below: ownership foundation source/composed and Linux native12/12 are integrated/verified; bounded read-only foundation accepted; fixed-selection/exact claim/revalidation/read-only inspection, verified backup, candidate/stage/handoff, two-move publication/recovery and authored dependency installation are separate serialized handbacks. Exact claim source and its545-case composed proof are now integrated; Linux native claim23/23 also passes at exact8f59d77b; bounded admission acceptance met, while overall Darwin/Windows qualification failures remain open. Root controls separate verified-backup release after the completed composed gate; no backup/public mutation/completion belongs to the claim handback. Their complete behavior remains required. The ExecPlan controls current root release and exact boundaries. Retained-original/prebind/nonempty-provider and Windows qualification remain open.

Implement a narrow dependency-environment replacement through the existing authenticated launcher, staged controller, exclusive maintenance claim, verified backup, and atomic no-replace helper. Do not call the full upgrade controller: it requires `kind=upgrade`, forward-schema state, a complete install candidate, and four hard-coded moves that replace runtime/Node and toolchain together. Dependency maintenance leaves `factory/install`, release/schema, providers, authoring files, application dependencies, worktrees and historical records unchanged.

The smallest complete selectable unit is **the shared toolchain environment and its explicitly selected lock closure**, not one arbitrary package directory. npm hoisting, transitive and optional packages make per-directory replacement an unsafe substitute for a coherent lock. The impact plan must say that the entire environment is replaced and list every resulting package/version/integrity. Do not claim per-package repair. Node belongs to the unchanged managed installation; repairing/replacing it remains authenticated installation repair/upgrade, not this task.

Deliver two serialized tasks; both are required to finish accepted dependency maintenance:

1. **T16-dependencies-repair-foundation:** reinstall the exact current manifest-authenticated compiler closure, including repair of known owned selected files that are missing or byte-mismatched. No new dependency declaration or lock is resolved/generated. This establishes dependency receipts and interruption recovery.
2. **T16-authored-dependencies-install:** consume an explicit user-maintained `.factory/package.json` and `.factory/package-lock.json`, install/update their complete selected environment under the same protocol, then support repair of that exact installed selection. This completes the accepted custom workflow dependency contract. It is not indefinitely excluded by the fixed compiler task.

Both wait for accepted T16b public first-install/upgrade and clean handback. Neither needs a new user policy decision. Reviews stay deferred until all implementation completes; provider qualification stays blocked and desktop tests remain last.

## Public input and exact selection

Extend the existing Python public entry, not runtime `invoke`:

    install.py dependencies inspect --repository REPO --bundle-root BUNDLE --manifest-sha256 SHA --node-archive ARCHIVE --mode repair
    install.py dependencies apply   --repository REPO --bundle-root BUNDLE --manifest-sha256 SHA --node-archive ARCHIVE --mode repair --selection-sha256 PLAN_SHA --confirm --offline --offline-cache-seed CACHE
    install.py dependencies resume  --repository REPO --bundle-root BUNDLE --manifest-sha256 SHA --node-archive ARCHIVE --operation UUID --selection-sha256 PLAN_SHA --operator-confirmed --note NOTE

`inspect` is read-only and prints a bounded deterministic plan plus digest, installed receipt/completion identity, exact target paths, current/target lock digests, package/version/integrity rows and complete replacement impact. `apply` recomputes this plan under the idle claim; digest mismatch refuses. No implicit destructive default. Offline flags keep their present semantics; online explicit maintenance may consume only selected integrity-bound lock artifacts. `--node-archive` authenticates the external bootstrap/controller runtime; it does not select Node replacement. Reject `--providers`, package names/specs, alternate target paths and extra artifacts on these routes.

For foundation repair, require the selected bundle manifest to equal the installed release manifest and the target lock to equal its authenticated toolchain lock. For a previously installed authored environment, `repair` uses its active dependency receipt's declaration/lock/closure, not the release's fixed compiler-only lock. An earlier lock/release cannot be selected as repair; no downgrade or version substitution occurs.

For authored `--mode install`, use canonical `.factory/package.json` and `.factory/package-lock.json` from the explicitly selected repository root. Require a complete npm v3 lock, `type: module`, exact managed TypeScript/@types pins in dependencies or devDependencies, no root scripts/workspaces, and lock-root declarations equal the supplied package declaration. Remaining direct specifications may use normal declared ranges only when the supplied lock fixes the exact resolved versions. Refuse file/link/git/workspace dependencies, local path tarballs, unpinned/credential-bearing/non-HTTPS sources, aliases or package engines/platforms that cannot be validated by the selected package manager profile. Support the complete integrity-bound HTTPS registry lock closure with scripts disabled; packages needing scripts fail actionably. No command edits authoring files or generates a lock. The operator prepares/updates those files explicitly using ordinary package tooling. These bounded validation rules are an implementation contract, not a new resolver.

Snapshot the selected authored bytes into the authenticated private operation stage before execution, hash and recheck original descriptors before admission/binding/commit, and include both hashes and resolved closure in `DependencySelectionV1`. Their provenance is the explicit digest-confirmed authoring selection; they are not falsely called release-approved. Keep release manifest schema 2 unchanged. The dependency operation manifest is a separate typed artifact. Installed `toolchain/manifest.json` records all selected direct dependencies for `buildWorkflow` (`src/build.ts:7`); public startup still fails before any phase for missing/incompatible dependencies and never installs.

## Journal, interruption and recovery

Use `factory/dependencies-<operationId>/` with immutable `original.json`, `selection.json`, `intent.json`, `new-receipt.json`, marker template, `old/`, and ordered `01-old-toolchain.json`, `02-new-toolchain.json`. Large inventory records use deliberate existing candidate-sized bounds; compact claim/ticket remains <=8KiB. All records bind IDs, hashes and directory identities.

1. `preparing`: atomically admit an idle current-schema ready installation and bind the prior completion digest. Before any managed-file/data mutation, create and bind an operation-owned consistent SQLite backup using existing verified backup checks. Only administrative claim/start records precede backup. Capture original expected ownership and observed selected-tree facts separately. Stage target toolchain and self-contained controller outside live paths, prove child closure, bind exact immutable candidate/intent/receipt and stage.
2. `handoff-ready`: reuse one-use ticket plus Python post-wait receipt. Revalidate dependency candidate/original facts in `prepareMaintenanceHandoff`, `consumeMaintenanceHandoff`, `reclaimMaintenance` and recorded-intent validation via an explicit dependency branch. Consumption persists `modifying`, repository incomplete and new controller owner before any move.
3. `modifying`: publish owned incomplete marker, move original observed toolchain into `old/toolchain` absent-only, flush parents, verify identity/inventory, then write receipt01. Move candidate toolchain to absent live target, flush, verify and receipt02. The layout verifier accepts exactly recorded position or one move ahead with all exact identities; only the latter may issue its missing receipt. No rename based solely on matching bytes.
4. `validating`: verify current live toolchain/lock/closure, unchanged install/authoring/source/index/history facts, retained original/backup and direct Node/npm/tsc commands; for authored installation also run a public workflow importing the selected package in proof. Exact completion transaction writes dependency completion, marks ready and releases only this claim. Cleanup exact owned marker only after ready commit; stage cleanup follows existing foreground Python ownership checks. Old tree/backup/receipts remain for explicit later cleanup.

Any absent/extra artifact, altered declaration/lock/target, uncertain closure, unowned destination, identity/receipt/order mismatch or interrupted preparation retains evidence and claim. No automatic release, restore, salvage or retry. Explicit resume reauthenticates the same selection and stage, refuses known-live controller/original or completing launcher, requires bounded operator clearance for inactive/unknown identity, reclaims exact operation/token and continues only missing publication/validation steps. Unbound partial preparation is inspectable and blocked; do not adopt it or relaunch npm automatically. A later bounded preparation-abandonment route may release only an untouched fully revalidated original; it is not required to invent cleanup of partial candidates. Ready-before-marker recovery verifies exact committed composite ownership and closed owners before unlinking only its own marker. Backups never rotate automatically.
