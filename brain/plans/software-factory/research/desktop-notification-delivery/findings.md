# Desktop notification delivery fit

Research date: 2026-10-15. This is a source-based platform comparison for the accepted foreground TypeScript runner. No native OS, notification library, Windows App SDK version, Linux distribution, or helper packaging format is selected. No notifications were triggered, platforms were not tested, and the runner was not modified.

## Finding

The native notification centers and desktop notification service are sufficient to accept a one-shot alert without adding a factory-owned daemon. The lowest-effort path differs by platform: AppleScript `display notification` on macOS, `notify-send` when libnotify and a session notification server are available on Linux, and a small Windows App SDK executable for the current documented Windows desktop API. A five-second runner timeout can bound the send operation; it does not set a portable on-screen lifetime or prove the alert was shown or noticed.

No uniform built-in command contract was found for clicking an alert after its sender exits. macOS and Windows can activate an installed native app to handle a later click. Linux offers an optional body hyperlink that the notification server can open without a sender callback, but that capability is not required. Linux notification actions otherwise send a callback to the client, and `notify-send --action` waits for user input. The practical product boundary is therefore a best-effort alert with conditional click-through and an observation-link fallback in the dashboard and CLI. This is an advisory fit, not a selected product mechanism.

| macOS | AppleScript Standard Additions `display notification` (invoked by a short `osascript` process) can set title, subtitle, body, and sound. Notification Center presents it as a banner or alert according to the user's notification settings. Apple says an alert's Show button opens the app that displayed it; opening a script app can run its script again. A proper click-to-detail flow therefore needs an installed native app identity, notification authorization, and a response handler that opens the observation URL. This can be an on-demand app launch, not a continuously running notifier. [Apple's scripting guide](https://developer.apple.com/library/archive/documentation/LanguagesUtilities/Conceptual/MacAutomationScriptingGuide/DisplayNotifications.html), [response handling](https://developer.apple.com/documentation/usernotifications/handling-notifications-and-notification-related-actions) |
| Linux desktop | `notify-send` is a command-line client supplied by libnotify's `libnotify-bin` package, not a universal Linux inbox command. It sends through the desktop's notification daemon. A desktop notification server is a session-scoped D-Bus service; auto-activation is optional, and clients must tolerate it being unavailable. [Debian `notify-send(1)`](https://manpages.debian.org/unstable/libnotify-bin/notify-send.1.en.html), [freedesktop notification spec](https://specifications.freedesktop.org/notification/latest-single/) | The protocol has an optional human-readable `app_name`, icon, and `desktop-entry` hint (the latter can help the server identify an app for its icon/logging). The server owns presentation and may show only the summary or omit optional capabilities. No cross-desktop authorization or presentation behavior is specified here. [freedesktop notification spec](https://specifications.freedesktop.org/notification/latest-single/) | The spec allows `<a href="URI">` hyperlinks in notification bodies, but servers are not required to support them; `body-hyperlinks` is an optional capability. Protocol-based inference: when supported, the server can open a localhost detail link without a live sender. This needs native validation on each target server. The normal notification click/action instead emits `ActionInvoked` back to the notification client, and servers may not support interaction. `notify-send --action` implies `--wait`, so it holds the caller open. [freedesktop notification spec](https://specifications.freedesktop.org/notification/latest-single/), [Debian `notify-send(1)`](https://manpages.debian.org/unstable/libnotify-bin/notify-send.1.en.html) |
| Windows | Microsoft's current desktop recommendation is `AppNotificationManager` in the Windows App SDK. Its local app-notification API works for packaged and unpackaged desktop apps, but it is an application API rather than an inbox shell command. A small helper executable is the practical native sender. [Windows notifications overview](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/), [app-notification overview](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/) | For unpackaged .NET apps, `Register()` sets up COM activation and retrieves the app display name/icon from the shell; an explicit package identity is not required by this API. Users or policy can disable notifications per app or globally. Elevated apps cannot send or receive these app notifications. [Microsoft .NET guide](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-dotnet), [registration API](https://learn.microsoft.com/windows/windows-app-sdk/api/winrt/microsoft.windows.appnotifications.appnotificationmanager.register), [settings enum](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.appnotifications.appnotificationsetting), [limitations](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/) | Microsoft documents that Windows launches an unpackaged app through COM when a notification is clicked while the app is not running. The helper's browser-launch behavior remains implementation work. ## Delivery limits and product boundary

- Keep the five-second timeout on the runner's notification-send operation. Do not use it as a promise about banner duration: macOS presentation follows user settings; Linux's `--expire-time` is not honored by all servers (the current Debian man page specifically calls out GNOME Shell and Notify OSD, and critical notifications in Plasma); Windows presentation and app-notification settings are controlled by the OS/user. [Apple scripting guide](https://developer.apple.com/library/archive/documentation/LanguagesUtilities/Conceptual/MacAutomationScriptingGuide/DisplayNotifications.html), [Debian `notify-send(1)`](https://manpages.debian.org/unstable/libnotify-bin/notify-send.1.en.html), [Windows settings enum](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.appnotifications.appnotificationsetting)
- Treat a successful API/command submission as “submitted,” not “visible” or “seen.” Sources describe posting/sending requests and expose permission, service availability, and capability limits; none of the reviewed interfaces provides a receipt proving pixels were displayed or the user paid attention. This is an inference from the documented interfaces, not a platform test.
- For the initial behavior, the runner can save the outcome first, make one bounded best-effort alert attempt, then exit. Do not attach workflow controls to the alert. A detail click should remain optional: use a conditional Linux hyperlink or native helper activation where available, and keep the dashboard/CLI observation URL as the fallback.
- This does not change the accepted reminder scope: opt-in grouped reminders remain dashboard-host-only, at the existing fifteen-minute interval.
- A localhost URL only works if the dashboard host is still running and reachable when clicked. Notification delivery and dashboard lifetime are independent; the notification cannot keep the dashboard host alive. This is an architectural inference from the separate processes, not a platform notification guarantee.
- A registered app bundle/COM executable is an install artifact, not a permanent notifier daemon. Bundling it still adds platform-specific native code, update/uninstall ownership, identity/registration, and native acceptance tests. Windows already needs an AppNotificationManager executable for the documented native alert path; on macOS and Windows, extra click-response handling is justified only if post-exit click-through is a product requirement.

## Version and evidence limits

Sources were inspected on 2026-10-15. The freedesktop page is its current “latest” specification snapshot; the Debian unstable manual page identifies `libnotify-bin` 0.8.8-1+b1. Microsoft's docs recommend Windows App SDK `AppNotificationManager` for current desktop apps; the exact SDK and Windows minimum version remain unselected. Apple’s AppleScript guide is archived (updated 2016), while the User Notifications pages are current documentation. These sources do not prove behavior on the target macOS, Linux desktop/server, or Windows builds.

Microsoft's documentation is inconsistent about self-contained packaging: the `AppNotificationManager.Register` API reference says the class depends on the Singleton package, while the Windows App SDK self-contained deployment guide says AppNotificationManager does not require that package. Resolve this against the exact SDK version and a native packaging test before sizing a Windows helper. [Register API](https://learn.microsoft.com/windows/windows-app-sdk/api/winrt/microsoft.windows.appnotifications.appnotificationmanager.register), [self-contained deployment guide](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps).

**UNVERIFIED:** notification visibility, retention, activation, and permission prompts on the target OS builds; whether each Linux notification server opens a body hyperlink after the sender exits; helper signing/packaging and removal details; dashboard availability at click time. No native validation was authorized or performed.
