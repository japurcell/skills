## SQLite read-only contract

- All ownership SQL is in one `DatabaseSync(...,{readOnly:true})` transaction. No schema configuration, migration, claim, event, history or readiness write is available in this reader.
- Primary source: [SQLite WAL documentation](https://www.sqlite.org/wal.html), especially sections 2.2 and 5. Read transactions include committed WAL frames at one endmark; readonly SQLite may create WAL/SHM bookkeeping. No immutable URI route was added.
- Actual pinned Node v24.22.1 probe: a table and row `42` committed solely to WAL are readable; DB and pre-existing WAL SHA256 remain unchanged, while SHM bookkeeping changes. With an open readonly transaction, a separate writer commits `43`; the existing transaction still sees only `42`, and the next transaction sees `[42,43]`.
- Another bounded probe and public RED establish that opening a closed WAL-mode database can create a zero-byte WAL plus SHM. The agreed contract permits only exact SQLite reader bookkeeping: validated regular, single-link, same-user/private SHM and newly created WAL with zero bytes/no frames. Existing WAL bytes, database bytes/committed rows/claims/history and every other managed path remain unchanged. Tests do not simply omit WAL comparisons.
