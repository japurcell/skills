# Live progress transport fit

Research date: 2026-10-13. This is an advisory protocol comparison for the browser transport seam. Sources are current WHATWG standards, HTTP RFCs, and Mozilla's browser documentation. No dashboard, browser matrix, local server stack, or latency target was tested.

## Recommendation

Use one Server-Sent Events (SSE) `EventSource` feed per active dashboard document for server-to-browser committed events, with ordinary Fetch requests for human Continue and other control commands. This matches the one-way event flow. `EventSource` supplies the SSE parser and reconnect behavior, while a separate command request keeps human actions as explicit HTTP operations with their own response. The human subsequently adopted SSE with separate HTTP controls; [Session events and live progress](../../tickets/session-events-and-live-progress.md#confirmed-answers-round-three) owns that decision and its application obligations.

Use Fetch streaming if the client needs request headers or startup-cursor control that `EventSource` does not expose, or needs to pace its own reader. WebSocket is appropriate if the product later needs frequent bidirectional messages on one application protocol. It adds no needed capability for a saved server event feed plus occasional human commands. The [HTML Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html) defines EventSource construction around a URL and credentials option, with server-to-client message events; the [WebSockets Standard](https://websockets.spec.whatwg.org/) defines a bidirectional message connection.

## Reconnect, cursors, and application replay

The HTML Standard defines SSE `id:` and `retry:` fields. For an open `EventSource` object, the browser retains the last event ID, waits the reconnection time after a dropped connection, and sends the cursor in `Last-Event-ID` on reconnection. A server-provided `retry:` can set that delay, but the initial delay is implementation-defined and the browser may wait longer, including exponential backoff. The standard sets a new object's cursor to empty. It also updates the cursor when parsing an event, before queuing its JavaScript dispatch, so the value is not an application acknowledgment. [HTML Standard: processing and parsing](https://html.spec.whatwg.org/multipage/server-sent-events.html#processing-model).

This is a reconnect cursor mechanism, not durable replay or exactly-once processing. The standard does not require a server to retain events, interpret IDs as ordered database positions, replay from storage, or wait for a consumer acknowledgment. For the factory's committed-before-display history, give committed events stable IDs tied to the saved event sequence, emit only after the database commit, and have the server replay later records when it receives a cursor. The UI should tolerate replay and deduplicate by event ID or sequence. Keep its applied cursor with application state only after applying the event. A reload or new tab creates a new EventSource whose protocol cursor starts empty, so bootstrap from saved UI state with a history/catch-up step or an explicit resume parameter. If recording an event fails, interrupt before publishing it, as already required by the product contract.

Fetch exposes a response body as a `ReadableStream`, but Fetch itself does not add EventSource's automatic retry or `Last-Event-ID` behavior. The application owns framing, reconnect timing, cursor persistence, replay, and deduplication; it can use request headers and an `AbortSignal` when reconnecting. WebSocket likewise has no EventSource cursor or automatic reconnect contract in its browser API. Its messages need application-defined IDs, replay, deduplication, and reconnect behavior. These responsibilities are application behavior for both alternatives, not protocol guarantees. [Fetch Standard: response body](https://fetch.spec.whatwg.org/#dom-body-body).

## Buffering and multiple sessions

SSE dispatches an event only after its event block ends with a blank line. The HTML Standard says user agents should buffer long-lived event streams appropriately and warns that block buffering or unaware HTTP chunking can delay or harm delivery. Ensure the serving path writes complete event blocks promptly and check intermediary buffering. This guidance does not guarantee a sub-second display time. Fetch readers can control chunk consumption; the Streams Standard defines backpressure propagation through stream pipe chains and queued chunks. That control does not establish a bound on browser, operating-system, server, or intermediary buffers. [HTML Standard: parsing and authoring notes](https://html.spec.whatwg.org/multipage/server-sent-events.html#authoring-notes), [Streams Standard: backpressure](https://streams.spec.whatwg.org/#pipe-chains-and-backpressure).

The browser WebSocket API has no inbound backpressure mechanism according to [Mozilla's WebSocket documentation](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket#backpressure). Its `bufferedAmount` reports bytes queued by outgoing `send()` calls, so applications sending faster than the network can drain must monitor and throttle that queue; it does not solve slow event consumption. For small progress messages and occasional commands, this is avoidable protocol machinery.

Connection counts are implementation-specific. The [HTML Standard's authoring notes](https://html.spec.whatwg.org/multipage/server-sent-events.html#authoring-notes) warn that multiple pages each holding an EventSource to the same domain can hit an HTTP per-server connection limit, and suggest sharing through a SharedWorker. [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.4) says HTTP/1.1 clients ought to limit simultaneous connections but specifies no fixed maximum. Mozilla's current [SSE guide](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events#warning_when_not_used_over_http2) documents a practical six-open-connection constraint for SSE over HTTP/1; treat that as browser guidance, not a universal or normative limit. Under HTTP/2, concurrent request streams are multiplexed on a connection and constrained by peer-advertised `SETTINGS_MAX_CONCURRENT_STREAMS`, not a standard browser-wide constant ([RFC 9113 §§5.1.2, 6.5.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.5.2)). Fetch streaming uses HTTP requests too. WebSocket instances also hold long-lived connections; the WebSocket API does not promise unlimited connections. For multiple workflows in one view, multiplex their saved events over one dashboard stream rather than opening one stream per workflow. If multiple tabs must share a feed, evaluate a shared worker.

The accepted 95% within-one-second target must be measured from factory receipt through browser display, including local batching and persistence delay, under the documented local load using the selected browser and actual serving path. Record reconnect/catch-up and multi-tab behavior separately. No source promises that latency, and this investigation did not test it.
