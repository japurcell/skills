## Decision and exact remaining causal question

**DEFER implementation/native tracing. No repair is justified.** `!htrace` is a documented way to inspect retained operation stacks. It is not, on the reviewed public contracts, a bounded complete provenance ledger for the actual aggregate-count failure. The missing retention, generation and process-context assurances matter even in a disposable, non-admitting context. A finite output parser can bound exported bytes; it cannot certify that the underlying trace history is complete or correctly attributed.

The narrow potential benefit is a positive observation of an operation occurrence for a source/API hypothesis. That could guide later contract reading. It cannot alone establish that the observed occurrence belongs to one of the original excess handles, that the same handle generation remained open at the final query, or that the application omitted a required close. A close stack proves an observed close operation, not absence of later reopen or discharge of every ownership obligation. BAD REFERENCE is an invalid-reference observation, not evidence that the retained count increase caused it.

**Still unknown:** Which specific object references account for the original baseline-to-final excess; when and through which operation they arose; whether each is intentional process state, observer-related state or an application resource; who has an applicable release obligation; and whether any missing release caused this original-profile refusal. No documented trace stack in isolation answers that chain.

No native experiment is selected now. If complete retained-excess attribution is required, this reviewed route fails the contract and should stop here. ## Documented tracing surface and its stopping boundary

The [Microsoft !htrace reference](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-htrace) documents user-mode `-enable`, `-snapshot`, `-diff`, `-disable`, and handle selection. User mode operates on the current process; enabling takes an initial snapshot. Later snapshots replace the comparison baseline. Diff compares with the last snapshot and displays still-open handles. Enabled tracing saves open, close and invalid-reference stacks. `Max_Traces` limits displayed traces. The reference lists WindowsXP and later and the Kdexts/Ntsdexts extensions. It warns that traces can originate in another process context and resolve to wrong symbols.

The reviewed reference leaves table capacity, retention, wrap/loss reporting, ordering/generation, atomicity, latency/memory bounds and disable/free/reset semantics unspecified. Parsed/dumped counters certify no loss model. These are contract gaps, not observed implementation failures. No private structures or undocumented process information classes may fill them.

The conceptual sequence would be: identify the single freshly spawned controller in the debugger; enable tracing before the interval; replace the comparison snapshot at the exact original baseline boundary; continue the unmodified first positive; stop after the original final count has been recorded; collect diff and the selected retained traces; disable once; resume normal termination and verify owned cleanup. This is an explanatory sequence, not a runnable release. Inference: starting after failure cannot reconstruct earlier operations; repeated snapshots or activation cycles confound the interval. In particular, the documented diff syntax has no display-limit argument. A streaming output cap does not bound diff's internal work; the conceptual sequence is not yet a valid bounded command program.

Numeric-handle equality across snapshots is not a generation proof. An old close and later open can reuse one value; duplication/inheritance can produce additional references to one object. No stable kernel-object identity or ownership follows from the handle value, displayed stack or equal total. Without documented ordering and loss semantics, the decoder must not pair records into a complete lifetime or classify an unmatched open as a missing close. Even a complete stack for a current entry would still require the applicable source/API ownership contract before selecting a repair.

Global installation and auto-updating GUI deployment are outside this route.

[Microsoft documents debugging a debugger](https://learn.microsoft.com/en-us/windows/win32/debug/process-functions-for-debugging), using a nested DEBUG_PROCESS creation sequence. [Creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) separately define DEBUG_ONLY_THIS_PROCESS as starting/debugging the new process, and DEBUG_PROCESS as establishing a descendant debug chain. Current `Child::Create` at `windows-owned-image-probe.cpp:225` uses only DEBUG_ONLY_THIS_PROCESS for the inner debuggee. General nesting support plus those flag definitions is promising, but the exact current nested flag combination is not established by the recipe. Do not change the flag to make the recipe fit or claim nested operation proven.

An outer observer must debug only the controller. [CDB options](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/cdb-command-line-options) make `-o` descendant debugging opt-in; [`.childdbg 0`](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-childdbg--debug-child-processes-) disables it. Normal source behavior remains: creator owns debug creation, WaitForDebugEvent/ContinueDebugEvent, detach, explicit suspend/resume checks, Stop, Release, publication and actual join. [WaitForDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-waitfordebugevent) is creator-thread constrained and separately specifies OS-managed event-handle closure and debugger-owned file-handle closes. ## Observer effects and time semantics

[Debugger events suspend all threads of their target](https://learn.microsoft.com/en-us/windows/win32/debug/writing-the-debugger-s-main-loop). [Software breakpoints](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/bp--bu--bm--set-breakpoint-) replace an instruction; source-line requests can move to the next valid location. An exact baseline/final boundary therefore needs verified pinned instruction mapping, not a guessed source line. Data/register modification, injected target calls, new target-side tracing helpers, freeze/suspend changes or API interception are outside this route.

[CDB-spawned targets](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/debugging-a-user-mode-process-using-cdb) normally get a debug heap and inherit debugger permissions; `-hd` can request the standard heap. Handle inheritance needs its own policy (`-noinh` exists), including a verified separate stdout/stderr arrangement. Neither flag proves observer neutrality. Tracing itself has no zero-allocation/zero-reference/zero-count-effect promise. Startup debug state, load events, exception delivery, breakpoints, symbol resolution and pauses alter scheduling and can affect retention and caches.

[GetTickCount64](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-gettickcount64) measures elapsed system milliseconds. Inference: pausing the controller does not make its original wall-clock deadline or the undebugged fixture's fallback stop advancing. Symbol downloads or breakpoint analysis inside the interval can therefore change the failure seam. Keep10000ms eligibility,12000ms transport,8000ms fixture fallback and all4000+1000ms waits unchanged. No pause subtraction, longer original wait, warmup, baseline relocation, settlement loop, requery, count allowance or threshold change is permitted. Any debugger run is explicitly a separate non-admitting profile even if its ELAPSED happens to pass. Its timings can never prove original-profile acceptance; timeout or another failure seam is inconclusive and stops it.

## Exact binary/PDB relation and finite offline symbols

The current recipe requests no source debug information, and its seven-binary pinned inventory includes no PDB (`native-build.ps1:130`, `native.qualification.mjs:15`). No verified matching private PDB is available in this bounded evidence. [MSVC debug-information formats](https://learn.microsoft.com/en-us/cpp/build/reference/z7-zi-zi-debug-information-format?view=msvc-170) produce function/type/line information; the default emits none. `/Z7` puts it into objects; `/Zi` uses a compiler PDB and requires matching signatures. A possible separate diagnostic build could keep the source bytes and original compiler/runtime settings and add `/Z7`, with an explicitly named linker PDB. It must not use `/ZI`, `/MTd`, extra optimization changes, or replace the original binary.

[`/DEBUG:FULL`](https://learn.microsoft.com/en-us/cpp/build/reference/debug-generate-debug-info?view=msvc-170) makes a deployable complete PDB, implies incremental linking and changes REF/ICF defaults. A future build contract must therefore explicitly retain `/INCREMENTAL:NO` and original effective REF/ICF settings after `/DEBUG:FULL`; merely appending `/DEBUG` is not equivalent. Even with explicit settings it is a changed binary/profile, with separately pinned source, compiler/linker, arguments, object, executable and PDB digests. Record the own-image debug identity privately. [DIA validation](https://learn.microsoft.com/en-us/visualstudio/debugger/debug-interface-access/idiadatasource-loadandvalidatedatafrompdb?view=visualstudio) checks replicated PDB signature/age against the executable. This is an available documented identity principle, not a selected new DIA implementation dependency.

[Exact-symbol mode](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/symbol-options) rejects discrepancies; LOAD_ANYTHING and ignoring CodeView records weaken matching. [`.reload /i`](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-reload--reload-module-) explicitly bypasses PDB version mismatch and is prohibited. Matching files still cannot cure the trace's process-context ambiguity, missing frames or stale module context. Module-range membership plus a plausible name is insufficient to certify the originating process. Unresolved, truncated, ambiguous or nearest-symbol-only frames remain unknown, never inferred into a source owner.

[Microsoft's public symbol service](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/microsoft-public-symbols) supplies free access and uses TLS1.2+; this is not an authenticated-account requirement. [Credential-provider behavior](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/programming-custom-credential-providers) depends on server authentication responses. [SymSrv proxy/authentication behavior](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/firewalls-and-proxy-servers) can introduce authentication requests; CDB defaults to refusal and NO_PROMPTS suppresses prompts. Those defaults do not prove zero network attempts or absence of configured provider invocation.

For this bounded context choose **zero online symbol/download/cache-fetch activity during diagnosis**. Require an independently authorized, pre-provisioned, local-only immutable manifest, at most16 exact files and256MiB total, each at most64MiB. These are proposed fail-closed caps, not measured sufficiency. Own private PDB plus any required exact-OS symbols must already fit, with no fallback server, source server, alternate store, credentials or cache eviction/retry. Missing required symbols refuse the attribution stage; optional frames become unknown. Public symbols are not guaranteed for all internals. The [symbol-path contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/symbol-path) supports local paths and distinct server caches, but automatic server resolution has no reviewed total download-count/bytes/latency guarantee. [Cached files survive sessions](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/using-a-symbol-server); they need explicit disposable ownership and deletion. No symbol package was fetched here.

This violates the no-global/IFEO/AppVerifier-change boundary and adds instrumentation/log lifecycle. Reject here, not a fallback.

- Kernel/global tracing, gflags, private Nt process-table formats, live API interception, PSS trace-section reverse engineering, dump upload, second observer target thread and retained-handle duplication are outside scope. No PSS census or creator-lifetime guess is revived.
