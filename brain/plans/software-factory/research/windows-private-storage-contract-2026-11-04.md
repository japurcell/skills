# Windows private SQLite storage prerequisite

Read-only C1 decision, 2026-11-04. Scope: `T16-cleanup-C1-Windows-private-storage-decision`, subordinate to existing C1 Windows qualification. This is a proposed contract and finite proof plan, not an implementation release, native acceptance, ACL repair or Windows support claim.

## Decision

Keep Windows C1 admission unqualified. Select a narrowly scoped, Windows-only, in-process Node-API storage binding as the prerequisite design. It must implement private creation for explicitly initialized new storage and a retained handle-based privacy/identity lease for an existing-only reader. Do not write an always-refusing platform adapter as a substitute for this capability. Do not replace the current sidecar predicate until the complete positive Windows route is qualified.

The binding is preferable to extending placement PowerShell because its native object handles can remain in the same process across `DatabaseSync` open, transaction establishment, every returned read and close. This avoids adding another runtime child, but it does NOT inherit qualified loader/bootstrap/image authority. Those are explicit unmet gates below. There is no documented standard Node owner-SID/DACL query identified in the pinned filesystem API. Windows `chmod`, mode bits and `fs.access` cannot establish this policy. [Node 24.22.1 filesystem](https://nodejs.org/download/release/v24.22.1/docs/api/fs.html)

It identifies the failing POSIX-bit predicate, establishes neither DACL insecurity nor Windows privacy, and still fails the genuine positive expectation. All original12, production privacy guards and native positive expectations remain mandatory. The separate synthetic `child.error` work belongs to another actor.

## Meaning of PRIVATE and the trust boundary

Proposed initial profile: one existing, trusted repository on one local Windows host, normal non-impersonating process identity, authenticated pinned Node/release code, cooperative same-user factory writers. Privacy means the current owner/DACL policy excludes other ordinary principals from reading or modifying the factory directory and DB/sidecars, and the reader remains bound to the admitted local namespace and objects while serving data.

Trust the current token user, LocalSystem, and local built-in Administrators as principals capable of administering the storage. Those privileged principals, kernel/filesystem/filter integrity, trusted OS namespace, trusted running code, and malicious code under the same user are outside the confidentiality/integrity adversary. Do not claim protection from an administrator, backup/restore privileges, injection into Node, or a hostile same-user thread modifying a DACL between checks. Do not claim historical confidentiality or revocation of handles another principal obtained before admission. Private creation provenance and trusted custody are prerequisites for such stronger claims, not facts obtainable from a present DACL.

The canonical Git common directory is the selected trusted repository anchor. The host namespace above it is a prerequisite, not a new general Windows sandbox. The lease checks and holds the resolved path chain to detect/restrict ordinary rename/reparse drift; it cannot make all DOS-device/mount mappings, hostile same-user namespace actions or concurrent security-descriptor updates atomic. Microsoft explicitly says `GetSecurityInfo` does not handle concurrent descriptor changes. Any observed change fails closed; absence of an observed change is not universal race immunity. [GetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo)

## Exact proposed ACL profile

This deliberately rejects many secure but more complicated ACLs. It is a sufficient private profile, not a general effective-access engine.

1. Obtain process token with `OpenProcessToken(..., TOKEN_QUERY, ...)`, query `TokenUser` with `GetTokenInformation`, validate the SID, retain a copy internally. Reject thread impersonation for this initial profile; an error other than the documented no-token condition is unknown. Compare binary SIDs, never localized names, environment USERNAME or string prefix membership. Use well-known LocalSystem and BuiltinAdministrators SID constructors/comparisons, not account lookup. These two privileged trustees are optional, not required for a passing user-only profile. [OpenProcessToken](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocesstoken), [GetTokenInformation](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-gettokeninformation), [OpenThreadToken](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openthreadtoken), [well-known SIDs](https://learn.microsoft.com/en-us/windows/win32/secauthz/well-known-sids)
2. Factory directory, main DB and present sidecars: owner must equal that exact TokenUser SID. Not merely a token group, Administrators, SYSTEM, CREATOR_OWNER placeholder or a SID that the process can read.
3. Retrieve owner plus DACL from the SAME held object via `GetSecurityInfo(handle, SE_FILE_OBJECT, OWNER_SECURITY_INFORMATION | DACL_SECURITY_INFORMATION, ...)`. Request no SACL and enable no privilege. Require a valid descriptor and a present, non-NULL, nonempty DACL. Missing and NULL DACLs are unsafe; an empty DACL is not a positive private working profile. [GetSecurityDescriptorDacl](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-getsecuritydescriptordacl)
4. Initial factory policy: protected DACL (`SE_DACL_PROTECTED`), 1-3 ordinary `ACCESS_ALLOWED_ACE_TYPE` entries, one per permitted trustee, no duplicate trustees. Each grants exactly `FILE_ALL_ACCESS`, with `OBJECT_INHERIT_ACE | CONTAINER_INHERIT_ACE`, effective on this directory. No deny, object-specific, callback/conditional, unknown, inherit-only, no-propagate or unresolved generic trustee entries. Require TokenUser's entry; SYSTEM/Administrators optional. Reject foreign trustees even if apparently harmless. Protection prevents upstream broad ACEs entering future sidecars. `GetSecurityDescriptorControl` reads the protection state; protected does not itself mean private. [descriptor control](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-getsecuritydescriptorcontrol), [ACE inheritance](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules)
5. DB and sidecars: same 1-3 trustee/full-control policy, entries effective on the object, either explicit/protected or inherited from this admitted factory. An inherited entry is acceptable only with the same exact trustee/mask policy, no inheritance-only flags and no broad entry. Revalidate the parent too. Do not treat the inherited flag as a certificate of origin. Full control is a consciously narrow provisioning profile for the same-user writer and SQLite bookkeeping; admission handles themselves request no write authority. Use SDK `FILE_ALL_ACCESS`, not numeric guesses or .NET enum parsing. [file access constants](https://learn.microsoft.com/en-us/windows/win32/fileio/file-access-rights-constants)
6. The Git common directory need not be confidential. Its effective ordinary allow entries may grant outside principals only the read/list/traverse/read-attributes/read-EA/READ_CONTROL/SYNCHRONIZE set. No outsider may receive DELETE, FILE_DELETE_CHILD, WRITE_DAC, WRITE_OWNER, create-child, write-data/EA/attributes or other mutation rights. Its owner must be within the trusted principal set. Reject unrecognized ACE forms rather than attempt general deny/group resolution. Higher OS-managed ancestors remain part of the trusted-host prerequisite. Factory and every child still need their own DACL; a private directory alone does not authorize a child file. [file security and access rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights)

Parsing uses documented descriptor/ACL validation, `GetAclInformation` and `GetAce`, with validated ACE lengths/SID bounds, SDK masks, bounded buffers and fail-closed unknown types. Proposed implementation limits: descriptor at most 256 KiB, ACL at most 64 KiB, at most 256 ACEs before policy-specific smaller limits; no unbounded enumeration or retries. These are proposed refusal caps, not measured timings. [GetAce](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-getace)

## Held-object and path protocol

Private native state owns all handles and binary identities. The JS caller cannot supply a raw HANDLE or SID, choose an executable/helper, select arbitrary native APIs, change DACLs through the reader, or receive an ACL dump.

- Accept only the already selected canonical local common directory and fixed child names `factory`, `history.sqlite`, `history.sqlite-wal`, `history.sqlite-shm`, `history.sqlite-journal`. Reject ADS, UNC/device paths, unexpected suffixes, ambiguous normalization and unknown placement. Internally use a normalized volume-GUID representation; do not change process CWD or DOS mappings. Fix a finite path/segment cap and refuse excess.
- Walk the canonical existing chain component by component from its trusted local volume. Open each directory with `OPEN_EXISTING`, `FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`, noninheritable handles. Query its attributes before descending; reject every reparse point, not only symbolic links. OPEN_REPARSE_POINT on the final component does not establish safety of intermediate components. Hold the common/factory and chain handles for the view's lifetime.
- For the chain and main DB, request `FILE_GENERIC_READ` (which includes READ_CONTROL and read attributes) and share `FILE_SHARE_READ | FILE_SHARE_WRITE`, deliberately omitting FILE_SHARE_DELETE. Use genuine read access rather than assuming an attributes-only handle pins deletion. Never request write, DELETE, WRITE_DAC, WRITE_OWNER, ACCESS_SYSTEM_SECURITY, OPEN_ALWAYS or truncate/create flags in admission. Sharing conflicts are refusal/unknown, not permission to weaken sharing. Native qualification must prove the chosen handles coexist with the actual pinned SQLite writer and prevent the intended owned rename/delete cases. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
- Query `FileAttributeTagInfo`, `FileStandardInfo` and `FileIdInfo` with `GetFileInformationByHandleEx`; also require `GetFileType == FILE_TYPE_DISK`. Require directories where expected; each DB/sidecar must be a normal disk file, no reparse attribute, `NumberOfLinks == 1`, not delete-pending. Store the 128-bit FileId plus VolumeSerialNumber internally; an unusable/unknown identity refuses. Do not substitute Node `ino`, a path string or content digest for Windows object identity. [handle information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex), [attribute/tag](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_attribute_tag_info), [standard information](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info), [file identity](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info), [file type](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfiletype)
- Obtain the held object's normalized final path through `GetFinalPathNameByHandleW` and compare the fixed expected parent/name relationship internally. Reopen the fixed expected canonical path to a temporary handle, compare volume/FileId with the held object, and recheck chain/factory security. Do this immediately before SQLite open, after BEGIN/first snapshot, and before and after each method. A matching string alone is not identity. [final path by handle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew)
- Open existing sidecars with `OPEN_EXISTING`, the same read/security metadata rights and `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`. Preserve their handles/IDs internally, but allow SQLite's own lifecycle sharing. Do not deny-delete-pin all sidecars without proof: that can interfere with WAL/SHM cleanup. Validate their DACL/type/link/identity before and after reads. Once a sidecar is admitted for an active view, unexpected disappearance or replacement invalidates the lease, even if the replacement is independently private. A newly appearing sidecar is admitted only through the bookkeeping transition below. File-not-found is allowed solely for an optional sidecar at a defined observation; access-denied/sharing/other error is never interpreted as absent.

This is a pathname binding under the stated trusted same-user boundary. Node's documented `DatabaseSync` accepts a path, not an externally supplied Win32 handle. The addon cannot honestly report that it inspected SQLite's internal handle. The held main/ancestor objects, private mutation namespace and bracketing reopens are the chosen bounded bridge. If policy instead requires atomic binding against hostile same-user rename/DACL actors, this design is insufficient: a qualified SQLite VFS/native SQLite ownership route would be a different, larger runtime decision, not a silent addon extension. [Node SQLite constructor](https://raw.githubusercontent.com/nodejs/node/v24.22.1/doc/api/sqlite.md)

## SQLite and explicit private creation

Keep `readOnly:true`, the current timeout, one BEGIN transaction and existing endmark/integrity checks. No `immutable=1`, exclusive locking, writable fallback, journal-mode change, checkpoint, schema migration or fresh DB from the reader. Immutable is wrong for a live concurrent writer. Readonly database opening can still require WAL/SHM creation or changes, and readers retain a WAL endmark while writers commit. [SQLite WAL](https://www.sqlite.org/wal.html)

Before SQLite open record the main and existing-sidecar identities/presence. After first snapshot and around reads admit only validated private, same-owner, regular, single-link SHM bookkeeping, and a newly created WAL only when exactly zero bytes. No new journal or nonempty new WAL is an allowed read-only transition. Preserve DB and pre-existing WAL bytes against reader-caused changes. Concurrent writer commits legitimately append WAL, so prove endmark stability plus writer-attributed changes; do not require the entire live WAL to remain byte-identical while the writer commits. Separate writer-paused intervals prove the reader-only byte-preservation claim. SHM byte equality is not required.

At terminal close only, previously validated SHM or a newly created still-zero WAL may disappear as bookkeeping. Do not excuse disappearance or replacement of a pre-existing WAL as reader bookkeeping. Any writer-caused checkpoint/removal needs independent fixture operation evidence and must not be confused with reader-only preservation. Unexpected identity changes during a served read still invalidate the lease.

Windows private creation is necessary for an honest positive, including the unchanged original12 whose fixture calls the real initializer. Existing `mkdir(...mode:0700)` and `open(...0600)` are not private Windows provisioning. A later released initializer must create its NEW factory directory with an explicit protected profile at birth and create the NEW main DB exclusively with explicit private security before SQLite opens it. Existing factory/DB must be inspected and refused on mismatch, never chmod/DACL-normalized by a read or silently repaired by initialization. SQLite-created sidecars must inherit the private factory policy and be inspected immediately afterward. The initializer stays explicit and exclusive; the reader stays existing-only. This requires a separate creator capability in the same narrow binding, not an ACL mutation API exported to general callers.

## Closed result and ownership

Suggested internal contract, names illustrative until source release:

    type Role = 'anchor' | 'factory' | 'database' | 'wal' | 'shm' | 'journal';
    type Reason = 'unsupported' | 'identity-context' | 'owner' | 'dacl'
      | 'type' | 'reparse' | 'links' | 'namespace' | 'changed'
      | 'bookkeeping' | 'access' | 'sharing' | 'native' | 'closed' | 'close';
    type Check = { state: 'valid' }
      | { state: 'refused' | 'unknown'; role: Role; reason: Reason };
    type Admission = { state: 'admitted'; lease: PrivateStorageLease }
      | Exclude<Check, { state: 'valid' }>;

`PrivateStorageLease` is a native-branded opaque owned capability with recheck and explicit close, not a caller-forgeable record or serializable identity. Native state fixes the input names and before/after phase internally; no path argument on recheck. Distinguish known policy mismatch (`refused`) from inability to establish facts (`unknown`). Both prevent a returned read. Unknown native codes map to `native`; do not emit original errors, raw Win32 codes, SID, username, pathname, environment, file ID or descriptor text. Fixed role/reason facts suffice.

Native handles are noninheritable, never duplicated into children and never borrowed from SQLite. Every successful open has exactly one owned close. Temporary reopen/token handles close on all outcomes; descriptors returned by GetSecurityInfo are released with LocalFree after bounded validation/copy, without separately freeing interior pointers. Partial admission failure unwinds every acquired resource. Retain no descriptor pointers after free.

Close SQLite first while the lease still protects the namespace; final-check allowed bookkeeping, then close the lease in reverse acquisition order. Attempt every owned release even after another close fails; terminal close state is `unknown/close` if any release cannot be established. No second CloseHandle on an already closed value, no successful data after invalidation, no automatic reacquisition/retry. Explicit close is required; Node-API finalizer/environment cleanup is a safety net only. `CloseHandle` success is not a process-lifetime or all-object-leak proof. [CloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-closehandle)

The binding has fixed operation/count/input/output caps and no retry loops. Synchronous Win32 metadata calls on local storage do not document a hard wall-clock completion guarantee; caps on accepted returned descriptors do not bound an OS call's internal allocation or scheduling. No in-process 10-second kill guarantee is claimed. Qualify latency under the unchanged product/test profile, and retain the existing synchronous filesystem trust assumption. If a separately cancellable native-call deadline is required, resolve that architectural gate before implementation rather than silently increasing a budget or adding an unqualified child.

## Loader/bootstrap gate and alternatives

Use plain stable Node-API, with an explicit supported API version, Windows x64, the pinned Node/SQLite release and supported OS profile. No direct V8/libuv/private Node handle extraction, runtime compiler, global install, npm lifecycle build or alternate SQLite. Node-API provides an ABI contract, not trusted-image admission or dependency security. [Node-API](https://nodejs.org/download/release/v24.22.1/docs/api/n-api.html)

Before any addon load, a trusted outer bootstrap must authenticate exact release inventory and addon bytes; bind its canonical regular/single-link image and parent identity; prevent untrusted replacement during load; qualify all loaded dependencies and their resolution; and retain the required image/parent custody. Hashing a pathname then requiring it is insufficient. Prefer an artifact with no private dependent DLLs and a fixed reviewed system dependency closure, but verify the actual PE imports/load behavior. A full addon path does not itself qualify its dependency search. Do not mutate global DLL search/registry policy. [DLL security](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-security), [LoadLibraryExW](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw)

Circular bootstrap is unresolved today: code cannot establish the trust required to execute itself by first running its own ACL function. Current Windows installed-tree/private ownership is unqualified. A trusted separately qualified installer/launcher custody mechanism must supply the pre-load authority, or the native mechanism must be incorporated into an independently authenticated bootstrap with an explicitly accepted trust basis. The current pin alone and the already-executed JS reader are not that proof. Source implementation should wait for this exact loader/custody decision; do not add an unqualified `.node` inventory slot and call it support.

Selected bootstrap prerequisite is an authenticated prebuilt addon placed in a canonical, independently provisioned trusted private code root before its first load, with that root/image custody retained through loading. The trusted provisioner must establish this independently of the addon being loaded. A fixture can obtain that custody from a root-approved disposable host setup; installed Windows support needs its own qualified bootstrap producer. Neither producer is assumed to exist today. No global install is proposed.

Rejected alternatives:

- One-shot `Get-Acl`/PowerShell/.NET pathname metadata: not a retained same-object capability; host, output and identity have separate proof obligations. Per-call snapshots cannot preserve handles across SQLite calls.
- Persistent fixed native/PowerShell helper: can theoretically own handles but needs a new bounded protocol, authenticated code-image/dependency/namespace admission, child lifetime and closure. The existing placement child does not supply these. Latest full-creator `41804985008` still fails the strict count condition although all reached closes are true; no helper is admitted. This route is currently blocked on those exact external-native gates, not authorized by using an inbox executable name.
- Transferring helper handles into Node or a custom VFS: more authority and ABI/lifecycle surface; no documented existing seam here. Not needed under the selected cooperative same-user boundary; a future hostile same-user atomicity requirement must reopen the runtime decision explicitly.
- ACL relaxation, chmod, fs.access, POSIX-bit exceptions, test skips/expectation flips, immutable SQLite or an always-refusing shim: do not provide the required positive capability.
