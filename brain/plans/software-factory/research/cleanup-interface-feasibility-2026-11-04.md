## Exact backup authority, without a registry or discovery scan

Use a discriminated result `OwnedBackup | ProtectedBackup | BackupRefusal` for one caller-supplied tuple. Never enumerate the filesystem or accept a caller-supplied path. `maintenanceBackupPath(common, operationId, backupId)` already validates UUIDs and derives `factory/maintenance-backups/<operationId>/<backupId>/history.sqlite` (`src/maintenance-backup.ts:11`). That derivation only locates bytes.

**Completed installed upgrade: a sufficient join is available in principle, but no current public function implements it.** Add a keyed reader for the unique committed `upgrade.completed` event with that operation ID. Its repository/claim/selection/receipt ID/hash/identity and original hashes are committed at `src/store.ts:1598`. Read exactly `factory/upgrade-<operationId>/new-receipt.json` with `readUpgradeInstalledReceipt` (`src/upgrade-installed.ts:19`); require the same committed receipt hash, identity and IDs. This authenticates the receipt's `backupReceiptSha256`, `originalSha256` and `intentSha256` (`:12`). Read the exact selected backup's `backup-receipt.json`; its bytes must hash to that committed `backupReceiptSha256`. Require its operation/backup/repository IDs, receipt ID, selection digest, source shape/release/identity, request digest, backup identity/hash/byte count and count digest (`src/maintenance.ts:444`). Then:

- Read `original.json` only at the authenticated upgrade's fixed path, check `hash(JSON.stringify(parsed)) === originalSha256`, and match root/common/repository/factory identity to the current canonical repository. The saved original contains these fields at `src/upgrade-original.ts:24`. It is historical evidence, not a request to reassert that the old installation is still live. `assertOriginalInstallation` (`:36`) intentionally checks live old trees and is inappropriate after successful replacement.
- Read the exact `intent.json`; check its byte hash against the authenticated receipt and its operation/repository/claim/selection/original/backup-receipt fields (`src/upgrade-publication-state.ts:12`, `:54`). Do not call the live-claim `readUpgradeIntent` with fabricated claim data. Its field relationships, not a fake capability, inform the new retained decoder.
- Verify `backup-request.json` is exactly the fixed source history path and selected target and hashes to the authenticated backup receipt. Verify selected backup regular/private/single-link file identity, length and hash using `backupFileDigest` (`src/maintenance-backup.ts:23`). Open only this immutable copy to check known source shape, integrity/foreign keys, count digest, repository identity/release/ready state and its sole original claim. The authenticated upgrade receipt supplies the originating `claimId`, which the forward backup receipt itself omits. Validate copied claim kind/operation/backup ID/source/selection and source-shape relationships. Never compare historical counts to today's live counts.
- Forward backup receipts do not persist directory birth identities. Do not invent them. The committed receipt chain supplies file ownership and byte identity; validate canonical private ancestry under the authenticated factory, record its currently observed directory identities in the cleanup impact, and recheck those identities before touching the selected file. If the eventual exact-file deletion implementation cannot preserve that path/identity boundary on a supported platform, refuse rather than infer historical directory ownership.

The committed event -> committed receipt -> backup receipt -> file/copy chain authenticates the selection; matching a loose sidecar hash does not. Retain all receipts, intent, original records and operation facts after any future deletion. Remove only the selected `history.sqlite`, never its directory or evidence sidecars. This leaves historical installed ownership verifiable: the retained installed reader uses `backupReceiptSha256` rather than requiring the backup file (`src/upgrade-installed.ts:53`, `:62`). New deletion receipts distinguish intentionally absent from missing/tampered.

**Incomplete forward upgrade:** the exact current claim retains `backupId` and full `forward.backup` (`store.ts:56`), verified by `maintenance.ts:346`. Return it as protected, along with operation/phase/claim/stage/marker dependencies. Any incomplete operation blocks a new cleanup admission anyway. A ready row with an upgrade marker is still incomplete; marker recovery after ready is explicit (`upgrade-publication.ts:86`). Cleanup must not replace recovery.

**Dependency preparation:** exact current claim, immutable `backup-attempt.json`, request, bound receipt and copied original claim establish concrete ownership (`dependency-maintenance.ts:146`, `:160`, `:186`, `:206`, `:272`). Return protected. The receipt includes originating claim ID, source identity/schema/release, original completion/ownership digests, attempt/request digests and full backup file facts; the attempt also binds root/operation/backup-directory identities. Present code has no dependency terminal completion producer. Until its later accepted publication task preserves and authenticates these facts after releasing the claim, completed dependency backup deletion is unsupported. Do not weaken current same-owner snapshot checks to accommodate cleanup.

**First install:** its intent starts with `backupId:null` (`maintenance.ts:76`) and its receipt/completion contain no backup ownership link (`install-publication.ts:20`; `store.ts:1561`). A first install alone proves no backup is selectable. A later completed upgrade from that baseline can use the sufficient join above. ## Small additive typed read contracts

Add types and pure decoders in proposed `src/cleanup-references.ts` and `src/cleanup-backups.ts`, with narrow SQL methods in `RepositoryStore`. No arbitrary predicates, JSON paths, provider decoding, filesystem search, scheduler or framework. Use string decimal cursors for new rowid/event interfaces, validated as signed SQLite 64-bit nonnegative integers; avoid adding numeric precision limits to new APIs.

Proposed signatures, not existing APIs:

- `readCleanupSnapshot(): CleanupSnapshot` returns repository ID/release/schema, database identity, source-domain high-water cursors and a digest of the typed recovery state. Internal claim-bound variant also checks exact `MaintenanceHandle`, sole claim and live owner; tokens never leave the controller.
- `pageCleanupCaptureHeaders({after, through, limit, byteBudget}): Page<CaptureHeader>` keyset-pages **all** headers, so sparse reports do not cause unbounded hidden row scanning. Header includes id/invocationId/attemptId/channel/state/lastSequence/logicalPayloadBytes, no text. `measureCleanupCaptures(exactKeys)` uses keyed SQL sums of `octet_length(text)` and returns zero/missing/pruned distinctly. These are logical bytes, not SQLite file bytes reclaimed.
- `pageCleanupInvocationFacts(...)` and `pageCleanupAttemptFacts(...)` return strict typed reference metadata plus `opaque` records carrying only stable ID/cursor/reason/size/digest. SQL computes `octet_length(data)` before `CASE ... THEN data ELSE NULL`; never fetch oversized JSON and then decide it is too large. Keep general invocations/attempt rows intact. Root/follow-up input references, priorAttemptId and agent capture IDs are the only persisted reference fields decoded here.
- `readCleanupCapture({invocationId,captureId,after,limit,byteBudget})` exposes an explicit budget and exact ownership, with header state/channel/sequence on every page. Reuse the underlying bounded `readCapture`, adding a typed header-only lookup and continuity checks rather than routing through eager previews. `readCleanupAttempt(exactKey)` and `readCleanupEvent({invocationId,cursor})` also apply SQL bounds and ownership checks. Event ownership follows explicit invocation first, otherwise exact attempt/capture ownership, as `learning.ts:211` requires.
- `readCleanupOperationEvidence({operationId})` returns bounded **known event kinds** and the exact current claim/marker relationships for this operation; `inspectCleanupRecoveryDependencies()` returns `clear | blocked` plus typed current dependencies, never assumes a missing claim means marker recovery finished. `resolveOwnedCleanupBackup({operationId,backupId})` performs only the exact authority join above. No backup-list discovery API is needed. A page over a caller-selected tuple list is sufficient for display.
- `inspectCleanupSelection(repository, selection, bounds): CleanupImpact` produces advisory read-only output. `CleanupSelection` is a tagged union of exact invocation/capture pairs **or** exact operation/backup pairs, never a path/glob/age threshold. Bound requests to 100 captures or 20 backup tuples, unique and sorted canonically. An invocation/run view can help a person choose, using existing run/invocation pages, but final confirmation lists the expanded exact capture IDs; no silent broadening.

Default bounds: rows/page <=100, metadata page <=256 KiB, invocation/attempt metadata record <=64 KiB, event/claim/sidecar records <=8 KiB (matching current writers), chunks/page <=20 and <=256 KiB, report bytes <=131,072, typed agent-input evidence <=393,216. A report is not exempt from its bound because its parser reads incrementally. Source report bytes are fully measured before concatenation; text is released after decoding. Keep the extraction producer limits (6 sources, 12 attempts/events per explicit source, 40 examined captures per source, 4 proposals, 16 supporting/contrary references and 12 suggested cases: `templates/workflows/learn.ts:13`, `:61`, `:79`) and evaluation limits (3 cases, two repetitions per side: `evaluate.ts:21`, `:364`). Define explicit caps for nested adoption/revert objects and canonical IDs (<=256 UTF-8 bytes).

For the first implementation, cap the whole analysis at 100,000 source rows, 1,000 reports, 16,384 normalized nodes, 65,536 edges, 32 MiB retained analysis state and 30 seconds elapsed; these are refusal limits, not truncation permissions. Each SQL page and decode is small, check the deadline between pages/records and never claim a hard interruptible SQL deadline without a verified runtime facility. Typed exact operation-event lookups can use SQL equality with `LIMIT 2`, without broad JS event enumeration. If measured scale later requires an operation-ID/reference index, justify a narrowly typed index in a separate schema/forward-migration task. Do not add DDL or a permanent reference registry merely to simplify this initial bounded implementation.

## Retained-reference closure and refusal rules

Preserve all run/worktree/invocation/operation/attempt rows, lineage, admission/settlement outcomes, allowance ledger, claims/clearances, native sessions, events, notifications/acknowledgments/preferences/reminders and capture headers including sequence. Ordinary output cleanup is not accounting repair or deletion of operational history.

Build a bounded ID-only graph from recognized persisted contracts. Header/fact pages stream through the analyzer; never accumulate full history or concatenate unlimited payloads. A referenced attempt conservatively protects all its owned captures and its prior-attempt chain. Cycle detection keys include object kind and owning invocation; a cycle does not itself authorize dropping evidence. Required edges are:

Recognition is a persisted-format claim, not source-code authentication. Current lifecycle stores a workflow path/selectedCommit and generic report bytes (`lifecycle.ts:98`, `:123`); `build.ts:50` does not persist a compiled closure digest. For learn/evaluate v1, require the saved workflow identity, declared version, exact bounded schema, correct attempt operation/validator identity and owned raw/validated/input relationships accepted by the retained evidence contract (`learning.ts:166`, `:190`, `:227`). Do not treat path or report channel alone as proof. Historical unversioned ordinary change/audit reports and custom producer variants remain opaque unless a separately explicit typed compatibility rule establishes their complete reference contract. A future runtime-emitted producer/reference-contract marker may make new variants recognizable; never backfill it from filenames or claim a historical authored-source digest exists.

Unknown producer/version, unknown fields carrying an unrecognized format, malformed JSON/metadata, incomplete/pruned/missing/foreign evidence, inconsistent digest/ownership, partial reports, overlarge objects, nonadvancing pages, incomplete closure or any budget exhaustion yield a blocker. A global opaque report can name any capture, so it blocks payload cleanup unless a typed rule proves non-dependence; it is never counted as reference-free. A report with an expected limitation still retains all resolvable references and never converts missing evidence into permission. Keep distinct reasons and the exact blocker IDs, without echoing untrusted raw text into diagnostics.

Default eligibility requires a finalized invocation, no occupied activity/uncertain owner, a closed capture and complete proof it is outside protected closure. Closed partial/unknown ordinary stdout/stderr may be candidates only if that proof is complete and their uncertainty is displayed; open captures refuse. All report/request/root-input payloads remain ineligible. Other unprotected channels require explicit per-capture impact review. Already-pruned selected captures report their retained headers and prior cleanup receipt; no inference that missing chunks alone prove intentional pruning.

Exceptional selection names exact otherwise-protected non-operational payload IDs, computes every reverse-dependent retained report ID to closure, displays that later retained verification will fail and obtains explicit confirmation of that exact impact. Never cascade, drop report/action/question facts, or widen the capture set. An opaque impacted record or unresolved dependency refuses. Persist deliberate breakage so a readable retained report can be labeled no longer verifiable, while existing prepareAdoption/prepareRevert fail closed.

## Later operation and mutation interfaces

Keep the 8 KiB claim small. Add a versioned cleanup binding containing compact selection/impact/snapshot digests, current progress and new backup binding; immutable operation-owned sidecar pages carry selections and impact. Each page <=8 KiB, numbered and hash-chained under a compact manifest; page/node/byte totals are bounded. Existing `readPublicationRecord`/`writePublicationRecord` enforce 8 KiB and absent-only writes (`install-publication-state.ts:11`, `:31`, `:52`), so do not pass a large impact object to them.

Proposed controller seams: `admitSelectedCleanup(...) -> MaintenanceHandle`, `prepareCleanupImpact(handle) -> CleanupImpact`, `confirmCleanupImpact(handle,{impactSha256,exactExceptionalCaptureIds,operatorConfirmed})`, `prepareCleanupBackup(handle)`, `pruneSelectedCapturePage(handle,{impactSha256,after,limit})`, `deleteSelectedBackup(handle, exactTuple)`, `completeSelectedCleanup(handle)` and exact-operation `resumeSelectedCleanup(...)`. These are distinct from advisory `inspectCleanupSelection`; an advisory digest is not an authorization token.

Recompute impact under the exclusive live claim, preserve exclusion through final display/confirmation, backup and mutation, and reject stale selection/identity/phase/token. A bounded foreground controller may wait for a small exact confirmation message on stdin after displaying final impact; timeout/decline before mutation follows a verified no-change cancellation path, not generic `releaseClaim` (which forbids typed maintenance claims at `store.ts:1856`). No daemon or durable execution engine. Reuse qualified stage/handoff/lifetime machinery with explicit cleanup dispatch and backup-owner transfer semantics; do not reuse a copied dependency backup's owner capability.

Snapshot binds DB/repository/schema/source high-water marks **and content digests** for relevant headers/metadata/report bytes and exact selected payloads. High-water marks alone miss updates to existing JSON. Revalidate before first mutation and on resume, accounting only for the exact operation's committed administrative/progress suffix. Fresh backup uses a newly allocated private directory and absent target, with exact attempt/request authority, consistent copy and integrity/schema/repository/count verification before any prune or delete. Keep this new recovery copy and its evidence; it cannot be among the selected old backups.

Chunk pruning is new closed-to-pruned mutation, not `appendCapture` (`store.ts:1902`). Each bounded transaction asserts claim/impact/expected header, deletes only exact selected chunks, sets state `pruned` while retaining id/ownership/channel/sequence, and commits its exact progress/event receipt atomically. Large captures need bounded chunk batches with durable in-progress state; do not expose a partially removed capture as complete. A compact claim checkpoint can mark that selected capture pruning is in progress while readers/startup remain excluded, and final state changes only when its selected chunk range is exhausted. Crash resumes exactly that range; old outcome/debits never change.

Backup deletion is a separate selection and task. Commit exact deletion intent before the filesystem call and a durable result after it. On interruption, absence without matching committed intent is a refusal; a matching one-file-ahead state may be reconciled only with the retained file/parent authority and exact intent. No recursive remove, linked file, current DB/WAL/SHM/journal, stage or incomplete operation's recovery copy. Retain receipt sidecars and deletion tombstone. Finish only after all exact results and unchanged installed ownership are validated, atomically return ready and release the sole claim. Use `maintenance.cleanup_completed` (and cancellation/progress event kinds), leaving installation ownership selection unchanged; do not emit unsupported `cleanup.completed` until its explicit installed-reader interpretation is implemented and proven.

Optional compaction is a final independent task, disabled until native proof. Show logical selected bytes separately from DB/WAL/backup file sizes and SQLite page/freelist counts. Prove relevant checkpoint/quiescence, temp placement and available capacity on each actual filesystem with conservative reserve after a verified retained backup. Low space, lock, interrupted checkpoint/VACUUM, disk error or unknown temp placement leaves backup, store and incomplete operation intact. Never delete more to make room, replace the DB, recreate an empty store, salvage or automatically retry destructive work. The prior cleanup decision supplies the exact-version backup/space rationale; this source-only packet makes no new runtime claim.
