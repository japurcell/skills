## Input and deterministic public output

For `inspect-cleanup`, Python parses all flags and reads and validates selection and bounds before any installed ownership or backend store read. Use a bounded descriptor-based regular-file read; reject non-regular files, oversize reads, changes during read and strict UTF-8 JSON with BOM, duplicate object keys, trailing data, lone surrogates, unknown fields or non-finite values. Existing `installed-state.ts:122-126` calls `readActiveInstalledCompletion`, whose `store.ts:452-454` path reads the existing SQLite store, so this order matters. The snapshot entry validates the staged bounded input again before its ownership read; no user JSON confers authority. Plain command help alone prints statically. Limit selection file to 256 KiB; bounds file to 8 KiB. Stage them as separate bounded files plus a small request referencing those exact private stage paths; do not embed all data in an existing 8 KiB maintenance request. These are input transport caps within existing page/state ceilings, not expanded analysis allowances. Selection object is exactly one of:

    {"kind":"captures","captures":[{"invocationId":"...","captureId":"..."}],"exceptional":[],"reviewNonOutput":[]}
    {"kind":"backups","backups":[{"operationId":"...","backupId":"..."}]}

Capture selections contain 1-100 unique exact pairs; backups 1-20 unique exact tuples. IDs are valid Unicode UTF-8, nonempty, NUL-free and at most 256 bytes; retain exact bytes, with no Unicode normalization or colon concatenation. `exceptional` and `reviewNonOutput` are disjoint explicit subsets of captures, each pair unique. Input order is accepted in any order. Match the accepted backend exactly: sort captures and their subsets by JavaScript string comparison of `JSON.stringify(['capture', invocationId, captureId])`; sort backups by comparison of `JSON.stringify([operationId, backupId])`. This is UTF-16 code-unit ordering of the escaped tuple string, not UTF-8 byte ordering. Order object properties exactly as shown above. Reject duplicates before sorting. The canonical representation is compact UTF-8 JSON with JavaScript JSON.stringify escaping, no BOM/newline; hash and pass the canonical semantic object to the backend. Selection is never expanded by channel, predicate, label or inferred path. Paths/revision/action labels in retained records are inert; no Git calls for them.

Bounds JSON is an object with only optional integer keys `rowsPerPage`, `metadataPageBytes`, `sourceRows`, `reports`, `nodes`, `edges`, `pages`, `stateBytes`, `payloadBytes`, `elapsedMs`; all values must be positive safe integers no larger than their existing defaults respectively 100, 262144, 100000, 1000, 16384, 65536, 4096, 33554432, 67108864, 30000. Reject zero, fractional, duplicate, unknown and increased limits; omitted means default. They may only tighten, not create truncation. Existing caps include 64 KiB metadata/record, 8 KiB event/operation data, 128 KiB report, 384 KiB typed agent input, depth 12 JSON, 64 embedded action objects, 128 report dependency depth, 20 chunks/256 KiB per capture read, 65536 bytes/chunk, and 100 records/256 KiB per metadata or public output page. All page, source, decoded bytes, state, deadline and traversal exhaustion blocks rather than truncates. Deadline is cooperative between records/pages.

The CLI calls the sole public async `inspectCleanupSelection(repository, canonicalSelection, bounds)`, which resolves repository identity internally and opens one genuine existing-only C1 WAL snapshot plus internally derived C2 recovery/tuple authority, rechecking identity and filesystem evidence. No raw DB, view, recovery assertion or ownership DTO comes from a caller. Page all invocation/attempt/header facts to high-water; bind raw metadata, reports, selected complete payload/sequence, required input/reference and C2 evidence into the content snapshot. Traverse recognized graph with dependent-to-dependency edges and bounded iterative cycle detection; reverse traverse from each explicitly selected exceptional payload to every dependent report, including transitive reports, with deterministic order. An opaque report anywhere blocks payload selection. Report, request and root input payloads remain protected; all retained metadata, history, events, lineage, claims, accounting and headers survive. Unknown/malformed/partial/missing/foreign/pruned evidence, an unproven prior prune receipt, inconsistent digest/ownership, cycle, recovery uncertainty or bounds exhaustion produces a blocker and never eligibility. Exact C2 backup results stay independent of payload closure but preserve their own protected/refused status.

Return one bounded public page per invocation, not the aggregate `CleanupImpact` arrays. Fixed envelope: `{version:1,kind:"cleanup-advisory",advisory:true,status,requestSha256,snapshotSha256,impactSha256,resultSha256,page:{index,count,publicPageSha256,records},summary:{selectedLogicalBytes,captures,backups,blockers}}`, where counts are integers and bytes are canonical decimal strings or null; page records are the backend's typed ID-only impact/backup/blocker DTOs. Never include raw report/input content, arbitrary exception text or paths. `status` is `inspectable` or `blocked`; blocked sets impact/snapshot digests null whenever completeness cannot be established, and all tentative eligible rows become refused. Exceptional records enumerate all affected report and attempt IDs and say verification will fail and explicit confirmation will be required by a future operation, but this route has no confirmation flag or capability. Logical byte totals are not physical space savings.

The actual `CleanupImpact` (`cleanup-references.ts:46-50`) has `advisory,status,impactSha256,snapshotSha256,blockers,captures,backups,pages,selectedLogicalBytes`; it has **no selectionSha256 field**. Preserve backend selection representation, exact `snapshotSha256`, `impactSha256`, and backend page hashes. Backend pages are hashed as SHA-256 of UTF-8 `JSON.stringify(records)` and the impact digest includes the original backend pages (`cleanup-references.ts:412-422`). Do not relabel or recompute these as public page hashes. Define new `requestSha256` as SHA-256 over compact UTF-8 JavaScript JSON.stringify of ordered `{domain:"factory-cleanup-public-request-v1",selection,bounds}`, where bounds contains every effective field in `CleanupAnalysisBounds` declaration order. Define `publicPageSha256` separately as SHA-256 over UTF-8 `JSON.stringify(records)` of the repacked public page. Define `resultSha256` over ordered `{domain:"factory-cleanup-public-result-v1",requestSha256,status,snapshotSha256,impactSha256,summary,pages}`, with `pages` the ordered complete list of `{index,publicPageSha256}`. Page zero returns this digest; later requests rerun the full analysis, validate the expected digest before returning the page, and refuse a mismatch with no page data. All request, result and page hashes are lowercase hex; changing bounds, selection, content or diagnostics cannot silently mix pages. An out-of-range page refuses.

Construct public pages only after the entire backend result and its existing digest/pages are complete. Preserve backend record order by traversing its pages in index order and each page's records in order; partition into consecutive public pages of at most 100 records. For each candidate append, serialize the complete final compact envelope plus newline (including all fixed-width 64-character digest placeholders and actual index/count), and require at most 262144 bytes; repeat deterministic packing until page count/index decimal widths stabilize. Pretty output must independently meet that same byte cap, or return a bounded refusal rather than silently overflowing. A single record unable to fit is a limit failure. Charge each extra public page and all retained public records/hash state and serialization bytes to the *same* existing `pages`, `stateBytes`, `payloadBytes` and cooperative deadline budget used by analysis, without lowering the requested backend bounds or silently reserving capacity. Minimal internal refactor is required because current `inspectCleanupSelection` returns only a completed DTO, not its live `Budget`: share a private budget-aware analysis/renderer path while keeping the public async API and existing backend digest algorithm unchanged. If budget or packing fails, discard all candidate pages and all eligibility claims, then return a single fixed-size blocked `limit` diagnostic with null snapshot/impact, no records from partial analysis, and freshly computed request/result/public-page digests; that failure envelope itself must fit and be accounted within the existing budget, otherwise return a fixed bounded stderr refusal with no stdout. No partial page can claim eligibility. This pagination is advisory, not a persistent snapshot or authorization.

Proposed public exits: 0 for a valid completed advisory, including `status:blocked`; 2 for malformed CLI/input or invalid page; 3 for installed binding/platform/repository/IO failure; 4 for stale `--expect-result`. Emit fixed redacted diagnostic code on stderr (`invalid-arguments`, `admission-refused`, `stale-result`) and no stdout on these errors. Keep help exit 0. This command-specific mapping must not change existing CLI exit behavior. Bounds exhaustion is a typed blocked result (exit 0), not a successful eligibility claim. Output framing and page size must include envelope/JSON newline overhead within 256 KiB, not just records; if it does not fit repack within the existing backend limit or block.
