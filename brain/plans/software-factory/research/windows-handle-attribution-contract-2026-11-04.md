## Decision

No reviewed documented own-process mechanism establishes all of retained-object identity, creation interval, creating API and responsibility for closure while preserving the original admission profile without observer effects. No missing-close repair is justified. Preserve the actual strict refusal.

PSS is documented and suitable for a bounded diagnostic handle-table/type census. It is not an attribution solution. DEFER even the smallest proposed PSS native experiment: a census performed after the original final result cannot distinguish excess handles from ordinary baseline entries or observation resources. A pair of earlier/later censuses adds observer effects and still cannot establish object identity or API responsibility. Neither discriminates the live explanations sufficiently to select a fix.

The next useful task is a bounded READ-ONLY feasibility contract for documented creation/close stack tracing, led by WinDbg `!htrace`, with Application Verifier Handles only as an explicitly assessed alternative. That task must resolve the gaps below before any source or native release. It must not assume that a finite display limit proves complete history, or that a stack proves a closure obligation. No native experiment is selected for immediate execution by this packet.

## What the documented mechanisms actually expose

`GetProcessHandleCount` reports the open-handle aggregate of the selected process, not an object inventory or creation history. It remains the authoritative original assertion. [Microsoft contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesshandlecount).

PSS `PSS_CAPTURE_HANDLES` captures table values; `PSS_CAPTURE_HANDLE_TYPE_SPECIFIC_INFORMATION` requests supported type information. Names, basic information and handle trace capture are distinct flags. Omitting VA clone avoids requesting a clone; it does not prove absence of internal allocations, references, handles or caches. No reviewed contract promises zero perturbation, instantaneous atomicity, or a cancellable/bounded capture. [Capture flags](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_capture_flags).

The finite PSS object enum is unknown, process, thread, mutant, event, section, semaphore. Unsupported types are unknown. A type is usable only when the entry's `PSS_HANDLE_HAVE_TYPE` validity flag is set; request flags are not proof of returned completeness. Types outside this vocabulary cannot be inferred from unknown. [Object types](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_object_type), [validity flags](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_handle_flags).

`PSS_HANDLE_ENTRY.Handle` is a value, not a documented retained caller-owned object reference. `CaptureTime` is information capture time. `CreationTime`, `HandleCount`, `PointerCount`, pool charges and granted access are explicitly reserved in this structure. They cannot be used to derive object age, generation, creation interval, identity or ownership. Type/name pointers are marker-lifetime data and may lack NUL termination. No field identifies the creating API or source owner. [Entry contract](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ns-processsnapshot-pss_handle_entry).

Consequently a repeated numeric handle, equal type, equal total or equal histogram is not a same-object proof. A changed histogram is type-composition evidence in that instrumented context, not proof that its positive bins are the original retained excess. A single census counts handles, not distinct objects.

`CompareObjectHandles` answers whether two currently valid kernel handles refer to the same underlying object. It does not turn stale captured values into live handles. Holding a `DuplicateHandle` result keeps another object reference and requires a close, affecting the lifetime being investigated. Duplicating all candidates therefore cannot be treated as a passive identity bridge. Neither operation identifies the creator or the party obliged to close it. No arbitrary sampled handle may be closed. [Comparison](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-compareobjecthandles), [duplication](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle), [kernel-object lifetime](https://learn.microsoft.com/en-us/windows/win32/sysinfo/kernel-objects).

## PSS ownership contract and why its smallest experiment is deferred

The smallest candidate would call `PssCaptureSnapshot(GetCurrentProcess(), PSS_CAPTURE_HANDLES | PSS_CAPTURE_HANDLE_TYPE_SPECIFIC_INFORMATION, 0, &snapshot)` once after the original probe returned. The documented API is Kernel32/processsnapshot.h, available since Windows8.1/Server2012R2, consistent with current Windows10 target headers. Success is the returned `ERROR_SUCCESS`, not `GetLastError`. [Capture](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psscapturesnapshot).

Use exactly one marker, created after capture with `PssWalkMarkerCreate(nullptr, &marker)`; default allocation uses the process heap. Walk `PSS_WALK_HANDLES` into one fixed `PSS_HANDLE_ENTRY`. `ERROR_NO_MORE_ITEMS` alone establishes normal walk completion. A proposed 4096-entry cap requires at most 4097 walk calls, with an extra successful entry causing capped/incomplete refusal, not a truncated census claimed complete. The cap bounds caller iteration, not snapshot allocation, capture latency or each synchronous call. [Marker creation](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psswalkmarkercreate), [walk](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psswalksnapshot).

After creation, attempt `PssWalkMarkerFree(marker)` once on every exit, then `PssFreeSnapshot(GetCurrentProcess(), snapshot)` once; check both returned statuses independently. A capture success followed by marker failure still requires snapshot free. A walk/cap/deadline failure still requires both owned releases. Never pass HPSS/HPSSWALK or entry.Handle through existing `Handle::Close`, and never call `CloseHandle` on them. Do not share descriptors concurrently, reuse freed descriptors, or retry an uncertain free. `PssFreeSnapshot` explicitly warns about concurrent access and undefined already-freed-descriptor behavior. The current-process pseudo handle is borrowed and needs no close. [Marker free](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psswalkmarkerfree), [snapshot free](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-pssfreesnapshot), [pseudo handle](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getcurrentprocess).

This explicit release protocol does not prove that PSS leaves no internal process resources or references. Without a native proof there is no claimed closure, latency or supported-type coverage. TYPE_SPECIFIC capture can populate sensitive process/thread fields even if code reads only the enum; those fields must remain unexported. No names/basic/trace/context/VA flags, duplicate handles, `OpenProcess`, helper, second observer thread, warmup, settlement loop or undocumented fallback is part of this candidate.

A separately named diagnostic wrapper could include the original `.cpp` with only its entrypoint renamed and invoke the original body before any PSS call. Its normal baseline/final query, final strict arithmetic, terminal rows and FILE flush/close would execute first. The census would then describe a later state: the original details FILE has already closed and original automatic scopes have ended, and the observer has begun. It must not be reconciled against the original count by subtraction. A single post-result census leaves the original measurement before PSS but cannot identify which surviving entries were absent at baseline. An earlier second census would invalidate that useful separation and still provide no generation or source responsibility. This is why the candidate should not consume the next native run.

## Better provenance direction and rejected alternatives

`!htrace` is the most directly documented candidate for the next research task: enabling tracing records handle open/close/invalid-reference stacks; `-snapshot` and `-diff` provide a comparison facility. User-mode commands act on the current process. Microsoft warns that some records originate in another process context and can resolve to wrong symbols. `Max_Traces` is a maximum display count, not a documented completeness or loss certificate. These contracts support investigating provenance but do not yet prove a loss-free bounded attribution pipeline. [Official !htrace reference](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-htrace).

- PSS handle-trace capture: rejected as a shortcut to creation stacks. Its public trace-information structure exposes a section handle and byte size, not a documented event-record schema, complete enablement protocol, retention/loss certificate or parsing/ownership contract adequate here. Do not reverse engineer a private section format. [Trace information](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ns-processsnapshot-pss_handle_trace_information).
- Application Verifier Handles: documented activation route for tracing, but changes process instrumentation/configuration, requires separately assessed installation/admin/lifecycle and cleanup contracts, and does not by itself bound or sanitize logs. Defer as an alternative in the tracing task. [Verifier overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/application-verifier).
- System Object ETW: a documented handle/object provider exists, requiring a system-logger session in the modern System Provider interface. That provider listing alone does not establish a complete versioned object-generation/stack schema, own-process filtering, finalized loss proof or safe export. A new collector would be a larger separate feasibility task. Do not repurpose the existing unrelated ETW qualification as proof. [System Providers](https://learn.microsoft.com/en-us/windows/win32/etw/system-providers).
- `NtQueryObject`: the published interface can query selected live-object information and type names, but does not enumerate handles or establish history. Microsoft warns it may change/remove. Combining it with guessed handle enumeration or querying possibly recycled snapshot values does not meet this contract. No undocumented information class or system-handle-table fallback. [Published interface](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntqueryobject).
- Process-global API interposition/tracker redesign, Job Objects, forced closing of discovered handles and another creator-lifetime guess are outside scope and provide no current repair evidence.
