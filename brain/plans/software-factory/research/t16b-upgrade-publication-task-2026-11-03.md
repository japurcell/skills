## Outcome and boundary

From a disposable real v7 installed baseline produced by the public installer, authenticate an explicitly selected new bundle and pinned Node before selected JS runs. Bind exact existing installed completion, receipt, runtime, toolchain and provider descriptors, then use the T16a sole claim and verified backup. A separately owned immutable new candidate and self-contained staged controller perform ordered operation-owned replacement and validate the actual new installation. Commit new installed completion, release and ready state plus exact claim release atomically. Validate completed ownership before removing any completion marker, and clean only the launcher's exact completed stage inventory after controller exit. Keep the backup and old owned bytes/evidence for later selected cleanup. Pre-v7 historical SQL fixtures prove store transition only, never invented installed ownership. No provider launches, downgrade, restore, salvage, implicit migration, replay or old runtime execution after handoff.

## Invariants and decisions

1. First validate original receipt and actual files read-only from new Node; bind their identities and hashes, original completion and selected target facts to durable intent before handoff, and recheck under admission and before replacements. No historical receipt means refusal. Preserve original provider and lock selection exactly; no provider/auth/credential calls or inspection beyond explicitly bound artifact descriptors.
2. Claim plus start event is the only pre-backup mutation. No domain/schema/installed/authoring mutation before verified backup. Stage/candidate paths are outside replaceable installation and separate from one another. Post-exit receipt only follows preparer and all owned children closing. No foreign same-byte target is accepted.
3. Journal each destructive rename through an operation-owned intent and identity-based receipt with fsync ordering, explicit source/destination states and deterministic crash inspection. Retain old owned bytes in absent operation-owned locations. Validate stage, backup, original/target selection, candidate and exact preceding receipts before each move; uncertain identity blocks and preserves evidence. Do not move authoring files unless the accepted install contract requires it and their original ownership is proven.
4. Completion revalidates new Node/npm/tsc, bundle, lock, provider descriptor sources and actual installed layout without provider execution. Record exact installed ownership evidence and atomically transition ready/release/delete claim. A crash after commit and before marker/stage cleanup requires exact completed receipt and actual installed validation before cleanup; never treat ready alone as ownership.
5. Windows ACL and closure stay fail-closed until explicit native qualification. No release publication, global install, real repositories, destructive local tests, provider qualification or desktop notifications. Dependencies, repair, uninstall and cleanup are separate later nodes.

## Selected publication design

Use a typed `src/upgrade-publication.ts` and `src/upgrade-publication-state.ts`; first-install layout has hard-coded absent targets and `kind=install`, so do not broaden it into an ambiguous generic state machine. Reuse its bounded, exclusive record I/O and candidate tree verification primitives after factoring only the minimum needed. The preparer obtains a read-only verified original descriptor under the new Node: repository ID, original completion event and receipt ID/hash, original release/manifest, install/toolchain directory identities and inventories, original publication record identity/hash, locked toolchain and exact provider descriptors. Bind a digest of this descriptor in the target `MaintenanceSelection.artifactDigests` before `prepareForwardSchema`, then persist the full immutable descriptor at an absent operation-owned path after admission/backup. Add a narrow admission transaction check that the exact original completion/repository release remains current when the upgrade claim commits; revalidate the actual files and descriptor after admission and at each applicable move. Target providers and lock must match the original selected facts.

Under `factory/upgrade-<operation-id>/`, create a mode-0700 operation directory, exclusive bounded mode-0600 `intent.json`, `old/`, immutable per-step receipt records, and `new-receipt.json`. The intent binds operation/repository/claim, target selection, backup identity/receipt digest, full original descriptor digest, old and new subtree identities/inventories, candidate binding, stage identity/digest and fixed ordered step names. Capture original evidence before creating the claim in memory; write and fsync this directory and intent only after backup verification, before handoff. Never overwrite records. The original `factory/installed-receipt.json` and original `install.completed` event remain untouched permanently through this operation; old installed subtrees move into `old/install` and `old/toolchain` with their identities preserved. Keep original authoring files and authoring receipt facts unchanged; upgrade never modifies authoring files.

Use a distinct `factory/upgrade-incomplete` marker with exact operation/claim/intent identity, created exclusively and fsynced after consumed handoff and before the first move. Normal installed reads and runtime startup must reject it; the upgrade controller has an explicit marker-aware path. Existing `bootstrap-incomplete` semantics and T16a forward opener stay intact. The repository is already incomplete at handoff, so a crash before marker creation still blocks startup. After completion, marker removal requires new installed receipt, active completion, real target files, stage/intent and marker identity validation. Cleanup must refuse foreign or changed marker; preserve all evidence on uncertainty.

Ordered states for each of `install` then `toolchain`, with all prior records verified at every gate:

| Step | Before rename | After rename, before receipt | Committed step |
| --- | --- | --- | --- |
| Preserve old install | original at factory/install, old/install absent | exact original inode and inventory at old/install, source absent | exclusive `01-old-install.json` records original identity and inventory digest |
| Publish new install | candidate/install present, factory/install absent, step 01 valid | exact candidate inode and inventory at factory/install, candidate source absent | exclusive `02-new-install.json` binds candidate identity and tree digest |
| Preserve old toolchain | original at factory/toolchain, old/toolchain absent, step 02 valid | exact original inode and inventory at old/toolchain, source absent | exclusive `03-old-toolchain.json` binds original identity and inventory digest |
| Publish new toolchain | candidate/toolchain present, factory/toolchain absent, step 03 valid | exact candidate inode and inventory at factory/toolchain, candidate source absent | exclusive `04-new-toolchain.json` binds candidate identity and tree digest |

Fsync both parent directories after each rename before creating and fsyncing the exclusive step receipt. On restart, the immutable intent, exact source/destination identities and inventories establish whether the immediately expected rename occurred; only then may the missing receipt be created. Both present, both absent, wrong identity, foreign same-byte content, out-of-order receipt, unexpected entries or a modified earlier receipt blocks. This is recovery of the same recorded operation, never adoption by bytes. Validate target bundle, Node/npm/tsc, lock, providers without execution and preserved authoring facts after step 04. Create and fsync immutable operation-specific new receipt before completion; include target publication intent hash and step receipt digests, original descriptor digest, candidate/stage bindings, target ownership identities and unchanged authoring ownership.

The SQLite transaction inserts one `upgrade.completed` event carrying the same completion fields as `install.completed` plus the bound new receipt hash and original operation/completion binding, updates repository release and ready, and deletes the exact sole upgrade claim. Validate v7 shape, exact original release, bound backup, candidate, consumed ticket, live staged owner, validating phase and token within or immediately around the CAS as appropriate. The old completion remains in history and is never updated/deleted; before commit, incomplete/claim blocks both old and new installed startup.

Select active completion from the last `install.completed` or `upgrade.completed` by `observation_events.cursor` in the same read-only SQLite snapshot as ready/release and absence of maintenance claims. Require its exact unique operation and matching repository ID/release; no fallback to an earlier event if the newest is invalid. For a first-install event, retain the existing fixed `factory/installed-receipt.json` path and validation byte-for-byte. For an upgrade event, derive the only permitted `factory/upgrade-<operation-id>/new-receipt.json` path from the validated operation ID and check the event receipt ID/hash, operation intent and target subtree facts. Update `loadInstalledBindings` to dispatch by completion kind; its installed module and `process.execPath` checks remain strict. This permits successive upgrades while preserving all previous events/receipts, and makes the single DB commit the active ownership switch rather than an unsafe filesystem pointer update. The upgrade verifier must also validate the original completion and prior operation receipt when a second upgrade begins. Reader uses one SQLite snapshot, then verifies files and marker again before returning, failing closed if a concurrent upgrade starts.

Add `bindUpgradeCandidate` alongside `bindInstallCandidate`, not a general SQL setter: in one immediate transaction require exact upgrade claim/token/repository, sole claim, preparing phase, verified bound backup, matching original descriptor digest/selection and no existing candidate or stage; check canonical operation candidate path, compact receipt/tree identities, stage identity/digest, bounded claim size; store candidate and stage, emit bounded event. `prepareMaintenanceHandoff` and `consumeMaintenanceHandoff` must require and revalidate upgrade-specific candidate evidence. Post-move checks use the upgrade layout verifier, since full candidate tree intentionally changes position. Reclaim uses `resumeForwardSchema` with the exact original selection and explicit clearance, and reissues/consumes handoff under the established controller rules; a consumed modifying operation resumes only with a separately authenticated staged controller and validated existing evidence, never an implicit fresh selection or a new repair feature. Preserve the existing prebind fresh-backup recovery rule.
