# Owned Windows main-image identity mechanism decision

Date: 2026-11-03. Read-only mechanism research, not implementation, independent code review, native qualification, or Windows support evidence. Only this `/tmp` note was written. No executable probe, debugger attachment, process-memory access, credential/provider access, repository/global mutation, or nested delegation was performed. RTK 1.1.0 read commands worked; its tracking dashboard could not open its database in this sandbox.

## Decision

There is a documented Windows primitive for the central missing guarantee: a controller that creates its own new child with `DEBUG_ONLY_THIS_PROCESS` can receive `CREATE_PROCESS_DEBUG_EVENT` before that child's first user-mode instruction, and the event supplies an actual main-image file handle. Querying `FileIdInfo` on this handle establishes the image file's volume/FileID independently of a mutable path. A continuously held `CreateProcessW` process handle supplies authority over that exact new process through completion.

A pre-user-mode detach sequence can be constructed from documented operations: at the first creation event, explicitly suspend the initial thread, validate the image handle, continue the creation event while the explicit suspension remains, detach the debugger, confirm detached state using the held process handle, then resume the initial thread once. This is a justified composition of documented primitives, **not an explicit Microsoft guarantee of that complete sequence**, and requires a bounded native canary proof before adoption. It can produce a new, qualified factory-internal native launch mode. It does not establish equivalence to Node's existing launch flags or erase debug-at-creation effects.

The primitive resolves actual main-image FileID acquisition. It does **not** resolve the entire currently refused helper admission: immutable controller/runtime and DLL/package namespaces, complete operation closure, and the observed extra console processes remain separate hard conditions. Under a requirement that a bare Win32 call itself freeze all ancestor/alias/DLL namespaces against arbitrary concurrent mutation, this mechanism is insufficient. No such guarantee was found. Keep refusal unless the independently trusted staging boundary and native evidence below are established. No libgit2 replacement is selected or required by this decision.

## Documented facts and their exact limits

- [Debugging Events, CREATE_PROCESS_DEBUG_EVENT](https://learn.microsoft.com/en-us/windows/win32/debug/debugging-events) says the creation event precedes user-mode execution and all other debug events for that process. On notification, every thread in the affected process is stopped until continuation. Thus neither application entry, its TLS callbacks, nor user-mode DLL loader/initialization code can run before this event is processed. Kernel creation activity and external OS console infrastructure are outside that statement. This is a creation-time guarantee, not the synthetic state obtained by attaching to an existing process.
- [CREATE_PROCESS_DEBUG_INFO, hFile](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-create_process_debug_info#members) identifies a handle to the process's image file; it may be NULL, which must refuse admission. Its optional `lpImageName` is unsuitable for identity. The creation-event documentation specifies GENERIC_READ and read-sharing for the image handle. Retain an owned duplicate while closing the event-owned original as directed. Never reopen an event pathname and describe that result as the image handle.
- [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex#remarks) documents `FileIdInfo`; [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info#members) identifies a file by the pair of volume serial and 128-bit FileID and explicitly describes comparing two open handles. Hash bounded bytes through the actual held image handle and compare its pair to the authenticated expected artifact's held handle. FileID is object identity, not provenance, hash identity, canonical location, or a cryptographic guarantee of mapped memory. Query/read/duplicate failure refuses.
- [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags#flags) documents `DEBUG_ONLY_THIS_PROCESS` for the created process, excluding descendant debugging; `CREATE_SUSPENDED` suspends the primary thread until `ResumeThread`. The docs do **not** state whether the creation debug event is deliverable while a `CREATE_SUSPENDED` primary thread has never been resumed. Do not rely on `CreateProcess(DEBUG_ONLY_THIS_PROCESS | CREATE_SUSPENDED)` followed by an unbounded wait for that event. `CREATE_SUSPENDED` alone returns no main-image file handle.
- [WaitForDebugEvent, remarks](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-waitfordebugevent#remarks) and [ContinueDebugEvent, remarks](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent#remarks) require the creator thread for their respective calls. Keep creation, event processing, continuation, and detach on one bounded controller thread. Debug-event process/thread handles have automatic close rules at exit; separately own the `PROCESS_INFORMATION` handles or proper duplicates.
- [SuspendThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-suspendthread#remarks) adds a suspend count. [ResumeThread, remarks](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread#remarks) says an explicit suspension survives a debug continue. A return of 1 from the final resume means the count reached zero; unexpected counts refuse rather than looping to force execution. [Controlling Processes and Threads, Freezing and Suspending Threads](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/controlling-processes-and-threads#freezing-and-suspending-threads) also describes suspension persisting through detach, but is debugger-engine guidance, not an atomic Win32 sequence contract.
- [Debugging a Running Process](https://learn.microsoft.com/en-us/windows/win32/debug/debugging-a-running-process) identifies `DebugActiveProcessStop` as detach after either creation or attachment; [DebugActiveProcessStop](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-debugactiveprocessstop) stops debugging by PID. It does not document a special first-event recipe or promise to undo creation-time state. [CheckRemoteDebuggerPresent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-checkremotedebuggerpresent) queries current debug state using a process handle. This is a postcondition check, not proof that no creation-time effects remain.
- [Process Handles and Identifiers](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers) says creation handles remain valid until closed, even after exit. Keep the original handle, never reopen a printed/event PID for signaling. [DebugSetProcessKillOnExit](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-debugsetprocesskillonexit) defaults to terminating the calling thread's debuggees on thread exit. Do not set FALSE as a shortcut: that would detach on controller loss and could release unvalidated work. Use one owned child per operation and retain the fail-closed default while attached. After successful detach, controller loss has no debugger kill guarantee.

## Concrete owned-child construction to qualify

1. Begin inside an already authenticated controller, with its runtime and namespace trust established externally as below. Accept only a closed private operation discriminator selecting the previously pinned native Git metadata or generated-config TypeScript modes. Resolve fixed application/argv/environment/cwd/stdio from that discriminator; no caller-supplied executable, shell, extra flags, public `noChildren` declaration, provider access, or startup compiler/download.
2. Open and authenticate the expected complete artifact inventory through held handles before creation. Bind the operation to exact artifact/version/config/cwd and staged namespace. Use explicit fully qualified `lpApplicationName`, exact quoted argv, Unicode allowlisted environment and a restrictive inherited-handle list. [CreateProcessW, security remarks and inherited-handle remarks](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw#remarks) documents why explicit application name and handle selection matter. Use only the intended console/window flags for this **new** mode. Do not claim Node's detached/window settings are equivalent.
3. Call `CreateProcessW` with `DEBUG_ONLY_THIS_PROCESS`, without depending on `CREATE_SUSPENDED`. Retain its process and primary-thread handles continuously. Wait within the operation's existing deadline for exactly the owned PID/TID's first creation event. Wrong/missing event, NULL image handle, early exit or unknown state refuses. The documented creation-event stop is the pre-user-mode barrier.
4. While that event is outstanding, add exactly one explicit `SuspendThread` to the initial thread; for this no-`CREATE_SUSPENDED` construction require its prior count to be 0. Independently verify actual event image FileID/hash against the held authenticated expected image. Duplicate the image handle for the operation and close the original. No child-memory reads/writes, thread-context manipulation, injected breakpoints, remote threads or foreign attachment are needed.
5. After successful validation, `ContinueDebugEvent(..., DBG_CONTINUE)` for this non-exception creation event. The explicit thread suspension must remain. Then `DebugActiveProcessStop` only for this operation's created PID, cross-checked against its still-held live process object. Confirm success and `CheckRemoteDebuggerPresent(...)=FALSE`. Do not detach with a pending uncontinued event as a purported portable shortcut. Do not resume before confirmed detach. A failure terminates only the exact held owned child and waits for observed completion; unresolved state retains cleanup unknown. Failure before detach also requires bounded debug-event draining to complete termination, without granting ordinary execution.
6. Resume the initial thread once, requiring the expected count of 1. Now execute the fixed operation with no attached debugger, retaining actual main-image handle, exact process handle, pin handles and private pipes through completion. Enforce existing stop/deadline/output/recording bounds. Completion still needs signaled owned process, verified exit and pipe closure; kill submission is insufficient. No descendants or console-host processes acquire termination authority from this design. Once detached, separately handle owner-loss uncertainty honestly.

The only necessary target execution before the main-image validation is **none in user mode**. Conversely, collecting subsequent `LOAD_DLL_DEBUG_EVENT` records or the initial breakpoint requires allowing loader progress past the creation-event barrier. [LOAD_DLL_DEBUG_INFO](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-load_dll_debug_info#members) offers an actual DLL handle, possibly NULL. It does not say every such event precedes all possible initialization code. [Initial Breakpoint](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/initial-breakpoint) places that later stop after static image/DLL loading and before DLL initialization, not before all user-mode loader activity. Do not use either as a pre-loader validation substitute. If actual DLL handles must be acquired before detaching, that is a different, longer debug-start profile needing its own loader/TLS and behavior proof.

## Root of trust and namespace limit

The controller cannot authenticate its own initial execution by checking its own pathname after it has started. The root is an authenticated release/installer or already trusted inbox launcher/runtime whose execution namespace and OS assumptions are accepted **before** launch. A packaged native controller must have pinned source/build inputs, architecture, digest, transitive runtime inventory and authenticated release-manifest binding, be staged by that trusted owner, and execute from that owner's qualified local namespace. A C# qualification bridge additionally relies on the exact trusted Windows PowerShell/.NET/runtime/compiler boundary; success there is not proof that a product can compile a controller at startup. A product payload needs the prebuilt authenticated controller and explicit inventory. No ambient toolchain acquisition or permission change follows from this note.

The trust assumptions must name the protected local volume/root and ancestor chain, ordinary OS loader/KnownDLL/API-set behavior, installer/controller ownership, permitted concurrent writers, and unsupported filesystem/reparse/case/alias forms. Repository contents and hostile PATH/config are untrusted; hostile kernel/admin instrumentation or a same-authority process able to rewrite the trusted controller/OS namespace cannot simultaneously be inside the assumed trust boundary. If the existing accepted namespace requirement includes such concurrent writers, no exemption is established here and admission stays blocked.

[CreateFileW, sharing modes](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew#parameters) constrains writes/deletes/renames of the opened file object for the lifetime of the share restriction. It does not freeze its ancestors or every alias. [Reparse Points and File Operations](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations) documents filesystem-specific redirection concerns. Read-sharing image/pin handles and pre/post path checks alone do not establish namespace stability. Never infer it from this proposed sequence.

Before releasing the primary thread, the staged executable/DLL/package/library namespace must already meet the independent accepted invariant. [DLL search order](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order) includes redirection, manifests, KnownDLLs, application/system/current/PATH locations and dependency searches by module name. Main-image identity does not pin those resolutions. Reuse the exact audited Git 2.54.0.windows.1 executable plus five DLL pins and TypeScript 7.0.2 executable plus full noembed package/library inventory. A complete trusted stage can be a candidate construction, but a writable/reparse-racy ancestor or unresolved DLL search source is a concrete refusal, not something the image handle repairs. Do not silently change Git environment/config semantics or TypeScript source/config behavior to achieve staging.

Debug-at-creation can affect behavior. [IsDebuggerPresent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-isdebuggerpresent#remarks) explicitly permits different application behavior. Microsoft's [CDB process creation guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/debugging-a-user-mode-process-using-cdb#spawning-a-new-process) also documents debug heap differences in that debugger's spawned processes. This does not prove the exact raw Win32 sequence has the same heap effect, nor that detach reverses every effect. Do not add `_NO_DEBUG_HEAP`, rewrite PEB/runtime flags or modify memory to manufacture old-mode equality. Qualify the new creation mode as such.

## Minimum bounded next proof and files

First implement only a disposable owned-child canary qualification, with product/helper admission fixed refused. Suggested additive files are `packages/software-factory/qualification/windows-owned-image-probe.c` (or an explicitly chosen exact-runtime native bridge), `windows-owned-image-fixture.c`, `windows-owned-image-fixture-dll.c`, `windows-owned-image.mjs`, `windows-owned-image.test.mjs`, `windows-owned-image-native.qualification.mjs`, and `windows-owned-image.md`. Build qualification assets from checked-in fixed source in the already qualified disposable Windows build job, never at product startup. Root owns the implementation/language choice and must load its language skill before source design/edits. These are proposed files, not existing accepted assets.

The first native acceptance is narrow and decisive:

1. The exact first owned creation event yields a readable/duplicable image handle whose volume/FileID matches the independently held pin. A wrong-image/mismatched-digest request is refused with no TLS, DLL-initialization or entry marker emitted. All OS failures remain explicit. Include an intentionally different same-basename image and path/ancestor/alias replacement attempts in disposable staging; success means detected refusal or independently enforced stability, never path-string equality.
2. A trusted fixed fixture has distinct bounded markers in an imported DLL's initialization, executable TLS callback and earliest controlled entry, using ordinary test code rather than injection or runtime mutation. None appears before validation, after continue while explicitly suspended, or after successful detach before final resume. After one resume, all expected markers arrive; the fixture reports `IsDebuggerPresent=FALSE` and exits with captured pipes closed. The controller independently queries false before resume. Stress repeated launches and stop/failure points; retain API results and expected suspend counts privately. Canary observations validate this declared OS/build profile, not every possible loader or third-party instrumentation.
3. Test event timeout, NULL/query/duplicate failure seams, suspend/continue/detach/postcondition/resume failure, owner interruption, child crash, deadline and bounded output. Failure cleanup targets only the held owned object. A separately created foreign same-basename control remains alive and untouched. Missing exit/pipe closure or owner-loss completion stays unknown. Preserve original bounds and verify no leaked suspended child after a conclusively successful cleanup; never clear uncertain occupancy to make a test green.
4. Only after this passes, run an additive seven-case representative observation using this exact controller mode with the existing ETW health/schema/loss/graph/console predicates unchanged, then the original 17 Git/3 TS matrix and hostile/PATH/tamper/deadline/output controls. Bind actual direct image FileID to the process object before release. Preserve the original Node-mode comparator receipts and refusal. New native-mode results can justify only the new mode. Bind loaded dependency identities and whole source-defined process closure; unexpected console/descendant events still refuse and never authorize their termination.
5. Before product integration, independently establish actual authenticated installed controller launch, complete staged namespace/inventory and stop/owner-loss semantics. The current candidate/install namespace proof is not supplied by the canary. A successful fixed Git/TS operation must still preserve all worktree/claim/build/emission/recording semantics. Worktree mutation and arbitrary authored commands remain outside the closed helper profile.

If the canary shows creation-event delivery itself requires user-mode execution, or explicit suspension fails to survive continue/detach, reject this construction for the required boundary. If it passes but namespace ownership cannot be established, the precise remaining blocker is pre-execution executable/runtime/dependency namespace integrity, not inability to obtain a main-image FileID. This result does not require replacing the Git engine.
