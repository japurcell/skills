## Accepted scope and what already exists

The accepted `brain/plans/software-factory/tickets/recovery-and-runtime-selection.md:209-219` requires explicit forward repair to reinstall the **same recorded intended version**, complete only uncommitted transactional migrations, and validate the managed installation/history pair before admitting work. Unknown ownership, corrupt/unknown schema state, or an unavailable intended installer requires preservation and refusal. It does not promise arbitrary repair. The same ticket at lines 307-317 requires interrupted uninstall to allow explicit completion **or installation repair**, with successful uninstall recording an absent installation. `brain/plans/software-factory/lifecycle-specification.md` requires a self-contained controller, exclusive maintenance, retained history/accounting/user files, and honest incomplete state. The ExecPlan currently names forward repair but lacks independently assignable tasks for its remaining file-reinstallation and uninstall crossover cases.

Existing public `install.py resume-upgrade` is already the explicit repair path when the original upgrade's authenticated stage, candidate, backup, original facts, intended manifest and ordered layout are intact. `resumeUpgradeRequest`, `reissueUpgradeHandoff`, `resumeUpgradePublication`, `continueUpgrade`, and `advanceForwardSchema` reclaim the exact operation, reuse its receipts, skip committed migrations, finish publication, and validate before ready. `recoverCompletedUpgrade` handles ready-before-marker cleanup. Do not add a parallel implementation for these cases or mark them missing merely because their command says resume. Read-only inspection should report `action: resume-upgrade` and the exact command.

That path does **not** repair a damaged or wholly missing selected tree: `inspectUpgradeLayout` requires every old/new tree at its recorded identity and full digest. `inspectInstalledOwnership(...,true)` still validates live install/toolchain bytes and reads the release manifest from the live runtime. It therefore cannot establish repair authority after those bytes disappear. A missing controller stage also cannot be executed by current `resume_upgrade`. Remaining accepted work is an explicit, same-selection **republication from independently authenticated input**, using retained authority rather than executing or blessing damaged installed files.

Required supported cases are:

1. Current owned install: missing/changed known managed regular files in runtime/Node/toolchain, or one/both whole fixed managed roots absent, with complete retained ownership authority. The normal full-install repair unit is both `factory/install` and `factory/toolchain`, and the impact plan explicitly says both are replaced. A toolchain-only request uses the separately implemented dependency repair instead.
2. Incomplete owned upgrade: prefer existing exact resume. If it cannot resume solely because attributable managed target bytes or controller payload are damaged/missing, explicitly rebuild its **recorded target**, preserve all surviving old/new trees and receipts, and use the existing forward-migration implementation. Damaged metadata needed to establish authority, lost original provenance, or an unexplained publication position still refuses.
3. Interrupted uninstall: after validating its retained inventory and exact deletion journal, explicitly select reinstalling the pre-removal active selection instead of continuing removal. Preserve the interrupted uninstall as a superseded operation, not a completed uninstall.
4. Completed uninstall (`state=absent`): explicit reinstall of its retained intended selection into absent fixed roots, preserving the existing repository ID, history, accounting and authoring. This is not first-install bootstrap over retained data. The public repair entry may describe the action as reinstall. It may not select an arbitrary older/newer release. A different version is a later explicit forward-upgrade contract, outside this packet.

Cases 3-4 depend on actual implemented uninstall receipts. Their absence at this head is a dependency, not grounds to fabricate them or permanently omit required crossover behavior. Interrupted dependency publication with an exact valid journal uses dependency resume; unsupported or contradictory dependency evidence refuses rather than being silently adopted.

## Authority and observed damage are different records

Factor one strict retained-authority reader, shared with the dependency ownership foundation. It authenticates DB completion, installed receipt, publication intent, candidate receipt, selection, original chain and step receipts **without requiring live target bytes**. Current entry points are `store.ts:219-254`, `installed-bindings.ts:81`, `upgrade-installed.ts:41`, `install-publication-state.ts:102`, and `install-candidate.ts:158`. Never weaken normal startup's full validation or interpret a caller boolean as verified ownership.

For first install, join `install.completed`, `installed-receipt.json`, `install-publication-OP.json` and the bound candidate receipt. For upgrade, join latest completion, `upgrade-OP/new-receipt.json`, `original.json`, `intent.json`, all four ordered receipts and the original/candidate chain. Include subsequent `dependencies.completed` and `repair.completed` through the same typed reader. Always select the newest relevant committed state; never fall back to an older valid receipt when the newest is invalid. A ready-only query is insufficient for an interrupted operation or absent installation: add controller-only read-only snapshots that validate the exact state/claim/operation being selected instead of disabling those checks globally.

The release manifest inventories packaged runtime assets only. The retained `CandidateReceipt.entries` additionally inventories extracted Node and the realized npm toolchain; dependency receipts replace only the toolchain authority. Join those facts to the external bundle's exact committed manifest digest and Node archive digest. Reauthenticating an arbitrary bundle is not ownership. Read the intended manifest from the external authenticated bundle when the live manifest is absent; it must equal the committed intended digest. Preserve original providers and exact dependency lock/declaration closure. Do not revert an authored environment to the release compiler-only lock.

Record expected rows separately from `ObservedRootV1`. For a present root, require its authoritative root `dev:ino` and canonical 0700 directory to match, then inventory it without executing its code. Permit absent expected files/subdirectories and changed bytes/allowed modes only at known expected regular-file paths. Each present path must retain its expected kind; refuse unknown extra paths, links/hardlinks, special files, collisions, unsafe names, oversized inputs, uncertain reads, root replacement or unexplained identity changes. Missing subtrees mean all their expected descendants are absent. Bind each observed surviving entry's actual identity, mode, size and digest, and a bounded expected-versus-observed diff. A missing entire root is an explicit `absent` observation under a held canonical factory parent and a retained authority naming that fixed root; it does not create a fictitious current root identity. Reappearing roots are collisions, even if their bytes match.

For an interrupted operation, its journal first establishes which old/new root identity is authorized at each location; the damage comparison is against that specific tree's retained expected inventory. Accept only a valid recorded layout or its one already-authorized filesystem-ahead step, not guessed missing prefixes. Any preserved recovery tree that cannot be attributed safely stays untouched and blocks the repair. Uninstall's expected deletion gaps are established by its deletion journal, not relabeled accidental damage.

Keep candidate receipt bounds: <=8192 entries, <=512 MiB regular bytes, <=128 MiB/file, <=8 MiB large inventory. Large immutable expected/observed inventories belong in separate hash/identity-bound private files, not <=8192-byte claims or `readPublicationRecord`. Do not scan history/captures or arbitrary directories to expand managed ownership. For first-install facts that did not historically persist a factory-root identity, bind the current canonical factory identity through read-only selection and admission, while checking the retained DB/receipts under it; do not pretend a historical identity was recorded. Preserve the existing local trusted-repository/same-user threat boundary.

## User-facing entry and typed selection

Extend `skills/default/software-factory/scripts/install.py` with explicit external-launcher commands:

    inspect-repair --repository R --bundle-root B --manifest-sha256 H --node-archive A [--operation SOURCE_OP]
    repair --repository R --bundle-root B --manifest-sha256 H --node-archive A --selection-sha256 PLAN --confirm [--operation SOURCE_OP] [--operator-confirmed --note NOTE] [--offline --offline-cache-seed CACHE]
    recover-repair --repository R --bundle-root B --manifest-sha256 H --node-archive A --operation REPAIR_OP --selection-sha256 PLAN --operator-confirmed --note NOTE

Inspection returns bounded JSON with source kind/state/operation, intended release/manifest/runtime/lock, expected/observed inventory digests, per-root present/absent facts, damage counts, exact replacement impact, retained-data policy, native support, and one of `resume-upgrade`, `repair`, `recover-repair`, `resume-uninstall`, or `refused`. It reports both alternatives for an incomplete uninstall; inspection never chooses repair for the user. A healthy installation reports no repair needed. Do not turn inspection into claims, package installation, cleanup or owner clearance.

`repair` recomputes the exact plan and compares its digest before admission and under the gate. Confirmation binds that concrete selection, not a generic yes flag. Existing incomplete source operations require exact source ID and informed bounded clearance; known-live owners/launchers refuse. `recover-repair` continues only the same repair operation, selection and stage. A fresh repair cannot silently replace an incomplete repair. Reject package/version overrides, arbitrary target paths, provider changes, inferred filesystem adoption and extra artifacts. Intended artifacts, external Python and offline cache retain existing explicit pin/identity/prerequisite semantics. There is no global runtime fallback or invocation-time repair.

Use dedicated discriminated records (names are the implementation interface, not existing exports):

    RepairSourceV1 =
      | {kind:'installed', activeCompletionSha256, installedReceiptSha256}
      | {kind:'upgrade', operationId, claimId, intentSha256, committedShape, priorCompletionSha256}
      | {kind:'uninstall-incomplete', operationId, claimId, inventorySha256, journalSha256, priorCompletionSha256}
      | {kind:'uninstall-absent', operationId, terminalReceiptSha256, priorCompletionSha256}
    ObservedRootV1 = {name:'install'|'toolchain', state:'absent'}
      | {name:'install'|'toolchain', state:'present', identity, inventorySha256, treeDigest}
    RepairSelectionV1 = {version:1, repositoryId, root, common, factoryIdentity,
      source:RepairSourceV1, intendedRelease, manifestSha256, nodeArchiveSha256,
      dependencyAuthoritySha256, expectedInventorySha256, observedInventorySha256,
      roots:ObservedRootV1[], controllerManifestSha256, retainPolicy:'repair-preserve-v1'}

Add compact `MaintenanceIntent.repair` binding selection, authority, expected/observed inventories, backup, candidate, publication intent, stage and final receipt. New `RepairInstalledReceiptV1` binds the previous authoritative chain, the target runtime/toolchain inventories, actual new root identities, repair operation/selection, preserved original facts, backup and publication receipts. Emit `repair.completed`, not synthetic install/upgrade completion. No new DDL is necessary merely to store typed JSON/events at schema7. Pending historical migrations use the existing historical recognition and forward transactions, not lowered-version fixtures.

## Publication, interruption and retention

Use `factory/repair-OP/` for immutable `source.json`, `selection.json`, `expected.json`, `observed.json`, `intent.json`, `new-receipt.json`, marker template, ordered receipts and `old/`. Candidate and self-contained controller live outside both fixed targets. Reuse authenticated external pinned Node/Python bootstrap, fixed controller inventories and npm preparation from `install.ts` / `install.py`; never execute installed damaged Node/npm/compiler or copy installed damaged controller code. Build the target from exact authenticated release and active dependency lock inputs, with scripts disabled and existing normalization. External selected providers remain borrowed, unchanged and unexecuted. Conservative refusal for unavailable/changed provider-source bindings is acceptable; no provider requalification occurs.

1. Read-only authority and observation preflight precedes the claim. Admit only through the same atomic gate as runner/dashboard/other maintenance. For ready/absent state, atomically insert the sole repair claim and bind source state. For interrupted upgrade/uninstall, atomically CAS the exact cleared original owner/token/phase and source journal into a sole new repair claim, append `maintenance.superseded_by_repair` linking both operations and all retained source digests, and prevent the old operation from resuming. There is no claim-free or ready interval. Preserve the original incomplete outcome; do not emit its success event. Refuse other active/uncertain claims and a running dashboard.
2. Administrative claim/supersession facts may precede backup. Before schema/file modification, create a new operation-owned consistent SQLite backup via existing verified backup I/O, private absent target, integrity/count/source-identity checks and durable receipt. Retain earlier backups as well. Never copy a live DB main file or reuse a partial backup target. Carry committed source migration markers unchanged. Backup failure keeps the source state and blocking claim/evidence; it does not authorize mutation or automatic claim release.
3. Prepare/bind candidate, inventories, controller, external Python and launcher; self-check closure. Reuse `prepareMaintenanceHandoff` / `consumeMaintenanceHandoff`, Python `bounded_child` / `publish_candidate`, one-use ticket and post-wait exit receipt. The preparer must exit, both streams close and its original owned group be absent before staged-controller admission. Consumption records repository incomplete and modifying before the first file move. Prior incomplete/absent installations remain unavailable during preparation too. Old launcher/controller known-live or uncertain closure cannot be disguised as a stale PID. No stored-PID signalling, global process scan, daemon, or automatic takeover.
4. For an upgrade source, run only remaining transactional schema steps with the existing `advanceForwardSchema` / `RepositoryStore.advanceForwardStep` / `applyForwardStep` implementation, guarded by a typed inherited upgrade-source binding. Preserve source DB identity, source release, verified backup and committed shape checks. Extend kind guards narrowly for this authenticated repair source; do not create new migration SQL or replay committed steps. Other repair sources require current known schema7 and perform no migration.
5. Use the existing no-replace helper and ordered one-move-ahead reconciliation for publication. Extract a small shared fixed-root move/receipt mechanism from `upgrade-publication-state.ts` / `upgrade-publication.ts` rather than copying the upgrade state machine or calling it with fake upgrade claims. Existing upgrade still has its identical four mandatory moves and receipts. Repair supplies at most four fixed steps: retain observed live install in `old/install` if present, publish new install, retain observed live toolchain in `old/toolchain` if present, publish new toolchain. A selected absent old root has an explicit prebound absent step, never a fabricated move receipt. Check its continued absence and flush the parent before recording the absence observation. Present observed roots must retain their selected identity/inventory when moved; all destinations are absent-only. Preserve preexisting source-operation old/candidate trees in place. Never overwrite or recursively delete them.
6. Before each move, validate sole exact claim/token/live owner/launcher, stage and relevant ancestor/source/destination facts. After helper closure, fsync both parents, verify moved identity and complete observed/target inventory, then durably record the step before the next move. A crash permits only the next authorized move to be filesystem-ahead. Recheck/flush and issue that missing receipt; do not infer multiple moves, adopt same-byte replacements, or undo automatically. Extra entries, changed roots/stage/receipts, missing untouched trees, uncertain helper result/closure or flush failure leave incomplete with evidence retained.
7. Validate all target bytes/identities against target receipt and active dependency closure, runtime/schema pair, retained source authority/backup/journal, and direct authenticated Node/npm/compiler commands. Preserve application/source/index and user-editable `.factory/` files; repairing managed installation must not run absent-template publication over existing authoring or rewrite declarations/locks. Record validating only when publication is fully receipted. Write durable `RepairInstalledReceiptV1`; in one exact validating-claim transaction append `repair.completed`, set ready/intended release, and release only matching ownership. Never expose an unrestricted ready setter.
8. Ready-before-marker recovery verifies the exact committed repair completion and installed bytes, then removes only its own marker after owner/launcher checks. Python cleans only the exact unchanged completed controller stage after child EOF/group closure. If stage cleanup is unsupported/uncertain, retain it and report that fact. All old observed damaged trees, source-operation trees, manifests, receipts, backups, history/captures/reports/questions/accounting/clearances, worktrees and user files stay retained until separate informed selected cleanup. No restoration, downgrade, history rewrite or automatic recovery-material deletion.

Before modification, a freshly admitted ready repair may be explicitly abandoned only after proving its original observed facts unchanged, no publication/schema mutation, and inactive/cleared owners, using the unchanged-preparation pattern. Damage means ordinary startup still fails its byte checks. An absent or already-incomplete source never becomes ready by abandonment; retain/return its prior blocked state under an exact atomic transition. After any repair modification, only exact recovery or a separately specified later explicit operation can proceed. Failed/unbound staging is inspectable, not adopted, auto-deleted or silently rerun.

No existing native primitive guarantees identity-conditional source-name moves against an arbitrary concurrent same-user namespace writer. Preserve `atomic-publication.ts`'s stated limit, private canonical directories, held parent checks, no-replace destinations and detectable-swap refusal. Selected external Python and its runtime/dependencies remain operator-trusted with immediate path/hash/identity rechecks. Darwin arm64 and Linux x64 are the only current publication profiles; Windows repair refuses before claim/file mutation until its ownership/closure/publication route is independently admitted. A helper-only pass is not product repair proof.
