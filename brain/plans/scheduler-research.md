# Runtime limits for dispatched subagents

Research for [todo 38's dispatch and deadlines plan](38-dispatch-and-deadlines-exec-plan.md), checked 2026-11-18. The locally installed versions were Codex CLI 0.170.0 and GitHub Copilot CLI 1.0.114. Evidence comes from documentation and source inspection. A live cancellation trial is still needed to establish when a worker and its writes actually stop.

## Controls available to a dispatching skill

| Harness | What the harness enforces |
| --- | --- |
| Codex CLI | I found no documented per-worker wall-clock limit on ordinary dispatch. Expiry of `wait_agent(timeout_ms)` returns control to the parent while the child can keep working. The V2 tool `interrupt_agent(target)` interrupts the child's current turn when called. In 0.170.0, the config parser retains `agents.job_max_runtime_seconds` as a compatibility no-op. [Pinned tool definitions](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/core/src/tools/handlers/multi_agents_spec.rs) · [Pinned config source](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/config/src/config_toml.rs) |
| GitHub Copilot CLI | For ordinary `task` and `/fleet` dispatch, `read_agent` checks status, `write_agent` sends a message, and a human can kill a selected worker with `/tasks` then `x`. I found no documented per-worker deadline or model-callable kill in that delegation interface. Dynamic workflows separately support `workflows.defaultLimits.timeoutSeconds`, which limits the whole run's active time and excludes pauses. [Delegation tools](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference#agent-and-task-delegation-tools) · [Fleet task controls](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/speed-up-task-completion#monitoring-progress) · [Workflow limits](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/dynamic-workflows#limiting-a-dynamic-workflow) |
| Claude Code | Custom subagents support a turn limit via `maxTurns`. Workflow agents accept `stallMs` to end an attempt after a period without output. The stall clock excludes time waiting on the agent's own tools, and a stalled attempt can restart up to five times. A worker producing output can therefore run past the stall interval. An application that owns a deadline can call `stop_task(task_id)` through the Python Agent SDK. [Subagent fields](https://code.claude.com/docs/en/sub-agents) · [Stall and retry semantics](https://code.claude.com/docs/en/workflows#when-an-agent-stalls-and-restarts) · [SDK stop implementation](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/client.py) |
| Gemini CLI | A local subagent definition accepts `timeout_mins`, with a ten-minute default. The executor signals timeout and allows a final recovery turn with its own one-minute grace period. Account for that grace period when evaluating the last permissible activity. [Subagent configuration](https://github.com/google-gemini/gemini-cli/blob/main/docs/core/subagents.md) · [Executor and grace timer](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/agents/local-executor.ts) |

## Open-source precedents

- **Microsoft Conductor** exposes both a soft session limit, `max_session_seconds`, checked between iterations, and a per-agent deadline, `timeout_seconds`, enforced by the engine using `asyncio.wait_for()`. The earlier of the agent deadline and the remaining workflow budget wins. Expiry raises a non-retryable `AgentTimeoutError`, giving the parent an explicit outcome to grade. [Conductor skill](https://github.com/microsoft/conductor/blob/main/plugins/conductor/skills/conductor/SKILL.md) · [Agent-level limits](https://github.com/microsoft/conductor/blob/main/plugins/conductor/skills/conductor/references/yaml-schema.md)
- **shinpr/sub-agents-skills** dispatches external coding CLIs with `--timeout`. Its Python runner computes a monotonic deadline and kills the launched process on expiry, including when the worker emits no output. This establishes direct-child termination. Descendant shutdown requires separate verification. [Skill instructions](https://github.com/shinpr/sub-agents-skills/blob/main/skills/sub-agents/SKILL.md) · [Executor](https://github.com/shinpr/sub-agents-skills/blob/main/skills/sub-agents/scripts/_executor.py)
- **Anthropic's skill-creator** launches `claude -p` per trigger-eval query and bounds the observation loop. Its cleanup calls `kill()` and `wait()` on a still-running CLI. Anthropic's engineering post describes the production motivation for bounded waits: one slow subagent could block a synchronous lead agent. [Eval runner](https://github.com/anthropics/skills/blob/main/skills/skill-creator/scripts/run_eval.py) · [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- **OpenAI Symphony** assigns a one-hour default timeout to each Codex turn and separately detects five minutes without activity. On a stall, the orchestrator terminates the worker and queues a retry. The same supervisor owns the clock and the termination action. [OpenAI's Symphony post](https://openai.com/index/open-source-codex-orchestration-symphony/) · [Orchestration specification](https://github.com/openai/symphony/blob/main/SPEC.md)

## Implications for todo 38

The scheduler computes the earliest pending event, requests a checkpoint at the assignment deadline, and emits a stop request when the checkpoint grace period expires. It requires explicit confirmation before ownership transfer. The host must carry out the stop and establish that writes ceased. This distinction matters on Copilot, where the parent can message a worker and the documented kill control is interactive. [Repository scheduler](../../skills/default/delegate-to-subagents/scripts/scheduler.py) · [Copilot fleet controls](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/speed-up-task-completion#monitoring-progress)

## Proposed eval

- Run the same two workers through both skills on the same host. One stays silent past its deadline. The other keeps writing timestamped heartbeats. The silent worker tests whether the parent wakes up. The active worker tests whether the time limit holds while work is progressing.
- Record the assignment deadline, when the parent detected expiry, when it requested a stop, when the harness confirmed interruption, and when the worker last wrote. Preserve any missing confirmation as an observed gap.
- Grade deadline detection separately from shutdown. Compare detection latency across the two skills. Use the heartbeat trace to check for writes after the stop request, after confirmation, and before ownership transfer. An expired wait or a delivered stop message establishes neither worker exit nor the time of its final write.
