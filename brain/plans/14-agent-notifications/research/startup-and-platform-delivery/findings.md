# Startup and platform delivery findings

Current requirement note: references to retained history below describe the original research brief. User subsequently selected a persistent pending-alert stack, deletion on dismissal with brief Undo, and no separate history window. Use [the current contract](../../phase-3-deletion-and-undo.md) for product behavior; durable pending storage still needs native feasibility checks.
Checked 2026-10-21. No application framework or minimum OS versions are selected yet, so this is an OS and desktop-protocol feasibility review, not a framework recommendation.

## Recommendation

Prototype a **lazy single resident** process as the default: the first hook invocation starts one per-user UI process, records the event durably, and delivers it; later hook invocations send events to that process over local IPC. Offer optional launch at login for users who want the first alert to avoid cold-start latency. Keep the event journal independent of the UI process, so a crash or explicit quit does not lose events. This hybrid makes one process responsible for persistent panels, audio settings, and history without requiring the app to sit idle from every login. The user selected this hybrid for prototyping; native feasibility and explicit Quit behavior remain unverified.

The recommendation is a design inference. A resident process naturally owns persistent panels and settings. A per-invocation process either exits before a custom panel can remain interactive, or stays alive per alert and creates many competing processes. A shared durable journal and single-instance IPC address concurrent hook calls and recovery in either resident model.

| Model | Startup and idle cost | Concurrency and recovery | Panels, history, and quit |
|---|---|---|---|
| Resident at login, with opt-in autostart | No event-time process launch after the app is ready. It consumes some memory and has an event loop while idle. Login launch itself is subject to OS and desktop-session behavior. | One receiver can serialize concurrent hook events. A crash still requires restart or event-spool behavior. | Best ready state for custom panels and history. It can restore history after relaunch if history is stored durably. Explicit Quit should stop the receiver for the session; otherwise the next hook can immediately relaunch it. |
| New process for every CLI invocation | No idle app process, but every event pays process and UI startup cost. | A burst can start many processes, causing racing history writes, overlapping panels, and simultaneous audio. A lock or IPC broker is needed to serialize events, which introduces a resident-like coordination mechanism. | A process that exits can post a system notification, but cannot own a custom panel that stays until dismissed. Keeping each process alive until dismissal duplicates UI and state. Durable history must be shared and stored separately. |
| Lazy single resident | First event pays a cold start. Later events are sent to the existing process. Idle use begins only after the first event. Optional login autostart removes the first-event delay. | One receiver can order and deduplicate concurrent calls. The CLI should persist or queue an event before acknowledging it, so launch failure or a crash does not lose it. | Strong fit for custom panels, sound preferences, and history. Define Quit explicitly: a hook must not silently undo it by relaunching the app. A session pause plus durable event queue is a candidate behavior to prototype. |

All three models can store durable history, but only if history is written to an app-owned local store. Native notification history is not a cross-platform application database. A logged-out, headless, remote, or unavailable desktop session cannot show a local panel; the CLI should preserve events for later review. These are design inferences from the product boundary and platform lifecycle behavior.

## Sourced platform facts

**Login startup and tray reachability.** Windows `Run` keys launch an app at user logon, but Windows may delay those apps and does not promise prompt execution ([Microsoft Run and RunOnce](https://learn.microsoft.com/windows/win32/setupapi/run-and-runonce-registry-keys)). Users can also disable startup entries in Task Manager ([Microsoft Startup apps](https://learn.microsoft.com/en-us/windows/win32/w8cookbook/startup-apps)). macOS `SMAppService.mainApp` registers the app to launch at later logins; registration is subject to user approval and the user can manage the item in System Settings ([Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), [register](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29)). Linux desktop autostart launches after the user logs into a desktop environment, and a user can disable an entry with `Hidden=true` ([freedesktop Autostart Specification](https://specifications.freedesktop.org/autostart/latest/)). Thus none of these mechanisms means “available before a graphical user session exists.”

Tray or menu-bar affordances are not a reliable sole control surface. Apple says status items are not guaranteed to be available at all times because menu-bar space is limited ([Apple NSStatusBar](https://developer.apple.com/documentation/appkit/nsstatusbar)). Windows lets users move notification-area icons into overflow and controls which icons are visible ([Microsoft notification area](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area)). GTK's status-icon docs warn that a notification area may not exist or may be removed, and that legacy `GtkStatusIcon` is deprecated ([GTK StatusIcon](https://gnome.pages.gitlab.gnome.org/gtk/gtk3/class.StatusIcon.html)). Provide a normal app window and a CLI way to open history even if the tray icon is hidden or unavailable.

**Custom panels and foreground focus.** Windows can keep a topmost window above non-topmost windows, including after deactivation, but that does not grant keyboard focus. `SetForegroundWindow` can be denied; Windows says an app cannot force itself to the foreground while the user works in another window ([SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos), [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)). macOS has a floating window level intended for palettes, while `NSApplication.activate()` is a request and does not guarantee activation ([NSFloatingWindowLevel](https://developer.apple.com/documentation/appkit/nswindow/level-swift.struct/floating), [NSApplication.activate](https://developer.apple.com/documentation/appkit/nsapplication/activate%28%29)). These support floating, user-dismissible panels but do not justify stealing focus.

On Linux, the freedesktop notification service is specified for passive asynchronous popups, and explicitly excludes other presentation types such as modal windows and window-manager decorations ([Desktop Notifications Specification](https://specifications.freedesktop.org/notification/latest/)). Its hints include `resident` and `sound-name`, but those are hints handled by notification servers, not a portable custom-panel or sound guarantee ([Hints](https://specifications.freedesktop.org/notification/latest/ar01s08.html)). Under Wayland, standard `xdg-shell` provides ordinary toplevels and parent-relative popups, not a general request for a fixed screen coordinate or global always-on-top layer ([upstream xdg-shell protocol](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/stable/xdg-shell/xdg-shell.xml)). The separate `wlr-layer-shell` extension can anchor surfaces to screen edges and choose desktop layers, but its availability must be checked per compositor ([wlr-layer-shell protocol](https://gitlab.freedesktop.org/wlroots/wlr-protocols/-/blob/master/unstable/wlr-layer-shell-unstable-v1.xml)). Wayland activation is also a request: a compositor may reject a token it considers unwanted ([xdg-activation protocol](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/staging/xdg-activation/xdg-activation-v1.xml)).

**Audio and accessibility.** Native app audio playback is available on all three platforms: Windows WASAPI provides app audio streams and sessions ([Microsoft WASAPI](https://learn.microsoft.com/windows/win32/coreaudio/wasapi)); Apple `AVAudioPlayer` plays audio from a file or buffer and exposes volume control ([Apple AVAudioPlayer](https://developer.apple.com/documentation/avfaudio/avaudioplayer)); PipeWire supports playback streams and a PulseAudio-compatible protocol for existing clients ([PipeWire audio](https://docs.pipewire.org/page_audio.html), [PipeWire Pulse protocol](https://pipewire.pages.freedesktop.org/pipewire/page_module_protocol_pulse.html)). The Linux audio server and session setup can vary. On macOS, system-delivered notification sounds are separately governed by notification settings and have custom-sound format and length restrictions ([Apple UNNotificationSound](https://developer.apple.com/documentation/usernotifications/unnotificationsound)). For user-selected alert sounds, direct app playback is the more controllable path; it still cannot overcome a muted device, missing output, or system volume policy.

Accessible custom UI is feasible, but depends on using platform semantics. Windows UI Automation exposes interface semantics to assistive technology ([Microsoft UI Automation](https://learn.microsoft.com/windows/win32/winauto/entry-uiauto-win32)); standard AppKit controls carry accessibility by default and custom elements must expose it ([Apple AppKit accessibility](https://developer.apple.com/documentation/appkit/accessibility-for-appkit)); GTK controls expose roles and attributes through AT-SPI, while custom widgets must supply correct semantics ([GTK accessibility](https://docs.gtk.org/gtk4/section-accessibility.html)). Verify the chosen toolkit against keyboard-only use and each platform's screen reader.

## Prototype checks before choosing

1. Measure first-event-to-visible-panel and first-event-to-audio latency for cold launch, login-ready resident, and warm lazy-resident cases. Set an acceptable p95 after a user reviews the prototype.
2. Send a burst of simultaneous hook events. Verify one process, ordered durable records, no lost or duplicated alerts, bounded audio overlap, and a useful history view.
3. Kill the resident while an event arrives, then log out and back in. Verify that the CLI acknowledges only persisted events and that reopening the app recovers history.
4. Test explicit Quit in each startup mode. Confirm whether the app pauses until manual relaunch or the next login, and whether later hook events stay queued without unexpectedly reopening panels or playing sounds.
5. Test visible panels and keyboard focus on Windows and macOS while another app is active, in full-screen spaces, and with multiple monitors. Do not assume a topmost/floating level can take focus.
6. Test Linux on GNOME Wayland without extensions, KDE Plasma Wayland, a wlroots compositor such as Sway, and X11. Check panel placement, stacking, dismissal, activation, tray presence, and the standard notification fallback. Do not make a wlr layer-shell panel a baseline requirement until target desktop coverage is agreed.
7. Test sound for each event with mute enabled, output devices disconnected or changed, and independent event-type settings. Confirm quiet hours and volume controls affect direct audio playback.
8. Run keyboard and screen-reader checks on the alert panel, dismissal controls, and history. Verify that visual and audio cues have accessible equivalents.

These checks are prototype work, not claims of tested behavior. The platform documentation establishes available mechanisms, not end-to-end latency or uniform desktop behavior.
