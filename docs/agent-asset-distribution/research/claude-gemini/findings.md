# Claude Code and Gemini CLI distribution findings

Research checked against official documentation and the official Gemini CLI repository on 2026-09-29. The docs are rolling pages, so this records the published behavior visible on that date rather than a release-pinned compatibility guarantee.

## Research conclusion

Use native repository layouts for team-committed assets and keep provider-specific adapters where behavior differs. The shared Agent Skills `SKILL.md` format is portable across both clients when content stays within the open specification. It does not standardize native custom-agent frontmatter, instruction discovery, hook events, settings, or plugin and extension installation. Keep the existing global installer path intact; make repository-local distribution additive and opt-in, with team-committed mode the default requested by the owner.

## Skills

Both clients support the open Agent Skills directory format, with a required `SKILL.md` and optional supporting files. Claude discovers project skills under `.claude/skills/` and personal skills under `~/.claude/skills/`; project skills can be committed. Gemini discovers workspace skills under `.gemini/skills/` or `.agents/skills/`, and personal skills under `~/.gemini/skills/` or `~/.agents/skills/`. Name collisions resolve by scope precedence, with workspace skills taking precedence over personal skills in Gemini. The portable path is shared content in the Agent Skills subset, installed or linked into each client's discovery root. Claude-specific frontmatter and body features are extensions, not portable guarantees. [Agent Skills specification](https://agentskills.io/specification), [Claude skills](https://code.claude.com/docs/en/skills), [Gemini Agent Skills](https://geminicli.com/docs/cli/using-agent-skills/).

Claude offers skill invocation through slash commands and model selection based on skill descriptions; skills shipped by a plugin are namespaced. Gemini's skill commands support listing, enabling/disabling, and installing a skill from a local path, Git source, or `.skill` archive; its docs describe user and workspace install scopes. The Gemini skill docs reviewed do not document a lockfile, version pin, or skill update command, so do not promise those semantics for skills installed as packages. Directly committed workspace skill directories avoid that package-update question. [Claude skills](https://code.claude.com/docs/en/skills), [Gemini Agent Skills](https://geminicli.com/docs/cli/using-agent-skills/).

## Custom agents

The native source formats and discovery roots differ. Claude uses Markdown agent definitions in `.claude/agents/` for a project and `~/.claude/agents/` for personal agents. Gemini uses Markdown definitions in `.gemini/agents/` and `~/.gemini/agents/`. Both support frontmatter, but tool identifiers and configuration fields are client-specific. Keep canonical agent intent in the existing source and render or maintain provider-specific definitions rather than copying one provider's Markdown unchanged into the other provider's agent folder. [Claude subagents](https://code.claude.com/docs/en/sub-agents), [Gemini subagents](https://geminicli.com/docs/core/subagents/).

There is a documentation-status ambiguity for Gemini agents. The Gemini extension reference calls extension-bundled subagents a preview feature. The core subagent page describes local custom subagents, while the current configuration reference gives `experimental.enableAgents` a default of `true`. These statements concern different surfaces and do not establish that extension-distributed agents have left preview. Record extension-packaged agents as preview/unclear; do not infer general GA from the setting default. The reviewed pages are rolling docs, not release-pinned evidence, so confirm again before making a release-specific claim. [Gemini extension reference](https://geminicli.com/docs/extensions/reference/), [Gemini subagents](https://geminicli.com/docs/core/subagents/), [Gemini configuration reference](https://geminicli.com/docs/reference/configuration/).

## Instructions and hooks

Claude's native instruction files are `CLAUDE.md` at user or project scope, loaded through the directory hierarchy. Current Claude Code documentation says `AGENTS.md` is read by default when there is no applicable `CLAUDE.md` starting with Claude Code v2.1.277; when a `CLAUDE.md` exists, both can be enabled with the documented `claude-md-and-agents-md` setting. Thus an `AGENTS.md`-only repository needs that version/configuration condition accounted for; a small `CLAUDE.md` import shim is the compatibility option described by Claude's docs. Gemini's default context files are `GEMINI.md` at user or workspace scope. Its `context.fileName` setting can name a custom context file or list of files, so a committed `.gemini/settings.json` can opt into loading `AGENTS.md` alongside `GEMINI.md`. These are client settings and should be treated as native configuration, not as an automatic shared instruction standard. [Claude memory](https://code.claude.com/docs/en/memory), [Gemini GEMINI.md](https://geminicli.com/docs/cli/gemini-md/), [Gemini settings](https://geminicli.com/docs/cli/settings/).

Hooks are provider-native. Claude project hooks are configured in `.claude/settings.json` or a plugin's `hooks/hooks.json`; personal hooks live in `~/.claude/settings.json`, and local-only settings use `.claude/settings.local.json`. Project settings can be committed, but Claude can require workspace trust before interactive sessions run project hooks. Gemini hooks use Gemini's own event names and settings schema, including project `.gemini/settings.json` and extension `hooks/hooks.json`. Gemini applies workspace settings above user settings and may ignore workspace settings in an untrusted folder. Hook definitions run commands with the user's privileges, so generated team hooks need review and explicit trust. Shared skill content does not create a shared hook runtime or event protocol. [Claude hooks](https://code.claude.com/docs/en/hooks), [Claude plugins](https://code.claude.com/docs/en/plugins), [Gemini hooks](https://geminicli.com/docs/hooks/), [Gemini extension reference](https://geminicli.com/docs/extensions/reference/), [Gemini trusted folders](https://geminicli.com/docs/cli/trusted-folders/).

## Native packages, physical storage, and activation

Claude's native plugin has a `.claude-plugin/plugin.json` manifest. Components such as `skills/`, `agents/`, and `hooks/hooks.json` can be bundled with it. Plugins can be installed from a marketplace or Git source. User, project, and local installation scopes control the settings where the plugin is enabled; project scope records enablement in committed `.claude/settings.json`, but collaborators still need to install the plugin separately. Marketplace entries can refer to a branch, tag, or full commit SHA. Plugin updates are tied to the plugin version metadata and marketplace update policy; local and third-party sources do not all share the official marketplace's default auto-update behavior. A committed enablement entry is therefore not a self-contained distribution or bootstrap. [Claude plugins](https://code.claude.com/docs/en/plugins), [plugin installation](https://code.claude.com/docs/en/plugins/install), [marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference).

Gemini's native extension requires a root `gemini-extension.json` manifest and can bundle `skills/`, `agents/`, `hooks/hooks.json`, MCP servers, and other extension components. `gemini extensions install` copies the extension into `<home>/.gemini/extensions`; Git installation requires Git. The install command supports `--ref` and `--auto-update`, and updates are performed with `gemini extensions update`. The reference documents `--scope user|workspace` on enable/disable, not install. The exact project workspace settings file is `<repo>/.gemini/settings.json`: workspace settings are stored there, and workspace-scoped enable/disable targets that scope. Current settings schema/source represents disabled extensions as `extensions.disabled`; extensions are enabled by default when discovered. Thus the project file can carry workspace-specific activation state, but cannot place or update the extension package for a teammate. Each teammate must separately install the extension under their own home directory. Treat an exact Git ref as a selectable install source, not as a repo-wide lockfile or automatic installation promise. [Gemini extension reference](https://geminicli.com/docs/extensions/reference/), [Gemini settings](https://geminicli.com/docs/cli/settings/), [Gemini settings schema](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/config/settingsSchema.ts), [Gemini extension enable/disable implementation](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/acp/commands/extensions.ts), [Gemini extension release guide](https://github.com/google-gemini/gemini-cli/blob/main/docs/extensions/releasing.md).

For practical team distribution, commit native workspace skill/agent assets and only reviewed project settings. Treat Claude plugin and Gemini extension installation as a separate user setup step unless a future installer explicitly installs a pinned package. Do not copy whole `~/.gemini/settings.json` into a repository: personal UI, authentication, model, account-linked MCP, and other user configuration belong to the user. Merge only the intended project keys while preserving existing settings and hooks. Gemini does not document a separate project `settings.local.json` equivalent in the reviewed sources; local-untracked mode should use user-scope configuration or untracked repo-local assets and must not silently overwrite a teammate's committed workspace settings. Claude does document `.claude/settings.local.json` and local plugin scope. [Claude plugin installation](https://code.claude.com/docs/en/plugins/install), [Gemini settings](https://geminicli.com/docs/cli/settings/), [Gemini extension reference](https://geminicli.com/docs/extensions/reference/).

## Shared Agent Plugins standard boundary

The Agent Plugins v1 specification defines a shared plugin manifest with two standardized component types: Agent Skills and MCP. It does not define a universal custom-agent, instruction, or hook runtime. Its current compatible-client list does not list Claude Code or Gemini CLI; this is evidence only about the published list, not proof that either client cannot consume a future adapter. Do not claim that a shared plugin manifest installs either provider's native hooks or agents. Use separate Claude and Gemini manifests for their native packages, and reuse only the portable skill source where the format permits. [Agent Plugins specification](https://agent-plugins.org/specification), [compatible clients](https://agent-plugins.org/compatible-clients).

## Repository implication

The repository already has canonical skill and agent sources and a fixed-home global installer. Distribution support should add an explicit repository-local mode that mirrors or links assets into provider discovery paths while preserving the global path. Team-committed mode can store provider-native `.claude/` and `.gemini/` assets and only the project settings needed to discover them. A local-untracked mode is straightforward for asset directories; settings-driven activation needs provider-specific handling, especially because Gemini has no documented local settings override file. Preserve current Codex, Copilot, and Gemini global behavior, and merge only selected hook/context keys into Gemini project settings. Existing canonical agent Markdown may need thin per-provider adapters because agent frontmatter and tools are not portable. Native Claude plugins and Gemini extensions can be added as optional distribution packages, but their separate manifests and installation locations mean they should not be described as repo-self-contained.
