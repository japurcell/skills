# ECC ownership and distribution findings

Research date: 2026-09-29. This is a static review of first-party ECC GitHub sources. No installer, package, or client was installed or executed.

## Version and source boundary

The [GitHub release list](https://github.com/affaan-m/ECC/releases) lists `v2.2.1` as the latest tagged release, published September 8, 2026. Its tag points to commit [`5064474d4d762dc9640234a41617cccb79185cec`](https://github.com/affaan-m/ECC/commit/5064474d4d762dc9640234a41617cccb79185cec). The live [`main` package metadata](https://github.com/affaan-m/ECC/blob/main/package.json#L3) says `ecc-universal` version `2.2.2`, while the GitHub release list still has no `v2.2.2` entry. Code findings below use the current `main` paths, not an assertion that those files are byte-identical to the `v2.2.1` tag. The release notes independently confirm the important file-update policy described below. ECC declares MIT in both its package metadata and [LICENSE](https://github.com/affaan-m/ECC/blob/main/LICENSE).

GitHub's Contents API could not be fetched from this runtime. I identified source paths from ECC's own repository tree, imports, and linked documentation, then read the exact first-party code paths. The release SHA and package version are linked separately so the moving-branch limitation stays clear.

## Catalog, profiles, and recorded source

ECC has a machine-readable module catalog and seven curated profiles. Each module describes its stable ID, kind, source paths, supported targets, dependencies, default selection, estimated cost, and stability. `workflow-quality` provides a concrete dependency-closure example: it declares `skill-unified-memory`, which itself records the separately required `ecc-universal` CLI runtime. This separates included asset dependencies from external runtime dependencies. See [`install-modules.json`](https://github.com/affaan-m/ECC/blob/main/manifests/install-modules.json#L5-L28), [the workflow modules](https://github.com/affaan-m/ECC/blob/main/manifests/install-modules.json#L282-L386), and [`install-profiles.json`](https://github.com/affaan-m/ECC/blob/main/manifests/install-profiles.json#L4-L45).

The install-state schema distinguishes home and project targets, records the request and resolved modules, and stores source `repoVersion`, `repoCommit`, and `manifestVersion`. Each operation records module ID, source-relative and destination paths, strategy, ownership, and optionally a content SHA-256; the source version and commit fields are nullable. This is useful lifecycle provenance, but it does not establish the approved contract's required immutable source revision plus source-tree digest. Keep the contract's stronger source identity. See [`install-state.schema.json`](https://github.com/affaan-m/ECC/blob/main/schemas/install-state.schema.json#L28-L60), [request and resolution fields](https://github.com/affaan-m/ECC/blob/main/schemas/install-state.schema.json#L62-L169), and [operation fields](https://github.com/affaan-m/ECC/blob/main/schemas/install-state.schema.json#L171-L216). The plan builder fills version and Git commit from its source checkout and labels copy operations `managed` ([`plan.js`](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/plan.js#L92-L111), [source attribution](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/plan.js#L275-L299)).

## Ownership and edit conflicts

The generic installer has the wrong conflict policy for this project's contract. `prepareUserOwnedFileGuard` defines ownership as a destination already recorded in prior install-state. For each planned copy to an existing, unrecorded path, it adds a warning and skips only that operation; it continues adding later operations to the apply list. It also removes skipped files from state so ECC does not claim them. If an unowned file appears after planning, the per-write guard errors. See [`ownership-guard.js`](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/ownership-guard.js#L25-L37), [collision filtering](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/ownership-guard.js#L64-L120), and [late collision check](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/ownership-guard.js#L122-L129).

For a path already recorded as ECC-managed, the generic guard allows reinstall/update. ECC's `v2.2.1` notes explicitly say successful upgrades continue replacing previously managed files and advise users to back up intentional edits. A changed managed file therefore does not trigger the approved preserve-edit, stop-before-any-writes behavior on this ordinary path. This is a direct incompatibility, not a pattern to copy. The release also notes a narrower safeguard: on failed installs, hashes refresh only for files actually written, preserving the previous hashes for untouched managed files. That checkpoint behavior can prevent failure from falsely changing ownership state, but it is not edit protection or rollback history. See the [v2.2.1 release notes](https://github.com/affaan-m/ECC/releases/tag/v2.2.1), and the generic ownership check in [`ownership-guard.js`](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/ownership-guard.js#L49-L79).

There is a stronger, target-specific Kimi managed-project path. Its preflight validates prior state identity and checks a planned managed file's digest against recorded `contentSha256`; changed content is rejected as unverified ownership. It classifies destinations as create, managed update, identical, JSON merge, or conflict before writing ([`multi-harness-setup.js`](https://github.com/affaan-m/ECC/blob/main/scripts/lib/multi-harness-setup.js#L161-L221), [classification and preflight](https://github.com/affaan-m/ECC/blob/main/scripts/lib/multi-harness-setup.js#L252-L344)). Guided setup builds previews for all selected harnesses before apply, then applies harnesses sequentially and can report `partial` if a later apply fails ([plan and apply loop](https://github.com/affaan-m/ECC/blob/main/scripts/lib/multi-harness-setup.js#L437-L489)). This is valuable evidence for a narrower implementation refinement: retain whole-operation conflict preflight, expose understandable operation classifications, and recheck state and destination classification immediately before writes to catch changes after preview. It does not make ECC's normal installer atomic, nor provide a global rollback if writing later fails.

## Shared configuration ownership

Manual Claude settings merge config semantically using stable managed hook IDs. Validation requires nonempty, unique IDs; update matches by ID, returns added/updated/unchanged/removed entries, and preserves other settings entries. The apply path rereads settings at the write boundary so settings added after planning survive; same-ID changes fail closed. State records the managed hook payload as a semantic ownership record. This is an implementation example for the contract's existing requirement to own config entries rather than whole shared files. See [`claude-settings.js`](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/claude-settings.js#L120-L181), [ID-based merge](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/claude-settings.js#L452-L531), and [`apply.js`](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/apply.js#L300-L326) and [write-boundary re-read](https://github.com/affaan-m/ECC/blob/main/scripts/lib/install/apply.js#L477-L506). The release notes also document atomic config writes and concurrent-edit detection.

## Pruning, paths, migration, and native channels

I did not verify the generic install code that reconciles previously selected files no longer in the current plan. The schema's current operation list and the existence of lifecycle commands do not, by themselves, prove safe deselection pruning. Preserve the approved rule: prune only installer-owned, unchanged items that are no longer required, and preflight conflicts across the complete operation before any writes. This portion remains unverified in this review.

ECC models `home` and `project` install roots in state, while guided Claude setup distinguishes `user`, `project`, and `local` plugin scopes. Its clients can use different delivery channels: Claude and Codex have native plugin paths, while the guided managed Kimi path writes project files. The README warns not to stack methods in the same harness because that duplicates assets or hooks. Native Claude plugins cannot distribute `rules`, so users copy those separately. The universal package requires Node.js 18+, and Claude terminal setup also requires Git and Claude Code 2.1+. ECC says it validates the exact packed artifact on Linux, macOS, and Windows. These are scope and packaging facts, not reasons to change the approved Python 3.11 standard-library lifecycle engine or committed-copy default. See the [guided target/scope table and runtime prerequisites](https://github.com/affaan-m/ECC/blob/main/README.md), [plugin rule limitation](https://github.com/affaan-m/ECC/blob/main/README.md), and [release test statement](https://github.com/affaan-m/ECC/releases/tag/v2.2.0).

The 1.x to 2.0 migration changes both the repository name and Claude plugin identifier. Its guide asks users to install the new plugin and separately uninstall the old one; manual home copies may need manual cleanup. Treat stable product identifiers and migration notes as necessary for future releases, but do not transfer ECC's manual cleanup into this project's update contract. See [MIGRATION-1X-TO-2.0.md](https://github.com/affaan-m/ECC/blob/main/docs/MIGRATION-1X-TO-2.0.md).

## Comparison with the approved contract

Retain the approved contract's committed copied payload, immutable source commit plus digest, per-file baseline and ownership, semantic config ownership, explicit dependency closure, conflict-before-any-writes rule, changed-file preservation, and conservative prune rule. ECC's dependency catalog and client target matrix are useful modeling evidence; its managed hook IDs are a concrete semantic-config pattern. The Kimi flow additionally demonstrates useful preview classification and apply-boundary revalidation. Do not adopt the generic skip-and-continue behavior or its replacement of edited managed files. Do not infer deselection pruning from the available schema or lifecycle descriptions. Native packages remain a later optional channel because ECC documents asset coverage gaps, separately installed runtime requirements, and different native lifecycle behavior.

The research task was static only. ECC installers and client commands were not run; source comparisons are not an end-to-end compatibility claim.
