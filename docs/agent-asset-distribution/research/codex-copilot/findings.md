# Codex and GitHub Copilot distribution findings

Research date: 2026-09-29

## Main finding

Repository-local skills and shared `AGENTS.md` instructions can cover the broadest common ground. Codex and Copilot both recognize `.agents/skills` in repositories, and both can consume `AGENTS.md` instructions. Native custom agents and hooks use different paths, formats, activation, and trust rules. A full team bundle therefore needs thin native adapters for those assets. The Agent Plugins format offers a portable core for skills and MCP, but it does not standardize agents or hooks. [Codex skills](https://learn.chatgpt.com/docs/build-skills), [Copilot skills](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills), [VS Code instructions](https://code.visualstudio.com/docs/agent-customization/custom-instructions), [Agent Plugins for Codex](https://developers.openai.com/plugins/build/plugins), [Agent Plugins for Copilot](https://docs.github.com/en/copilot/concepts/agents/about-plugins)

## Capability and path matrix

| Asset | Codex | GitHub Copilot |
| --- | --- | --- |
| Skills | Repository `.agents/skills/<skill>/SKILL.md`; personal `$HOME/.agents/skills`; also `/etc/codex/skills`. Codex CLI, desktop app, and IDE extension support standalone skills. Plugin-bundled skills also work in supported Codex plugin surfaces. A skill is discovered from metadata, then its body is loaded when selected. | Repository `.github/skills`, `.agents/skills`, or `.claude/skills`; personal `~/.copilot/skills` or `~/.agents/skills`. Copilot CLI, cloud agent, code review, Copilot app, and VS Code support skills. Duplicate skills are not merged; the first matching skill location wins in the CLI search order. [Codex](https://learn.chatgpt.com/docs/build-skills), [Copilot](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills), [Copilot CLI discovery](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) |
| Custom agents | Local Codex clients use TOML files in project `.codex/agents/` or personal `~/.codex/agents/`. Each requires `name`, `description`, and `developer_instructions`. These are local Codex custom agents, not plugin components. The docs describe these as local Codex clients; hosted Codex cloud agent discovery is **UNVERIFIED**. | Project `.github/agents/`; personal CLI/Agent Host `~/.copilot/agents/`; organization and enterprise locations also exist. Use `.agent.md` with YAML frontmatter for cross-client repo compatibility. Copilot CLI also documents `.md` profiles in some contexts, and VS Code detects `.md` files in `.github/agents`; using `.agent.md` avoids relying on that variation. [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Copilot CLI](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-custom-agents), [Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-custom-agents), [VS Code](https://code.visualstudio.com/docs/agent-customization/custom-agents) |
| Hooks | User `~/.codex/hooks.json` or `~/.codex/config.toml`; project `.codex/hooks.json` or `.codex/config.toml`. Matching hook sources combine rather than override each other. Project hooks require a trusted `.codex/` layer; non-managed hooks require review and trust for the current definition hash. Plugin hooks use Codex's hook schema and the same trust review. | CLI loads repo `.github/hooks/*.json`, user `~/.copilot/hooks/*.json`, settings-inline hooks, and plugin hooks; these sources combine. The same repo hook files are the only hook configuration available by default in Copilot cloud agent. Cloud execution is a non-interactive, ephemeral Linux sandbox with restricted network and a smaller event/runtime set. [Codex](https://learn.chatgpt.com/docs/hooks), [Copilot](https://docs.github.com/en/copilot/reference/hooks-reference) |
| Instructions | `AGENTS.md` is discovered from the global Codex home and from project root through the current directory, with nearer files taking precedence. Repository guidance is committed with the project. [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md) | `.github/copilot-instructions.md`, `.github/instructions/**/*.instructions.md`, and `AGENTS.md` are recognized in documented Copilot contexts. Copilot CLI also supports personal `~/.copilot/copilot-instructions.md` and personal modular instructions. GitHub's support matrix differs by surface, so path-specific instructions should be checked against the target surface. [Support matrix](https://docs.github.com/en/copilot/reference/custom-instructions-support), [Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions) |

The canonical `agents/*.md` source must be installed into each client's discovery path. Codex requires conversion to TOML with its three required fields. Copilot can consume compatible Markdown profiles, but a repository adapter should use `.github/agents/*.agent.md` for consistent discovery across its clients. Keep shared prompt text canonical and generate client-specific metadata or filenames where needed. [Codex agent format](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Copilot profile format](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-custom-agents), [cloud creation path](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/create-custom-agents)

## Plugins and activation

Both vendors document Agent Plugins as a portable package format. Put `plugin.json` at the package root, `skills/` and optional `mcp.json` beside it. Codex-specific presentation, MCP mappings, and hooks belong under `extensions.com.openai`; Copilot-specific agents, hooks, commands, and rules belong under `com.github.copilot/`. The plugin manifest does not define custom agents as a portable component, and Codex's plugin docs currently list skills, MCP, assets, and lifecycle hooks without plugin agents. An OpenAI plugin cannot replace the repo `.codex/agents/` TOML adapter. [OpenAI packaging](https://developers.openai.com/plugins/build/plugins), [Copilot packaging](https://docs.github.com/en/copilot/concepts/agents/about-plugins), [VS Code plugin component matrix](https://code.visualstudio.com/docs/agent-customization/agent-plugins)

Codex supports a repo marketplace file at `.agents/plugins/marketplace.json`, with plugin directories such as `plugins/`. The project enables a local-marketplace plugin in `.codex/config.toml` using `[plugins."plugin-name@marketplace-name"] enabled = true`. Project config only loads for trusted projects. These local marketplace settings are documented for Codex CLI and the ChatGPT desktop app; the Codex IDE extension does not support plugins. Personal marketplace examples use `~/.agents/plugins/marketplace.json` and `~/.codex/plugins/`. [Codex plugin packaging and activation](https://developers.openai.com/plugins/build/plugins), [Codex plugin availability](https://learn.chatgpt.com/docs/plugins), [Codex project config trust](https://learn.chatgpt.com/docs/config-file/config-basic)

Copilot CLI installs plugins imperatively or uses `enabledPlugins` in user `~/.copilot/settings.json` or repository `.github/copilot/settings.json`. Copilot cloud agent uses committed `.github/copilot/settings.json` with `enabledPlugins` and, for non-default sources, `extraKnownMarketplaces`. VS Code can recommend workspace plugins through the same Copilot settings file, but plugin support is off by default and installed/enabled state is separate from shared workspace settings. The GitHub Copilot app uses its plugin UI. [Copilot plugin activation](https://docs.github.com/en/copilot/concepts/agents/about-plugins), [VS Code plugins](https://code.visualstudio.com/docs/agent-customization/agent-plugins), [VS Code settings](https://code.visualstudio.com/docs/agents/reference/ai-settings)

The Codex IDE extension and hosted Codex cloud surfaces should not be inferred from desktop/CLI behavior. Standalone Codex skills are documented for the IDE extension, while plugins are explicitly unsupported in that extension. Codex cloud checks out a selected Git revision in an ephemeral environment, but this research found no official Codex cloud documentation for local plugin marketplace, custom agent, or hook discovery. Those cloud-specific paths remain **UNVERIFIED**. [Codex skills](https://learn.chatgpt.com/docs/build-skills), [Codex plugins](https://learn.chatgpt.com/docs/plugins), [Codex cloud environment](https://learn.chatgpt.com/docs/environments/cloud-environment)

## Team committed and local-only repository modes

For a committed team setup, Codex can discover `.agents/skills`, `.codex/agents`, and `.codex/hooks.json` from the repository. Copilot can discover `.agents/skills`, `.github/agents`, and `.github/hooks`; `.github/copilot/settings.json` can activate plugins for Copilot CLI and cloud agent. Copilot cloud runs from the repository revision and does not receive a developer's uncommitted local files, user hooks, settings, or installed plugins. This last distinction follows from the documented cloned-repository sandbox and configuration discovery behavior. [Codex paths](https://learn.chatgpt.com/docs/build-skills), [Copilot paths](https://docs.github.com/en/copilot/reference/hooks-reference), [Copilot cloud sandbox](https://docs.github.com/en/copilot/reference/hooks-reference)

For Copilot CLI, the exact local override path is `.github/copilot/settings.local.json`, not `.settings.local.json`. It has higher precedence than `.github/copilot/settings.json`, and GitHub says to add it to `.gitignore`. It supports repository-scoped overrides such as plugin enablement and inline hooks. This is a documented local-only configuration path; it does not put local agent/skill/hook files into cloud runs. [Copilot CLI configuration](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference), [hooks](https://docs.github.com/en/copilot/reference/hooks-reference)

Codex documents no analogous `settings.local.json` file. A local-only Codex project overlay can be kept as untracked files at the normal repo discovery paths, with project plugin enablement in an untracked `.codex/config.toml`; this is an inference from ordinary repo path discovery plus trusted project config, not a special Codex local profile contract. Project-local Codex settings and hooks are ignored for untrusted projects. [Codex configuration](https://learn.chatgpt.com/docs/config-file/config-basic), [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Codex skill discovery](https://learn.chatgpt.com/docs/build-skills)

## Selection, updates, versions, and trust

Selection is currently coarsest for Codex local marketplace plugins: project config enables or disables a plugin, while the docs do not specify a general component selector for choosing particular skills, agents, or hooks inside a plugin. Codex skills can be individually disabled through `[[skills.config]]` by skill file path, but that is user config rather than a repo plugin selection mechanism. Copilot CLI exposes skill list/add/remove/enable/disable commands, and repository plugin activation is by plugin ID. Copilot's `gh skill` workflow supports installing a skill from a tag or commit and pinning it against updates. [Codex skills config](https://learn.chatgpt.com/docs/build-skills), [Copilot CLI commands](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference), [Copilot skill install/update](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills)

Committed files inherit the repository's Git history and review. Plugin marketplaces add package versions and update commands: Copilot marketplace entries have versions and CLI updates; Codex can refresh a local marketplace. The docs reviewed here do not establish a uniform cross-client rollback or pin contract, nor a repo-level pin for every individual component. Treat fixed Git SHAs, plugin semantic versions, and skill pins as separate mechanisms and validate each client before promising reproducibility. [Copilot marketplaces](https://docs.github.com/en/copilot/concepts/agents/about-plugins), [Codex local marketplaces](https://developers.openai.com/plugins/build/plugins), [Copilot skills](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills)

Hooks are executable code, with distinct schemas and runtime assumptions. Codex requires review/trust of each non-managed hook definition. Copilot CLI combines hook sources on the local machine; cloud agent runs repository hooks automatically in its restricted sandbox without interactive prompts. VS Code hook behavior depends on the selected harness. Bundle and activate hooks explicitly per client, and treat review/trust separately from plugin installation. [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Copilot hooks](https://docs.github.com/en/copilot/reference/hooks-reference), [VS Code hooks](https://code.visualstudio.com/docs/agent-customization/hooks)

## Current-repository implications

The existing installer inventory supplied for this research supports Codex, Copilot, and Gemini in global mode, with fixed home targets and no scope or component selection. Preserve that global path. Repository distribution needs a separate repo-scoped setup path that can choose assets and either commit generated files or leave them untracked. Keep `agents/*.md` canonical, and serialize separate Codex TOML and Copilot `.agent.md` files where custom agents are selected. The portable plugin can bundle shared skills/MCP, with Codex and Copilot hooks/agents in their native extension directories. This is a research recommendation, not an approved implementation design.
