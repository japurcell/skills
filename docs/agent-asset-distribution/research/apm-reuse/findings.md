# Microsoft APM reuse findings

Research snapshot: 2026-09-29. This evaluates Microsoft APM against the approved [distribution contract](../../tickets/choose-distribution-contract.md). The recommendation is to **not use APM as the initial installer or lifecycle engine**. APM is mature and capable, but its file lifecycle does not satisfy the contract's stop-before-write treatment of edits and conflicts. Its committed-payload audit and hash-gated pruning are useful patterns, and a read-only committed-payload verifier is a small candidate refinement for the local design.

## Scope and provenance

The latest GitHub release shown during research is [v0.32.0](https://github.com/microsoft/apm/releases), published 2026-09-25 at release commit `f0509d7`. The repository's current [`pyproject.toml`](https://github.com/microsoft/apm/blob/main/pyproject.toml#L3-L40) also reports version 0.32.0 and declares Python `>=3.10` plus runtime dependencies when installed from Python. APM is [MIT licensed](https://github.com/microsoft/apm/blob/main/LICENSE). The [official installation guide](https://microsoft.github.io/apm/getting-started/installation/#requirements) says Git is required, Python 3.10+ is needed only for pip or source installs, and standalone binaries are available for macOS, Linux, and Windows. Binary installation therefore avoids imposing APM's Python dependency set, but still requires a separate CLI installation and update channel.

Source was inspected beyond the README, including the install pipeline, target integrator, transaction boundary, lockfile, and prune command. GitHub's Contents API was unavailable in this research environment, so exact source paths were found through GitHub's official repository UI. Source links below point to `main`; the visible `pyproject.toml` version matches the latest release, but these inspected files were not pinned to the release commit. No APM CLI, installer, or client integration was executed.

## Fit against the contract

| Contract area | APM evidence | Fit |
|---|---|---|
| Package/dependency model | APM resolves `apm.yml` dependencies, including transitive remote packages, plugins, MCP entries, and local/package refs. It writes `apm.lock.yaml` and deploys package primitives. See [`apm install`](https://microsoft.github.io/apm/reference/cli/install/#description) and the [lifecycle](https://microsoft.github.io/apm/concepts/lifecycle/#2-install). | The key abstraction differs. This contract needs a catalog and required-dependency closure maintained inside one source repository. APM's multi-repository transitive package resolver is broader than needed; adopting it would introduce a second manifest, package model, CLI, lock lifecycle, and upstream repository boundaries. This is an inference from the two models. |
| Committed team payload | APM can write harness output files and lock state. Its [CI guide](https://microsoft.github.io/apm/enterprise/enforce-in-ci/#audit-only-ci-pattern) explicitly supports committing deployed outputs and auditing them without rewriting the checkout. Its ordinary setup flow still uses the APM CLI to install or update. | Generated committed files are feasible. The approved no-bootstrap default is also feasible if the repository commits the selected files, but APM does not remove the need for a separate APM CLI when maintainers regenerate them. |
| Update, preview, and pins | [`apm update`](https://microsoft.github.io/apm/reference/cli/update/) re-resolves dependencies allowed by manifest refs and presents added, updated, removed, and unchanged items. `--dry-run` previews without deployment writes. [`apm install --frozen`](https://microsoft.github.io/apm/reference/cli/install/#common) requires a lock and rejects manifest/MCP state drift before deployment; it is a structural lock check. | Strong update UX and lock provenance, but the ref-resolution policy is tied to APM's package manifest. The approved contract instead updates from this repository's selected branch or explicit tag/commit and restores from the currently recorded immutable source revision. |
| Content integrity | The [lockfile implementation](https://github.com/microsoft/apm/blob/main/src/apm_cli/deps/lockfile.py) records `LockedDependency.deployed_files`, `deployed_file_hashes`, `resolved_commit`, and `resolved_ref`. The raw-file view did not expose reliable line numbering for this large file, so this is a path-only code reference. Frozen install alone does not verify deployed file bytes; APM directs users to `apm audit --ci` for that. The CI guide's `setup-only: true` mode leaves checked-out files untouched and replays pinned content in scratch before comparing. | Useful provenance and integrity patterns. A local read-only verifier could check that each committed selected output exists and matches its recorded digest, and fail on missing, modified, or stale payload without installing or repairing it. APM's `audit --ci` is a larger package replay, not a drop-in component for this repository's catalog. |
| Existing generated/owned file modified locally | The pipeline builds `managed_files` from lockfile `deployed_files` ([`pipeline.py`](https://github.com/microsoft/apm/blob/main/src/apm_cli/install/pipeline.py#L645-L650)). `BaseIntegrator.check_collision` returns no collision for those managed paths without comparing current bytes; the branch is visible in [`base_integrator.py`](https://github.com/microsoft/apm/blob/main/src/apm_cli/integration/base_integrator.py#L167-L206). APM's own CI guide confirms normal `apm install` overwrites a modified managed file before audit ([CI guide](https://microsoft.github.io/apm/enterprise/enforce-in-ci/#audit-only-ci-pattern)). | **Does not meet contract.** The contract requires preserving local edits and stopping the entire update before writes when upstream conflicts. APM's normal installer can replace locally edited managed outputs. |
| Existing unowned/authored path collision | For an existing path absent from the managed set, `BaseIntegrator.check_collision` records a skip or warning unless `--force` is used ([`base_integrator.py`](https://github.com/microsoft/apm/blob/main/src/apm_cli/integration/base_integrator.py#L167-L206)). APM documents its pipeline as resolve, policy, scan, then integrate ([install reference](https://microsoft.github.io/apm/reference/cli/install/#description)); the integration phase follows the managed-set construction in [`pipeline.py`](https://github.com/microsoft/apm/blob/main/src/apm_cli/install/pipeline.py#L645-L719). | This protects an unowned path from silent overwrite, but it is a per-path skip/warning during integration, not the contract's whole-operation preflight failure. Other outputs can already be written or continue to be integrated. This sequencing conclusion is source-based inference. Do not conflate the unowned-file behavior with the managed-file overwrite behavior above. |
| Pruning and shared ownership | APM tracks deployed files and hashes in lock state. The `prune` command builds `cleanup_claims`, reconciles paths still referenced by remaining owners, then supplies only unretained paths and their recorded hashes to stale-file cleanup ([`prune.py`](https://github.com/microsoft/apm/blob/main/src/apm_cli/commands/prune.py)). Exact source line numbering was unavailable for this file. The [lifecycle docs](https://microsoft.github.io/apm/concepts/lifecycle/) say APM removes only unchanged files it owns. | Strong pattern for precise ownership, unchanged-file deletion, and retaining shared outputs. Reusing APM only for pruning would still require translating the local catalog and ownership state into its lock/ledger model. |
| Configuration merge | APM adapters transform and merge target-specific hook formats; the [hooks guide](https://microsoft.github.io/apm/producer/author-primitives/hooks-and-commands/) documents distinct target schemas and path handling. The target matrix describes Copilot, Codex, and Gemini output formats. | Capable adapter work, but merge and ownership semantics become APM-specific. A wrapper would still need to know which config entries APM plans to modify so it can preflight local edits and conflicts before calling it. |
| Required clients/assets | The [target matrix](https://microsoft.github.io/apm/reference/targets-matrix/#summary) lists Copilot, Codex, and Gemini adapters and shared `.agents/skills` deployment. It lists Codex agents/skills/hooks/MCP but no per-file instructions; Codex compile output is `AGENTS.md` ([Codex target](https://microsoft.github.io/apm/reference/targets-matrix/#codex)). Gemini supports skills, commands, hooks, and MCP, but no agents; instructions compile into `GEMINI.md` ([Gemini target](https://microsoft.github.io/apm/reference/targets-matrix/#gemini)). | Substantial overlap, including Copilot hooks and shared skills, but not a complete match for the approved existing Codex/Copilot/Gemini workflows. Gemini has no agent primitive and Codex does not install per-file instructions. APM also transforms source primitives under its own `.apm/` conventions. |
| Interrupted operation recovery | `InstallTransaction` says its resolution journal is limited to `apm_modules`; native target integration is outside the transaction ([`transaction.py`](https://github.com/microsoft/apm/blob/main/src/apm_cli/install/transaction.py#L69-L88)). Its rollback restores the manifest and only prepared resolution paths ([source](https://github.com/microsoft/apm/blob/main/src/apm_cli/install/transaction.py#L169-L178)). | Does not provide all-output rollback/recovery for interrupted target writes. A wrapper cannot count on APM's transaction to restore its native integrations. |

## Decision

Do not use APM as the underlying installer or as a narrow dependency/provenance component for the initial contract. The reason is not that APM lacks package-manager features. The decisive mismatch is ownership and mutation semantics: its own documentation says an ordinary install overwrites locally modified managed outputs, while unowned-file collisions are handled per path during integration. To restore the required guarantee, an APM wrapper would have to calculate all transformed destination paths, config merges, and ownership first, detect conflicts across the full update, preserve hashes, and control pruning before invoking APM. That wrapper would own much of the safety lifecycle while APM independently owns package resolution and deployment, creating two overlapping authorities.

Build the narrow repository-local catalog/materializer around dependency closure within this single maintained repository. Retain patterns worth copying: immutable source commit plus digest, per-output hashes, explicit owner references for shared paths, hash-gated pruning, target-specific configuration merge rules, and a read-only CI verifier for committed payload drift. The CI verifier is a refinement candidate, not an approved change to the closed contract. Do not add rollback history; restore from the currently recorded immutable revision remains distinct from rollback.

## Evidence limits

The evidence separates official documentation promises from source inspection. No installer or `apm` command was run, no client files were generated, and no local/global home was changed. The source was the GitHub `main` view, not a tag-pinned checkout. The exact behavior of an unexecuted release binary and all client discovery/runtime details remain unverified. The recommendation concerns lifecycle fit to this repository's approved contract, not a general quality judgment about APM.
