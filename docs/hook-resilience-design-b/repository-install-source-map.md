Current requirements are B3 CLI behavior, B4 trusted configuration, and B6 explicit repository-only installation. There are no background scans, retries, workers or checkpoint triggers. Status is historical and never permission. Pre-commit uses `selected_staged_v1`, inspecting changed staged files in full; pre-push covers actual outgoing history, including intermediate messages and blobs. ## Effective Git configuration and repository identity

[ProtectedRepository.prepare:155](../../hooks/runtime/scan_repository.py#L155) discovers canonical root, Git directory, common Git directory and object format using `rev-parse --path-format=absolute --show-toplevel --absolute-git-dir --git-common-dir --show-object-format`. Its [query:145](../../hooks/runtime/scan_repository.py#L145) uses bounded capture/deadlines, and [read_selected_index:104](../../hooks/runtime/scan_repository.py#L104) opens selected files through held parents, including a native Windows branch. Those are concrete reusable mechanisms.

It deliberately disables system/global config and injects `core.hooksPath=os.devnull`, hooks/fsmonitor/maintenance overrides and a private home at [prepare:166](../../hooks/runtime/scan_repository.py#L166). Its `config --includes --null --show-scope --list` read at [line 211](../../hooks/runtime/scan_repository.py#L211) retains only conversion/attribute settings from local/worktree scope. Therefore this API cannot answer the installer question "which hooks would Git currently run?" Reusing its effective environment unchanged would hide global/shared hooks and overwrite their behavior by omission.

The metadata-only [scan_status.discover:100](../../hooks/runtime/scan_status.py#L100) reads `.git` directory/file, `HEAD`, and `commondir` with bounded ancestry/size checks without executing Git. It returns root/gitdir/common and a display identity. [Status identity:144](../../hooks/runtime/scan_status.py#L144) hashes normalized common+gitdir; gate identity hashes root+gitdir+common. Keep those domains distinct. Metadata discovery does not evaluate effective configuration, includes, hooksPath, worktree overrides, or hook managers.

The official configuration interface supplies `--null`, `--show-origin`, `--show-scope` and `--includes`. `core.hooksPath` may be absolute or relative to hook execution cwd. `--worktree` targets `config.worktree` only when its extension is enabled; otherwise it aliases local config. These distinctions require installer handling, not an assumption that `.git/hooks` or `git config --local` describes the effective setup. [Git configuration reference](https://git-scm.com/docs/git-config/2.54.0).

Proposed T7 discovery seam: a bounded `RepositoryInstallSnapshot` with canonical root/gitdir/common/object format; exact config sources/scopes/values and original bytes/identities of files eligible for mutation; effective hooks directory; original hook paths/types/executable state/digests; linked-worktree set/scope; and known owned installation state. Use one pinned Git executable and argument-list, non-content queries. Preserve legitimate system/global/include inputs for discovery while removing inherited `GIT_DIR`, object/index redirects, command config injection and execution-affecting settings. Do not import those settings into content scanning. Cap captured config output/entries and subprocess duration; never run hooks, manager commands, credential helpers, remote queries, or implicit downloads during discovery.

T7 must implement and verify origin-aware NUL framing, absent versus duplicate hooksPath, path-valued interpretation, relative paths, conditional include precedence, and stable-file checks. Treat includes/linked files that cannot be safely bounded and attributed as unsupported ambiguity. A manifest records original effective paths and the exact local value being changed, rather than rewriting the effective global/include source. Recheck snapshot identities under the installation lock immediately before mutation. Git's config lock is a separate contention domain; avoid check-then-write restoration that can erase a concurrent user edit.

**Concurrent-edit feasibility limit:** the bundle `.install-lock` coordinates this installer, while Git `config.lock` coordinates writers that honor Git's lock protocol. Neither prevents arbitrary direct replacement of a config file. A final fingerprint check followed by ordinary `os.replace` is not atomic compare-and-swap; a replacement can land between them. Existing backup/atomic-write helpers do not close that gap. Candidate 1 already encountered the absence of a general macOS replace-if-unchanged primitive. Before T7, the coordinator must resolve how B6's concurrent-edit promise is bounded: prove an available conditional mutation mechanism, or explicitly define supported cooperating writers and refuse arrangements that cannot meet the retained promise. This document does not weaken that requirement or authorize a check-then-replace implementation as universal no-overwrite protection.

Worktree cases require explicit scope output before writes: ordinary main worktree, linked worktree without `extensions.worktreeConfig`, enabled worktree configuration, existing worktree override, separate Git directory, shared common directory, and linked/reparse metadata. Common-local hooksPath can affect siblings. Do not enable an extension or silently broaden coverage to resolve that uncertainty. The exact supported cases and refusal/recovery text need coordinator reconciliation in the active plan before T7 implements them.

Existing fixtures to extend rather than cite as installation proof:

- [CLI linked conversion configuration:204](../../scripts/test-scan-secrets-cli.py#L204), [ordinary linked worktree:217](../../scripts/test-scan-secrets-cli.py#L217), [missing/malformed config.worktree:234](../../scripts/test-scan-secrets-cli.py#L234) establish useful disposable construction patterns.

## Composition, destination binding and uninstall

Changing hooksPath redirects every Git hook lookup. Installing only `pre-commit` and `pre-push` would strand `commit-msg`, `prepare-commit-msg`, post hooks, and existing repository OKF hooks. Preserve the complete supported set through generated passthrough launchers or an equivalent explicitly verified mechanism. Launch original hooks at their original paths; copying executable bytes changes `$0`, sibling-resource resolution and path-dependent behavior. Snapshot executable state and original identity; detect changed hooks, prior owned wrappers/recursive wrapping, symlinks/reparse paths and unsupported managers before enabling the gate. Refusal is safer than inferring manager behavior from a basename. Runtime drift must also deny before upload rather than silently reclassify a hook.

Git specifies hook cwd/environment and hook-specific argument/stdin conventions. [Hook contract](https://git-scm.com/docs/githooks/2.54.0). Proposed common launcher generation should preserve those original semantics for unrelated hooks; gated hooks scan first, then replay the original arguments and a fresh original stdin copy to each supported downstream step in declared order. Do not pass unrelated hooks through a pre-push-only parser or bounded transaction grammar. T7 must prove passthrough behavior with real Git actions and a path-sensitive fixture, including hooks that delegate to another hook. A passthrough wrapper that inadvertently reenters itself must be detected/refused.

Use [Transaction:25](../../hooks/runtime/scan_transaction.py#L25), [identities:32](../../hooks/runtime/scan_transaction.py#L32), and [capture_transaction:62](../../hooks/runtime/scan_transaction.py#L62) for exact raw pre-push input, bounded records/deadline and digest over both remote name and destination URL. They do not resolve configured remotes. T7 must generate installation binding from an explicitly supported destination selection, account for push URLs/multiple push destinations or refuse ambiguity, and compare the actual invocation's remote+URL exactly. Never alter remotes or expose credential-bearing URLs in dry-run, status, diagnostics, JSON, or manifests intended for ordinary display.

The owner-only repository installation manifest should be separate from the neutral bundle manifest and record schema/build/interpreter/runtime/data/budget location, repository/scope identity, original effective configuration and original hook identities/order, owned file hashes, intended installed config value, and recoverable operation phase. Distinguish absent local hooksPath from a local value that merely equals an inherited value. On uninstall, remove only exact owned files and restore/unset only the owned local binding that still equals the recorded installed state. Preserve concurrent edits and unowned files, retain private audit/status data unless removal is separately explicit, and diagnose drift instead of deleting the entire directory or restoring a stale whole config backup.

Dry-run uses the same immutable discovery and admission path but creates no directory, lock, report, backup, manifest, hook or config. Emit a redacted preview of scope, affected config, owned actions, preserved hooks and supported/refused composition. Idempotence compares desired semantic state and existing owned bytes: identical install is a no-op, budget content edit is not a reinstall, a changed binding requires an explicit install, and repeated uninstall has a documented safe result. Ordered config/asset changes need phase-aware recovery; activate only after complete assets exist, roll back only if state still matches this invocation's ownership, and never delete unrelated content to "recover".

The provider configuration mergers offer limited patterns: [merge_hooks:84](../../scripts/install-provider-hooks.py#L84) preserves unrelated JSON entries, and [main:148](../../scripts/install-provider-hooks.py#L148) backs up semantic changes and repairs private copies. Their basename/provider-path ownership heuristics and path-based JSON writes are not exact Git hook ownership, held-directory Git config mutation, or transactional uninstall. [trusted launch serialization:12](../../scripts/trusted_hook_launch.py#L12) is useful quoting context; repository hooks still need their own supported native delivery proof.

## Windows seams, implementation gaps and proof limits

[WindowsDirectoryHandles:12](../../hooks/runtime/scan_native_file.py#L12) is dependency-neutral. `pin_root`, `descend`, `open_handle`, `open`, `stat`, `replace`, and `remove` use held native parents; `OBJ_DONT_REPARSE`, reparse rejection and single-link regular files prevent common pathname substitution. It intentionally owns no ACL, budget, scanner or timeout policy. Its component validator is not an entire Git-for-Windows path/case/namespace policy. T7 should reuse this seam instead of introducing another ctypes handle layer.

The packaging-specific [private:17](../../scripts/scan_install_windows.py#L17) verifies/applies protected owner DACLs and distinguishes trusted ancestors/creation parents. [PackageDirectory:127](../../scripts/scan_install_windows.py#L127) provides bounded enumeration/read-tree, held-parent directory operations, synced write-tree, rename, exact-inventory removal and [nonblocking byte lock:307](../../scripts/scan_install_windows.py#L307). [install:336](../../scripts/scan_install_windows.py#L336) validates owned current/backup bundles, stages, promotes and rolls back with finite cleanup allowances. These are concrete reusable package operations; their fixed inventory/depth limits and owner-only tree policy must not be blindly applied to an arbitrary existing repository/config tree.

Required T7 work includes a shared platform adapter for held repository-install files and config staging/restoration; native private invocation directories and cleanup; launcher delivery and exit propagation through Git for Windows; path normalization/drive/UNC/device/ADS/case collision refusal rules; permission/readonly/ACL behavior; and bounded child-tree cancellation through the existing [capture_git:23](../../hooks/runtime/scan_git.py#L23), [Windows descendant enumeration:300](../../hooks/runtime/scan_git.py#L300), [stop process:347](../../hooks/runtime/scan_git.py#L347) seams. Changing the required shared native API contract requires updating [validate_native_api:232](../../scripts/install-scan-secrets.py#L232) and exact installed-closure tests together. Do not fork scanner policy per platform.

Available fixture entrypoints are [InstalledScannerTests:18](../../scripts/test-install-scan-secrets.py#L18), [PowerShell Invoke-InstallProcess:527](../../scripts/test-install.ps1#L527) with isolated HOME/USERPROFILE/APPDATA/LOCALAPPDATA, [junction fixture:1143](../../scripts/test-install.ps1#L1143), and the native-only [scanner capture suite:1](../../scripts/test-scan-secrets-windows.ps1#L1) / [Codex suite:1](../../scripts/test-codex-hooks-windows.ps1#L1). Existing generated-provider Windows tests do not establish the new installed gate/dispatcher contract. macOS `pwsh` exercises PowerShell parsing/quoting but never proves NTFS DACLs, native file handles, junction refusal, Windows lock contention, process-tree cleanup, Git hook invocation, or source-free installed publication. Native Windows execution with both positive and adversarial controls remains required; unavailable execution is an unmet check, not a pass.
