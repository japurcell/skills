# T16 selected cleanup reference decision (read-only, 2026-10-22)

Scope: decision input for the future T16-cleanup task. No repository or user history was changed, no cleanup path was exercised, and this does not claim an installed cleanup interface exists. The accepted task boundary is `docs/software-factory/ExecPlan.md:391-399`. T16-upgrade and the installed maintenance controller must precede implementation.

## Actual persisted shapes

The current schema is version 7. `packages/software-factory/src/schema.ts:8-42` stores run/worktree/invocation/operation/attempt/allowance/claim/clearance/session/notification/event facts as rows, capture headers (`invocation_id`, `attempt_id`, `channel`, `state`, `sequence`), and capture text in `capture_chunks(capture_id,sequence,text)`. There is no reference index, backup registry, or `maintenance_operations` table in this base. `src/store.ts:970-1042` exposes `pruned` as a capture state on reads, but `appendCapture` cannot change a closed capture to pruned. `readHistory` and `readInvocationCapture` provide bounded pages (`src/store.ts:267-305`). Report capture IDs alone do not identify a validated learning artifact.

## Chosen selection and reference policy

1. Under the future installed controller's exclusive idle maintenance claim, list **exact** selected invocation IDs/capture IDs and **exact** registered backup IDs/paths from its owned manifest/operation record. A run selection expands through indexed `invocations.run_id` using keyset pages; never accept a directory glob or an age threshold as a deletion request. Show selected capture IDs/channels/states, current payload-byte sum, protected dependencies, and backup file sizes before confirmation. The selection/impact receipt is tied to database identity, schema version, operation ID, source row high-water marks and backup file identities; revalidate before the first mutation and after interruption. Current schema lacks stable content revisions for all these rows, so the controller must hold exclusion for the whole impact/confirm/mutate interval. The receipt is a review aid, not an authorization token.
2. Default prune removes **only `capture_chunks` text** of selected ended, unprotected captures and updates each `captures.state` to `pruned` in small transactions. Keep capture header/ID/channel/attempt/invocation/sequence and every invocation, run, operation, attempt, allowance, claim/clearance, session, event, notification, acknowledgment and question fact. Keep all `request` chunks and root invocation input `context` chunks. Never remove rows merely to satisfy foreign keys. Keep adoption/revert preparation and outcome report chunks, including applied/reverted identities, regardless of selection. `pruned` must be distinguishable from missing or partial in history/UI and learning reads. An unreferenced stdout/stderr chunk is a straightforward default candidate; other capture channels require explicit per-capture impact review even when no dependency is found.
3. Construct a conservative graph from **known persisted fields**, not arbitrary provider output. Keyset-walk captures with `channel='report'` and bounded `capture_chunks` pages, classify only version-1 learn/evaluate reports and T14 `kind` preparation/outcome reports, then validate typed references/ownership through keyed lookups. Keyset-walk invocation metadata for `inputCaptureId/question/contexts`, and attempt metadata for agent capture IDs and `priorAttemptId`; use indexed FK columns for owned capture sets and event cursor keys. Store/reconcile a bounded normalized edge index or temporary keyed protection table during T16-upgrade (implementation choice), with source report ID/version/digest and destination invocation/capture/attempt/event IDs. Page through edges and reverse dependencies; do not materialize all history in JS, concatenate unlimited captures, or parse arbitrary stdout/stderr/provider JSON. Treat an unknown, partial, malformed, oversized, or unsupported-version report or metadata row as an **opaque blocker** for any destructive selection whose non-dependence cannot be proved. A complete report exceeding the existing 131,072-byte T14 retained verifier cap cannot be assumed usable or reference-free. If global unknowns prevent a safe impact proof, report the blocker and leave the requested selection untouched.
4. The default graph roots include all retained recognized learning/evaluation/adoption/revert reports, selected saved question/context references, all actual applied/reverted facts, and any unfinished maintenance operation's recovery backup/stage. Traverse report-to-report and report-to-source edges to closure, including embedded `originalAdoption`. Treat an examined source capture as protected even if only a text prefix appears in extraction context: `verifyProvenance` reopens its complete bytes (`src/learning.ts:267-278`). A referenced attempt protects its owned raw, normalized, output and input captures as a conservative unit. A referenced event protects its exact cursor/data; no event row deletion in this task.
5. Exceptional history selection means an operator explicitly selects exact otherwise-protected *payload capture IDs*, sees every affected retained report and the fact that later verification will fail, and confirms that exact impact while exclusion remains held. The future implementation may prune those selected non-question chunks only after proving the reverse dependency closure and showing all dependent report IDs; it does **not** cascade-delete report bytes, metadata, action/revision facts or backups. Do not silently broaden the selection to dependencies. If any impacted report is opaque, any protected operational/question fact would be lost, or any cross-reference cannot be resolved, refuse. A subsequent `prepareAdoption`/`prepareRevert` must fail closed on pruned evidence as today. Keep an operation receipt listing deliberately broken references so UI can label still-readable reports as no longer verifiable. A mere human approval reference is retained evidence data, not proof of authorization for this exceptional cleanup.
6. Backup cleanup is a separate exact-file selection. Show each owned backup's measured size, verified identity and dependency on incomplete upgrade/repair/cleanup stages. Never select the current database, WAL/SHM, controller stage, or last recovery copy needed by an incomplete operation. An absent, unregistered, changed, linked or unreadable backup is not a safe deletion target; refuse and preserve it for inspection. Current schema does not define backup metadata or stage naming, so T15b/T16-upgrade must provide that interface before this can be coded.

Bounded implementation sketch: in the controller's exclusive connection, read a small `rowid > ? ORDER BY rowid LIMIT ?` page of candidate report headers/metadata rows, with SQL `octet_length` prechecks before transferring text. Each recognized report may use the T14 131,072-byte evidence cap; cap nested fields and lists to the producer's limits, stage normalized edges in a temporary keyed table, and iterate a recursive reachability frontier in batches with cycle detection and a finite edge/time budget. A budget hit is a blocker, never proof of no references. Lookup exact captures by `(id, invocation_id)` and attempts/events by primary key; verify state/ownership/digests where the format requires them. SQL `sum(octet_length(text))` by exact selected capture IDs measures text payload bytes, **not** reclaimed SQLite file bytes. The existing `capture_history`, `capture_chunks` PK, `attempt_operation_target` and `observation_invocation_page` indexes (`src/schema.ts:13-35`) help; T16 may add narrowly targeted indexes for metadata/reference reconciliation after query-plan checks. No current public store API does this work.

## Backup, compaction, and space decision

Stack is pinned Node v24.22.1 with `node:sqlite` and bundled SQLite (repository qualification says 3.53.4; `qualification/runtime.md:5-9`). The exact-version [`sqlite.backup`](https://nodejs.org/download/release/v24.22.1/docs/api/sqlite.html#sqlitebackupsourcedb-path-options) accepts an open `DatabaseSync`, target path, page `rate` and progress callback, and **overwrites an existing target**. The future controller must first hold its verified exclusive idle maintenance claim, atomically create a new private operation-owned backup directory on the approved local filesystem, verify its ownership/path identity, and pass `backup()` only an absent target name inside that directory. The directory and target must never be reused, including after a crash; a collision, changed path, or incomplete earlier attempt requires inspection rather than an overwrite retry. Keep the backup inside that exclusive-owned boundary, await completion, open the result read-only, run `integrity_check` and `foreign_key_check`, verify schema/repository identity and essential counts, then record its exact path/identity as verified before pruning or upgrade mutation. `qualification/runtime.ts:114-121` already probes backup and integrity on a disposable store, but does not establish this maintenance sequence. SQLite's [online backup API](https://www.sqlite.org/backup.html) gives a consistent source snapshot; it can restart on concurrent writes, so exclusion still matters for bounded timing and an exact operation receipt.

Node's exact-version [`fs.statfs`/`fs.StatFs`](https://nodejs.org/download/release/v24.22.1/docs/api/fs.html#class-fsstatfs) exposes available bytes as `bavail * bsize` (prefer BigInt), measured for the database and actual temporary/backup locations. A preflight is a point-in-time measurement, not a reservation or a promised reclaimed amount. Show logical selected text bytes, current DB/WAL/backup sizes, `page_count`, `freelist_count` and the measured available bytes separately. SQLite's [`VACUUM`](https://sqlite.org/lang_vacuum.html) rebuilds the file, may need as much as **twice the original DB file size in additional free space**, cannot run in an open transaction, and may fail against another connection's lock. WAL [checkpointing](https://www.sqlite.org/wal.html) can be blocked by readers; do not treat a failed/busy checkpoint as proof of quiescence. `VACUUM INTO` creates a separate consistent copy but can leave a corrupt/incomplete output on interruption and is not an automatic replacement strategy. The future compactor should run in-place only after a verified retained backup, complete claim exclusion, no open transaction/readers, successful relevant checkpoint/space preflight with a conservative reserve on every filesystem it uses, and native fixture proof of its temporary path. If temp placement or free space cannot be established, skip compaction and leave already-pruned logical state plus its retained backup/receipt. On compaction failure, preserve the store and incomplete maintenance state for explicit inspection/completion; do not retry by deleting more captures/backups, replace the DB, recreate an empty store, or salvage automatically.

## Future T16-cleanup contract and proof

Required narrow store/controller additions: typed paged read of report headers and bounded capture text; explicit selected-capture `pruneCaptureChunks` transition that is atomic with state and preserves header/sequence; persisted operation impact/exception receipt and exact owned-backup inventory from T15b/T16-upgrade; optional normalized reference-edge index populated only from verified known formats. These are interface dependencies, not current APIs. Do not add a broad arbitrary-history search service or re-decode providers. Recheck controller schema/phase fields after that worker integrates.

Future tests must prove: (a) ordinary selected stdout/stderr pruning leaves headers, run/invocation/attempt/lineage/debits/events/questions/notifications unchanged; (b) extraction -> revised supported evaluation -> preparation -> applied adoption -> revert nesting protects every actual report, baseline/candidate, source capture, event, command context and agent input/raw/validated capture by default; (c) explicit exceptional selection shows exact reverse report impact and only prunes confirmed chunks, while subsequent retained validation fails closed; (d) missing/foreign/pruned/partial/malformed/oversize/unknown-version references and budget exhaustion refuse an unprovable selection, without guessing edges; (e) a new follow-up's `question`/`contexts` and original invocation input survive; (f) incomplete owner/maintenance/backup states block cleanup, and backup selection never deletes a recovery copy; (g) low-space, lock, interrupted backup/checkpoint/VACUUM and compaction failure preserve DB/backups, create no empty store, and cause no extra automatic deletion. Use disposable initialized repositories and the accepted `test:maintenance -- --operation cleanup` route; there is no read-only product test to run for this decision note.
