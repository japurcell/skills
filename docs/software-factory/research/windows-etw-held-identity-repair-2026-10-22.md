## Exact private identity flow

1. **Pin the file before launching anything.** The Node driver extracts the pinned archive member and computes its SHA-256, verifies the on-disk `node.exe` against it, and passes that member digest into the bridge. In C#, open the supplied executable with read access and sharing that permits reads but denies write/delete replacement. Hash bytes from this **held file handle**, require exact digest equality, query `FILE_ID_INFO` (volume serial plus 128-bit file ID), and retain the handle until all fixture and decode work is done. A sharing failure, unsupported file-ID query, hash mismatch, or path/handle instability is a native failure. The 30-second internal observation bound remains authoritative; if hashing cannot fit, fail rather than extend it silently.
2. **Launch and hold the root.** Start the pinned Node with the new fixed fixture file, cleared environment and private stdio as today. Hold `Process.Handle` through decode. Require its `QueryFullProcessImageNameW(..., 0)` result to identify the same pinned path and require a fresh open of that image path to have the held pin's `FILE_ID_INFO`. Capture root PID and creation FILETIME. Do not use process self-report as identity. The held pin's no-write/no-delete share protects the image file between hash, process launch and verification.
3. **Acquire the child before it exits.** Read exactly one bounded decimal PID line from root stdout with a short timeout, while the child waits on stdin. Reject extra bytes, malformed PID, duplicate PID, early root exit, or any stderr output. `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE | PROCESS_TERMINATE, FALSE, childPid)` before sending release; require the handle's PID, image path, `FILE_ID_INFO`, and creation FILETIME to match the pinned file and the expected root/child ordering. Keep the child handle open. Only then send the fixed release byte; wait for child and root with bounded timeouts, require zero exit statuses and empty remaining controlled output, and record both exit FILETIMEs from the **held** handles. On every failure, terminate the held child if alive, stop the root, stop the owned ETW session, close handles, and preserve a typed failure. The child also self-times out if the bridge dies before acquisition.
4. **Bind the classic process events to those objects.** Process start/end `ImageFileName` may be `name-only`; require only a well-formed basename equal to the pinned file basename, after the independent held-handle path/file-ID/hash checks. For each held PID, require exactly one live start and one live end, nonzero equal `UniqueProcessKey` across that pair, and distinct root/child keys. Reject any extra start/end with either held PID, including an earlier PID occupant, rather than selecting a convenient one. Require the start timestamp at or after the handle's creation and within the existing five-second upper window; require the end timestamp after start and close to the handle's exit time within that same bounded window. Require child start/end `ParentId` to equal the held root PID; root parent must be stable; require zero exit status and `root start < child start < child end < root end`. The kernel key is never logged and is not claimed to be directly obtainable from a process handle. The association rests on the held PID's non-reuse during its object lifetime, handle creation/exit bounds, unique live event cardinality and key continuity together. `DCStart`/`DCEnd` stay rundown only.
5. **Bind each main-executable image load to the pinned file.** `Image_Load` has a PID and timestamp but no `UniqueProcessKey`, so select only a load inside the already verified process event lifetime and the held process creation/exit bounds. Consider only full absolute `FileName` forms that can resolve against OS-returned pinned-file paths. For a DOS path, open the exact bounded local candidate, verify its final path stays on the pin's local volume, and compare `FILE_ID_INFO` to the held pin. For a native device path, require a segment-boundary match to `GetFinalPathNameByHandleW(pinHandle, VOLUME_NAME_NT)`; if mapping to a DOS path is required, derive the drive/device mapping through `QueryDosDeviceW`, then open the exact resolved candidate and compare file IDs. Do not construct a path from a guessed `C:` or device prefix. Reject UNC, relative, name-only, ambiguous mappings, reparse escapes, inaccessible candidates, same-basename foreign files, duplicate pinned loads, and any load outside the held lifetime. Keep all path strings and file IDs in memory. If the next Windows run reveals only a basename for the executable load, stop at typed `image-identity-unresolved`; no other event property is assumed to supply file identity.
6. **Emit unchanged positive labels only at commit.** Buffer private event records and the eventual `SCHEMA`, `RUNDOWN`, `COUNTS`, `HEADER`, and `EVENT` lines. The current code writes some of these before `CloseTrace`; move their publication after a zero close result and all held identities, keys, parent, exit/order/lifetime, exactly two verified pinned loads, stopped-session loss, and finalized-header checks pass. Then append the six existing fixed-label `EVENT` rows and `COMPLETE` according to the existing receipt grammar. Callback/API success alone never emits a positive. Every failure emits at most one fixed diagnostic immediately before one `FAIL decode`, with no selected events or positive summary rows. Preserve 100,000 callback, TDH size/property size, 65,536-byte receipt, 64 MiB ETL, 30-second internal observation, exact owned session/mode, zero loss, and raw-ETL cleanup gates.

The file-identity comparison is a qualification predicate for this controlled, pinned Node fixture. If `QueryFullProcessImageNameW`, `GetFinalPathNameByHandleW`, `FILE_ID_INFO`, or the image-load path cannot jointly prove the same held file, the native run fails. A `node.exe` basename and a close timestamp are not substitutes for that proof.

## Test-first build order and stop rules

The proposed test seams are the fixed fixture process protocol, the public bridge receipt produced by `WindowsEtwProbe.Run`, and the upload/qualification interface in `windows-etw-probe.mjs`. Then add `windows-etw-child-fixture.cjs` and the C# handshake. 3. **Red event binding.** Preserve the real native 39869638463 failed receipt as the end-to-end red. Build private bounded event-validation cases against the decoder's typed input interface for earlier same-PID start, duplicate start/end, changed key, foreign basename, wrong parent, creation/exit mismatch, wrong exit status, and image outside lifetime. 4. **Red file-identity admission.** At the same decoder contract seam, a same-basename foreign full path, name-only image load, device path without verified OS mapping, file-ID mismatch, and reparse/UNC ambiguity must fail with a closed reason. 5. **Public forgery/privacy gate.** Extend the fixed failed `DIAG` grammar in `windows-etw-probe.mjs` only for new reasons that the producer can emit, then assert malformed diagnostics are removed, valid failures remain failed, and forged pass summaries are downgraded. 6. **Native acceptance.** Compile under the actual Windows PowerShell 5.1/Windows 2025 path and run the complete fixture. Green requires real root and child handle/file identity, exactly the six positive root/child start/end/main-executable load rows, `SCHEMA`, `COUNTS`, zero-loss `STATS`, finalized nonzero `HEADER` with zero loss, exact `QUERY`/`MODE`, under-cap ETL, completion marker, and successful raw-ETL deletion. If the image-load field is name-only or the file/namespace mapping fails, preserve the failed native result and report this route infeasible pending a different independently verifiable observation method. ## Primary contracts and unresolved native facts

- [Microsoft Process_V2_TypeGroup1](https://learn.microsoft.com/en-us/windows/win32/etw/process-v2-typegroup1) documents live start/end opcodes, `UniqueProcessKey` and `ImageFileName`; its path description does not override the observed name-only field on this host. [PROCESS_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_information) explains when PID reuse becomes possible after process handles close.
- [GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes), [OpenProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess), [GetProcessId](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessid), and [QueryFullProcessImageNameW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew) support held-object PID, timing and full executable path checks.
- [Microsoft Image_Load](https://learn.microsoft.com/en-us/windows/win32/etw/image-load) documents the load opcode, PID and `FileName`, but does not promise that `FileName` is a full DOS or device path. Its actual form in this native trace is unknown.
- [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew), [QueryDosDeviceW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-querydosdevicew), [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info), [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/desktop/api/winbase/nf-winbase-getfileinformationbyhandleex), and [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) are the OS-backed file/path mapping contracts. `FILE_ID_INFO` identifies two open handles to the same file by volume serial plus file ID. File-share behavior and mapping availability still need a native Windows result.
- [EVENT_TRACE_LOGFILEW](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/ns-evntrace-event_trace_logfilew) documents default timestamp conversion to system time. It does not promise exact equality with process creation or exit FILETIME, so the bounded lifetime checks may fail closed on a real run.
- [Node child_process](https://nodejs.org/api/child_process.html) documents asynchronous `spawn`, `shell: false`, PID and pipe control. Exact v24.22.1 documentation was unavailable in this research; the fixed fixture protocol must be tested with the pinned binary.

No product helper/comparator admission follows either partial node.

For eventual main-image path admission, prefer exact case-insensitive comparisons against complete OS-returned paths of the held pin (Win32 process path, final DOS path, final NT path). Do not open arbitrary event-named files, construct guessed drive/device prefixes, or add general namespace mapping when exact OS-returned forms suffice. Only an already matching bounded local full path may be opened for final FileId comparison. Unrecognized image-load form remains fail-closed; an additional bounded decision is required if exact OS-returned forms cannot resolve the actual field.

Before a printed child PID becomes an owned termination target, independently verify its parent PID equals the still-held live root using the documented Toolhelp PROCESSENTRY32W snapshot while both process handles remain live. File identity and creation time alone cannot authorize terminating an unrelated same-Node process. A controlled fixture that reports a foreign same-pinned-Node PID must fail while that unrelated process survives. Snapshot use proves this positive parent relationship only; it never proves descendant absence.
