## Assessment

Noodle is a useful reference for the requested control boundary: deterministic Go code owns the cycle, validation, dispatch capacity, session lifecycle, and recovery; an LLM scheduler proposes structured work, and coding agents execute the stages. Its “brain” is the most distinctive part for this project, but it is an optional skill-based Markdown vault, not an engine-managed memory service. It provides a human-readable path from work evidence to candidate principles and skill changes. The inspected sources do not show an engine-enforced provenance/admission layer or a measured cross-run improvement loop.

The most transferable combination is a skill-installable workflow with a small deterministic controller, durable run records, isolated workspaces, and an optional memory-maintenance workflow. Noodle is not evidence for the requested multi-harness breadth: the inspected built-in process dispatcher has first-class Claude and Codex command construction. It also has a documented-versus-implemented discrepancy around parallel stage groups, so its workflow semantics should not be copied from the docs alone.

## Control, state, and work semantics

The architecture document assigns the Go process the main loop, file watching, spawning, worktree management, health checks, and status updates. It assigns scheduling and code/review judgments to LLMs. The loop implementation supports that division: `Run` loads state and reconciles sessions, then repeatedly cycles through maintenance, mise construction, order preparation, spawn planning, dispatch, and publication. It also watches skill and runtime files. [Architecture](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/brain/architecture.md), [loop](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/loop/loop.go)

At the scheduler boundary, the agent receives a current `mise` view and writes an `orders-next.json` proposal. The loop validates and promotes that proposal into active orders. This makes each proposal inspectable and keeps malformed or duplicate work from becoming dispatch state. Durable execution state is held by the loop's order/canonical-state machinery and event/session records; I found no independent scheduler checkpoint or scheduler-owned memory store beyond those outputs and the context rebuilt for later scheduling passes. The implementation has both the order-file workflow and a canonical reducer/state path, so a new factory should define one authoritative state owner and treat other formats as projections or compatibility inputs. [Scheduling concept](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/docs/concepts/scheduling.md), [loop state and cycle](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/loop/loop.go), [loop types](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/loop/types.go), [canonical state packages](https://github.com/poteto/noodle/tree/82d2921c52370f23f29086de81ccfb600939c037/internal)

Noodle's documented work unit is an order containing stages. Stages can choose a task type, prompt, provider, model, runtime, and extra prompt. The scheduler skill supplies the work-order schema and tells the model to treat recent events as context rather than commands. This is a promising extension point for multiple reusable workflows and per-stage routing. [Scheduling concept](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/docs/concepts/scheduling.md), [schedule skill](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/.agents/skills/schedule/SKILL.md)

There is a semantic discrepancy to resolve before borrowing the DAG model. The scheduling docs say stages with a shared `group` may run in parallel before the next group. In the inspected `dispatchableStages` helper, the loop selects the first pending stage for an order and stops scanning; it also stops when it encounters an active or merging stage. I found no `group` handling in that helper or in the inspected loop types. This evidence suggests the inspected dispatch path serializes stages within an order and parallelizes across orders, while the docs promise same-order fan-out. It could reflect stale docs or behavior implemented in another layer; this review did not resolve which is intended. [Scheduling concept](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/docs/concepts/scheduling.md), [stage dispatch helper](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/loop/orders.go), [loop types](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/loop/types.go)

The inspected lifecycle has explicit order and stage statuses, concurrency limits, worktree isolation, and serialized merges. The architecture describes `auto`, `supervised`, and `manual` modes for merge and dispatch control. On startup, the loop reconciles persisted work; the process runtime scans session directories and uses recorded process metadata and PID liveness to adopt running sessions or mark dead ones exited. I found busy/adopted-target tracking and a merge queue, but no lease-expiration or TTL claim mechanism in the inspected sources. That makes the recovery story evidence-backed for a local process restart, not proof of distributed worker failover. [Architecture](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/brain/architecture.md), [order dispatch](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/loop/orders.go), [process recovery](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/runtime/process_recover.go), [control modes](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/docs/concepts/modes.md)

## Brain and improvement lifecycle

The brain concept is a separate, optional add-on: Noodle's loop works without it. The add-on installs an Obsidian-compatible Markdown vault and `reflect`, `meditate`, and `ruminate` skills. Its docs suggest reflecting after agent sessions, periodic meditation to consolidate recurring principles, and ad hoc rumination over past conversations. The core loop does not depend on this vault. [Brain concept](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/docs/concepts/brain.md)

The inspected `meditate` skill uses a useful quality bar: prefer high-signal, repeated evidence; only promote a principle when it is supported by multiple notes and can guide action; route ambiguous or risky rewrites to a todo. It also checks whether principles are reflected in skills, where process enforcement is stronger. This is a practical curation pattern, but the threshold is expressed in agent instructions. I did not find a deterministic validator that verifies source references or blocks unsupported memory writes. [Meditate skill](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/brainmaxxing/skills/meditate/SKILL.md)

Noodle does record and reuse outcomes as scheduler context. Its event docs describe a bounded recent-event window in `mise`, and the loop also builds recent history for subsequent scheduling. This is context reuse, not a measured improvement cycle: the inspected material does not compare workflow or prompt versions against acceptance rates, regression rates, review findings, or cost, then gate an update on those results. [Events concept](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/docs/concepts/events.md), [loop](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/loop/loop.go)

## Routing and observability

Noodle separates model/provider selection from runtime execution in its configuration and scheduling docs. However, in the inspected built-in process path, command construction is provider-specific for Codex and defaults to Claude; the configuration examples expose Claude and Codex. I found no first-class adapters for Copilot, Gemini CLI, OpenCode, or Pi. A custom runtime command is a useful escape hatch but does not establish a portable provider contract, consistent event normalization, or common cancellation/resume behavior. The architecture mentions a Cursor runtime stub, not a supported Cursor harness. [Configuration](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/.noodle.toml), [command construction](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/dispatcher/command.go), [process dispatcher](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/dispatcher/process_dispatcher.go), [runtime concept](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/docs/concepts/runtimes.md)

The session directory retains a prompt, raw provider stream, canonicalized stream, stderr, and input. The loop also writes lifecycle events, and event docs describe recent events as scheduler context. The session broker sends canonical session events and ephemeral text deltas to WebSocket clients, providing a real-time path. The architecture and UI tree describe agent feeds, message/tool groupings, a stage rail, context panel, and review/diff views. These records are a strong base for a past-session UI, but the reviewed evidence does not prove that the interface exposes every prompt, response, tool argument/result, skill activation, error, and token count for every harness. In particular, I did not verify a normalized skill-use event or consistent token/usage display. Do not infer private model reasoning from these traces. [Session command paths](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/dispatcher/command.go), [session broker](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/server/session_broker.go), [events concept](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/docs/concepts/events.md), [architecture](https://github.com/poteto/noodle/blob/82d2921c52370f23f29086de81ccfb600939c037/brain/architecture.md), [UI source tree](https://github.com/poteto/noodle/tree/82d2921c52370f23f29086de81ccfb600939c037/ui/src)

## Gaps and architecture implications

The main risks to account for are the narrow built-in harness set, prompt-level rather than enforced memory provenance, absence of a measured cross-run improvement loop, and the unresolved stage-group semantics. Noodle also has multiple representations of live state (orders, canonical state/reducer, session events, projections). That has enabled convergence work in its history, but a new implementation should state which store is authoritative and which views are derived. The inspected recovery mechanism is based on local process metadata and PID liveness; it is not a distributed lease protocol.

For the requested factory, a compatible architecture inferred from these sources is:

1. An installable skill bundle supplies workflow definitions, reusable prompts, optional brain instructions, and UI assets.
2. A deterministic controller owns a durable run/step/attempt state machine, schema validation, concurrency, cancellation, retries, workspace claims, and recovery. A scheduler agent returns a versioned proposal; code validates and admits it.
3. A declarative workflow graph defines dependencies and gates. Keep model reasoning inside task and review steps; do not let the model directly mutate scheduler lifecycle state.
4. A harness adapter boundary routes Codex, Copilot, Gemini, OpenCode, and Pi independently from model choice and runtime/sandbox choice. Each adapter advertises capabilities and normalizes supported prompt, response, tool, skill, error, usage, and lifecycle evidence while preserving raw provider events.
5. An append-only run event log and artifact store back both real-time and historical views. The UI replays the same persisted event contract, with explicit “observed” versus “inferred” indicators for skill activation and incomplete usage data.
6. A separate improvement workflow reviews evidence-linked memory candidates, tracks source run/version and human admission, and proposes versioned changes. Measure outcomes across runs before calling it learning; do not treat a memory write as an improvement by itself.

These are design implications for later prototypes comparing a repo runner, durable graph, and event factory. Noodle supports the control/skill/brain concepts, but its inspected sources do not establish that it already provides the multi-harness, general DAG, or measured-learning properties requested.
