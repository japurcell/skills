# Pinned Node Windows launch equivalence audit

Observed 2026-10-22. This is a read-only source and qualification-design decision for T17. No Windows executable was run, no product helper was admitted, and no inference about who creates `conhost.exe` follows from this audit.

## Decision

The existing C# `DEBUG_PROCESS | DETACHED_PROCESS` diagnostic is useful evidence about that particular launch, but it is **not equivalent to `child_process.spawn()` in pinned Node 24.22.1**. A future helper must first pass a native trace in which the actual pinned Node binary calls `spawn()` with the exact proposed production option tuple and handles its own pipes, exit, and stop. The full exact Git/TypeScript matrix then has to pass under that same tuple. Until both gates pass, keep Windows startup scope unknown and do not admit the private helper.

The factory currently calls `spawn()` with `detached: process.platform !== 'win32'` and `stdio: ['ignore','pipe','pipe']` for workspace metadata and workflow commands, with no `windowsHide` option in those calls ([workspace source](../../../packages/software-factory/src/workspace.ts), [workflow source](../../../packages/software-factory/src/workflow.ts)). Thus on Windows its current tuple has `detached:false`, `windowsHide:false`, `shell:false` for metadata. A candidate detached helper would be a **new** tuple, for example `detached:true`, `windowsHide:true`, `shell:false`, `stdio:['ignore','pipe','pipe']`, with exact absolute executable, argv, cwd, and private environment. Qualify the tuple actually proposed for implementation; changing any member invalidates the comparison.

## Actual source mapping

The [versioned Node API](https://nodejs.org/docs/v24.22.1/api/child_process.html#optionsdetached) promises that Windows `detached:true` can let a child outlive its parent, and [stdio documentation](https://nodejs.org/docs/v24.22.1/api/child_process.html#optionsstdio) describes `ignore` and `pipe`. `windowsHide` promises to hide a normally created console window; none of these promises says that an executable creates no other process. The following is implementation mapping at the pinned source commit, not an API guarantee for other versions.

1. [`normalizeSpawnArguments()`](https://github.com/nodejs/node/blob/ce7aaf1cee78b8cf0ce17364260535c418d3ed26/lib/child_process.js#L599-L778) defaults `detached` and `windowsHide` to false; `shell:false` leaves the requested executable and arguments direct. [`spawn()`](https://github.com/nodejs/node/blob/ce7aaf1cee78b8cf0ce17364260535c418d3ed26/lib/child_process.js#L805-L813) hands them to `ChildProcess.spawn()`.
2. [`getValidStdio()`](https://github.com/nodejs/node/blob/ce7aaf1cee78b8cf0ce17364260535c418d3ed26/lib/internal/child_process.js#L1055-L1153) maps `['ignore','pipe','pipe']` to one ignored stdin and two pipes. [`ChildProcess.spawn()`](https://github.com/nodejs/node/blob/ce7aaf1cee78b8cf0ce17364260535c418d3ed26/lib/internal/child_process.js#L385-L448) separately encodes detached and windowsHide flags. [`process_wrap.cc`](https://github.com/nodejs/node/blob/ce7aaf1cee78b8cf0ce17364260535c418d3ed26/src/process_wrap.cc#L150-L188) maps ignore to `UV_IGNORE`, pipes to `UV_CREATE_PIPE`, and inherited fds to `UV_INHERIT_FD`; [its spawn bridge](https://github.com/nodejs/node/blob/ce7aaf1cee78b8cf0ce17364260535c418d3ed26/src/process_wrap.cc#L306-L327) maps the two Boolean flags to `UV_PROCESS_DETACHED` and `UV_PROCESS_WINDOWS_HIDE`.
3. Vendored libuv [creates a `NUL` stdin handle and child pipe ends](https://github.com/nodejs/node/blob/ce7aaf1cee78b8cf0ce17364260535c418d3ed26/deps/uv/src/win/process-stdio.c#L169-L254). Its [`uv_spawn()`](https://github.com/nodejs/node/blob/ce7aaf1cee78b8cf0ce17364260535c418d3ed26/deps/uv/src/win/process.c#L898-L1108) supplies them through `STARTF_USESTDHANDLES`, calls `CreateProcessW` with handle inheritance enabled and `CREATE_UNICODE_ENVIRONMENT`, and sets `SW_HIDE` for `windowsHide:true`. With no `UV_INHERIT_FD` in this three-entry stdio tuple, `windowsHide:true` also adds `CREATE_NO_WINDOW`. `detached:true` additionally adds `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_SUSPENDED`, then resumes the thread; it bypasses libuv's assignment of non-detached children to its global job. The job's own source comment says its `SILENT_BREAKAWAY_OK` policy does not contain those children's descendants, so it is no descendant-quiescence proof. Microsoft's [process creation flag reference](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) says `CREATE_NO_WINDOW` is ignored when combined with `DETACHED_PROCESS` and describes detached console and process-group behavior. A requested `SW_HIDE` is a window setting, not a process-count assertion.

For the candidate tuple above, the source predicts `CREATE_UNICODE_ENVIRONMENT | CREATE_NO_WINDOW | DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_SUSPENDED`, plus `SW_HIDE` and the libuv `NUL`/pipe handles. For the current metadata tuple, it predicts `CREATE_UNICODE_ENVIRONMENT`, `SW_SHOWDEFAULT`, and the same `NUL`/pipe handles, without the detached flags. These predictions need native observation of behavior using the pinned executable; debugger events do not themselves reveal every `CreateProcessW` input flag.

The current [C# tracer](../../../packages/software-factory/qualification/windows-startup-trace.cs) instead starts the target directly with `DEBUG_PROCESS | CREATE_NO_WINDOW` or `DEBUG_PROCESS | DETACHED_PROCESS`, `STARTF_USESTDHANDLES`, a `NUL` input, and inheritable **file** handles for stdout/stderr. Its detached diagnostic has no Node, no Node pipes, no `CREATE_NEW_PROCESS_GROUP`, no `CREATE_SUSPENDED`/resume step, and no `SW_HIDE` request. `DEBUG_PROCESS` itself is a tracer addition. Therefore even a no-child result for the direct detached case cannot establish the behavior of either Node tuple.

## Native experiment to resolve the gap

The smallest useful next qualification is a fixed Node launcher script under the already pinned Windows Node archive, run in a disposable repository with the existing pinned Git and TypeScript archives. The script calls real `spawn()` directly, no shell or wrapper, with the exact candidate tuple, and records its own child PID, `spawn`, `exit`, `close`, bounded stdout/stderr, timeout, and direct kill outcome. Give it the same fixed Git `rev-parse --show-toplevel` mode and the same generated successful direct `tsc.exe -p` mode, with separate fresh compiler output. Also run the current tuple for those two modes to show the actual factory baseline. Under the same candidate Node route and tuple, run the intended nested-`cmd.exe` positive child and the qualification-only native stop/output fixture independently reviewed at `2f4292aa`. Its deadline branch flushes `deadline-ready` before sleeping; its output branch writes more than 256 KiB before sleeping. Require the marker before the existing 500 ms direct-stop request and the threshold before the existing 10 second output-limit stop, followed in each case by observed termination. A zero exit before either observable action fails the control. PowerShell may run as a separately labeled applicability comparison, but it cannot be the sole stop/output proof until its detached command execution is observed.

Observe process creation **independently of the Node script**: launch pinned Node as the debug root from the native C# tracer with `DEBUG_PROCESS` (not `DEBUG_ONLY_THIS_PROCESS`), record every descendant `CREATE`/`EXIT`/DLL event, and independently verify event PID/image through its process handle as the current tracer does. Microsoft's [DEBUG_PROCESS definition](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) covers descendants; the nested `cmd.exe` control proves that this particular observer did not silently lose child events. The tracer's outer launch conditions should mimic the production host's console, standard handles, cwd, and environment as closely as the CI fixture permits, and the report must record them. The pinned Node archive hash, its on-disk `node.exe` hash/path, Git/TypeScript package hashes and loaded module paths must be checked before accepting a trace. The helper cases may show only the Node root and one expected direct Git/TypeScript process; any `conhost.exe` or other additional `CREATE` is unexpected, without attributing its origin. Match the debug child's PID/image to Node's reported PID and the pinned native executable. Retain exact stdout content/path or generated compiler output, direct exit status, pipe closure, 256 KiB capture cap, timeout and observed stop, and the intended nested child image. An incomplete debug loop, failed process-handle verification, missing modules, missing positive-control child, unexpected child, or uncertain stop fails qualification.

If the observer's own `DEBUG_PROCESS` root changes the result, add an independent OS process-start trace of a non-debugged Node run before claiming equivalence; the difference is unresolved until both paths agree. Never infer absence from polling or from Node's own event stream alone. This experiment does not prove that the reviewed source exactly built the executable; it verifies the official pinned artifact's behavior under these inputs.

The [current handoff](../handoff.md) records native run `39835816416`: original `DEBUG_PROCESS | CREATE_NO_WINDOW` Git 17/17 and TypeScript 3/3 fail strict no-child checks with observed `conhost.exe`; representative detached Git/TypeScript and nested cmd pass, while detached PowerShell stop/output controls exit 0 before exercising their commands. The exact PowerShell internal cause remains unproved. The independently reviewed qualification-only native-fixture repair at `2f4292aa` still awaits a native run. Do not substitute its source review for that run. The full alternate exact Git/TypeScript matrix remains required after a valid representative Node experiment: all seventeen Git registration/mode cases and all three compiler success/error/no-output cases, hostile config/source and PATH canaries, package/DLL tamper refusal, module identity, exact output and exit, no-child records, deadline, direct-stop and output-bound controls must match the accepted contract. Representative success cannot promote only the sampled cases into production.

No factory Job Object subsystem, global process tracker, public `noChildren` switch, weakened child/identity/exit/output/stop guard, startup download, credential/provider call, desktop work, or product implementation follows from this note.
