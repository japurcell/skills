# Lifecycle platform constraints

Research date: 2026-10-15. This source review informs the accepted Node LTS and built-in SQLite path and the native macOS, Linux, and Windows targets. It does not select a runtime patch pin, Windows App SDK version, or notification package. No code, runtime, helper, package, or native platform was changed or exercised.

## Process identity and stop behavior

Give each invocation a fresh application-owned invocation ID, distinct from any run-history or accounting grouping ID. Use it to identify the lifecycle record across persistence; it is not proof of native process identity. While the owning foreground host is alive, keep the `ChildProcess` object and use it to control the direct child; record its PID for diagnostics. Node documents that `subprocess.kill()` sends a signal to that child, and that `.killed` only means a signal was sent, not that the child has exited. Wait for the child exit/close event before recording it stopped. Do not restore a stale PID from the database and signal it after the owner has restarted. A POSIX PID is unique only for its process lifetime; a Windows PID is valid only until the process terminates. In the absence of a verified native identity token, treat prior-owner processes as orphaned and leave cleanup to the user. [Node child-process API](https://nodejs.org/docs/v24.22.0/api/child_process.html), [POSIX process ID definition](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap03.html), [Windows process handles and identifiers](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers).

On macOS and Linux, Node's `spawn` option `detached: true` makes the child a new process-group and session leader. POSIX `kill()` accepts a negative process ID to signal the corresponding process group, so a live owner can signal `-child.pid` to stop members of that run group. A process group covers only members that remain in it; a descendant can create another session or group and escape. This is useful bounded cleanup, not universal descendant control. `ChildProcess.kill()` remains direct-child-only; Node explicitly documents that on Linux killing a shell child does not also terminate a grandchild. A cooperative `SIGTERM`, bounded wait, then `SIGKILL` can stop a group that remains in scope, but the grace interval is an implementation choice and a signal submission is not exit confirmation. [Node child-process API](https://nodejs.org/docs/v24.22.0/api/child_process.html), [POSIX `kill()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/kill.html), [Linux `setsid(2)`](https://man7.org/linux/man-pages/man2/setsid.2.html).

On Windows, Node does not support process-group signaling through `process.kill()`. Its `SIGTERM`, `SIGINT`, and `SIGKILL` names all cause abrupt termination, so `child.kill('SIGTERM')` is not a graceful-stop protocol. A Windows Job Object is the native process-tree scope: assigned children join the job by default, the job can terminate its members, and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` terminates them when its last handle closes. Breakaway settings can let descendants escape. Node's core child-process API does not expose Job Objects, so guaranteed tree cleanup would require a native helper or another reviewed native integration. That is not required by the accepted lifecycle policy. [Node process API](https://nodejs.org/docs/v24.22.0/api/process.html), [Node child-process API](https://nodejs.org/docs/v24.22.0/api/child_process.html), [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

If durable Windows process recovery later becomes necessary, native code can open a process by PID, read its creation time with `GetProcessTimes`, compare it with a recorded creation-time token, and act through the opened handle. The handle continues to refer to that process object after exit, whereas the PID is only valid during the process lifetime. Node core does not expose `OpenProcess` or `GetProcessTimes`. Without that addition, a stored PID is diagnostic only after the controlling host exits; manual cleanup is the accepted fallback. [Windows process handles and identifiers](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers), [Microsoft `GetProcessTimes`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes).

## Windows basic notifications

The existing sources disagree about the Windows App SDK Singleton package. The `AppNotificationManager` class and `Register` API references describe a Singleton-package dependency; the self-contained deployment guide says app-notification APIs do not require that package. The sources do not establish one unambiguous dependency rule for every SDK version and packaging mode. [AppNotificationManager API](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.appnotifications.appnotificationmanager), [Register API](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.appnotifications.appnotificationmanager.register), [self-contained deployment guide](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps).

**First-pass candidate, source-supported but not runtime-qualified:** use a small, installed MSIX-packaged desktop helper built with the Windows App SDK's default framework-dependent deployment and call `AppNotificationManager.Default.Show` for a local basic alert. Microsoft's quickstart uses a packaged WinUI desktop app and separates showing the alert from registering click activation; before activation is configured, clicking the alert performs no app action. This fits the accepted basic-alert scope without making click activation mandatory. Keep the Singleton dependency as a packaging qualification item for the exact SDK version. Do not claim an unpackaged self-contained executable or xcopy deployment until that dependency is resolved and tested. The candidate adds an MSIX install/update lifecycle and a Windows App SDK runtime dependency; it does not add a resident factory notifier. Elevated helpers cannot send these app notifications. [Windows App SDK app-notification quickstart](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-quickstart), [Windows App SDK deployment guide](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps), [app-notification limitations](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/).

The installed helper and runtime were not built, packaged, activated, signed, or tested. A call to `Show` supports the source-level candidate; it does not prove that Windows displayed or retained the notification. The notification remains best-effort, and a dashboard/CLI observation link remains the fallback. No activation callback is required by this finding.

### Follow-up: inbox WinRT toast route for an unpackaged native helper

Microsoft still documents a direct Win32 desktop route using the inbox `Windows.UI.Notifications` API: create basic toast XML and a `ToastNotification`, then call `ToastNotificationManager.CreateToastNotifier(appId).Show(toast)`. The desktop-specific quickstart lists `Runtime.object.lib` for C++ and a Start Menu shortcut carrying `System.AppUserModel.ID` as prerequisites. It does not list MSIX, Windows App SDK, a shared App SDK runtime, or a COM activation server for this send path. The general Windows notifications overview labels `ToastNotificationManager` as an inbox API with no NuGet package. The native WinRT build guidance and `RoInitialize` reference establish that Windows SDK metadata/import libraries are build inputs and Windows supplies the WinRT API at runtime; treating this as requiring no separately installed Windows App SDK runtime is an inference from those documented prerequisites. [Win32 desktop toast quickstart](https://learn.microsoft.com/en-us/windows/win32/shell/quickstart-sending-desktop-toast), [ToastNotificationManager API](https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.toastnotificationmanager.createtoastnotifier?view=winrt-28000), [Windows notifications API comparison](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/), [Windows SDK overview](https://learn.microsoft.com/en-us/windows/apps/windows-sdk/), [RoInitialize](https://learn.microsoft.com/en-us/windows/win32/api/roapi/nf-roapi-roinitialize).

The identity setup is explicit and owned: install a valid per-user `.lnk` under the Start Menu Programs folder, set its `System.AppUserModel.ID` property to a stable repository-specific AUMID, and pass the same AUMID to `CreateToastNotifier`. Microsoft says the shortcut need not be pinned; without a valid shortcut in Start or All Programs, a desktop toast cannot be raised. The documented AUMID convention is `CompanyName.ProductName[.SubProduct][.VersionInformation]`, at most 128 characters, no spaces, and intended to identify the app. Microsoft's shortcut example supports per-user or per-app placement and recommends installer creation. This is a Windows shell registration/cleanup responsibility, but it does not create package identity or a resident notifier. [Desktop toast identity setup](https://learn.microsoft.com/en-us/windows/win32/shell/enable-desktop-toast-with-appusermodelid), [AppUserModelIDs](https://learn.microsoft.com/en-us/windows/win32/shell/appids).

There are two material limits. First, the current API-selection page calls this the UWP API, says it may work in some desktop scenarios, marks it maintenance-only, and recommends `AppNotificationManager` for unpackaged Win32. The separate desktop quickstart still documents Win32 `Show`, but was last updated in 2022; the newer guidance makes this a legacy-compatible candidate, not Microsoft's preferred new-desktop contract. Second, the desktop quickstart says a desktop sender must subscribe to `ToastNotification.Activated` so it can handle selection. It shows `Show` without a COM server, but does not document omitting that event subscription. Therefore no COM activator is a documented property of the basic send path, while a strict zero-click-callback implementation remains unqualified. A no-op in-process event handler may satisfy the documented event expectation without adding click behavior, but that implementation detail has not been tested. [Windows notifications API comparison](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/), [Win32 desktop toast quickstart](https://learn.microsoft.com/en-us/windows/win32/shell/quickstart-sending-desktop-toast), [ToastNotification.Activated](https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.toastnotification.activated?view=winrt-28000).

Keep this route limited to a basic foreground visual alert. The current desktop-notification guidance distinguishes legacy templates from modern `ToastGeneric` activation; it states legacy templates do not activate the COM server and documents that COM activation is what supports activation after the sender exits and notification persistence in Action Center. Do not claim durable notification history, click-through, or an app callback for this candidate. By comparison, the current Windows App SDK quickstart explicitly sends with `AppNotificationManager.Show` before any activation is configured and states clicking has no action yet. That is clearer documentation for no-click behavior, at the cost of its Windows App SDK packaging/runtime dependency. [Windows desktop toast activation guidance](https://learn.microsoft.com/en-us/windows/apps/design/shell/tiles-and-notifications/send-local-toast-desktop-cpp-wrl), [Windows App SDK notification quickstart](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-quickstart), [Windows App SDK deployment overview](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/deploy-overview).

**Qualification conclusion:** `ToastNotificationManager` is a source-documented, lower-deployment-complexity option for a per-repository native helper if a legacy desktop API and Start Menu shortcut are acceptable. It avoids an App SDK runtime package, but Microsoft no longer recommends it for new unpackaged desktop apps, and strict callback-free behavior is not resolved by the desktop quickstart. Keep exact API use, shortcut registration/removal, notification settings, and click behavior as Windows-native qualification gates; do not substitute PowerShell wrappers or another app's AUMID.

## SQLite recording and maintenance

WAL supports readers alongside a writer, but SQLite still permits only one writer at a time. All connections to a WAL database must be on the same host, and WAL does not work over a network filesystem. Keep the shared repository database on a local filesystem, keep write transactions short, and handle `SQLITE_BUSY`. Node 24's `DatabaseSync` APIs run synchronously; its `timeout` option bounds how long a connection waits for a lock and defaults to zero. A bounded timeout followed by the already accepted stop-on-recording-failure behavior avoids an unbounded retry loop. [SQLite WAL](https://www.sqlite.org/wal.html), [Node v24.22 SQLite API](https://nodejs.org/docs/v24.22.0/api/sqlite.html), [SQLite busy timeout](https://www.sqlite.org/c3ref/busy_timeout.html).

Do not copy or remove only the main database file while it is open in WAL mode: the WAL can contain committed state and is part of the database's persistent state. Node's built-in `sqlite.backup(sourceDb, path)` returns a Promise and uses SQLite's online backup API to create a consistent backup while the source is open. Mutations through other connections can cause the backup to restart. This is available for the accepted idle maintenance/migration path; it does not create a canonical secondary text log. [SQLite WAL](https://www.sqlite.org/wal.html), [SQLite backup API](https://www.sqlite.org/backup.html), [Node v24.22 SQLite API](https://nodejs.org/docs/v24.22.0/api/sqlite.html).

`VACUUM` rebuilds a database and reclaims free pages, but it fails if its connection has an open transaction and can need free space up to twice the original database size. `VACUUM INTO` creates a compact copy and leaves the original unchanged, so it is useful for a compact snapshot but does not itself reclaim space in the original file. Keep vacuuming in the accepted idle-maintenance gate, close statements and transactions first, and check free space before starting. No history-retention or recurring vacuum policy is inferred here. [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html).

One version-sensitive WAL fact is resolved for the current accepted runtime candidate. SQLite documents a rare WAL-reset corruption bug fixed in SQLite 3.51.3 and later. The official Node v24.22.0 source tag's bundled SQLite header declares 3.53.4, which is past that fix. This is source evidence for that Node tag, not native-runtime qualification; the exact Node patch pin remains open, so implementation should re-check the selected runtime's bundled SQLite version or source before relying on WAL. [Node v24.22.0 SQLite header](https://raw.githubusercontent.com/nodejs/node/v24.22.0/deps/sqlite/sqlite3.h), [Node v24.22.0 release](https://nodejs.org/en/blog/release/v24.22.0), [SQLite WAL](https://www.sqlite.org/wal.html), [SQLite 3.51.3 release notes](https://www.sqlite.org/releaselog/3_51_3.html).

## Boundary and unresolved qualification

The source-supported minimum assigns a fresh invocation ID to the lifecycle record, distinct from run-history/accounting grouping IDs, and holds a live `ChildProcess` reference for direct native control; the invocation ID itself does not prove native process identity. Unix runs may use a per-invocation process group, while Windows stops the direct child unless a future native job integration is accepted. Stale processes left after owner failure may be cleaned up manually. Windows basic alerts have two source-backed candidates with different limits: a framework-dependent MSIX helper using Windows App SDK `Show` has the clearest documented no-action-before-activation behavior but adds the Windows App SDK runtime and retains the Singleton packaging qualification; the inbox WinRT `ToastNotificationManager.Show` path avoids that runtime but is maintenance-only guidance and leaves strict callback-free behavior unqualified. Neither candidate is natively tested. Keep one SQLite database on a local filesystem, use bounded busy waits and short transactions, use the online backup API for a safe copy, and gate `VACUUM` on idle state and disk capacity.

The material source-level uncertainty is the Singleton-package requirement for the selected Windows App SDK release. Native qualification also remains necessary for process signaling and group behavior on target macOS/Linux/Windows builds, the helper's package dependency and basic alert submission, and the expected SQLite locking and disk behavior. No such native checks were run or authorized in this research task.
