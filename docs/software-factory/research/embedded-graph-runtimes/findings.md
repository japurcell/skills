# Embedded graph runtimes: LangGraph TypeScript and Mastra

**Research date:** 2026-10-12
**Scope:** Browser-only review of current official docs, package manifests, registry pages, CI files, and reported upstream defects. No package installation, build, or runtime test was performed.
**Policy:** TypeScript functions calling managed operations remain accepted factory policy. This report compares engines; it does not select or adopt one.

## Finding

LangGraph's TypeScript Functional API is the closest fit for the accepted authoring model and documents checkpointed task replay. However, its sibling-task persistence after a Functional API fan-out failure or hard process kill is not established by the documentation reviewed. The separately documented `checkpoint_writes` guarantee applies to successful nodes in a Graph API superstep and must not be transferred to Functional API tasks. LangGraph is a conditional prototype candidate only, pending crash proof with the SQLite saver, the exact sync durability setting through the Functional API, native Windows integration, and the factory's operation/effect protocol. Its current persistence documentation classifies `SqliteSaver` as local file-based storage **for development** and identifies `PostgresSaver` for production use. This is not a prohibition on a local factory choosing SQLite, but it is not production-support evidence for SQLite either. [Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence) **Docs / Inference**

Mastra is a viable alternative when the team prefers schema-typed workflow graphs and first-class parallel/suspend/resume operations. It has current APIs for explicit run IDs and recovery, but its documented server boot behavior restarts all active runs. The embedded selected-run path after an abrupt kill, plus persistence of individual successful branches in a failed parallel block, is less explicit than LangGraph's. Mastra also brings a higher minimum Node version and a native libSQL dependency with weaker Windows evidence.

Neither engine can make a CLI, Git host, PR creation, publication, or other external effect exactly once. Both require operation IDs, idempotency or reconciliation, and effect-specific approval checks. **No runtime is selected.**

## Recommendation and constraints

If TypeScript function authoring is dominant, prototype **LangGraph TypeScript Functional API plus SQLite only as a candidate**, with task boundaries around every CLI or remote effect. The Functional API fits ordinary functions directly and documents durable task result replay, but no sibling-task persistence guarantee after fan-out failure or abrupt kill was found. The documented pending-write guarantee applies to completed nodes in a Graph API superstep. The factory's next-invocation policy can map the selected run to one `thread_id` and invoke only that thread. Use a stable, per-repository DB path and a versioned workflow identity. LangGraph's persistence page labels `SqliteSaver` as storage **for development**, so any production use in the factory requires explicit hard-kill, corruption, concurrency, and upgrade evidence; Windows adapter integration is also unverified. [Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence) **Docs / Inference**

Choose **Mastra** instead if the accepted team wants a typed, explicit workflow graph and favors its integrated `suspend`/`resume` and state reader. Keep generic boot-time recovery disabled for the factory or avoid its local server recovery sweep; select and resume a stored `runId` from the foreground runner. Do not choose it until a test proves selected `running` run recovery after hard kill, durable sibling outputs after parallel failure, and clean Windows installs with the exact pinned `@mastra/libsql` chain.

**UI Continue as policy proposal:** a Continue action can record an explicit human-triggered recovery request and dispatch the selected stored run ID to the next foreground runner, avoiding blanket startup replay and reducing startup supervision. This is a policy alternative, not an adopted engine or authoring change. It still requires durable checkpoints, partial-parallel result rules, run ownership/locking, stale-approval checks, and CLI/PR/publication reconciliation. It does not fulfill the present automatic next-invocation recovery requirement unless that requirement is changed.

**Python is a tradeoff, not an adopted alternative.** Its SQLite checkpoint package is more established and ships as a universal wheel, but the accepted authoring interface is TypeScript. A Python engine means introducing a Python environment and either a Python workflow module or a TypeScript-to-Python process/IPC boundary for every run. The inspected project CI is Linux-only, and current Windows evidence includes a defect report rather than a passing platform claim. It merits consideration only if a prototype demonstrates a materially better recovery guarantee that outweighs this policy/runtime change.

## Prototype proof list

1. Pin exact versions and lockfiles; record `workflowVersion`, checkpoint schema version, repository identity, and run ID in the persistent record. Confirm process restart under the chosen Node/Python version on macOS, Linux, and native Windows.
2. With abrupt kill (not orderly shutdown), crash before/after task start, after a Functional API parallel sibling finishes, during another branch, and after the final child-process output but before task commit. Verify whether the Functional API actually persisted each sibling result and which operations rerun. Separately verify LangGraph Graph API `checkpoint_writes`; do not use that result as a proxy for Functional API behavior.
3. Prove one invocation can recover exactly one selected interrupted run while a different run remains untouched. Verify concurrent Continue/start requests use a durable claim/lease or other single-driver rule.
4. Interrupt at a human checkpoint, mutate the artifact or source revision, then submit the old approval. Confirm the engine resumes only after the application rejects stale decision metadata and revalidates the target effect.
5. Simulate ambiguous CLI outcomes: child exits but result is uncommitted, child process outlives the runner, PR exists but its ID was not stored, and publication completed before runner crash. Require reconciliation or idempotency before retry.
6. Upgrade the engine/runtime and workflow definition with active, suspended, and completed runs in a copied repository DB. Prove safe migration, explicit rejection, or a compatible retained definition. Do not silently resume changed code against old state.
