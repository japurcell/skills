# Maintenance controller boundary decision, 2026-10-22

Scope: read-only design against source `dea5f4db`. This note decides T15b-controller admission and the T16 survival contract. It does not claim an implemented installer or a native Windows run. `docs/software-factory/ExecPlan.md` still owns task status.

## Verified facts and current seams

- `packages/software-factory/src/store.ts` resolves the Git common directory's `factory/` child, opens SQLite only at the current `schemaVersion`, refuses `bootstrap-incomplete` and corrupt stores, and makes `ready()` reject an incomplete repository or a maintenance claim. `claimResource({kind:'maintenance'})` checks for *any* claim in one immediate transaction. Runner admission and dashboard acquisition use the same store. The fixture `initializeRepositoryStore()` creates a marker, then inserts `ready` before any installation exists; production install cannot call it unchanged. `clearOwner()` can currently delete a maintenance claim, so the controller must reserve maintenance clearance for its own recovery path.
- `packages/software-factory/src/schema.ts` creates schema 6 and has no migrations or `maintenance_operations` table. The active plan requires explicit 3-to-4 indexes, 4-to-5 notification records, 5-to-6 preferences/acknowledgments, and any later reminder transition. No old schema may be relabeled by changing only `user_version`.
- `packages/software-factory/src/release.ts` has schema-2 exact inventory, a pinned Node v24.22.1 platform table, authoring template and dedicated toolchain lock. `packages/software-factory/src/installation-bindings.ts` validates an external release-manifest digest, exact local Node archive, and qualified optional provider artifacts, returning source descriptors only. Neither creates destination ownership. The installed Windows helper needs its dedicated owned root and exact shortcut owner token as described in `packages/software-factory/qualification/notifications.md`.
- Node's pinned v24.22.1 documentation says a Windows detached child *can* outlive its parent; by default the parent still waits, `unref()` removes the child from the parent's event-loop reference count, and inherited stdio can keep the child attached. This does not state that replacement of the parent's running image succeeds. [Node v24.22.1 child processes](https://nodejs.org/download/release/v24.22.1/docs/api/child_process.html#optionsdetached).
- Microsoft states that executable images are mapped into process address spaces and a filesystem can prevent deletion even without an ordinary open file handle. `DeleteFileW` can fail for open or mapped files; movement/replacement of open files depends on sharing and closure. Therefore moving controller code outside `install/` is insufficient if a still-running *old* `install/node.exe` waits for the staged process. Windows deletion/rename success cannot be inferred from POSIX unlink/exec behavior. [Executable images](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/executable-images), [DeleteFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew), [moving and replacing files](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files).
- Pinned Node exports `sqlite.backup(sourceDb,path)`; its destination is overwritten if present. SQLite's backup API produces a consistent snapshot. Use an absent, operation-specific backup destination, then verify it and record its identity before migration. Do not copy the live WAL file as the backup. [Node v24.22.1 SQLite](https://nodejs.org/download/release/v24.22.1/docs/api/sqlite.html#sqlitebackupsourceDb-path-options), [SQLite Online Backup API](https://www.sqlite.org/backup.html).

## Decision 1: first-install exclusion and ownership

Resolve the canonical Git common directory through the existing read-only `repositoryIdentity()` path and validate local placement before touching storage. A fresh installation is allowed only when `<common>/factory` is absent. Create that directory with nonrecursive, exclusive `mkdir`; `EEXIST`, any linked/non-directory component, an existing marker, an existing database, or any unrecognized child refuses. Never treat an existing empty or matching-looking directory as owned. The successful `mkdir` is the first contender's path reservation, and `<common>/factory/bootstrap-incomplete` is the **only** bootstrap marker. Create it exclusively, write bounded versioned intent, flush/close it, and verify its regular-file identity before SQLite creation. The marker contains a random operation ID, canonical common-directory/repository identity, intended `install`, selected release and full selection digests, target schema, original owner identity, plus an immutable stage directory name. It is an intent/stop marker, not another post-bootstrap lock.

There is an unavoidable crash interval between `mkdir(factory)` and a complete marker. Its safe interpretation is *ambiguous storage*, never permission to continue or adopt it. A zero-byte/partial marker, `factory/` without marker and database, or a database without a matching complete marker similarly refuses. The product cannot infer whether those paths were foreign or an interrupted attempt. Explicit human inspection may resolve such an orphan outside the product; the recovery command has no recorded operation to reclaim. Node documents that nonrecursive `mkdir` errors on an existing directory and that `mode` is not supported on Windows, so the implementation must verify Windows ACL/placement assumptions instead of treating POSIX `0700` as a Windows protection guarantee. [Node v24.22.1 filesystem](https://nodejs.org/download/release/v24.22.1/docs/api/fs.html#fsmkdirpath-options-callback).

With a valid marker, initialize a **new** schema-current database and repository `incomplete` row plus one maintenance claim for the marker's operation in a single schema/bootstrap transaction. The claim's `resourceKey` is that repository ID. The marker is retained through all first-install phases. If the database is absent after a complete marker, explicit repair may resume only that recorded selection after safe owner inspection; an existing partial/corrupt database is preserved and refused, never recreated by opening it in create mode. Normal `openRepositoryStore()` continues to refuse any marker. Commit `ready`, validated installed receipt and claim release together only after the whole installation validates. Remove the marker after that commit. A crash after the commit but before unlink still blocks normal startup; explicit repair verifies the completed operation and installed bytes, then removes only that matching marker. A missing marker with an incomplete database is a refusal, not a reason to create another marker.

After SQLite exists, the existing `owner_claims` table is the **sole admission authority**. Keep the intended operation as typed maintenance metadata on the maintenance claim, with a matching bounded event/receipt for completed history. This works even for older supported schemas that already have `owner_claims` and avoids requiring a new operation table before the first forward migration. The plan mentions `maintenance_operations`, but source does not have it; adding it later must be an explicit schema transition, not an implicit second admission service. Factor the existing store admission predicate so typed `beginMaintenance` creates the claim **and** its operation ID/selection digest/phase atomically. Do not call `claimResource` and later append intent in a separate transaction, since a crash would leave a claim with no recoverable operation. `clearOwner` must reject maintenance claims; `reclaimMaintenance` retains the recorded operation, writes clearance, rotates the claim token and owner in one transaction, and never clears a known-live owner. No normal opener, runner, or dashboard may override this path.

## Decision 2: synchronous handoff outside the replaceable image

The public maintenance entry is a small **foreground launcher outside `<common>/factory/install/`**, with `skills/software-factory/scripts/install.py` as the planned entry. It may invoke the currently installed Node only for selection/admission/staging. That child must return a bounded handoff ticket and **exit fully**; the launcher waits for its process close before invoking the staged Node. It never keeps an installed Node process awaiting the controller. The launcher then runs `<common>/factory/controller-staging/<operation-id>/node[.exe]` with `dist/maintenance-entry.js` from that same stage and waits for its exit, reporting its result to the user. Its executable, code, cwd, logs and required inputs are outside `install/`; the stage is a self-sufficient, hash-checked copy of the verified controller/Node and any required assets. Do not resolve imports, npm, helper binaries or provider payloads back through the old tree after handoff. Do not use `process.execPath` blindly, a shell string, an unrefed background child, a daemon, or a restart-time job.

The prepare result is `{operationId, repositoryId, claimId, stagePath, ticketPath, stageDigest}`. The external launcher drains bounded output and waits for the old child to terminate, then writes a one-use handoff-exit receipt bound to the ticket nonce and operation ID. The staged entry requires that receipt; calling it directly before the launcher has waited is a refusal. Python's documented `subprocess.run()` waits for completion, and its Windows `Popen` uses `CreateProcess`; pin the supported Python floor and test this exact entry on Windows. [Python subprocess](https://docs.python.org/3.11/library/subprocess.html#subprocess.run). The private ticket contains the exact claim token and selected artifact/target digests and handoff nonce, is created only under the matching stage, and is consumed by the staged entry after it revalidates path identities, stage bytes, marker when applicable, store schema/claim/token/phase, and the launcher's matching post-wait exit receipt. The token is never a public CLI option or printed in diagnostics. A handoff failure leaves the maintenance claim and intent blocked for explicit repair. The staged entry may first record `modifying` and `repository.state='incomplete'` in one transaction only after the old child has exited and it has itself verified no other recorded runner/dashboard/maintenance claim besides its exact claim. No destructive replacement precedes this point.

For a fresh install there is no old installed child: the external bootstrap validates the pinned Node archive and release bytes before executing them and hands control to the staged controller after the marker/claim exists. For a later operation, the launcher is the synchronous bridge over the Windows image lifetime. This is an architectural inference from the cited file and process APIs, **not** native proof that every mapped DLL, antivirus handle, shortcut, or process has released the old tree. A sharing violation or uncertain exit leaves `incomplete`, with no fallback to delayed reboot replacement or broad directory deletion. The staged process cannot remove its own Windows `node.exe`; after it exits, the launcher may delete only the exact completed stage inventory. A failed operation retains stage and ticket for repair.

## Small internal contract

The following shapes are internal controller/store APIs, not a new public SQL surface. Exact spelling may follow source conventions, but the fields and atomicity are required:

```ts
type MaintenanceKind = 'install' | 'upgrade' | 'dependencies' | 'repair' | 'uninstall' | 'cleanup';
type Phase = 'preparing' | 'handoff-ready' | 'modifying' | 'validating';
interface MaintenanceIntent {
  operationId: string; repositoryId: string; kind: MaintenanceKind;
  targetReleaseSha256: string | null; selectionDigest: string; targetSchema: number;
  stagePath: string; stageDigest: string | null; phase: Phase;
  ownedReceiptId: string | null; backupId: string | null;
}
interface MaintenanceHandle {
  operationId: string; claimId: string; token: string;
  repositoryId: string; commonDir: string;
}
beginRepositoryBootstrap(commonDir: string, intent: MaintenanceIntent, owner: Owner): Promise<MaintenanceHandle>;
beginMaintenance(commonDir: string, intent: MaintenanceIntent, owner: Owner): Promise<MaintenanceHandle>;
recordMaintenanceStage(handle: MaintenanceHandle, expected: Phase, next: Phase, receipt?: string): Promise<void>;
inspectMaintenance(commonDir: string): MaintenanceIntent | Refusal;
reclaimMaintenance(commonDir: string, operationId: string, clearance: Clearance): Promise<MaintenanceHandle>;
completeMaintenance(handle: MaintenanceHandle, installedReceipt: string | null, finalState: 'ready' | 'absent'): Promise<void>;
```

The intent is stored in the exact maintenance claim's JSON, not in a separate filesystem lock. Store methods own `BEGIN IMMEDIATE`, exact token/operation/phase compare-and-set, state transitions and event writes. `MaintenanceHandle` stays private to the controller. `completeMaintenance` may release only that claim after full validation. The public `inspect` path may show redacted selection, owner, phase, backup and recovery status even while normal store open refuses. It cannot mutate. Public `repair --operation ID` names one recorded intent; it cannot choose a new release, schema or target. If stage/selection/backup needed for that intent is missing or different, or the database is corrupt/unsupported, it stays blocked. PID age alone is not clearance. The operator must confirm an unknown owner only after inspection, and a known-live owner is never reclaimed.

## Observable operations and recovery limits

`install` reports exact selected repository, bundle digest, Node archive, provider artifacts and owned paths before accepting the plan-defined explicit supplied confirmation, including noninteractive invocation. This adds no separate approval gate for already-authorized disposable qualification. It creates absent-only authoring templates, a dedicated locked toolchain through the staged Node/npm, an installed receipt with exact owned files/hashes and Windows shortcut token/identity, and finally a ready current-schema store. A repeated identical request verifies that receipt; matching bytes without ownership are a collision. Changed source bytes, foreign directory/shortcut, symlink, or customized incompatible declaration refuses. The source and index of a dirty repository remain untouched.

`upgrade` and `dependencies` first acquire the same idle claim, stage the new exact inputs, take a fresh consistent `sqlite.backup` at `backups/<operation-id>.sqlite`, verify integrity/schema/repository ID and persist its receipt, then record `modifying` before replacing owned files. The backup survives success until explicit selected cleanup. Dependency maintenance changes only the factory-owned toolchain/lock; ordinary startup performs compatibility checks only. Every schema transition, specifically 3-to-4, 4-to-5, 5-to-6 and the later reminder transition if integrated, runs as its own transaction with its version/phase marker and exact expected prior shape. No skipping, implicit startup migration, downgrade, automatic restore, or salvage. An unsupported/corrupt store refuses before claim or file mutation. If an older known schema cannot prove compatible `owner_claims` admission, it remains blocked pending a separately designed bridge.

`repair --operation ID` revalidates the exact persisted intent and stage, waits for safe owner clearance, and resumes from the last committed phase. It does not rerun a workflow or silently select new inputs. File steps are checked against owned receipts before repeat; uncertain partial native shortcut publication remains a conflict for inspection. The gate is released only when release/runtime/toolchain/provider/helper ownership, schema and database integrity all agree. `uninstall` removes the owned shortcut with its exact token before its helper, and removes only listed, rechecked installed files; directories are removed only if empty. It marks repository `absent` while preserving SQLite history, authoring `.factory/`, worktrees, backups, and any incomplete controller stage. A modified or foreign path remains in place and keeps uninstall incomplete. `cleanup` is a later explicit selection under the same gate; it protects backups required by incomplete recovery and learning references, records impact before bounded deletion, and never uses a whole-`factory/` purge.

## Bounded split and acceptance

The indivisible rules are: first-install absence plus marker-before-database, maintenance claim plus intent in one transaction, old installed process exit before staged mutation, verified backup receipt before an existing-store schema or installed-file mutation, and final runtime/files/schema validation before claim release. Each task may stop with an incomplete operation; none may claim success by weakening these rules.

1. **T15b-controller admission only**, after reminders finish shared `store.ts`/`schema.ts`/`dashboard.ts` work. Own `packages/software-factory/src/maintenance.ts`, narrow `src/store.ts` and `src/schema.ts` changes, `test/maintenance-controller.test.mjs`, and release inventory registration only if the stage entry adds a compiled module. Keep fixture `initializeRepositoryStore` behavior or deliberately migrate its callers. Expose typed controller methods above, marker refusal, atomic claim/intent, handoff ticket validation and exact recovery. Do not publish install files or migrate old schema. Check the real callers `src/lifecycle.ts:invokeOwned`, `src/dashboard.ts:startObservationHost`, and `src/cli.ts`'s clear-owner route without adding a public SQL escape. Test disposable Git common directories with two first installers, preexisting empty/foreign/symlinked `factory/`, crashes before/within/after marker, partial DB, claim-without-intent prevention, ready-commit-before-marker-unlink, stale token, and runner/dashboard/maintenance races.
2. **T15b-install plus public entry**, after controller and verified selection. Own `src/install.ts`, `src/cli.ts`, `skills/software-factory/scripts/install.py`, its skill references, and focused tests. The external entry stages and waits as specified. Exercise a complete disposable install and command-only invoke through installed Node/toolchain, byte-preserved dirty source/index and customized templates, collisions and interrupted publication. Source selection remains in `src/installation-bindings.ts`; do not broaden provider qualification by assertion.
3. **T16-upgrade/dependencies/repair**, after installed handoff proof. Own operation-specific `src/maintenance.ts` implementation and explicit `src/schema.ts` migration functions, plus `test/maintenance-upgrade.test.mjs`. Verify real prior-schema fixtures, backup integrity, interruption at every transaction/file boundary, exact forward replay and refusal for corrupt/unknown versions. Serialize `maintenance.ts` ownership with subsequent T16 tasks.
4. **T16-uninstall, then T16-cleanup**, with separate focused tests `test/maintenance-uninstall.test.mjs` and `test/maintenance-cleanup.test.mjs`. Prove exact owned-path deletion and preservation first; cleanup additionally checks retained learning references and recovery backups. Parent integrates `scripts/test.mjs` selector registration and the composed race/crash E2E. A public test count with zero skips must include the new files, not only isolated tests.

Native Windows acceptance remains **unverified** here. In a disposable NTFS repository/profile using the pinned `node-v24.22.1-win-x64.zip`, exercise the real external launcher and installed old `node.exe`: prepare upgrade/uninstall, observe the old child exit before staged mutation, verify the staged process image and modules are wholly outside `install/`, replace/remove the old Node executable and helper, wait for staged exit, then remove its exact stage from the external launcher. Inject a crash after prepare and a held old-image handle; both must leave an inspectable blocked operation, with no false success or foreign deletion. Repeat runner/dashboard/maintenance races and owned/foreign shortcut cases. This is the native gate for the Windows lifetime claim; local source review and macOS fixtures cannot substitute for it.
