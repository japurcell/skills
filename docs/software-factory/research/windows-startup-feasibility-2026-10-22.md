## Recommendation

Implement and qualify a small, factory-internal set of **exact native startup helpers**, first for `--worktree` reuse. Keep arbitrary workflow commands, harnesses, and checkout on the current conservative Windows process scope. Do not add a public `noChildren` flag or reinterpret `childScope:'process-group'` as evidence.

The two candidate helper families are:

1. Verified actual Git for Windows native `git.exe`, with only `rev-parse --show-toplevel`, `rev-parse --path-format=absolute --git-common-dir`, `rev-parse --path-format=absolute --git-dir`, and `worktree list --porcelain -z`. Use fixed argv, `--no-pager`, stdin ignored, bounded stdout/stderr, current explicit repository cwd, and no shell. These are the existing-worktree identity/registration modes already needed by `repositoryIdentity` and `worktreeIdentity`. A source review of the exact Git for Windows release must establish that these paths do not start external programs. Upstream v2.54.0 source supports the narrow candidate, but is not a substitute for review of the selected Windows build.
2. The actual pinned TypeScript 7.0.2 native `tsc.exe` from `@typescript/typescript-win32-x64`, directly invoked with only `-p <factory-generated-tsconfig>`. Keep the existing compiler behavior and one build. The factory generates and validates the complete config; no authored tsconfig extension, plugins, watch/build mode, executable transformers, arbitrary CLI flags, or compiler API server. Exact native compiler source review and native adversarial proof remain prerequisites.

Treat a helper as having a bounded direct-process lifetime only after its executable identity, argv/config mode, and no-external-program source contract match a supported qualification record. Then child exit plus closed streams can settle that exact scope. Failure to establish that profile is a refusal or existing unknown cleanup, never an inferred successful cleanup. Preserve the native owner-inspection limitations: this does not add Windows boot/start identity or fix `inspectOwner`.

This recommendation removes the universal startup barrier for existing-worktree workflows if qualification succeeds. It does not establish full accepted Windows behavior for `--new-worktree`.

## Decisive findings

`src/native/process.ts` makes every Windows `LiveProcessScope` uncertain and `groupAbsent()` false. `src/workspace.ts` now uses that scope before store admission for metadata. `src/build.ts` uses `runner.execute` for the compiler after invocation/worktree admission. Consequently even successful metadata probes or a successful empty-workflow build cannot currently establish quiescence on Windows. Source inspection establishes this consequence; no native Windows CLI reproduction ran in this task.

There are two real wrapper traps:

- Git for Windows documents that `<Git>/cmd/git.exe` is a wrapper that spawns the actual program. Its documented direct native path is `<Git>/mingw64/bin/git.exe`. Therefore `spawn('git', ...)` through PATH cannot qualify as a single-process helper just because `rev-parse` is a builtin. [Official wrapper documentation](https://gitforwindows.org/git-wrapper.html).
- The immutable package/lock pin TypeScript 7.0.2 and native platform packages. Supplementary inspection of the existing, ignored installed 7.0.2 dependency found `bin/tsc` importing `lib/tsc.js`; that launcher uses `execFileSync(exe, args, {stdio:'inherit'})` on Windows. `lib/getExePath.js` resolves `@typescript/typescript-win32-x64/lib/tsc.exe`. The unstable async API client also spawns a server. These installed files were read only and are not immutable Git source evidence. The official repository confirms TypeScript 7 is a native port, and its compiler API wiki says the old API guidance covers versions below 7. [Official native-port repository](https://github.com/microsoft/typescript-go), [official API warning](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API).

A Node Worker around the current TypeScript launcher therefore does not remove the descendant problem. Worker termination stops the thread; it does not supply native subprocess containment. Node's Worker docs promise asynchronous termination of JavaScript and an exit event, and warn that most Node APIs remain available. [Node 24.22.1 Worker documentation](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html#workerterminate).

## Identity, ownership and recording

The helper profile must be owned by factory code and bind the real executable path and artifact/hash identity, architecture/version, exact operation mode, config identity, cwd and allowed environment. `--version` text, a basename, PATH position, a caller declaration, and stdout are insufficient identities. Before any pre-admission spawn, locate a candidate without executing it, canonicalize it, and validate it against release-owned supported artifact metadata. For Git, reject the ordinary wrapper path as a no-child candidate. Do not auto-download or install a missing helper. For TypeScript, extend the explicit installed toolchain manifest to name and verify the platform artifact/executable; do not import private `getExePath` code as an API.

Use actual Git to preserve authoritative current repository/worktree identity. Do not parse `.git`, `commondir`, refs, reftable, alternate ref layouts, or configuration into a new Git library. Preserve `realpath` checks of root/common/selected worktree, exact registered worktree membership and current git-dir registration comparison. Preserve opaque path whitespace. Revalidate the selected worktree identity under the acquired exact claim before compiling/entering. A changed registration/root/common, malformed output, or missing helper refuses entry.

Before repository discovery, retain the current live early-owner controller: bounded direct handles, command timeout, SIGINT/SIGTERM and 1 MiB semantic output cap, with no repository database fabricated from partial identity. Establish root/common first; only then open the verified store. Existing worktree registration and exclusive invocation claim stay transactional. Compiler launch stays after the claim and before activation, with the current admitted command attempt/capacity accounting, request capture, launch evidence and persisted filtered stdout/stderr. Tie its result and emitted entry to the exact invocation output directory/config/helper identity. A failed build creates no harness or agent attempt and never imports partial output.

Use the same invocation shutdown barrier, recording-failure propagation, deadlines and bounded drain. A helper's timer or stop submission is not completion; wait for the live direct process's exit and streams closing. If observation cannot settle in the existing bound, retain uncertain occupancy/claim and partial captures. Never signal a persisted PID, return capacity early, or allow a late result to activate a stopped invocation. Native Windows signals are abrupt termination. Microsoft explicitly says terminating a process does not terminate its children. [Node child-process lifecycle and kill semantics](https://nodejs.org/docs/latest-v24.x/api/child_process.html#subprocesskillsignal), [Microsoft process termination](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process).

## New checkout is a separate consequential conflict

`git worktree add --detach` is not a metadata helper. Upstream v2.54.0 `checkout_worktree` invokes another Git process (`reset --hard --no-recurse-submodules`). Checkout may run smudge/process filters; `post-checkout` also runs for `worktree add` unless `--no-checkout` is used. Those programs can spawn arbitrary descendants. [Exact upstream worktree source](https://github.com/git/git/blob/v2.54.0/builtin/worktree.c), [official checkout filters](https://git-scm.com/docs/gitattributes#_filter), [official post-checkout hook](https://git-scm.com/docs/githooks#_post_checkout).

Important pre-existing behavior: `src/workspace.ts:git` supplies an empty global config and `core.hooksPath` pointing at an empty temporary directory, for checkout as well as metadata. This already suppresses user hooks/global filter configuration; it cannot be used as a newly asserted safety proof, and this task does not endorse or expand it. The requested no-silent-filter/hook-disable constraint requires this to be reconciled explicitly for checkout.

Under the task's prohibition on a Job Object subsystem, universal process tracking, and invented child absence, there is no defensible automatic general Windows checkout cleanup guarantee. Do not label all of `worktree add` trusted, silently strip configured extensions, use `--no-checkout` as a completed worktree, or replace checkout with raw blob copying.

The narrow existing-worktree work can proceed without choosing a new containment subsystem. Users may explicitly prepare a fresh registered worktree outside the factory, then invoke `--worktree` after fresh verification. This honors Git filters/hooks and supplies a useful Windows entry path.

The accepted informed-manual-cleanup fallback can also support two explicit factory invocations: first prepare the new worktree and honestly finalize with cleanup unknown, then let the operator inspect/stop unsupported activity and clear the exact old claim; a fresh invocation revalidates and enters the current workflow from entry. It must retain the original failure/unknown history, attempt charges, current inputs and candidate files. This does not claim same-invocation `--new-worktree` success.

However, that preparation fallback is **not currently implementable by clearance alone**. In the immutable source, `createWorktree` returns through the command runner before `finalizeWorktree` records Git registration. Windows uncertainty throws first, leaving `registration:'reserved'`. `clearOwner` only reconciles occupancy and deletes the exact claim. Reuse by ID then compares actual Git registration against `'reserved'` and refuses; reuse by path calls `registerWorktree`, which refuses that changed registration. A separate bounded preparation-reconciliation task would need a fresh exclusive claim on that exact reserved worktree, proof of the old operator clearance, current supported Git identity/registration verification, and a guarded reserved-to-registered transaction. It must not copy an unverified path, reuse a stale token, or rewrite the first invocation as successful. Add crash/race tests before promoting this recovery path. That scope touches `src/store.ts`, `src/lifecycle.ts` and the CLI recovery contract, so it must be serialized with T7 and reviewed independently.

Only if the required product outcome is automatic **same-invocation** Windows checkout and workflow entry with arbitrary configured extensions does the current containment exclusion create a consequential conflict: authorize a separately designed native containment scope, or explicitly accept the two-invocation/manual fallback. Do not ask the human to relax existing exclusions merely to implement the already accepted manual fallback. Do not silently label the fallback full same-invocation checkout support.

`selectedCommit(ref^{commit})` is excluded from the first helper set. It parses object identity and is unnecessary for reuse. If later qualified, use fixed `--verify --end-of-options` argument construction and an explicit local-objects-only policy: Git documents that `--no-lazy-fetch` / `GIT_NO_LAZY_FETCH=1` prevents a promisor fetch. A missing local object must fail visibly, not trigger remote helpers, credentials or an automatic fetch. The first metadata profiles should also set the fixed no-lazy-fetch policy as defense in depth, subject to exact-source review. This flag alone is not proof that the complete helper call path never launches external programs. This research did not complete a source call-graph proof that the current `ref^{commit}` path fetches; lazy fetching is a concrete documented capability and a mandatory qualification case. That is a new behavior to state, not a hidden claim that all read-only Git is child-free. [Git 2.54.0 process flags](https://git-scm.com/docs/git/2.54.0).

## Alternatives rejected

- Worker around current TypeScript 7 launcher/API: native subprocess remains. A truly in-process older JS compiler would require changing the accepted toolchain pin and compiler semantics/requalification, with no quality advantage over a qualified direct native compiler here.
- Compile synchronously in the foreground: prevents bounded signal/timer response.
- General `trusted`, `noChildren`, executable allowlist, or version-string switch exposed to workflows: declares proof without fixing wrappers, mutable artifacts, flags or extension modes.
- In-process Git metadata parser/library: adds a second implementation of Git discovery/registration/configuration/ref formats while still leaving native compilation and checkout.
- Treat direct exit/closed pipes as universal descendant absence: false on Windows, including closed-pipe detached descendants. Keep arbitrary commands unknown.
