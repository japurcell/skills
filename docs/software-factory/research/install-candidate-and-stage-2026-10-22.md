# T15b-install staging decision, read-only planning input

Source checked at integrated `82a401ef9f88b50724a5a04997f5f01fe7adb05c`. This chooses an install preparation order; it is not installed acceptance or a request to change T15b-controller's 512-file/256 MiB handoff payload limit. No source, Git, database, product test, native process or provider was changed or run for this note.

## Decision

Use two operation-owned trees under the already admitted Git-common `factory/` root. Keep the **complete future installation** in an absent-only private `factory/install-candidate-<operationId>/` candidate, with proposed `install/runtime/` (the exact release bundle), `install/node/` (the extracted Node distribution), and `toolchain/` subtrees. Keep only a **self-sufficient controller** in the existing `factory/controller-staging/<operationId>/payload/`: a copied regular Node executable, release `package.json`, the compiled JS/controller closure (the complete bounded `dist/` is simpler if its exact inventory fits), and a new compiled `maintenance-entry.js`. Its entry may read the candidate and SQLite by their recorded paths, but must execute/import/npm nothing from a previous `install/`. The candidate is data to validate and publish, not a second admission lock. The sole gate remains the exact `owner_claims` maintenance claim.

This split is necessary. The pinned macOS and Linux archives each have 5,888 members and 197,423,496 / 201,757,420 expanded regular bytes; Windows has 2,459 members and 107,345,970 bytes. The separately locked toolchain has 652 files and 32,728,715 bytes. Copying the whole future installation into `payload/` violates `maintenance.ts:315-374`'s 512-file limit even though some byte totals fit. The stage needs one direct Node executable plus compiled assets, not Node's full npm distribution or the installed toolchain. The exact manifest currently lists compiled runtime modules in `release.ts:48-54`; any new `install`/`maintenance-entry` module must enter that inventory and pass release validation.

## Concrete first-install order

1. **External bootstrap, before `factory/` exists.** Proposed `skills/software-factory/scripts/install.py` receives the explicit selected release-manifest digest, bundle path, Node archive path, repository and optional qualified source paths. It resolves the canonical Git common directory read-only and preflights destination/authoring collisions. Before executing any selected JS, Python independently checks the externally selected schema-2 manifest SHA256 and its **complete manifest-bound bundle inventory**: every listed compiled module, map, declaration, web asset, template, package/lock file and selected helper has its recorded size and SHA256; paths, directory inventory, regular types, links, extras and collisions are checked against the release contract. Checking only the entry file would permit a tampered imported module to execute before JS self-validation. Python also independently verifies the Node archive against the fixed platform pin. This bootstrap trust check is required because `validateInstallSelection()` is JS inside the selected bundle and cannot safely authenticate itself before execution. Inspect the entire archive's paths/types/duplicates and selected omission table before extracting it into a private temporary directory **outside** `factory/`; use the direct regular Node executable from that verified temporary tree. The present source has no Python bootstrap or independent pre-execution bundle check. The Python check copies every manifest-bound file into a private owned snapshot, authenticates the copied bytes and complete inventory, and executes/imports only that snapshot. Hashing mutable original paths and later importing them would leave a check-to-import race. The bundled JS then performs full semantic `validateReleaseBundle()` and selection checks on the snapshot; future candidate binding separately revalidates selected original source descriptors.

2. **Archive policy.** Apply the measured, platform-specific policy in `research/node-archive-extraction-boundary-2026-10-22.md`: on macOS/Linux deliberately omit only `bin/corepack`, `bin/npm`, `bin/npx` with their exact recorded targets; reject any other link or special member. Do not follow or recreate the three links. For POSIX invoke `bin/node` with `lib/node_modules/npm/bin/npm-cli.js` directly. For Windows the observed ZIP has no links/reparse flags and its direct paths are `node.exe` and `node_modules/npm/bin/npm-cli.js`; still validate each ZIP destination/type. Keep the 8,192-member, 256 MiB regular-payload, 128 MiB/member extraction policy separate from controller-stage limits. Exact SHA256 pins are in `release.ts:29-33`; measured layouts are retained in `/tmp/factory-node-other-platform-layout-proof.json` and `/tmp/factory-node-archive-omission-proof.json`. Only macOS direct execution and no-link extraction have disposable proof; Linux/Windows layout inspection is not native execution proof.

3. **Selection and sole admission.** Run a verified bundled preparer with that temporary Node. It calls `validateInstallSelection(InstallSelection): VerifiedInstallSelection` (`installation-bindings.ts:13-30,86-136`) to rehash the complete schema-2 release bundle, exact archive, optional qualified artifacts and selected modes. Derive `MaintenanceSelection` deterministically from the frozen descriptor: release version, external manifest SHA as `targetReleaseSha256`, ordered bundle/Node/provider artifact digests, target schema 7, and a canonical digest that includes platform and provider modes. `maintenance.ts:17-21` currently validates only the shape of that digest; T15b-install must derive it from verified bytes, not accept an arbitrary caller string. The preparer calls `beginRepositoryBootstrap(repository, selection, currentOwner())` (`maintenance.ts:201`) only after source validation. Its nonrecursive absent-only `factory/` reservation, complete marker before SQLite, and atomic incomplete repository+claim remain unchanged. Keep the returned private `MaintenanceHandle` inside the preparer; never print its token or place it in CLI arguments.

4. **Prepare the complete candidate while phase is `preparing`.** Derive `install-candidate-<operationId>` directly under `factory/` from the recorded operation, create it absent-only with private ownership, and refuse a preexisting/linked/partial candidate unless a matching persisted operation receipt proves an explicit recovery path. Recheck source descriptors during bounded copy. Put the exact release bundle under candidate `install/runtime/`; copy the already safely extracted temporary Node distribution under candidate `install/node/`, verifying its per-member bytes/modes against the archive extraction receipt and omission policy. This avoids assuming Node has a built-in tar.xz extractor. Copy only factory-owned runtime, Node, dedicated toolchain and selected notification helper assets; **do not copy Codex or Copilot provider code** into the candidate. `installation-bindings.ts:13-30,86-136` returns exact canonical **source** descriptors, `adapters/codex.ts:94-115` consumes an external executable path/SHA256, and `adapters/copilot.ts:62-112,190-228` consumes an external package root/manifest SHA256 and checks the full closure. Copying either provider into a new destination would need a separate installed-destination and qualification contract; the accepted release contract excludes provider artifacts. Keep selected provider sources canonical, external to the old installation and candidate, and exact hash-bound in the operation/installed descriptor. Revalidate them without launching a provider before enabling a selected mode. Never copy auth, config, home directories or credentials. Copy the two approved toolchain declarations, then run the candidate's direct regular Node/npm entry with `ci --ignore-scripts --no-bin-links`, an explicit private cache and controlled user/global npm configuration. Explicit installation may obtain **only** integrity-bound entries declared by the selected lock; refuse floating or extra resolution, changed lock bytes, scripts, links and an incomplete closure. Offline qualification must refuse a missing cache, but this does not impose offline-only product installation. Validate the installed closure's exact lock/integrity, regular-file inventory, modes and absence of links; write the `toolchain/manifest.json` expected by `build.ts:13-24` (schema 1, Node 24.22.1, TypeScript 7.0.2, `@types/node` 24.19.2, declared dependency versions). The existing disposable macOS proof confirms direct npm 11.19.1, `--no-bin-links`, and direct tsc 7.0.2 without links, but is not a production installer.

5. **Bind candidate ownership before handoff.** Write a private candidate inventory/receipt containing operation/repository/claim IDs, selected manifest and archive digests, exact link-omission policy, toolchain lock and closure inventory, candidate subtree/target paths, file hashes/modes, tree digest and a random receipt ID. Give this thousands-of-file record its **own deliberate file-count, byte, path and parse bounds**, with streamed hashing and exact inventory verification; it is separate from the controller marker/ticket's existing 8 KiB bound and does not relax that bound. Flush and verify regular receipt identity. Record only a compact typed binding on the existing maintenance claim in one exact-token/operation/`preparing` CAS: deterministic candidate path, directory identity, tree digest, receipt ID and receipt SHA256. Ticket and claim carry this small identity/digest, never the inventory. This is the smallest clear install-owned addition; `MaintenanceIntent.ownedReceiptId` currently denotes eventual installed ownership and `backupId` is for later operations, so neither should silently stand in for a prepared candidate. A crash before this binding leaves an inspectable incomplete operation and partial candidate, never automatic adoption. Reclamation must check a bound candidate even when phase remains `preparing`.

6. **Build the bounded controller stage.** Create the recorded `stagePath/payload/` absent-only. Copy the candidate's verified direct Node executable into `payload/node` (or `payload/node.exe`) and the selected package metadata/compiled controller assets into `payload/`; verify all copied hashes, imports and relative paths. No npm CLI, installed-node path, user-global module, symlink or foreign sidecar belongs in this payload. `prepareMaintenanceHandoff(repository, handle)` (`maintenance.ts:380-424`) currently validates/hashes only this payload and emits a private one-use ticket bound to selection, stage identity/digest and nonce. T15b-install must additionally require the candidate binding/receipt before issuing an install ticket and include its digest/identity in that ticket. The actual launch paths are under `stagePath/payload/`; the older boundary note's illustrative `<stage>/node` path predates current `stageEvidence()`.

7. **Foreground process handoff.** The preparer returns only the public `{operationId,repositoryId,claimId,stagePath,ticketPath,stageDigest}` and exits. External Python drains bounded output and waits for the preparer **and every child it owns** (including npm) to finish; plain child close alone is insufficient if descendants can retain an old image. If child closure or ownership is uncertain, do not issue the post-wait receipt. Otherwise write the existing private nonce/operation/stage-digest `handoff-exit-<nonce>.json` receipt and launch `payload/node[.exe] payload/dist/maintenance-entry.js` in the foreground, outside `install/`. Never put the claim token on argv or in diagnostics. `consumeMaintenanceHandoff(ticketPath)` (`maintenance.ts:427-463`) already rechecks ticket, receipt, marker, stage, selection and exact claim, then transfers owner to the verified live current process while atomically setting `modifying`/repository `incomplete`. T15b-install must revalidate the candidate binding/receipt at this gate and again immediately before each publication step. The stage ticket and claim remain one-use; they are not a second lock.

8. **Publish and finish, with no ready shortcut.** The staged process preflights absent `factory/install`, `factory/toolchain`, owned helper/shortcut target, and every authoring template path. Publish only exact candidate subtrees to their absent targets, preferably by same-filesystem rename, with durable operation-bound ownership receipts/markers in each moved subtree before rename. Since runtime and toolchain need separate target directories (`build.ts:13` reads `factory/toolchain`), their publication is not one filesystem transaction. Persist ordered step intent and verify exact target ownership before resuming after a crash; matching bytes alone at an unowned target are a collision. Create `.factory/` authoring files with exclusive absent-only writes and record only files created by this operation. Preserve existing customized files and Git index/source bytes; require existing package/dependency declarations to be compatible rather than overwriting them. Once all targets exist, validate the **actual published** runtime against the release manifest and Node archive/omission inventory, run direct Node/npm/tsc checks, validate toolchain closure, owned helper/shortcut where selected, authoring compatibility, schema 7/SQLite integrity and single exact claim. Where a provider mode was selected, revalidate its persisted external canonical source path, exact SHA256 or complete manifest-bound closure and qualified modes; a missing or changed source blocks that selected installed state. Neither staged controller execution nor final validation launches a provider. Only then atomically save the installed ownership receipt, set repository `ready`, and release the exact claim in one SQLite transaction. Remove `bootstrap-incomplete` only after that commit. The current controller intentionally has no such completion API or marker-unlink recovery; `recordMaintenanceStage()` only reaches `validating` (`maintenance.ts:466-485`). A crash after ready commit but before marker unlink must be resolved by an install-owned validator that proves the recorded completed operation and installed bytes before unlink, not by generic claim clearance. After the staged child exits, Python may remove only its exact completed stage inventory; Windows cannot have the running staged `node.exe` delete itself. On failure, retain the claim, candidate, ticket and stage for explicit inspection/repair.

## Source additions and proof still required

- Add the external Python bootstrap/foreground launcher and independent **whole-bundle** first-execution inventory check; no `scripts/install.py`, `src/install.ts` or compiled `maintenance-entry.js` exists now. Bind any new compiled entry in `release.ts`'s explicit runtime inventory, so Python authenticates that entry and every import before running it. Pin the supported Python floor and qualify child/descendant wait, private receipt writes, ACLs, Windows mapped-image replacement and stage cleanup natively. No current source proves those.
- Add bounded full-candidate extraction/copy/toolchain validation and its separately bounded operation-owned inventory/receipt; a compact typed candidate binding and exact CAS in the existing claim; candidate checks in prepare, consume, reclaim and publication; ordered partial-publication receipts; and a validated final ready/claim-release transaction plus marker-unlink repair. These are install-owned seams on the current controller/store, not a new lock, generic SQL getter or background service.
- Keep optional Codex/Copilot provider bytes at their already qualified **external** source paths. The source selection/adapter APIs accept these paths and exact hashes; no copied-provider destination contract exists. T15b-install/CLI needs the narrow missing installed contract: persist the frozen source path/digest/modes in a private owned descriptor, refuse sources under the replaceable old installation, revalidate them at final ready and before selected adapter use, then wire those exact descriptors into the existing adapters. If stable external binding cannot be proven, block that selected provider mode instead of copying bytes or claiming ready. No authentication/configuration files are part of this descriptor.
- Prove a disposable public first install and command-only invocation through its **installed** Node/toolchain, two-installer collision, foreign/linked/customized destinations, dirty source/index preservation, hostile archive entries, changed selected bytes, candidate/stage/receipt tampering, crash at marker/candidate/handoff/each publish/ready-before-unlink boundary, and no credential leakage. Native Linux/Windows archive execution and Windows old-image lifetime remain distinct gates. The selected provider modes remain limited to existing qualified descriptors; this staging decision authorizes no provider call.
