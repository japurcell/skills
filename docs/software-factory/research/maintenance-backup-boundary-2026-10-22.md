## Admission and backup ordering

Use a **short committed administrative admission transaction first**, then a consistent SQLite backup, then schema or installed-file mutation. The word "backup before mutation" applies to domain rows, DDL, schema version, installed bytes, and authoring files. The one exception is the administrative `owner_claims` claim plus typed intent and bounded `maintenance.started` event needed to exclude runners and dashboards. Backing up the committed claim is intentional and makes interrupted backup recovery attributable to one recorded operation. Do not create a second lock or mark the repository incomplete yet.

1. Authenticate the selected new release and Node through the existing Python whole-bundle route before any selected JS. On the selected new Node, inspect the existing factory, installed ownership receipt if one exists, and exact database shape read-only. Reject missing/linked/foreign paths, marker, corrupt/unsupported shape, repository identity mismatch, all existing claims, and mismatched original release/provider/toolchain facts. Normal `openRepositoryStore()` stays schema-7-only and unchanged for normal callers. A dedicated existing-only forward opener is required.
2. Open the exact existing database for write without create, using a canonical `file:` URL with `mode=rw` on pinned Node 24.22.1, and recheck file identity, `user_version`, known schema signature, repository ready row, owner absence, integrity, and installed ownership under `BEGIN IMMEDIATE`. Commit one typed upgrade claim with owner/token/operation ID, exact target selection and original installed-state binding, allocated `backupId`, state `backup-pending`, and an event. Any other writer begun earlier completes before admission; later public writers acquire their immediate transaction and see the maintenance claim. Existing readers can finish, but they do not grant admission. Keep the repository `ready` until staged handoff consumes its one-use ticket; the claim blocks runner/dashboard mutations in the meantime. Do not use current `beginMaintenance()` as-is for old schemas: it calls `openRepositoryStore()` and refuses them.
3. Only after the committed claim, create an absent mode-0700 private operation directory such as `<common>/factory/maintenance-backups/<operation-id>/<backup-id>/` with an absent `history.sqlite` target. The claim is the gate; this directory is evidence, not a lock. Back up from a **separate read-only** `DatabaseSync` connection with `sqlite.backup(source, absentTarget, {rate, progress})`; never back up from a connection holding an active write transaction and never copy `history.sqlite` or WAL sidecars. Run this bounded backup in an owned foreground helper process using the existing `src/native/process.ts` closure discipline so the controller can enforce a deadline and confirm full helper exit. Node's documented backup options have `rate` and `progress`, but no documented cancellation signal. A timed-out helper or uncertain closure leaves the claim and private target for inspection, not a retry over the same path. Do not let helper output carry token or private provider paths.
4. After the helper exits, verify that the destination is the exact regular one-link mode-0600 file in the owned directory, fsync file and directory, open **read-only**, run full `PRAGMA integrity_check` and `PRAGMA foreign_key_check`, check exact historical schema signature and `user_version`, repository ID/release/state, recorded sole claim and operation, and bounded essential per-table counts against a new source read under the still-exclusive claim. Record database identity, SHA256, size, source schema variant, repository identity, count digest, and backup receipt ID in a separate bounded private receipt. CAS the receipt digest/identity into the exact claim/token and mark `backup-verified` in one transaction. The backup stays until an explicitly selected cleanup operation, including after successful upgrade. If a crash leaves a target but no complete validated receipt or no bound claim, preserve it and refuse overwrite. A complete private receipt can be deliberately inspected and bound only while source is still in the pre-DDL state and exact claim/selection match; otherwise operator-confirmed recovery must allocate a new absent backup ID without deleting the old target.
5. Backup verification is still preparation. Forward DDL is permitted only after the existing one-use handoff transfers the claim to the live staged new controller (`phase=modifying`, `ticketConsumed=true`) and makes the repository incomplete. Each transition is a separate `BEGIN IMMEDIATE` transaction that rechecks exact token, sole claim, bound backup, prior schema signature and recorded step, applies only the fixed DDL for that step, updates `PRAGMA user_version` where applicable, records new step in the same owner claim and observation event, then commits. A crash leaves either the old or new recognized signature and checkpoint. Never infer a step only from `user_version` and never use broad `IF NOT EXISTS` to mask unknown objects. Recheck integrity and foreign keys before advancing. A failure preserves the backup and incomplete claim; it never restores or recreates the live store automatically.

The alternative of holding `BEGIN IMMEDIATE` open while a separate read-only connection backs up the **pre-claim** database is feasible on the pinned Mac/WAL runtime, but I do not recommend it for production. It holds the only SQLite writer slot for the duration of a potentially large backup, and a crash before the claim commits leaves an unbound backup directory with no durable admission record. The committed administrative claim gives a shorter critical section and a recoverable operation identity while preserving all domain rows and schema before backup. No ordinary runner/dashboard is permitted after that claim. The historical v3 `ready()` and `claimResource()` source at `ba460e3a` already checks maintenance claims; still prove each supported historical writer path and current clearance race in tests rather than assuming it.

`src/store.ts` needs a narrow existing-only `openForwardMaintenanceStore()` and transaction methods for admission, backup binding, step CAS, and explicit reclaim. The current ordinary `openRepositoryStore()` and `readInstalledCompletion()` remain strict. `src/maintenance.ts` needs an operation-specific start/inspect/reclaim path that validates old-schema intent and backup before handoff; its current `beginMaintenance()` and `reclaimMaintenance()` both depend on current-schema `openRepositoryStore()`/`openMaintenanceStore()`. Add a compact typed backup binding to `MaintenanceIntent`, keeping the full receipt outside the 8 KiB claim. Preserve current exact token/owner/phase CAS, redacted inspection, explicit operator-confirmed reclaim, and known-live rejection. No generic clearance may delete this claim.

Suggested trusted API for the first node: `prepareForwardSchema(repository: string, selection: MaintenanceSelection, owner: Owner): Promise<MaintenanceHandle>` admits and binds the backup while retaining the private handle; `advanceForwardSchema(handle: MaintenanceHandle): Promise<{sourceSchema:3|4|5|6|7; targetSchema:7; state:'incomplete'}>` requires consumed staged handoff and a verified backup. These are package/controller APIs, not public CLI routes; tests may call them at the exported operation seam in disposable repositories without printing tokens. `inspectForwardSchema(repository, operationId)` is read-only and redacted. `resumeForwardSchema(repository, operationId, operatorClearance)` requires the same original/target selection and an inspected non-live/unknown owner; it never reselects, restores, or replays a workflow. An implementation may name these differently, but keep the operation boundary stable and store primitives narrow. Existing `inspectMaintenance()` should report a known old version as explicitly supported/incomplete or blocked with a precise reason, never relabel corrupt or unknown storage as ready.
