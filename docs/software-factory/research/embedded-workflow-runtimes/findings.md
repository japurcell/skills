# Embedded TypeScript workflow runtime fit

Research date: 2026-10-12

## Decision

Keep **Effect v4's `ClusterWorkflowEngine` + `SingleRunner` + `@effect/sql-sqlite-node`** as the leading prototype candidate. This is the only examined path whose official documentation explicitly describes a single-process embedded runner and pairs it with SQL-backed durable workflow messages. It is a real workflow engine composition, not a database presumed to provide durability. Its workflow and cluster APIs are currently marked unstable, so it is a candidate for a bounded proof, not a selection.

Keep **TanStack Workflow** as a second, experimental candidate only if the project is willing to own a SQLite store adapter. Its plain async authoring and recovery/version model fit well, but the maintained adapters documented today are Postgres and Cloudflare D1. No first-party local SQLite or filesystem `WorkflowExecutionStore` was found.

Do not shortlist Vercel Workflow DevKit's Local World as a production local runtime: it persists to disk and recovers active runs, but Vercel labels that backend for development and testing. Do not shortlist Resonate TS as an embedded runtime: its default local SDK store is memory-only; durable modes require either a separate server process or an external PostgreSQL service.

No runtime is selected. A UI-driven **Continue** action can select a persisted run when the runtime exposes run-ID resume, but that API alone does not prove that starting the shared engine will isolate recovery to that run. Before claiming that Continue avoids unrelated work, verify per-run state/worker isolation or an engine recovery-dispatch gate. Effect's `SingleRunner` uses persisted mailboxes and `SqlMessageStorage` redelivers unprocessed messages after restart; TanStack documents lease recovery and bounded sweeps. Their run-ID APIs do not by themselves show that other pending work will not be claimed. Continue still requires durable checkpoints, partial-parallel recovery, approval reconciliation, and idempotent reconciliation of external CLI/session effects.

## Evidence and limits

### Effect

The critical distinction is between the test/development [`WorkflowEngine.layerMemory`](https://effect.website/docs/v4/api/effect/workflow/WorkflowEngine) and the durable wiring. The [`ClusterWorkflowEngine`](https://effect.website/docs/v4/api/effect/cluster/ClusterWorkflowEngine) documentation says workflow executions, activities, deferred completions, resumes, interrupts, and clock wakeups are represented as persisted cluster entity messages. The [`SingleRunner`](https://effect.website/docs/v4/api/effect/cluster/SingleRunner) documentation says it is a single-process layer intended for local, embedded, or small single-node use, while still requiring a SQL client. Its runner communication and health layers are no-ops, so this is not multi-runner coordination: independent foreground invocations must not be assumed safe when they create separate `SingleRunner`s over the same engine database. Provide one runner owner, per-run isolation, or a different coordination composition and prove it. The [`SqlMessageStorage`](https://effect.website/docs/v4/api/effect/cluster/SqlMessageStorage) documentation supplies the missing recovery claim: stored mailboxes are recoverable, unprocessed messages are redelivered, duplicate requests are deduplicated, reply chunks are replayed until acknowledged, and its constructors run migrations. Together these are evidence of a persistence-backed workflow engine. SQLite by itself would not establish that.

The Effect repository README identifies v4 as LTS and says the Node SQLite integration requires Node 22.16+. The [`SqliteClient` source](https://github.com/Effect-TS/effect/blob/main/packages/sql/sqlite-node/src/SqliteClient.ts) imports `node:sqlite`, creates a file-backed database, uses WAL by default, and serializes access through one connection. The [`Workflow`](https://effect.website/docs/v4/api/effect/workflow/Workflow), [`Activity`](https://effect.website/docs/v4/api/effect/workflow/Activity), [`DurableDeferred`](https://effect.website/docs/v4/api/effect/workflow/DurableDeferred), and [`ChildProcess`](https://effect.website/docs/v4/api/effect/process/ChildProcess) APIs supply execution IDs/resume, persisted named steps, human completion tokens, and OS process execution. Their docs mark workflow and cluster APIs unstable. [The Effect README](https://github.com/Effect-TS/effect#requirements) calls Effect 4 LTS but does not extend that stability promise to these APIs.

What remains unproven: exact automatic restart behavior when a process dies mid-Activity; branch replay under parallel failure; current v4 Windows/macOS integration CI; migration and code-version behavior for paused runs; and startup indexing/listing of runs. The public workflow API accepts `resume(executionId)`, but does not provide an agent-facing run browser. Persist the run ID in the product's own run record. The Node SQLite client serializes one connection, which may constrain parallel review writes; test the intended fan-out before adopting it. No documented workflow version router was found, so upgrades must preserve replay-compatible workflow/activity names and schemas or explicitly migrate/restart in-flight runs.

### TanStack Workflow

The [`overview`](https://github.com/TanStack/workflow/blob/main/docs/overview.md) labels the durable runtime and store adapters experimental. The [`guide package map`](https://github.com/TanStack/workflow/blob/main/docs/guide/index.md) lists its current first-party store adapters as Drizzle/Postgres and D1. The [`runtime model`](https://github.com/TanStack/workflow/blob/main/docs/guide/runtime-model.md) and [`persistence guide`](https://github.com/TanStack/workflow/blob/main/docs/guide/persistence.md) distinguish the in-memory core store from the production execution store, explicitly enumerate what must persist, document lease expiry recovery, and say a host invocation claims and drives work to completion or pause. The [`replay and resume guide`](https://github.com/TanStack/workflow/blob/main/docs/concepts/replay-and-resume.md) documents checkpoint events, selected `runId` resume, human approval delivery, and keeping previous workflow versions until old runs terminate. The persistence guide requires atomic append/leases/timers/approval idempotency and package-owned schema migrations; a generic database is not enough.

The package versions above are the exact versions in the [TanStack website's current dependency manifest](https://github.com/TanStack/tanstack.com/blob/main/package.json), not independently verified latest npm releases. The primary docs show Postgres and D1 stores. No SQLite adapter or Windows test matrix was found in the upstream workflow repository. A local SQLite store would need to implement and test the complete store contract, especially atomic event append, ownership leases, timers, approvals, stale-run recovery, and migrations.

### Workflow DevKit

The [official repository instructions](https://github.com/vercel/workflow/blob/main/AGENTS.md) describe `world-local` as filesystem-based for local development and testing, and distinguish it from Vercel's production World and the production reference Postgres World. The [`world-local` config source](https://github.com/vercel/workflow/blob/main/packages/world-local/src/config.ts) defaults to `.workflow-data` and automatic recovery. Its [`start()` source](https://github.com/vercel/workflow/blob/main/packages/world-local/src/index.ts) initializes disk storage and re-enqueues pending/running runs. The [`v5 transform docs`](https://github.com/vercel/workflow/blob/main/docs/content/docs/v5/how-it-works/code-transform.mdx) confirm compiler transformation, while the [workflow/step docs](https://github.com/vercel/workflow/blob/main/docs/content/docs/v5/foundations/workflows-and-steps.mdx) describe event-log suspension and webhook waits.

The [5.2.0 release](https://github.com/vercel/workflow/releases/tag/workflow%405.2.0), signed at `da356d5` on 2026-10-08, pins core 5.2.0 and world-local 5.1.0. Its world-local change explicitly deletes prior local data on upgrade. It also warns that changed step IDs can cause replay divergence for existing self-hosted runs and advises restarting those runs. The current [CI file](https://github.com/vercel/workflow/blob/main/.github/workflows/tests.yml) runs unit tests on Ubuntu and Windows but local dev E2E on Ubuntu. A separate local server/API endpoint is normally required by the queue configuration. Consequently, the Local World is useful for local testing but lacks the productized local persistence/upgrade contract this system needs.

### Resonate

The [TypeScript SDK guide](https://docs.resonatehq.io/develop/typescript) states v0.11.4 is current, supports ordinary async workflows in `@resonatehq/sdk/async`, requires Node 22+, and uses in-memory state by default. It explicitly directs users who need state to survive restart to a server; its direct [`PostgresNetwork`](https://docs.resonatehq.io/develop/typescript#postgres-backed-durable-execution) option removes the server but requires Postgres 16+ and is pre-1.0. In that topology, no connected worker means timers are suspended. The [server guide](https://docs.resonatehq.io/deploy/run-server) confirms `resonate serve` is a separate server process and defaults to a durable SQLite file, while `resonate dev` is in-memory. The [quickstart](https://docs.resonatehq.io/get-started/quickstart) shows restarting a worker with the same execution ID resumes the run, but it keeps the server running.

Resonate's SDK has strong explicit invocation IDs and a durable promise API for waits, and its [simulation tests](https://docs.resonatehq.io/evaluate/how-resonate-is-tested) exercise worker/server failures across Ubuntu, Windows, and macOS. Those are useful properties, but the documented persistent boundary is still a separate server or an external database, so the SDK does not meet the selected embedded-runtime scope.

## Continue policy and CLI reconciliation

If product policy changes from automatic recovery to a UI **Continue** action, use the durable run identifier as the selection key: Effect exposes `Workflow.resume(executionId)`; TanStack drives `runWorkflow` with its existing `runId`; Resonate can reattach to an existing invocation ID but only with its durable network. These APIs identify the requested run; they do not prove that starting a shared embedded engine will only dispatch that run. Effect's persisted mailboxes can redeliver unprocessed messages, and TanStack documents lease recovery sweeps, so per-run state/worker isolation or an engine recovery-dispatch gate must be verified. WDK Local World explicitly re-enqueues active runs as a group at startup. Do not claim Continue avoids unrelated work until the selected runtime's dispatch behavior has been proven.

The button still needs to inspect current durable status before dispatch: already-finished steps should be skipped; completed review branches should stay completed; any still-running or failed branch must be deliberately retried or reconciled; and approval payloads must be tied to an outstanding durable wait, not an old UI view. Every candidate persists a result only after its durable operation completes. If the host dies while an agent CLI runs, replay may start the step again even when the CLI session or remote publication partially survived. Pass a stable operation/session ID into the CLI or external API, query that ID on Continue, and record the resolved outcome in a separate durable step. None of the reviewed engines discovers or resumes an external child-process session on its own.

## Proof required before selecting Effect

1. A single foreground process starts a workflow with a durable SQLite file and a stable user-visible run ID; kill the host between activities, start a new process, and Continue that exact run. Verify that engine startup and recovery dispatch do not also claim unrelated runs, or add a gate/isolation layer and prove it. Verify that concurrent foreground invocations cannot start independent `SingleRunner`s against the shared database; serialize them, isolate them, or use a proven coordination composition.
2. Run three parallel reviewer Activities; kill after one and two complete; verify completed outputs are not repeated and only unfinished branches reconcile.
3. Suspend on a human token, terminate the process, resolve the token, and Continue; reject duplicate/stale approvals deterministically.
4. Kill the host while a CLI agent process is active; use a stable CLI session ID and prove Continue discovers, resumes, cancels, or safely retries that external session.
5. Run the same acceptance cases on Windows, macOS, and Linux; test SQLite lock behavior, node:sqlite version checks, schema migration, backup/restore, and startup with multiple historical runs.
6. Upgrade the application with paused and interrupted runs; prove code changes are replay compatible or provide an explicit version/migration policy.
