## Accepted identity and retained accounting

On 2026-10-15 the human accepted all three recommendations below. This section owns the identity and retained-accounting contract without introducing workflow recovery. Existing numeric limits, current-script entry execution, explicit input resolution, and exclusive worktree ownership remain settled. This acceptance does not close the lifecycle ticket or authorize runtime implementation.

1. **Identity:** use a run ID for the explicitly selected history/accounting scope, a fresh invocation ID for every script launch, and a fresh attempt ID for every managed agent/command execution. The UI can show a run containing invocations containing attempts, grouped into phases. A run is a history grouping, not a suspended workflow instance. Worktree identity and native conversation IDs remain separate references. Continuing the same job explicitly selects its run ID; starting a genuinely new job explicitly creates a new run, optionally referencing previous work. Merely opening history, changing a script, or reusing a conversation creates no new allowance. Do not merge/fork accounting scopes or infer job identity from prompt similarity.
2. **Retained allowances:** keep the shared additional-agent allowance on the run and use explicit stable logical operation/correction-loop keys for applicable local allowances across invocations. A repeat of an existing logical agent operation is additional work even when the script starts again from entry; an explicitly new planned operation is distinct. Record repeat/correction/retry purpose and the prior operation or attempt being followed up. Workflow code supplies this relationship; do not infer it from prompts, source diffs, or native session IDs. If edited workflow code makes required follow-up lineage ambiguous, stop that dispatch and require explicit lineage or an explicit new-run scope. Renaming an existing operation does not authorize resetting its allowance. Ordinary workflow code is trusted to declare purpose honestly; this is not a semantic anti-evasion engine or a hard spending boundary. Explicit allowance increases remain recorded. Commands and opaque internal children retain their previously accepted accounting treatment. A new run is an explicit new accounting scope, not automatic recovery from exhaustion.
3. **Crash-safe charging:** before launching managed work, atomically check applicable limits and save the attempt admission/debit in SQLite. Parallel admissions share the same check-and-record transaction rule. Record completion separately. An admitted attempt whose launch/outcome is uncertain keeps its charge and appears uncertain; release a reserved charge only when non-launch is positively established and record that release. No automatic refund based on missing output or parent exit. If admission cannot be saved, do not launch; if later recording fails, use the accepted stop-dispatch/interruption policy. Explicit budget increases can permit further work after ownership/safety checks, but never rewrite uncertainty as success. These rows are accounting facts, not resumable execution checkpoints, and they do not prove child termination.

Example under the accepted contract: a run consumes three of twenty additional agent attempts and returns `needs_input`. A later invocation joins that run and executes its chosen current script from entry with seventeen additional attempts left. A repeated implementation/review operation uses that remaining allowance; no earlier phase is automatically skipped. A correction loop that already consumed its two corrections stays exhausted until an explicit increase or an explicitly different job scope. A crash between admission and confirmed launch conservatively retains the debit unless non-launch can be established.

Acceptance must cover distinct invocation/attempt IDs under one run, retained shared and local allowances across follow-up invocations, explicit new-job scopes, ambiguous follow-up lineage blocking dispatch, recorded allowance increases, concurrent admissions at the remaining limit, failure to persist admission preventing launch, and uncertain launches retaining charges until non-launch is established. Verify that history/context reuse neither skips phases nor grants permissions, and that missing child telemetry is not treated as zero usage or proof of termination.

Exact field names, storage schema, logical-key validation, and process proofs remain specification work. No runtime or accounting behavior has been implemented or tested.

## Accepted history preservation for learning

On 2026-10-15 the human accepted the revised recommendation: preserve full history for learning, keep extraction traceable, and make cleanup exceptional and idle-only. This replaces the earlier proposed ordinary transcript-pruning approach. It refines the accepted saved-history and explicit-retention contracts without adding durable workflow execution or authorizing implementation.

1. **Preserve the full captured record by default.** Retain delivered prompts, effective settings and skill inputs, available traces/tool results, outputs, checks, reviews, failed attempts, and corrections. Summaries and extracted lessons supplement this evidence; they do not replace it. Existing known-secret/configured filtering applies before persistence. Full history means the content actually captured through supported interfaces, not a promise of unavailable telemetry, hidden reasoning, or automatic archival of referenced external files. Partial/unknown capture and missing external references remain honestly labeled. No age-based expiry or routine automatic pruning is authorized.
2. **Make learning extraction traceable.** Record which source invocations/attempts were examined, what was extracted, and the relationship between each proposed improvement and its supporting sources. Retain whether a proposal was evaluated or adopted and references to that evidence/change when available; do not infer effectiveness from extraction or adoption alone. Extraction never marks its source history disposable. Use source references and a small extraction record; no knowledge graph, vector database, or autonomous learning service is required. [Skill and prompt improvement](skill-and-prompt-improvement.md) owns the now-accepted explicit extraction, comparative evaluation, and human-adoption policies.
3. **Make cleanup exceptional and informed.** Before any explicit deletion of selected captured detail, show the selection, storage estimate, which runs have been examined for learning, and which recorded improvement proposals reference them. Require deliberate confirmation. Unknown/unexamined learning status must be distinguishable from examined history with no extracted proposal. Keep operational records needed for accounting, lineage, outcomes/questions, ownership, and extraction/source references; label deliberately removed detail so references do not silently appear complete. Cleanup cannot reset allowances, release ownership, acknowledge questions, or delete worktrees and ordinary external files. Built-in full repository-data purge is removed under the [accepted full-purge decision](#accepted-removal-of-built-in-full-purge); complete removal is documented manual operator work. This is not a guarantee that every sensitive copy has been erased, nor a requirement to retain deleted source text inside the extraction record.
4. **Keep cleanup idle-only.** Refuse cleanup while any repository invocation or uncertain owned work remains. Require the dashboard host to stop and exclude runner/dashboard startup during maintenance, using the [shared repository maintenance gate](#accepted-shared-repository-maintenance-gate). Do not introduce online pruning coordination. Preserve operational facts if cleanup is interrupted; exact transactional deletion, storage reclamation, and repair mechanics remain specification work and are not adopted merely from the earlier proposal.
5. **Manage storage before discarding evidence.** Show storage use and growth. Consider compression only when measurements justify it; no compression algorithm or capacity threshold is selected now. 3. **Explicit stale validation:** provide a read-only ownership inspection and an explicit stale-clear/reuse action. That action serializes against new claims, revalidates the original ownership identity and all relevant managed execution scopes, and clears only when the old runner and workspace-accessing owned work are established inactive. A missing PID, old timestamp, terminal history outcome, or absent output is insufficient proof. Proven-dead claims can be released without deleting/resetting files or rewriting outcomes/accounting; uncertain claims remain blocked with a specific diagnostic and next checks. Stopping a confirmed surviving owned process is a separate explicit interruption/cleanup action, not an implicit side effect of inspecting or clearing a record. There is no force-clear option that relabels uncertainty as safety. After release, a new invocation still validates the selected repository/worktree and current inputs, preserves dirty work, acquires a fresh claim, and starts the current script from entry. These actions do not authorize cleanup of user files or restore an old workflow.

Tradeoff: crashes can require an explicit inspection/clear step, and unsupported child-lifecycle behavior may block a harness mode. This preserves safe reuse without a continuously running supervisor. Exact platform proof, atomic launch-to-scope association, crash windows, handling inaccessible identity evidence, and worktree registration validation remain specification/qualification work. No mechanism has been implemented or tested.
