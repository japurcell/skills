Workflow inputs belong to configuration or CLI arguments; local view controls must not mutate execution. Prototype annotations do not establish a product feedback form.

Work with the human using the prototype skill after recovery and improvement contracts settle their visible states. Refine the accepted [observability prototype](../prototypes/observability-prototype.html), keeping synthetic behavior clearly labeled.

Resolve:

- Apply [accepted upgrade-backup retention](recovery-and-runtime-selection.md#accepted-upgrade-backup-retention): include retained backup files in storage-use visibility and provide CLI cleanup guidance. Keep cleanup explicit and idle-only; no dashboard deletion, rotation, or restore controls.

- Apply the [accepted shared repository maintenance gate](recovery-and-runtime-selection.md#accepted-shared-repository-maintenance-gate): maintenance excludes dashboard startup; CLI diagnostics identify the operation and any interrupted/blocked state. Do not imply a live dashboard survives maintenance or add browser gate-release/repair controls. After validated upgrade/repair completion, reopening the dashboard reads saved history normally. Under [accepted uninstall admission](recovery-and-runtime-selection.md#accepted-uninstall-through-the-maintenance-gate), the host must also stop for uninstall; after successful removal, factory history viewing requires a compatible installation. No browser uninstall control is added.

- Apply [no factory-level automatic infrastructure retries](verification-and-review-policy.md#no-factory-level-automatic-infrastructure-retries): show the failed attempt, cleanup status, saved output, and guidance for explicit follow-up. Do not present automatic infrastructure retry countdowns or controls. Distinguish quality/format correction attempts from a later explicit invocation.

- Apply [selected profile or failure](agent-execution-profiles.md#selected-profile-or-failure): show the requested/effective profile, the unsupported setting or provider failure, and guidance for explicit later-invocation selection. Do not design automatic-fallback status, fallback-chain controls, or browser profile switching. Optional missing telemetry remains distinct from a required-capability failure.

- Lane grouping, nested scopes, collapse/filter behavior, long labels, dense concurrency, dynamic insertion, and declared versus observed work without invented progress. Use phase/parent-session lanes with observed subagents where supported, not factory task/integration lanes. Include an explicit parent-only example with limited child telemetry, and avoid assuming reported child visibility proves shutdown control.
- Selection, deep links, keyboard focus, attempt/session navigation, history versus live following, and preservation of reading position while events arrive. Apply [invocation-scoped correction conversations](agent-execution-profiles.md#invocation-scoped-correction-conversations): one native conversation may span correction attempts within an invocation, but later invocations start fresh. Keep historical native IDs visible without resume controls; joining history or reusing a worktree does not reuse an earlier conversation.
- Apply [accepted identity and retained accounting](recovery-and-runtime-selection.md#accepted-identity-and-retained-accounting): distinguish the run's shared history from individual invocations and managed attempts, grouped into phases. Keep native conversations and worktrees distinct from those identities. Show retained allowances, recorded increases, and uncertain launch charges without suggesting resumable execution or a hard cap on opaque child usage.
- Phase content hierarchy, long output, saved-output and file-reference navigation, effective configuration, unknown telemetry, and version/change provenance. Remove immutable evidence/registered-artifact and managed-publication fixture claims. Distinguish saved traces/prompts/outputs from file references that may change or disappear. Show pre-phase workspace preparation, the resolved starting commit for new worktrees, and one shared run worktree. Apply [committed-revision-only creation](task-scheduling-and-integration.md#committed-revision-only-worktree-creation); do not design local-change selection or snapshot previews. Distinguish a newly created worktree from explicit reuse of preserved unfinished work; distinguish managed attempts from internal child activity and avoid usage double-counting.
- Loading, empty, disconnected/reconnecting, stale, failed, skipped, ended needs-input, cleanup-uncertain, interrupted, cancelled, and completed states. Distinguish a new invocation joining history/context from resumed execution. Replace prototype text implying live human/native approval waits, durable saved waits, Continue from an interrupted position, factory task queues, separate task/integration worktrees, or dependency refresh. Show CLI invocation guidance without browser execution controls.
- Design attention presentation under [the accepted notification policy](human-control-and-publication.md#notifications): prominent desktop notices for needs-input/failure, configurable quiet success, persistent dashboard status and actionable CLI guidance. Show repository/run, reason, and suggested answers where useful. Apply [accepted optional notification links](recovery-and-runtime-selection.md#accepted-optional-notification-links): native detail links are optional; provide access to saved details through the CLI/dashboard, including guidance when the dashboard host is stopped. Do not assume clicking an old notification starts the host. Distinguish missing desktop delivery from the saved outcome. Reminders are configurable, off by default, and run only while the dashboard runs. Reopening shows outstanding items without replaying missed alerts. Preferences and acknowledgment affect notification metadata only; acknowledgment silences reminders without answering questions or changing outcomes. Links open observation, never execute or answer.
- Apply the [accepted manual-cleanup fallback](recovery-and-runtime-selection.md#accepted-manual-cleanup-fallback): show supported automatic cleanup separately from operator-required cleanup, known process/session/worktree details, and persistent uncertain ownership after the invocation ends. Apply the [accepted cleanup confirmation and ownership release contract](recovery-and-runtime-selection.md#accepted-cleanup-confirmation-and-ownership-release): show operator-confirmed clearance distinctly from shutdown established by automatic checks, including the saved cleanup note. Offer CLI/native-tool guidance without browser execution/release controls or a false machine-verified stopped/safe indicator. Ownership release does not change the earlier invocation outcome.
- Apply the [accepted needs-input and invocation finalization contract](recovery-and-runtime-selection.md#accepted-needs-input-and-invocation-finalization): distinguish a saved question from a finalized invocation, show needs-input together with manual cleanup required, and show incomplete/outcome unknown after a crash before finalization. Retain questions and independent failures received during shutdown; distinguish calls interrupted for shutdown from calls that independently failed. Exact summary presentation must not conceal either the question or cleanup requirement.
- Apply [accepted idle-upgrade coordination and failure handling](recovery-and-runtime-selection.md#accepted-idle-upgrade-coordination-and-failure-handling): explain that the dashboard process must stop for an upgrade and can be reopened afterward; a closed browser tab is not process-shutdown evidence. No browser upgrade/repair controls or live version-compatibility promise are introduced. Distinguish installation unavailability from missing saved history. Under [accepted forward-only repair](recovery-and-runtime-selection.md#accepted-forward-only-upgrade-repair), provide CLI guidance for completing the intended upgrade; do not offer downgrade, automatic backup restore, or general salvage controls. The dashboard stays stopped during repair and reopens only after validation.
- Apply [accepted saved-history consistency](recovery-and-runtime-selection.md#accepted-saved-history-consistency): distinguish complete, partial, or unknown capture from invocation success/failure and from unsupported telemetry. Show saved chunks after interruption and separate later-attempt records. - Apply [accepted explicit learning invocations](skill-and-prompt-improvement.md#accepted-explicit-learning-invocations): present source selection as CLI/workflow guidance, extraction outcomes and exact source references, candidate reports, and examined sources with no justified proposal. Keep approval distinct from successful application, and inconclusive evaluation distinct from passing. Use CLI/authoring guidance without adding browser approval or execution controls.
- Apply [accepted history preservation for learning](recovery-and-runtime-selection.md#accepted-history-preservation-for-learning): show source-linked learning extraction, examined versus unexamined invocations, and evaluation/adoption evidence without implying effectiveness. Show storage use/growth and explicitly pruned or missing source detail. Extraction never marks history disposable. Exceptional cleanup remains CLI maintenance with repository-idle/dashboard-stop requirements; do not add dashboard deletion controls by implication.
- Apply [accepted notification defaults and reminder ownership](recovery-and-runtime-selection.md#accepted-notification-defaults-and-reminder-ownership): show a combined initial invocation notice, opt-in grouped repository reminders, configurable five-second delivery timeout and fifteen-minute reminder interval, and persisted per-invocation acknowledgment. Explain dashboard-host lifetime versus browser tabs; reopening shows items without replayed alerts. Do not imply acknowledgment answers questions or clears ownership.
