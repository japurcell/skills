# Provider CLI settings for Git-metadata protection

**Question:** Can Copilot CLI, Gemini CLI, or Codex CLI prevent every direct modification of a repository's Git metadata—including an arbitrary Python or PowerShell script—while preserving normal Git commands?

**Conclusion:** No documented local-CLI setting supplies that complete, command-identity-aware boundary across all three providers. A filesystem sandbox or OS ACL controls paths, not whether the writer is `git`, Python, or PowerShell. If it makes the Git directory read-only, state-changing Git commands fail too. Hooks, custom instructions, ignored-file rules, tool allow/deny patterns, and approval prompts can reduce accidents, but none is a complete control over writes performed after an allowed arbitrary shell command starts.

Codex is the closest turnkey protection: its `workspace-write` sandbox recursively makes the workspace `.git` path read-only and, for a `gitdir:` pointer file, also makes the resolved Git directory read-only. It consequently also denies Git operations that need to update the index, refs, or other metadata while they stay sandboxed. This checkout demonstrates the relevant worktree shape: `.git` is a pointer file; its resolved Git directory is `/Users/adam/dev/skills/.git/worktrees/skills`, and its common Git directory is `/Users/adam/dev/skills/.git`. A complete path policy for a linked worktree must account for all three locations, including the external common directory; protecting only the pointer file does not express the desired security boundary.

## What counts as enforcement

An OS-enforced sandbox applies to child processes, so it covers `python`, `pwsh`, redirection, and other arbitrary programs once started. It cannot grant a path to `git` while denying the same path to Python unless the underlying OS policy has a separate executable-specific rule; the documented CLI policies here do not expose such a rule. Tool permissions and hooks decide whether a tool invocation begins. They do not supervise its child processes or each later filesystem syscall. Ignore files and natural-language instructions only affect discovery or model behavior.

| Provider | Documented hard local boundary | Does it protect `.git` / resolved worktree Git directory? | Can it still permit state-changing Git? |
| --- | --- | --- | --- |
| Codex CLI | Yes: OS-level sandbox policy. | Yes, automatically and recursively for the in-root `.git` path and a `gitdir:` target. The documentation does not explicitly say that it follows from that target to the common Git directory, so that part is **unverified**. | No, while that protection remains: writes needed by `git add`, `commit`, `checkout`, `restore`, etc. are denied. Escalation or full access removes the protection. |
| Copilot CLI | Yes for shell child processes when local sandboxing is on: OS sandbox; built-in file tools enforce the same policy in software. | On macOS and Linux it can deny specific absolute paths, and configured denials override automatic Git grants. In a worktree, configure the pointer-file path, resolved Git directory, and common Git directory after verifying `/sandbox policy`. On Windows, the ProcessContainer backend rejects a policy with `deniedPaths` rather than enforcing it. | No documented way to allow Git alone to write a denied metadata path. Copilot's default policy deliberately grants Git metadata writes. |
| Gemini CLI | Yes when the optional sandbox is enabled: macOS Seatbelt, Windows native sandbox, or a Linux/container backend. | No documented `.git`-specific deny setting. Default macOS and container profiles make the project writable; containers bind-mount the project read/write. A custom Seatbelt profile or custom container policy may deny exact paths, but that would deny every program in the sandbox, including Git. | No documented command-specific exception. |

## Codex CLI

The installed CLI reports `codex-cli 0.155.1`. OpenAI documents OS-level sandbox enforcement, the `read-only`, `workspace-write`, and full-access modes, and the default `workspace-write` protection for a `.git` directory **or file**. For a `.git` pointer, it also protects the resolved Git directory; protection is recursive. [`Agent approvals & security`](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots)

This is a hard path boundary for arbitrary scripts while they remain in `workspace-write`. It is not an allowlist of Git commands: the same source says the standard Auto mode permits work in the workspace, whereas `danger-full-access` has no sandbox or approvals. A state-changing Git command needs metadata writes and therefore cannot succeed under the protected-path rule. Approval policies and automatic approval review govern escalation requests; they do not preserve the filesystem block after an approved outside-sandbox run. [`Agent approvals & security`](https://learn.chatgpt.com/docs/agent-approvals-security#common-sandbox-and-approval-combinations)

The documented protection covers the pointer and its resolved Git directory but does not state whether Codex recursively discovers the worktree's `commondir` parent. **UNVERIFIED:** automatic protection of `/Users/adam/dev/skills/.git` for this checkout's linked-worktree layout. Treat a successful mutation test or the reported sandbox policy as required evidence before claiming complete worktree protection.

## GitHub Copilot CLI

With local sandboxing enabled, Copilot CLI runs shell commands as OS-sandboxed child processes (Seatbelt on macOS, Bubblewrap on Linux, and ProcessContainer on Windows). Thus a denied path blocks direct script writes at the OS boundary. Its built-in create/edit tools run in the CLI and check the same policy in software, which is meaningful protection but is explicitly not OS enforcement. Local sandboxing is public preview, and Windows requires a Windows Insiders build. [`Understanding filesystem policies`](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/understanding-local-sandboxing), [`CLI configuration directory`](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference#local-sandboxing)

Copilot automatically adds associated Git grants when the working directory is included; default behavior permits writing Git metadata. On macOS and Linux its policy supports configured absolute `deniedPaths`, and a configured denial wins over automatic grants. On Windows, the ProcessContainer backend cannot enforce per-path denial; a policy containing `deniedPaths` is rejected and the command fails. The Filesystem UI also offers a `Read-Only` path rule, but these sources do not establish whether the Windows backend can enforce it for a nested `.git` path under a writable workspace; that remains **unverified**. The effective policy is path- and directory-dependent, so `/sandbox policy` is the required verification for each checkout. [`Understanding filesystem policies`](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/understanding-local-sandboxing#how-the-policy-is-built), [`CLI configuration directory`](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference), [`Configuring local sandbox settings`](https://docs.github.com/en/copilot/how-tos/cloud-and-local-sandboxes/configuring-local-sandbox-settings#adding-filesystem-path-rules)

On macOS and Linux, this can hard-block arbitrary scripts from the three verified worktree-related paths, but it necessarily blocks Git metadata writes as well. It is also only durable if sandbox bypass is disabled: GitHub documents that a user can otherwise run a blocked command outside the sandbox or disable sandboxing for the session. Enterprise-managed settings can require sandboxing, fail closed if it cannot be established, forbid bypass, and add denied paths; that is the strongest documented Copilot deployment control on supported platforms. [`Enterprise managed settings`](https://docs.github.com/en/copilot/reference/enterprise-administrators/enterprise-managed-settings#sandbox)

Copilot's `--deny-tool='write(path)'` and pre-tool hooks are useful admission controls, but are not a substitute. In particular, documented shell-path inspection covers only recognized redirects and a small set of `sed -i` forms; commands whose target comes from a variable fall back to normal shell rules. [`CLI command reference`](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference#tool-permission-patterns)

## Gemini CLI

Gemini sandboxing is optional (enabled with `--sandbox`, `GEMINI_SANDBOX`, or `tools.sandbox`) and uses macOS Seatbelt, Docker/Podman, Windows Native Sandbox, gVisor/runsc on Linux, or experimental LXC/LXD. Its sandbox protects shell and file modifications at the process boundary, but the documented stock profiles are project-root boundaries, not Git-metadata policies. [`Sandboxing in Gemini CLI`](https://geminicli.com/docs/cli/sandbox/)

On macOS, the default Seatbelt profile confines writes to the project. The CLI supports a custom `.gemini/sandbox-macos-<profile>.sb` profile. Docker/Podman mounts the current project directory at the same host path with read/write access; additional mounts default to read-only only when separately listed. On Windows the documented native sandbox applies low integrity labels; on Linux, gVisor is an optional stronger process-isolation backend. These mechanisms can protect a path only by denying it to all sandboxed processes. [`Sandboxing in Gemini CLI`](https://geminicli.com/docs/cli/sandbox/#sandboxing-methods)

`.geminiignore` and `.gitignore` govern context/file filtering, not shell access or write authorization. Approval modes and hooks can deny a tool invocation, but a permitted `run_shell_command` can launch arbitrary Python or PowerShell. Gemini's sandbox-expansion request can also extend a command's permissions if a person approves it. [`Gemini CLI configuration`](https://geminicli.com/docs/reference/configuration/#sandboxing), [`File management`](https://geminicli.com/docs/cli/tutorials/file-management/#advanced-controlling-what-gemini-sees)

Gemini's policy engine is request-level too: a `commandPrefix = "git"` rule checks only the beginning of the serialized command argument. It cannot observe later filesystem operations, command chains, aliases, scripts, or Git hooks. System-wide policy locations exist for macOS, Linux, and Windows, but centralizing this rule does not change that limit. [`Policy engine`](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/policy-engine.md#special-syntax-for-run_shell_command)

## Decision implication

Use provider hooks and tool permissions as a consistent warning/blocking layer for named destructive commands and direct editor tools. Describe them as defense in depth, not complete repository-state protection. For a requirement that no local agent process may mutate Git metadata while still allowing ordinary repository edits, use an OS-enforced path policy and run state-changing Git work outside that policy only through a separately controlled human workflow. If the requirement also demands unattended state-changing Git commands, none of the documented provider settings can simultaneously satisfy it; a separate privileged Git service or OS-level executable-specific policy would be outside the documented CLI settings researched here.
