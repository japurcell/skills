# Markdown Health Hook

**Type:** grilling
**Status:** closed
**Blocked By:** provider-hook-capabilities.md
**Research Dir:** none

## Question

What user-level Markdown validation behavior should the three providers share: which edited files and Markdown formats count, which local and remote links count as broken, when checks run, and whether uncertain failures block or warn? Choose observable diagnostics and runtime limits that can work across supported platforms.

---

## Resolution

Create a user-level Markdown health hook for local Copilot CLI and VS Code, Gemini CLI, and Codex on supported platforms. Copilot cloud agent is outside this ticket because it loads repository hooks, not user-level hooks; the user confirmed this boundary. Check every agent-touched `.md` and `.markdown` file in the current workspace, including README and agent documentation. Validate the entire touched file, including older defects, rather than only changed lines. Do not scan untouched Markdown during every turn. `.mdx` is outside this checker because JSX needs different parsing.

Check only clear, deterministic Markdown syntax and structure defects and broken local links. The implementation specification should name and test its supported findings, including unclosed fenced code blocks, undefined link references, missing workspace-local file and image targets, and missing heading fragments. Resolve relative links from their containing file. Account for fenced and inline code, reference-style links, URL escapes, and repeated heading slugs so text that is not a link does not produce false positives. Do not impose full Markdown style rules, such as heading style or line length. Do not request HTTP(S) URLs or mark them broken. If a local path resolves outside the workspace, report `outside workspace, not checked` without opening it; do not count it as a broken link.

Use a focused checker shipped with this repository and no new runtime dependency. Share one validation policy across provider adapters; keep each provider's installed hook entry point and JSON envelope native to that provider. Existing `scripts/lint-okf.py` is limited to `.agents/instructions/` and `.agents/memory/` and skips remote URLs, so it is a source of test cases or reusable logic, not a sufficient user-level checker for arbitrary workspaces.

Run after successful edit tools for immediate feedback, and check the session's touched Markdown again before final completion to catch shell edits or missed post-tool paths. Show concise, actionable diagnostics to the agent and user: file, line, rule, target where relevant, and rerun command. For definite findings, require a repair attempt before completion, with at most two completion retries per turn; then surface unresolved findings and allow a final answer. A checker crash, timeout, or unreadable file should produce a visible warning and let the agent explain the uncertainty rather than strand the task. Post-tool feedback cannot undo an edit. Provider-specific completion hooks may differ: the ExecPlan must verify Copilot `agentStop`, Gemini `AfterAgent`, and Codex `Stop` against deployed versions, especially the known Gemini `AfterAgent` delivery issue, and specify a tested fallback before claiming all-provider coverage.

Write one audit entry for each validation batch with at least one Markdown candidate, whether the outcome is `pass`, `fail`, or `incomplete`. A batch may include several files; never write one entry per file or per finding. Suppress a redundant final-check entry only when the same files, their contents, and the outcome are unchanged since the previous batch. Keep the single physical line at most 4 KiB: record a sorted, sanitized list of workspace-relative paths actually checked, total checked count, and omitted count when the list must be shortened. Also record finding count and existing session/event context where available. An early failure may report zero checked files with `incomplete` status. Do not log document contents, link targets, commands, or diagnostic text. Follow each provider's audit format and secure write rules, reusing helpers where possible: Copilot and Gemini write to their `hooks/audit.log` with sender and timestamp fields; Codex uses its `hooks/logs/audit.log` key/value format. If the audit write fails, surface an audit-unavailable warning without changing the validation result. No-op invocations with no Markdown candidates write no audit entry. The ExecPlan must test pass, fail, incomplete, duplicate-final suppression, changed-file revalidation, line cap, sanitization, permissions, and audit-write failure.

Bound synchronous work to a 10-second hook timeout with an 8-second checker budget; if the budget expires, report incomplete validation rather than claim success. Show at most 20 diagnostics within an 8 KiB serialized response, with an omitted count. The ExecPlan must test multi-file edits, shell-created Markdown, untracked files, Windows paths and PowerShell delivery, repeat-stop behavior, local link fragments, skipped external paths, malformed input, checker failure, and installed-copy behavior. Windows acceptance uses automated tests plus a documented live-check checklist; a live Windows run is not a gate. Official event contracts: [Copilot](https://docs.github.com/en/copilot/reference/hooks-reference), [Gemini](https://geminicli.com/docs/hooks/reference/), and [Codex](https://developers.openai.com/codex/hooks).
