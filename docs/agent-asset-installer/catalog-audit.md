# Initial Bundle Catalog Audit

Audited 2026-09-29 for milestone 2. This is a source inventory for catalog implementation, not a declaration that every workflow is deliverable or that provider hooks have been live-tested. The milestone defines three roots: bundle `review` rooted at `skill:code-review`, bundle `security-hooks` containing `hook:tool-guard` and `hook:scan-secrets`, and bundle `required-context` containing `hook:required-skills` plus its declared skill files ([ExecPlan](ExecPlan.md#L177)).

## `security-hooks`

Literal IDs are `hook:tool-guard` and `hook:scan-secrets` ([ExecPlan.md:177](ExecPlan.md#L177)). Canonical generator sources are [hooks/families/tool_guard.py](../../hooks/families/tool_guard.py#L1) and [hooks/families/scan_secrets.py](../../hooks/families/scan_secrets.py#L1). Both embed the allowlist implementation from [hooks/families/allowlist.py](../../hooks/families/allowlist.py#L1); the family modules also refer to `hooks/manifest.py` and `hooks/providers.py` for rendering metadata ([tool_guard.py:5-6](../../hooks/families/tool_guard.py#L5), [scan_secrets.py:5-6](../../hooks/families/scan_secrets.py#L5)). Those are build/source lineage, not imports needed at installed runtime.

For the currently maintained Codex, Copilot, and Gemini outputs, `hooks/manifest.py` declares these physical entry points ([lines 34-39](../../hooks/manifest.py#L34)):

| Hook | Codex runtime file | Copilot runtime file | Gemini runtime file |
| --- | --- | --- | --- |
| Tool Guard | `.codex/hooks/tool-guard.py` | `.copilot/hooks/scripts/tool-guard.py` | `.gemini/hooks/scripts/tool-guard.py` |
| Secret scanner | `.codex/hooks/scan-secrets.py` | `.copilot/hooks/scripts/scan-secrets.py` | `.gemini/hooks/scripts/scan-secrets.py` |

Each installed script imports provider-local `helpers.common` and/or `helpers.audit`; ship both helper files with either selected security hook. The exact runtime helper pairs are `.codex/hooks/helpers/{common.py,audit.py}`, `.copilot/hooks/scripts/helpers/{common.py,audit.py}`, and `.gemini/hooks/scripts/helpers/{common.py,audit.py}`. Canonical inputs are [hooks/families/common.py](../../hooks/families/common.py#L1) and [hooks/families/audit.py](../../hooks/families/audit.py#L1), while provider-specific output paths are listed in the manifest ([lines 24-31](../../hooks/manifest.py#L24)). `helpers.observability` is attempted dynamically by `common.py` but exceptions are suppressed; it is optional observability, not required for the security decision path. The allowlist code is embedded at generation, so no installed-time import of `hooks/families/allowlist.py` is needed.

Registration is client-specific. Codex runs both security hooks at `PreToolUse` and the scanner again at `Stop` ([global-hooks.json:18-44](../../.codex/global-hooks.json#L18)). Copilot runs Tool Guard and block-mode scan at `preToolUse`, then warn-mode scan at `agentStop` ([hooks.json:4](../../.copilot/hooks/hooks.json#L4), [line 59](../../.copilot/hooks/hooks.json#L59)); Gemini runs both at `BeforeTool` and warn-mode scan at `SessionEnd` ([global-settings.json:317](../../.gemini/global-settings.json#L317), [line 400](../../.gemini/global-settings.json#L400)). The concrete commands are in `.codex/global-hooks.json` ([line 31](../../.codex/global-hooks.json#L31)), `.copilot/hooks/hooks.json` ([line 71](../../.copilot/hooks/hooks.json#L71)), and `.gemini/global-settings.json` ([line 330](../../.gemini/global-settings.json#L330)); scanner commands also appear at [Codex lines 24 and 44](../../.codex/global-hooks.json#L24), [Copilot lines 80 and 151](../../.copilot/hooks/hooks.json#L80), and [Gemini lines 336 and 414](../../.gemini/global-settings.json#L336). These are mixed global config sources. A bundle must merge only the selected hook entries through the client adapter; copying the whole global settings file would include unrelated user settings. The contract's complete repository setup targets Codex, Copilot CLI/VS Code, and Gemini; other initial clients are skills-only ([contract](../agent-asset-distribution/tickets/choose-distribution-contract.md#L17)).

Runtime requirements: Python 3 for every hook process, native provider hook support/trust, and Git on PATH for `scan-secrets` (it probes for Git and invokes it to scan repository changes at [scan_secrets.py:191](../../hooks/families/scan_secrets.py#L191) and [line 231](../../hooks/families/scan_secrets.py#L231)). The config commands show the OS launch split: Codex uses `python3` on POSIX and `py -3` on Windows ([global-hooks.json:9](../../.codex/global-hooks.json#L9)); Copilot provides Bash and PowerShell commands, with PowerShell invoking `python` ([hooks.json:71](../../.copilot/hooks/hooks.json#L71)); Gemini's source uses `python` ([global-settings.json:332](../../.gemini/global-settings.json#L332)). Both hooks write provider-scoped audit/log state, so runtime needs writable state paths or configured overrides; defaults derive from the user's home ([tool_guard.py:909](../../hooks/families/tool_guard.py#L909), [scan_secrets.py:1095](../../hooks/families/scan_secrets.py#L1095)). The installer plan baseline is Python 3.11+ and Git ([ExecPlan.md:63](ExecPlan.md#L63), [line 242](ExecPlan.md#L242)); exact client/OS execution remains an acceptance gate, not a catalog fact.

## `required-context`

Literal ID: `hook:required-skills` ([ExecPlan.md:177](ExecPlan.md#L177)). Its only currently declared skill file is `caveman/SKILL.md`: Codex hard-codes that path ([.codex/hooks/load-required-skills.py:14](../../.codex/hooks/load-required-skills.py#L14)); Copilot and Gemini configs set `AGENTS_REQUIRED_SKILL_FILES` to the same path ([.copilot/hooks/hooks.json:175](../../.copilot/hooks/hooks.json#L175), [.gemini/global-settings.json:241](../../.gemini/global-settings.json#L241)). Therefore add `skill:caveman` and its complete directory, including any support files used by that skill, to this bundle's closure. The loader accepts additional configured skill paths, but no additional path is declared by these source configs.

Provider runtime files are `.codex/hooks/load-required-skills.py`, `.copilot/hooks/scripts/load-required-skills.py`, and `.gemini/hooks/scripts/skill-context-injector.py`. Copilot and Gemini require their provider-local `helpers/common.py` and `helpers/audit.py` imports ([Copilot loader lines 9-10](../../.copilot/hooks/scripts/load-required-skills.py#L9), [Gemini loader lines 13-14](../../.gemini/hooks/scripts/skill-context-injector.py#L13)); these are the same six helper paths listed for security-hooks. Codex's loader is standalone apart from Python standard library ([imports at line 5](../../.codex/hooks/load-required-skills.py#L5)). Codex registers this as `SessionStart` ([global-hooks.json:3-10](../../.codex/global-hooks.json#L3)); Copilot as `sessionStart` ([hooks.json:160-175](../../.copilot/hooks/hooks.json#L160)); Gemini as `SessionStart` ([global-settings.json:224-241](../../.gemini/global-settings.json#L224)). Use the OS launch forms in those registrations: Codex `python3`/`py -3`; Copilot Bash/PowerShell; Gemini `python`. The complete provider helper file list overlaps the security bundle; shared files should have both owners in selection/ownership metadata.

The loader roots differ: Codex currently reads `Path.home() / ".agents" / "skills"` directly ([line 232](../../.codex/hooks/load-required-skills.py#L232)); Copilot prefers `COPILOT_SKILLS_DIR`, then `AGENTS_SKILLS_DIR`, then `~/.agents/skills` ([loader lines 88-90](../../.copilot/hooks/scripts/load-required-skills.py#L88)); Gemini reverses those first two overrides ([loader lines 80-82](../../.gemini/hooks/scripts/skill-context-injector.py#L80)). Repository installation needs explicit adapter configuration for relocated checkouts; it cannot assume the personal root works. Python 3.11+ and client-native hook registration/trust apply as above.

## Gaps and catalog implementation notes

- `domain-modeling` is an already-known unavailable workflow dependency ([ExecPlan.md:48](ExecPlan.md#L48)); it is not declared by these three bundle roots in the inspected files. Keep it represented as unavailable wherever another catalog entry requires it. Do not mark that dependent workflow complete or silently drop the edge.
- `skills/code-review/SKILL.md` itself explicitly disables automatic model invocation. Bundle installation cannot make the skill run unless the client/user invokes it.
- The audited initial bundle sources use the root `LICENSE`. The wider maintained inventory also contains `skills/skill-creator/LICENSE.txt`; preserve that notice inside its skill directory. Carry repository license/provenance with distributed files and do not imply independently verified per-file licensing.
- Files listed as conditional references or skills are real source dependencies, but a curated `review` bundle should state whether it guarantees those conditional branches. Missing dependencies should remain visible in `list` and fail selection before writes per the accepted contract.
- This audit establishes repository source paths and declarations only. It does not prove availability of required specialist agent types in every client, provider hook execution, native trust, or successful discovery after relocation.


## Milestone 2 implementation audit

Source verification on 2026-09-30 UTC covers the 51 regular top-level published `skills/*/SKILL.md` entries, 19 canonical `agents/*.md` entries, the three initial hook families, both root checklists, and explicit notice assets. Stable IDs use the type plus the maintained directory/file basename. The catalog has 80 entries and three curated bundles. Archives, `*-workspace` trees, evaluation fixtures/results, bytecode caches, and ignored runtime logs are outside the maintained payload inventory. Every maintained regular supporting file under each selected skill is explicitly enumerated, including README files, reference trees, workflow scripts, assets, and the skill-creator notice. Source lists are authored catalog inputs, never inferred at install time.

`skill:exec-plans` is an explicit maintained dependency of `skill:execplan-implement`. Its canonical tracked source is `.agents/skills/exec-plans/SKILL.md`. The optional `source_root` field permits exactly `skills/<asset-name>` or `.agents/skills/<asset-name>` for skills, defaulting to the former. This narrow declaration copies this prerequisite under its native skill name without editing the protected source or distributing the entire internal knowledge base. Dirty-source and transform preflight cover the actual declared root and all its tracked files, including unlisted same-length files. `domain-modeling` has no maintained source and remains unavailable for `wayfinder` and `improve-codebase-architecture`.

Required calls include conditional branches that explicitly invoke another skill. The quality skill says to follow security-hardening for supply-chain triage; the security skill says to follow `addy-debugging-and-error-recovery` for a privacy-incident postmortem. That skill is absent. The complete review workflow therefore remains unavailable through this explicit branch, with both dependency chains visible. The issue-tracker setup branch explicitly runs the absent `setup-matt-pocock-skills`, so `to-issues` remains unavailable. Conditional required branches in wayfinder (research/prototype), architecture improvement (grilling/domain modeling), task execution (TDD), and skill benchmarking (grader/comparator/analyzer) retain their dependencies.

Optional detail links and descriptive mentions are not required edges. Examples excluded from required closure are quality's performance-optimization profiling pointer, security's descriptive observability mention, TDD's review-stage pointer, and the web skills' related web-quality-audit/core-web-vitals links. Both quality checklist references are shipped as supporting reference assets; preserving their bytes does not promote the optional performance skill to a requirement. The named runtime `generalist`, fast-tier subagents, parallel delegation, model selection, native agent/hook trust, and externally supplied CLIs/runtimes are recorded as runtime requirements, not invented repository assets.

Source/dependency availability and installer rendering capability are separate. Listing reports `available`, full `missing` chains, `resolved_assets`, `installable`, and `restrictions`, including equivalent bundle details. Hook and agent sources can be available while `installable` is false with `ASSET_RENDERER_UNAVAILABLE` pending milestone 4. Claude Code, Cursor, and OpenCode initially refuse hook/agent selection with `ASSET_CLIENT_UNSUPPORTED`. No hook registration, generator, installed hook, client, or real home is executed by milestone 2.

The documented shared skill destination is `.agents/skills` for Codex, Copilot, Gemini, Cursor, and OpenCode. Claude uses the separately documented `.claude/skills` destination. Each shared destination is materialized once for any combination of shared clients. Copilot documentation specifies first matching location wins when both shared and Claude paths exist; the installer does not add extra Copilot-specific copies. This is documented-path and fixture evidence only, not live discovery proof. Official links and the reviewed precedence are retained in the adjacent distribution research reports for [Codex/Copilot](../agent-asset-distribution/research/codex-copilot/findings.md), [Claude/Gemini](../agent-asset-distribution/research/claude-gemini/findings.md), and [Cursor/OpenCode](../agent-asset-distribution/research/portable-methods/findings.md).

Schema preflight validates stable IDs, source roots/paths, declared representations, clients, OS/runtime metadata, bundles, duplicate keys, cycles (including unselected entries), and case-folded collisions. Missing declared committed files become unavailable reasons with dependency chains. Installation refuses undeclared runtime files under selected roots before copies. Runtime prerequisites are reported for consumers to supply; installing instructions does not provision those external tools or prove runtime capabilities.
