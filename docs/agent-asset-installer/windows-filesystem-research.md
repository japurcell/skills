# Windows filesystem contracts for agent-assets M6

Research date: 2026-09-29. Scope: first-party API contracts and proposed proof boundaries for a Python 3.11-3.14 backend. This note contains no implementation and no native Windows execution evidence. CI inventory remains in [ci-runtime-audit.md](ci-runtime-audit.md); provider discovery remains a separate audit.

The supplied M3 baseline pins POSIX parent descriptors, checks identities and preimages around replacement, authenticates ownership, and refuses ambiguous recovery. Keep `ASSET_PLATFORM_UNSUPPORTED` for Windows mutation until an equivalent composition is proved. The APIs below supply useful primitives; their individual documentation does not certify the installer transaction.

## Documented primitives and their limits

| Requirement | Documented contract | Consequence for the proposed backend |
| --- | --- | --- |
| Open a directory and inspect a link itself | `CreateFileW` requires `FILE_FLAG_BACKUP_SEMANTICS` for directory handles. `FILE_FLAG_OPEN_REPARSE_POINT` opens an existing symbolic link itself; it is incompatible with `CREATE_ALWAYS`. `CreateFileW` cannot create directories. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) | Open existing components without truncation, inspect the returned handle, and reject reparse points. The call has no parent-handle argument. Its flags are not a documented whole-path equivalent of a POSIX descriptor walk. |
| Keep an opened object from being renamed/deleted through later opens | Omitting `FILE_SHARE_DELETE` disallows other delete-access opens; delete access includes rename. Sharing constraints last until handle close and apply to existing opens too. Attribute/EA access is unaffected by sharing flags. [CreateFileW sharing](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) | Candidate parent guards must fail on incompatible existing handles and remain open through reconciliation. A guard on a child directory alone does not establish the identity of every ancestor. Denying delete sharing does not alone freeze attributes or child contents. |
| Inspect all reparse kinds | `GetFileInformationByHandleEx` can return `FILE_ATTRIBUTE_TAG_INFO` containing attributes and a reparse tag. [FILE_ATTRIBUTE_TAG_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_attribute_tag_info) | Reject `FILE_ATTRIBUTE_REPARSE_POINT` on each opened parent and managed leaf, including junctions, mount points, and unknown tags. A symlink-only predicate is insufficient. Revalidate relevant metadata; do not assume a tag allowlist makes traversal safe. |
| Compare opened object identities | `FILE_ID_INFO` combines a volume serial number and 128-bit file ID to compare handles on one computer. [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) | Use a handle-derived identity, including volume, for root, parents, stage, and leaves. A normalized path or case-folded string is not object identity. Unsupported queries must fail closed. |
| Detect links and identity limitations | `BY_HANDLE_FILE_INFORMATION` includes link count. File-ID behavior depends on the filesystem; IDs can be reused over time. Its 64-bit ID is insufficient on ReFS. [BY_HANDLE_FILE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information) | Refuse multiple hard links before any content/attribute mutation, then recheck through the retained handle. Persisted IDs alone cannot authenticate objects after death. Start proof on local NTFS; do not generalize to ReFS/FAT/network volumes. |
| Rename a retained source to a parent-relative destination | `SetFileInformationByHandle(FileRenameInfo)` operates on a source handle. `FILE_RENAME_INFO.RootDirectory` may identify the directory for a relative new name; `ReplaceIfExists=false` rejects an existing target. Length is in bytes. [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle), [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) | This is a documented Win32 candidate for publish-to-pinned-parent. Restrict the new name to a validated single component. The target is named, not supplied as an expected file-ID handle. No compare-and-replace precondition is documented here. |
| Replace while retaining old handles | The Native rename structure documents `FILE_RENAME_REPLACE_IF_EXISTS` plus `FILE_RENAME_POSIX_SEMANTICS`: old handles remain usable while new target-name opens see the renamed file. Rename stays within one volume. Its older open-file restrictions and newer flags need careful interpretation. [FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) | `FileRenameInfoEx` is a candidate, not established safety. Prove the exact Win32 flag/handle-sharing combination on supported Windows builds. Do not silently close the checked target and retry with a path operation. |
| Delete the inspected object | `FileDispositionInfo` marks the file named by a handle for deletion, requiring appropriate access; Microsoft's example uses `DELETE` and deletion on close/termination. [SetFileInformationByHandle deletion](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle), [FILE_DISPOSITION_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_disposition_info) | Prefer deletion through the authenticated retained handle. Prove exact-link behavior, pending deletion, and directory emptiness. Recursive path cleanup of a replaced parent is unacceptable. |

`GetFileInformationByHandle` may fail or return partial information on network filesystems. Therefore local NTFS proof must not become an SMB/UNC safety claim. [GetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle)

Microsoft's Win32 rename documentation currently presents an unusual generated structure layout containing both a union and an extra `ReplaceIfExists`, while its source Markdown describes the union and `RootDirectory`. Do not derive a `ctypes` ABI solely from that rendered syntax. Validate offsets, union size, pointer width, UTF-16 byte length, and flexible tail against the exact SDK header before shipping. The source confirms relative-root wording; it does not resolve runtime behavior or ABI by itself. [MicrosoftDocs rename source](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winbase/ns-winbase-file_rename_info.md)

## Replacement is the central unresolved composition

The integrated M3 code was cross-checked read-only in `scripts/agent_assets/core.py:68-164`: it walks components with `O_NOFOLLOW`, retains the final parent descriptor, checks parent visibility and leaf bytes/mode/identity immediately before `os.replace`, then checks parent visibility and the stage inode/postimage afterward. It does not perform an atomic conditional-ID replacement. Matching this accepted check-before-replace/postcheck boundary is the Windows requirement; absence of a conditional-ID API alone is not a reason to reject an equivalent backend. Do not advertise either composition as stronger than its demonstrated race coverage.

Inference from the contracts: parent delete-sharing guards do not reserve child names, and a target guard may block replacement. Sharing compatibility is checked against existing opens. A Windows candidate must explain which races are prevented and which are checked at the same before/after boundary as M3. Postchecking is detection, not permission to weaken preflight or traverse a foreign parent. [Creating and opening files](https://learn.microsoft.com/en-us/windows/win32/fileio/creating-and-opening-files)

Opening every existing ancestor without `FILE_SHARE_DELETE` and `FILE_SHARE_WRITE` is a plausible path-creation experiment, not an established no-reparse walk. In Microsoft's object-store specification, `FSCTL_SET_REPARSE_POINT` requires either `FILE_WRITE_DATA` or `FILE_WRITE_ATTRIBUTES`, rejects nonempty directories, and applies symbolic-link permission checks specifically to the symlink tag. Attribute-only opens are outside ordinary sharing checks. Therefore those sharing flags alone do not establish that an empty pinned directory cannot acquire a junction/reparse tag before a path-based child creation. The protocol contract is relevant evidence, not a substitute for proving exact local NTFS behavior. [MS-FSA reparse-setting algorithm](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/4aeefef8-92c3-4abc-af7a-a610caf8a165)

The Win32 FSCTL page names a symbolic-link privilege requirement; it does not state that `GENERIC_WRITE` is always mandatory. Do not assume that denial of write sharing blocks `FILE_WRITE_ATTRIBUTES`-only reparse mutation, or that absence of symlink privilege prevents junction creation. Prove acquisition/creation against both new and preexisting attribute-only handles, including empty newly created parents. [FSCTL_SET_REPARSE_POINT](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_set_reparse_point)

The reviewed rename APIs do not document a condition equivalent to "replace only if this target still has the identity and bytes I checked." Retain/hash inspected objects where possible, compare visible leaf identity and exact preimage immediately before rename, and verify stage identity plus exact postimage afterward. Existing write mappings, hard-link creation, attribute changes, same-name replacement, and preexisting delete-access handles need explicit investigation against the accepted M3 boundary. A whole-operation installer mutex coordinates cooperating installers; it is not protection against unrelated processes.

For absent targets, a retained stage handle plus parent-relative rename with replacement disabled is a simpler candidate: an unexpected occupant must produce a conflict. Existing-target updates, pruning, and recovery still need their own proof. A rename-away/publish sequence would introduce intermediate states and expand recovery obligations; this note does not recommend it as an established equivalent.

## Why ordinary replacement APIs are insufficient evidence

`ReplaceFileW` takes paths, opens the replaced file with delete access and broad sharing, and merges metadata such as DACLs and named streams. Its write-through flag is unsupported. Documented errors can leave the original absent or renamed and the replacement carrying merged attributes. It also keeps the replacement's file ID. These are significant journal states, not a guarantee that failure means no mutation. [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)

`MoveFileExW` also takes paths. `MOVEFILE_COPY_ALLOWED` permits cross-volume copy/delete, and can report success while retaining the source after deletion fails. Its write-through wording explicitly covers flushing a copy/delete move. Exclude copy/reboot modes from any transaction candidate, and do not infer compare-and-replace or directory-journal durability from this flag. [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)

CPython's reviewed 3.11 and 3.14 `internal_rename` uses `MoveFileExW`; `os.replace` selects `MOVEFILE_REPLACE_EXISTING`. Directory-descriptor arguments are rejected where `renameat` is unavailable. Thus switching to `os.replace` on Windows does not preserve POSIX parent-descriptor safety. These are branch-source observations, not immutable release pins. [CPython 3.11 source](https://raw.githubusercontent.com/python/cpython/refs/heads/3.11/Modules/posixmodule.c), [CPython 3.14 source](https://raw.githubusercontent.com/python/cpython/refs/heads/3.14/Modules/posixmodule.c)

`RemoveDirectoryW` removes an empty directory by path, but removes a junction itself even if its target is nonempty. That behavior avoids deleting the junction target; it does not authenticate which parent/name is removed under a race. Never use recursive path deletion to compensate for failed handle deletion. [RemoveDirectoryW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-removedirectoryw)

Transactional NTFS is not an acceptable dependency shortcut: Microsoft recommends alternatives and warns it may be unavailable in future versions. [Alternatives to TxF](https://learn.microsoft.com/en-us/windows/win32/fileio/deprecation-of-txf)

## Native NT alternative and compatibility risk

`NtCreateFile` is documented as a user-mode equivalent of `ZwCreateFile`. Its `OBJECT_ATTRIBUTES.RootDirectory` supports relative open/create; it can create directories, enforce directory/non-directory type, and open the reparse object itself. This addresses the missing Win32 rooted child-open/create primitive in principle. [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile)

`OBJECT_ATTRIBUTES.OBJ_DONT_REPARSE` documents failure with `STATUS_REPARSE_POINT_ENCOUNTERED` when parsing encounters a reparse point. It differs from opening the reparse object for inspection. Prefer single child components from retained parents and inspect every successful handle. The user-mode `NtCreateFile` page narrows some attribute/option wording compared with the object/driver contracts; exact supported combinations remain a native experiment requirement. [OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes)

This would still rely on Native NT APIs. Microsoft expressly describes Winternl functions/structures as internal and subject to change, recommends public equivalents, and notes that dynamic lookup cannot detect every signature change. Treat this as a visible compatibility decision with build/filesystem capability gates and fail-closed behavior. A documented driver routine is not automatically a stable application API contract. [Calling Internal APIs](https://learn.microsoft.com/en-us/windows/win32/devnotes/calling-internal-apis), [Native API libraries and headers](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/libraries-and-headers)

## Process death, journal authenticity, and preservation

M6 implementation evaluation, 2026-09-30: a fresh fetch of the user-mode `NtCreateFile`, `OBJECT_ATTRIBUTES`, and driver rename contracts confirmed the rooted-name route but not a complete safe composition. In particular, the user-mode page permits only zero or `OBJ_CASE_INSENSITIVE` in its object-attribute wording, while the object structure documents `OBJ_DONT_REPARSE`; its `FILE_DIRECTORY_FILE` compatibility list omits `FILE_OPEN_REPARSE_POINT`. This is not proof those flags cannot work, but it prevents treating the combined behavior as established solely from these pages. A native experiment must verify the exact combinations, single-child traversal after concurrent parent reparse changes, retained-target sharing during replacement, and reopened journal namespace after death. No native runner or verified ABI boundary is available here. An unexecuted ctypes backend would add an unsupported mutation path, so none is enabled or described as implemented. Windows implementation itself remains unfinished, separately from missing CI execution. The unchanged production refusal is the only shipped mutation behavior.

Proposed recovery rule, not an API assurance: after death, reacquire the root and every parent without following reparse points before reading or mutating pending-operation state. Match journal identities, authenticated ownership, immutable operation/renderer/source digests, exact pre/postimage bytes, stage identities, and directory-creation state. An ID match alone is inadequate because IDs can be reused. Refuse changed parents, foreign occupants, malformed/tampered records, unexplained missing objects, and mismatched modes; retain the unresolved journal for diagnosis. Strict verification remains read-only and must not initiate recovery.

Handles and share guards disappear when the owning process terminates. Recovery therefore needs a new safe acquisition protocol, not reused handle integers or trusted saved paths. Prove kill points before/after stage creation, journal writes, each rename/delete, records publication, and journal cleanup. Journal removal must happen only after the operation is unambiguously reconciled.

`FlushFileBuffers` flushes a writable file handle; volume-wide flush requires administrative privileges. The reviewed documentation does not provide a general unprivileged directory-fsync transaction guarantee. Distinguish process-death recovery from power-loss durability, and state any unproved durability boundary. Do not introduce an elevation requirement to mask it. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)

Preserve all unrelated files and settings byte-for-byte. For managed existing files, define which metadata is owned before replacement: Windows read-only attributes, ACLs, named streams, encryption/compression, and Unix executable intent are not interchangeable. Never clear attributes or chmod a hard-linked/reparse target through a path to make a rename succeed. Preserve foreign metadata or refuse when it cannot be preserved under the approved contract.

## Python, Windows, and path boundaries

- Python 3.11, 3.12, and 3.13 documentation lists Windows 8.1+; 3.14 lists Windows 10+. The installer plan requires Python 3.11+, but that language floor does not establish a safe backend or client-OS support. Require exact Windows 10/11 build and Server runner-image evidence separately. [Python 3.11 Windows](https://docs.python.org/3.11/using/windows.html), [3.12](https://docs.python.org/3.12/using/windows.html), [3.13](https://docs.python.org/3.13/using/windows.html), [3.14](https://docs.python.org/3.14/using/windows.html)
- Python's Windows chmod only controls read-only status. Python 3.13 added Windows descriptor/follow-symlink chmod support and special handling of mkdir mode `0o700`; these do not provide Unix mode parity. Check `os.supports_*` at runtime instead of inferring capabilities from function signatures. Python's no-follow stat covers name-surrogate reparse points, not a general reparse-refusal transaction. [Python 3.11 os](https://docs.python.org/3.11/library/os.html), [Python 3.14 os](https://docs.python.org/3.14/library/os.html)
- `ctypes` can call Windows DLLs using the proper calling convention and explicit argument/result types; `use_last_error` provides error capture. Use pointer-sized handles and exact structure layout, noninheritable handles, and one clear owner per handle. These bindings require native ABI/error-path tests. [ctypes](https://docs.python.org/3.14/library/ctypes.html)
- `msvcrt` bridges OS handles and CRT descriptors; its bridge is inheritable by default unless `O_NOINHERIT` is passed, and text/binary translation is explicit. Hash and copy literal binary bytes, including intended LF/CRLF, through the retained object. Do not use text normalization to accept drift. [msvcrt](https://docs.python.org/3.14/library/msvcrt.html)
- Windows 10 version 1607+ long-path behavior requires both process manifest opt-in and OS configuration, or applicable Unicode extended paths. Extended prefixes change path parsing. Test supported behavior without changing real registry settings. Reject traversal, drive-relative/device/stream names, reserved names including extension variants, trailing dot/space, and case collisions before interpreting paths. [Long-path rules](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation), [Naming rules](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)
- Junctions can cross local volumes and are implemented through reparse points. A junction beneath an otherwise legitimate target is still a refusal case. Do not substitute resolved paths or `realpath` followed by mutation for retained-parent acquisition. [Hard links and junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)

## Required native experiments before changing the gate

These are recommended boundaries, not completed tests or authorization to provision machines. Use only uniquely created disposable source, Git target, and external sentinel roots. No installs, real-home mutations, remote execution, or unsupported support claims occurred during this research.

1. Prove handle ABI, errors, same-volume parent-relative create/open/rename, and exact no-replace behavior on native Windows with Python 3.11 and 3.14. Add 3.12/3.13 coverage for the chmod/metadata boundary. Record architecture, OS build, filesystem, interpreter patch, Git, PowerShell, and runner image. Server CI is Server evidence; separately establish any advertised Windows 10/11 behavior.
2. Run the public installer subprocess with real Git repositories and commits through install, repeated install, preview, update, restoration, pruning, status/check, wrapper forwarding, and ownership/adoption cases. Assert exits, distinct streams, complete target fingerprints, literal independent hashes, and unchanged unrelated bytes/attributes. Existing POSIX-only skips cannot count as Windows equivalents.
3. Use synchronized competing processes at observable filesystem boundaries. Attempt parent rename/swap, junction insertion/retarget, leaf reparse creation, target rename/replacement, hard-link creation, competing writes, preexisting delete-access opens, and read-only/mapped/executing-file failures. Place sentinels outside the target and prove they never change. The installer must refuse or complete safely without a path fallback.
4. Terminate the process at each journal/publish boundary, then rerun the public authorized recovery operation. Repeat after replacing a parent, stage, managed leaf, or records directory with a foreign regular object, junction, or hard link. Assert ambiguous recovery performs no foreign mutation and strict verification performs no recovery writes.
5. Commit and clone payloads using real Git with `core.autocrlf=true` and false, then run strict verification before repair/acquisition. Assert literal LF/CRLF and binary hashes, narrow owned attributes, Git index preservation, long Unicode/space paths, reserved/case names, relocation, and installed launcher execution. macOS PowerShell, cross-compilation, mocks, and a green unsupported-gate test are not native mutation proof.

UNVERIFIED: a complete stable Win32-only component-acquisition/create protocol; exact `FileRenameInfoEx` minimum-build/flag/ABI behavior across the intended matrix; checked-existing-target replacement matching M3's preimage/identity and postimage boundary; protection against reparse/metadata mutation through already-open or attribute-only handles; hard-link races and exact-link deletion semantics; safe journal namespace reacquisition after death; directory metadata durability. Atomic conditional-ID replacement is additionally undocumented and must not be claimed, but is not a new M3 acceptance condition. Keep Windows mutation unavailable until the equivalent composition is resolved and tested without weakening M3 guarantees.
