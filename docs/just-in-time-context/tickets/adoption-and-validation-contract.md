## Question

How will the reusable system be adopted and verified in this repository before use across the user's other repositories?

Define installation and repository configuration boundaries, compatibility with existing instructions and source ingestion, migration and rollback expectations, and provider-specific proof requirements. Choose representative pilot tasks and the evidence required to declare the specification ready for implementation. This ticket specifies adoption and verification; it does not perform migration or implementation.

Use [Lifecycle Guarantees](lifecycle-guarantees.md) to select deployed-version and mode certification for Codex desktop and the three CLIs, including fresh interactive, resume/compaction, noninteractive CLI, and supported child paths. Verify actual stage execution, normal and incomplete outcomes, recovery, and any automatic fallback. Do not infer desktop parity, child inheritance, or support from configuration alone. Both VS Code harnesses remain outside the first version.

Apply [Context Organization and Skill Boundary](context-organization-and-skill-boundary.md): specify the agent-brain bundle, Python/dependency and launcher requirements, adapter distribution, native registrations, and concrete metadata/stage schemas. Consumers need no hooks/families or source generator. Exercise repositories without hooks, unrelated existing hooks, existing KB layouts, and protected whole-artifact mappings. Preserve compatible existing skill entries and one source-ingestion pass. Validate explicit invocation context, side-effect-free help, standalone informational recall, actionable nonzero learn/dream errors before mutation, clean machine output, and actual semantic outcomes. Certify foreground execution without assuming an independent model runner or reliable desktop attachment. Report total observable provider task usage/credits and stage boundaries separately from delivered-guidance measurements, disclosing missing data and adding no new cost threshold.

Apply [Maintenance Scheduling and Pruning](maintenance-scheduling-and-pruning.md): specify schedule initialization and configuration for the seven-calendar-day default, concrete routine batch limits, and observable review coverage. Choose batch limits against the accepted token and timing targets. Validate coalesced missed intervals, eligible-event foreground execution, progress through quiet areas, scoped no-change, and cycle-clock reset only after verified complete coverage. Test 30-day operational cleanup while preserving pending work, unresolved candidates, required evidence, and reversible history. Include routine dream work in longitudinal paired workloads and observable task usage; batching must not hide its cost.

Apply [Failure and Concurrency Contract](failure-and-concurrency-contract.md): specify worktree-local SQLite prerequisites and durable settings, invocation identities and renewable lifetimes, ownership generations, obligation/input-generation schemas, and journaled publication records. Select concrete bounded waits while preserving the default budget of three total attempts and at most one semantic repair, with tighter provider limits taking precedence. Certify explicit handles, stale-owner rejection, duplicate/reentrant events, compatibility/source-ingestion joins, and parent/child completion. Validate shared external read-only mappings and the first-version exclusion of shared writable roots across worktrees.

Choose predetermined cases for interruption before/during/after publication, changed base inputs, unrelated edits, partial references, and safe completion or restoration from recorded versions. Verify managed retrieval sees coherent guidance or exposes affected gaps; do not claim filesystem-wide atomicity from SQLite. Exercise missing/corrupt expected state, scoped no-change evidence, compaction/resume, stable IDs through moves/merges/retirement, cancellation without task restart, and next-event recovery. Test finite dream targets, invalidated review credits, later routine additions, full-cycle clock reset, and reference-aware retention with portable evidence/history. Include deterministic assertions and independent semantic review under Success Criteria. Count retries, repair, required learning, dream, and recovery in paired task timing, guidance delivery, and observable provider usage. These are planned certification cases, not tests executed by this decision ticket.
