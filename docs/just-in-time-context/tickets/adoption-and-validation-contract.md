## Question

How will the reusable system be adopted and verified in this repository before use across the user's other repositories?

Define installation and repository configuration boundaries, compatibility with existing instructions and source ingestion, migration and rollback expectations, and provider-specific proof requirements. Choose representative pilot tasks and the evidence required to declare the specification ready for implementation. This ticket specifies adoption and verification; it does not perform migration or implementation.

Use [Lifecycle Guarantees](lifecycle-guarantees.md) to select deployed-version and mode certification for Codex desktop and the three CLIs, including fresh interactive, resume/compaction, noninteractive CLI, and supported child paths. Verify actual stage execution, normal and incomplete outcomes, recovery, and any automatic fallback. Do not infer desktop parity, child inheritance, or support from configuration alone. Both VS Code harnesses remain outside the first version.

Apply [Context Organization and Skill Boundary](context-organization-and-skill-boundary.md): specify the agent-brain bundle, Python/dependency and launcher requirements, adapter distribution, native registrations, and concrete metadata/stage schemas. Consumers need no hooks/families or source generator. Exercise repositories without hooks, unrelated existing hooks, existing KB layouts, and protected whole-artifact mappings. Preserve compatible existing skill entries and one source-ingestion pass. Validate explicit invocation context, side-effect-free help, standalone informational recall, actionable nonzero learn/dream errors before mutation, clean machine output, and actual semantic outcomes. Certify foreground execution without assuming an independent model runner or reliable desktop attachment. Report total observable provider task usage/credits and stage boundaries separately from delivered-guidance measurements, disclosing missing data and adding no new cost threshold.
