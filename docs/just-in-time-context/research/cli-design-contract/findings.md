# CLI design contract: factual extraction

Scope: raw text sources and accepted ticket language only. The source principles below are recommendations unless marked as an accepted contract. This is not an architecture decision. Updated after the final Adoption and Validation Contract confirmation on 2026-09-30; that resolution owns the selected product behavior.

## Checklist for later CLI acceptance tests

- **Help, discovery, version, flags.** Sources recommend top-level and command help, familiar `-h`/`--help`, examples, expressive and stable flags, and visible commands when a multi-command CLI is invoked bare. The closed contract requires top-level and per-command help with purpose, inputs, effects, common examples, and cooperative-execution requirements; `-h` and `--help` work before invocation validation; bare invocation lists commands and performs no work. Adoption Q7 also requires help on all commands and explicit JSON mode. A version query is recommended by 12 Factor; Adoption Q17 requires side-effect-free version reporting. Test bare/help/version paths for zero work/mutation and assert help discoverability. The exact version flag is an ordinary CLI implementation detail constrained by these requirements. [12 Factor, lines 21-52, 76-88, 216-234](../../../../.agents/sources/12-factor-cli-apps.md#L21); [CLI Design, lines 24-30, 56-58](../../../../.agents/sources/cli-design-guidelines.md#L24); [clig.dev, lines 293-356, 731-798](../../../../.agents/sources/clig-dev.md#L293); [closed CLI contract, section `CLI help and automation` (currently lines 86-96)](../../tickets/context-organization-and-skill-boundary.md#cli-help-and-automation); [Adoption Q7, `Public CLI shape` (currently lines 41-42)](../../tickets/adoption-and-validation-contract.md#runtime-cli-and-metadata)
- **Machine streams and JSON.** Sources favor composable text, machine-readable formats, and keeping logs/progress off structured output. Their stream advice differs: 12 Factor places warnings and errors on stderr (12 Factor, 92-107); CLI Design says information/warnings on stdout and errors on stderr (CLI Design, 60-66); clig.dev recommends human-first output, optional JSON, and terse success output (clig.dev, 533-576). The closed contract resolves this for this product: structured results on stdout, diagnostics and progress on stderr, explicit JSON mode, and a warning cannot stand in for a failed required stage (context-organization, 96). Test that JSON stdout parses alone while diagnostics/progress are on stderr, and required failure is nonzero and represented in the machine result. [12 Factor, lines 92-107](../../../../.agents/sources/12-factor-cli-apps.md#L92); [CLI Design, lines 60-66](../../../../.agents/sources/cli-design-guidelines.md#L60); [clig.dev, lines 533-576](../../../../.agents/sources/clig-dev.md#L533); [closed CLI contract, `CLI help and automation` (currently lines 86-96)](../../tickets/context-organization-and-skill-boundary.md#cli-help-and-automation)
- **TTY, color, and automation.** clig.dev recommends using TTY detection, disabling color when the relevant stream is not a TTY, `NO_COLOR`, `TERM=dumb`, or `--no-color`, and avoiding animation for redirected output (clig.dev, 535-540, 639-656). Both 12 Factor and CLI Design recommend optional prompts for interactive guidance/critical confirmations but explicitly say never to require prompts for scripts (12 Factor, 149-159; CLI Design, 32-40). The accepted contract forbids hidden prompts in noninteractive use and terminal-only presentation when output is piped; automatic stages are driven by enabled integrations. Test redirected stdout/stderr and non-TTY execution for plain deterministic output, and test automated setup/apply and stages do not wait on input. Never make a prompt mandatory for automatic stages. [closed CLI contract, `CLI help and automation` (currently lines 86-96)](../../tickets/context-organization-and-skill-boundary.md#cli-help-and-automation)
- **File input and output.** clig.dev recommends accepting `-` for stdin/stdout when a command already consumes/produces files, and avoiding secrets in flags in favor of files or stdin (lines 834-871). Adoption Q10 selects an invocation file and JSON input from a file or `--input -` for stdin. Test those accepted forms, including noninteractive stream behavior. Do not infer that secret flags are needed. [clig.dev, lines 834-871](../../../../.agents/sources/clig-dev.md#L834)
- **Errors and exit status.** Sources recommend actionable errors, early input validation, nonzero exit on errors, and next-step guidance; CLI Design explicitly says nonzero iff error (lines 60-66), while clig.dev asks for human-focused error rewriting (lines 704-730, 916-921). Accepted behavior is more specific: learn/dream without valid integration-issued context must fail actionably with nonzero status before mutation; all errors explain cause and next action; stage outcomes remain explicit and incomplete cannot be converted to success by a warning or agent claim (context-organization, 78-84, 92-96). Test missing, mismatched, and stale context; assert exact lack of mutation and nonzero exit. Adoption Q10/Q15 specify the machine records; Q11 selects exit codes 0, 1, 2, and 130 while distinguishing operation success from semantic completion. [CLI Design, lines 60-66](../../../../.agents/sources/cli-design-guidelines.md#L60); [clig.dev, lines 704-730 and 916-921](../../../../.agents/sources/clig-dev.md#L704); [closed CLI contract, `Cooperative invocation and outcomes` and `CLI help and automation` (currently lines 76-96)](../../tickets/context-organization-and-skill-boundary.md#cooperative-invocation-and-outcomes)
- **Cancellation, retries, recovery, and progress.** clig.dev recommends responsive feedback, progress on long work, configured/default timeouts, recoverability, crash-only behavior, and prompt Ctrl-C handling (lines 916-982, 1031-1049). The accepted failure/adoption contracts own cancellation, retries, and recovery details: three total attempts by default, at most one semantic repair, tighter provider limits win; interruption preserves pending work and next-event recovery; cancellation does not restart a task (adoption, 18-22). CLI output should expose progress and incomplete status without contaminating stdout; test interruption at agreed lifecycle points, bounded retry/repair counts, durable pending state, prompt cancellation, and later recovery. Adoption Q11 allows up to two seconds of safe deterministic reconciliation and an immediate second-interrupt exit. Progress rendering remains an ordinary CLI implementation detail constrained by stderr separation, TTY behavior, and responsive feedback. [clig.dev, lines 916-982 and 1031-1049](../../../../.agents/sources/clig-dev.md#L916); [adoption contract, lines 18-22](../../tickets/adoption-and-validation-contract.md#L18)
- **Configuration, precedence, paths, and side effects.** Sources recommend flags for per-invocation choices, project config for shared stable project behavior, user config/environment for machine-local preferences, XDG locations, and explicit consent before editing another program's config. clig.dev's generic precedence is flags > process environment > project > user > system, while 12 Factor recommends XDG (`~/.config`, `~/.local/share`, platform cache dirs) (clig.dev, 1051-1107; 1126-1167; 12 Factor, 236-240). These are generic recommendations, not the accepted path contract. Accepted choices require worktree-local SQLite/state and durable settings, repo/worktree-isolated knowledge/evidence/obligations, and the explicit setup plan/apply flow. Plain setup reports a plan; `setup --json` emits a machine-readable plan; `setup --apply --plan PATH` applies a still-valid reviewed plan. Doctor/status are read-only and do not create state or call a model. Apply validates, preserves unrelated configuration, records reversible managed changes, enables only certified provider paths, and is idempotent (adoption, 32, 41; context-organization, 44, 106-114). Adoption Q9/Q15 select concrete configuration, metadata, and checkpoint records. Test their paths and precedence, read-only commands against missing state, setup plan non-mutation, reviewed plan application, preservation/rollback, and repeat setup idempotence. Do not replace accepted repo-scoped paths with XDG defaults or treat generic precedence as settled where contracts do not specify it. [clig.dev config/environment, lines 1051-1107 and 1126-1167](../../../../.agents/sources/clig-dev.md#L1051); [12 Factor XDG, lines 236-240](../../../../.agents/sources/12-factor-cli-apps.md#L236); [adoption contract, lines 32, 41](../../tickets/adoption-and-validation-contract.md#L32); [closed contract, `Authoritative knowledge and repository boundaries` and `Distribution and provider integration` (currently lines 38-44 and 104-114)](../../tickets/context-organization-and-skill-boundary.md#authoritative-knowledge-and-repository-boundaries)
- **Explicit side effects and discovery.** Sources recommend that actions be transparent and implicit external reads/writes/network be explicit (CLI Design, 50-54; clig.dev, 576-620, 1090-1107). Accepted contract says help/bare invocation are side-effect free; setup/doctor do not call a model; learn/dream use the active foreground provider and never silently launch another model; installation and repository activation are separate; setup must show exact planned registrations and preserve unrelated hooks (adoption, 32; context-organization, 80-84, 90-96, 106-114). Test filesystem/provider call traces for every command, and ensure missing context never triggers fallback model work. The source's XDG and consent guidance applies as a recommendation; Adoption Q9 binds enabled stages to configuration identity/revision, preserves authority over presentation overrides, and requires base revisions and stale-plan rejection. [CLI Design, lines 50-54](../../../../.agents/sources/cli-design-guidelines.md#L50); [clig.dev, lines 576-620 and 1090-1107](../../../../.agents/sources/clig-dev.md#L576); [adoption contract, line 32](../../tickets/adoption-and-validation-contract.md#L32); [closed contract, `Cooperative invocation and outcomes`, `CLI help and automation`, and `Distribution and provider integration` (currently lines 76-114)](../../tickets/context-organization-and-skill-boundary.md#cooperative-invocation-and-outcomes)

## Source conflicts and conditions to preserve

1. **Warnings and streams:** 12 Factor and CLI Design give opposing warning stream rules. The already accepted contract selects structured results on stdout and diagnostics/progress on stderr. Follow that contract and test machine cleanliness.
2. **Prompting:** CLI sources recommend optional prompts only when useful and interactive; none require them. Accepted setup requires explicit plan/apply, while automatic stages use the foreground agent. Prompts must never become a hidden prerequisite for automatic stage execution.
3. **Config placement/precedence:** XDG paths and generic flag/env/project/user/system precedence are recommendations. They do not override worktree/repository isolation, durable repo configuration, managed-registration preservation, or active-agent mutation checks. Adoption Q9 selects precedence constraints and configuration identity/revision binding.
4. **File input:** `-` is conditional on file-shaped input/output. Adoption Q10 explicitly accepts file input and `--input -`; validate both transports.
5. **Informational recall and machine output:** standalone informational recall is permitted, but displaying a map is not delivery to an agent. Test interactive rendering and JSON representation separately from required agent-context delivery (closed CLI contract `Cooperative invocation and outcomes`, currently line 82; Adoption question, currently line 16).

## Validation traceability

The later CLI acceptance suite should cover: (a) bare invocation and all help aliases, zero side effects; (b) JSON stdout parseability and stderr-only diagnostics/progress; (c) TTY versus redirected color/animation; (d) noninteractive commands with no prompt; (e) setup plan, apply, review freshness, idempotence, and unrelated-config preservation; (f) doctor/status read-only behavior with missing state; (g) invocation-context failures before mutation; (h) successful, no-change, incomplete, and failed semantic outcomes with correct exit status; (i) cancellation, bounded retries/repair, pending work, and next-event recovery; (j) standalone recall versus verified agent delivery. The raw CLI sources do not independently choose product details. The final adoption resolution owns file/stdin transport, configuration constraints, version-only acceptance, exit codes, schemas/checkpoints, and signal grace behavior. Exact version-flag spelling and progress rendering remain routine implementation details within those accepted constraints.
