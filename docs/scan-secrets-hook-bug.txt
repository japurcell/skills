Summary

The  scan-secrets  hook blocks every tested tool request before execution because candidate content exceeds its read limit.

Current decisive error:

Denied by preToolUse hook: scan-secrets blocked: tool scan; scan incomplete; potential secrets could not be checked. file_bytes_limit/candidate_read: candidate byte limit exceeded (measured 2030848 bytes, limit 1048576 bytes). Check pending file sizes and unintended generated artifacts.

Measured candidate size:

2,030,848 bytes

Configured limit:

1,048,576 bytes

Excess:

982,272 bytes

The candidate set is about 1.94 MiB, while the limit is 1 MiB.

This is an incomplete scan, not a confirmed secret finding.

User impact

The hook currently prevents normal repository work, including read-only and metadata-only operations.

Confirmed blocked operations include:

•  git status --short 
• Bounded file reads
• Repository searches
• Bash inspection commands
• Agent dispatch
• Skill loading
• Copilot CLI documentation retrieval
• Extension reload
•  apply_patch  file creation

Because  git status --short  is blocked, the agent cannot identify which pending files caused the candidate set to exceed the limit.

This creates a deadlock:

1. Hook says to inspect pending file sizes.
2. Hook blocks the metadata-only command needed to identify pending files.
3. Agent cannot reduce or diagnose the candidate set safely.

Likely design defect

Current evidence indicates that the hook collects or reads candidate content before deciding whether the requested tool operation needs content inspection.

That causes metadata-only requests such as:

git status --short

to fail because unrelated pending content exceeds the aggregate byte limit.

A robust design should separate:

1. Tool-request inspection
• Check whether the requested operation itself exposes or transmits content.
2. Candidate discovery
• Identify paths and sizes without loading file contents.
3. Content scanning
• Read and scan only content the operation will expose or mutate.
4. Large-input handling
• Scan individual files or bounded chunks.
5. Policy result
• Distinguish detected secrets from scanner inability.

Required behavioral fixes

1. Permit metadata-only operations

Operations that return paths, statuses, hashes, or sizes should not require reading all candidate contents.

Examples:

git status --short
git diff --name-only
git diff --stat
git ls-files
git ls-files -s
git rev-parse HEAD
git log --oneline

The hook may inspect command arguments, but it should not scan unrelated file bodies.

2. Report candidate paths and sizes

When a byte limit is exceeded, return enough sanitized metadata to diagnose it:

candidate set: 2,030,848 bytes across 9 files
largest candidates:
- Frontend/.../impl-comp-scores-report.component.html: N bytes
- Frontend/.../eff-corr-adapt-report.component.html: N bytes
...

Do not include file content in this diagnostic.

3. Scan per file or in bounded chunks

A 1 MiB aggregate cap makes ordinary multi-file work impossible.

Safer alternatives:

• Per-file byte limit
• Streaming scanner
• Fixed-size chunks with overlap
• Batched candidate scanning
• Scan only changed ranges for diff-aware operations

The scanner must preserve detection across chunk boundaries where relevant.

4. Distinguish outcomes

Use different result categories:

allowed
blocked_secret_detected
blocked_scan_incomplete
blocked_input_too_large
blocked_scanner_unavailable
blocked_scanner_timeout
blocked_scanner_error

Current wording starts with  scan-secrets blocked , which can be mistaken for a confirmed secret finding.

5. Provide sanitized underlying diagnostics

Include:

• Hook source/version
• Scanner name/version
• Candidate count
• Measured bytes
• Configured limit
• Phase that failed
• Sanitized exception class/message
• Scanner exit status
• Timeout duration, if relevant
• Reload requirement

Never print discovered secret values.

6. Avoid self-repair deadlock

At minimum, allow these when scanning infrastructure is broken:

• Hook/extension reload
• Read-only hook diagnostics
• Hook version query
• Metadata-only repository inspection
• Reading the hook’s own sanitized logs

This must not become a general scan bypass. Scope it to operations that cannot disclose candidate contents.

7. Confirm updated code is active

Expose a hook identity in diagnostics:

hook: scan-secrets
version: <version>
source: <sanitized path or extension ID>
config hash: <hash>
loaded at: <timestamp>

This would explain why two reported updates produced identical behavior.

Security requirements

Do not fix this by:

• Disabling secret scanning
• Allowing all requests after incomplete scans
• Raising the limit without understanding memory/runtime effects
• Treating scanner errors as successful scans
• Logging secret values
• Skipping scanning for content-returning tools
• Trusting filename extensions as proof that content is safe

The fix should fail closed for actual content exposure while remaining usable for metadata and diagnostics.

Acceptance criteria

The issue is fixed when all are true:

1.  rtk git status --short  succeeds in the current worktree.
2. Current changed paths and sizes can be inspected without reading their contents.
3. Benign content reads over 1 MiB can be scanned safely in chunks or batches.
4. A secret-containing fixture remains blocked.
5. Scanner failure remains fail-closed for content-returning or content-writing operations.
6. Hook reload/version state is observable.
7. Diagnostics identify candidate count, bytes, phase, and sanitized cause.
8. No secret values appear in logs or errors.
9. Tool requests rejected by the hook remain atomic.
10. The agent can inspect remaining lint diagnostics and update the ExecPlan afterward.
