# Subagent Model Router

Choose the lowest-cost dispatchable configuration at the task's capability floor. Use a higher tier when no capable configuration at the floor is available.

## Dispatch contract

A dispatchable route specifies one tier and an exact model-and-effort pair accepted by the dispatch interface. Defaults, inheritance, placeholders, ranges, and conditional values are not exact values. If either value cannot be confirmed, return `dispatchable: false`; this includes interfaces that expose no effort value.

Apply both returned values explicitly when delegating. Never dispatch a `dispatchable: false` route.

## Constraints and independence

Honor explicit user model or effort constraints already in scope, then apply this skill's capability and cost rules. Missing constraints mean `none`, not ambiguity. Persistent configuration does not override routing. Use configured defaults only when explicitly requested by the user; resolve them to exact values that satisfy the floor.

Select independently without asking the user to choose, approve, confirm, or restate a model, effort, or default. Request only essential missing task facts. If constraints prevent meeting the floor, return `dispatchable: false`.

A routing attempt uses the task facts, runtime capabilities, and constraints in scope when it begins. Solicited preferences cannot retroactively justify it; changed constraints require a fresh attempt.

## Capability tiers

- **Fast**: bounded, low-risk work with clear requirements and straightforward verification, including exploration and mechanical or repetitive tasks.
- **Standard**: substantive judgment, cross-file behavioral reasoning, interactive or agentic coding, deep debugging, or ordinary substantive review.
- **Premium**: security-sensitive or high-stakes work, difficult long-horizon reasoning, complex large-codebase work, prior important review misses, repeated reasoning failures, or user-requested best quality.

Tiers classify task requirements and model-and-effort configurations. Price, latency, provider, model family, and recency do not establish capability. File count, language mix, platform scope, and test count alone do not raise the floor. Prefer Fast for bounded low-risk work unless a concrete requirement establishes a higher floor.

## Routing procedure

1. Gather objective, work class, stakes, security sensitivity, ambiguity, reasoning difficulty, affected behavior, context size, review history, verification approach, existing constraints (or `none`), and exact runtime model/effort capabilities.
2. Determine the lowest permitted tier. For code/PR review and audits, load [review-routing.md](reference/review-routing.md). Otherwise use the tier definitions above.
3. For failures, changed risk, or context-fit problems, load [escalation-policy.md](reference/escalation-policy.md).
4. Load [model-catalog.md](reference/model-catalog.md) for candidate configurations. Confirm runtime acceptance, context capacity, and applicable restrictions. Exclude models scheduled to retire before the subtask runs.
5. Apply the availability rule below. Load [pricing.md](reference/pricing.md) and compare all eligible candidates at applicable context and cache rates. Task defaults are provisional starting points, not preference orders.
6. Return one exact route and the lowest-cost eligible alternative at its selected tier, if any.

Reuse a route only when the facts gathered in step 1 are materially unchanged.

### Availability

Preserve the capability floor. First seek a capable configuration at that tier, including for large context. If none is available, select the lowest-cost capable higher-tier configuration permitted by user constraints. If none qualifies, return `dispatchable: false`.

When a selected configuration becomes unavailable, apply the same rule starting at its selected tier. A higher-tier selection caused only by availability does not raise the task's capability floor. Report the selected tier and explain the original floor and availability-driven increase.

### Evidence

Use evidence in this order: task-specific local evaluation, demonstrated success on materially similar work, platform/provider guidance, then provisional catalog defaults.

Prefer the latest version unless an older version has lower expected completion cost or demonstrated better task fit.

## Output

Return the complete structured decision; the caller controls storage and presentation. If capability is based on provisional guidance, explicitly label it provisional and state the required verification in `reason`.

```yaml
dispatchable: <true|false>
tier: <Fast|Standard|Premium>
model: <exact dispatch value or unresolved>
reasoning_effort: <exact dispatch value or unresolved>
reason: <task fit, capability floor, cost assumptions, uncertainty, and any availability-driven increase>
escalation_trigger: <concrete trigger or none>
fallback:
  model: <exact same-tier dispatch value>
  reasoning_effort: <exact dispatch value>
```

Use `fallback: none` only when no other exact same-tier configuration meets task requirements, runtime capabilities, and user constraints. Explain what excludes alternatives. For a failed selection, report the required floor and unresolved values with the reason dispatch is blocked.

A dispatchable result is a decision, not a request for approval or pending confirmation.

# Escalation Policy

This file owns escalation policy. For review work, first establish the floor using [`review-routing.md`](review-routing.md).

## Escalation triggers

Escalate when:

- verification reveals a reasoning or correctness gap after instructions, inputs, and environment are checked
- material constraints are repeatedly missed
- reasoning is inadequate for the demonstrated complexity
- required context cannot fit in a suitable same-tier configuration
- new task evidence raises the capability floor
- the user requests a stronger tier or best quality
- stakes, ambiguity, or security sensitivity materially increase
- repeated failures demonstrate inadequate capability

For non-review work, a prior important miss on materially similar work normally raises the route one tier. Move directly to Premium when the miss establishes high stakes, security sensitivity, or unusually difficult reasoning.

For review work, follow the prior-miss rule in [`review-routing.md`](review-routing.md).

## Diagnose first

Before escalating, check:

- instructions and inputs
- files and context
- dependencies and permissions
- tools and environment
- model and effort availability
- whether the task should be split
- whether verification is adequate

A failing test ordinarily indicates a code or environment issue, not a model-capability issue.

Do not escalate merely because:

- tests, lint, builds, formatting, scripts, search, or file enumeration are being executed mechanically
- the work is deterministic and directly verifiable
- several files or languages are involved
- a newer or more expensive model exists
- an ordinary correction is required
- the preferred model is unavailable but a capable same-tier alternative exists

Authoring, reviewing, or diagnosing tests, scripts, or build logic may still require a higher tier when substantial judgment or risk is involved.

## Escalation path

| Current tier | Next action |
| --- | --- |
| Fast | Standard |
| Standard | Premium |
| Premium | Better-fitting Premium configuration, more context, task decomposition, stronger verification, or human review |

Move directly to the tier required by a changed capability floor; stepwise escalation is not mandatory.

Before escalating the capability floor, confirm that the change addresses a specific capability, context, or risk gap.

For unavailable configurations, apply [the availability rule](../SKILL.md#availability).

# Routing Patterns

Non-authoritative examples. Follow [SKILL.md](../SKILL.md), [review-routing.md](review-routing.md), and [escalation-policy.md](escalation-policy.md) if an example conflicts.

## Boundary cases

| Situation | Decision |
| --- | --- |
| Mechanical rename across many files, straightforward verification | Fast |
| Substantive one-file review | At least Standard |
| Bounded feature review | Standard; budget-review starting candidate |
| Cross-component behavioral review | Standard; general-work starting candidate |
| Review authentication or subtle concurrency/cache-consistency risk | Premium |
| Similar review previously missed an important issue | Premium floor |
| Non-review task previously missed an important constraint | Apply general escalation, normally one tier |
| Tests fail or a dependency is missing | Diagnose code/environment before capability escalation |
| Preferred configuration unavailable | Apply the availability rule; never go below the floor |
| Scope, risk, context, constraints, or runtime capabilities change | Route again |
| Premium work still fails | Better-fitting Premium configuration, decomposition, stronger verification, or human review |

## Cost rule

Estimate:

```text
expected_cost =
    uncached_input
  + cached_input
  + cache_write
  + output
  + retries
  + verification
```

Also consider tool use and additional workers. Use a dominant token rate as a shortcut only when other factors are comparable.

Assume uncached input unless cache reuse is confirmed for the platform, model, and request shape. A higher token rate may cost less overall when it reduces retries, token volume, or verification.

| Token shape | Compare primarily |
| --- | --- |
| Large input, short output | Input and cached-input rates |
| Large output | Output rate |
| Reused context | Cache write plus confirmed cached-input savings |
| Uncertain task fit | Retries and verification |
| Input crossing a threshold | The matching long-context row |

# Review Routing

This file owns capability floors for code review, PR review, change auditing, and security review.

## Routing order

1. Use **Premium** if any Premium condition below applies.
2. Otherwise, use **Fast** only for mechanical or non-semantic changes with straightforward verification.
3. Otherwise, use **Standard**.
4. Apply [`escalation-policy.md`](escalation-policy.md) if verification reveals a reasoning gap or risk increases.

## Floors

### Fast

Examples:

- whitespace or formatting
- non-behavioral comments or documentation
- reproducible generated output
- mechanical renames or transformations

File count does not determine the floor. A mechanical multi-file change may remain Fast, while a substantive one-file change is at least Standard.

### Standard

Use for ordinary substantive review, including:

- features and bug fixes
- behavioral configuration
- tests or guard logic
- cross-file interactions
- meaningful refactoring
- ordinary correctness and maintainability analysis

Use the budget-review default for a bounded, clear-scope diff and the general-work default for broader behavioral or cross-component reasoning.

### Premium

Use for:

- security review or security-sensitive changes
- authentication, authorization, secrets, credentials, cryptography, or trust boundaries
- high-stakes correctness
- subtle concurrency, cache-consistency, or false-pass risk
- a prior important miss on materially similar review work
- repeated reasoning failures
- user-requested best-quality review
- unusually difficult review over a large or highly connected codebase

A prior important review miss establishes a Premium floor, not merely a one-tier suggestion.

## Fallback and verification

Apply [the availability rule](../SKILL.md#availability) without lowering the review floor.

Model selection does not replace verification. Use checks appropriate to the review, such as tracing affected behavior and callers, checking tests and failure paths, validating trust boundaries, reproducing generated output, running focused checks, or obtaining independent high-stakes review.
