# Bounded SDK registration metadata source

This qualification source asks only which Windows SDK 26100 uninstall registration DisplayVersion and product-code clues appear in the local HKLM 64-bit and 32-bit uninstall views. The clues do not authenticate an SDK, select tools, establish a build tuple, or release native execution. All three authority flags remain false.

The PowerShell collector emits schema 2 with `sdkRegistration` version 1. It opens the fixed uninstall root and immediate product children read-only with explicit view flags and `REG_OPTION_OPEN_LINK`, checks `SymbolicLinkValue` absence, and queries only `DisplayName`, then `DisplayVersion` and `Publisher` for exact SDK name matches. It makes two complete bounded passes and emits no partial records on failure. The fixed Reflection.Emit declarations target only `C:\Windows\System32\advapi32.dll` in the already trusted Windows PowerShell process. There is no compiler, installer, executable discovery, registry-provider inventory, or native query on non-Windows hosts.

The v2 validator is a separate closed route. Historical schema 1 validation remains exact. The inner metadata CLI uses strict v2 admission, so an old schema 1 record cannot pass as a new collector result. The coordinator owns the outer wrapper v2 admission, new source hashes, historical selection preservation, and full integrated gate. Source handback carries no native Root release. Pure PowerShell mock queries and source declaration inspection cannot establish the Windows ABI, protected DLL loading, actual link handling, or actual close behavior. Those require a separate Root native decision and observation.
