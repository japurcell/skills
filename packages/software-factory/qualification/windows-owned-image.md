## Boundary and mechanism

`windows-owned-image-probe.cpp` creates only its own new fixed native canary with `DEBUG_ONLY_THIS_PROCESS`, without `CREATE_SUSPENDED`. The creator thread requires the first event to be `CREATE_PROCESS_DEBUG_EVENT` for the held creation handles' PID and initial TID. It adds one explicit initial-thread suspension, requiring prior count zero. It duplicates the actual event `hFile`, closes that original file handle, queries `FileIdInfo`, hashes at most 16 MiB through each held file handle, and compares the actual image's volume/FileID and SHA256 with an independently held read-sharing expected image. The image and pin handles remain held through process exit and pipe closure.

Only a matching image permits `ContinueDebugEvent`. The explicit suspension must survive continuation. Detach uses only the exact created PID, checked against its continuously held live process handle. `CheckRemoteDebuggerPresent` must report false before one `ResumeThread`, whose prior count must be one. No existing-process attach, process memory/context access, remote threads, injection, Job Object, ETW, global process tracker, or arbitrary resume loop is used. Event process/thread handles are retired after detach if still valid and still the exact known event objects; exit-event processing otherwise uses the documented automatic closure. Actual final handle counts and every owned handle close are checked.

The DLL's `DllMain`, executable TLS callback, and earliest controlled `main` each mark an inherited shared mapping. `main` is the first controlled application entry, not a claim to precede the static CRT startup. Every marker also records whether permission was absent. The mapping and only stdin/stdout/stderr are selected in a restrictive inherited-handle list. No marker or output may appear at the created, suspended, validated, continued, or detached barriers. All three markers must arrive after release, with `IsDebuggerPresent` false. A separately created non-debug same-image canary must survive the target's cleanup and then be stopped through its own held creation handle.

This sequence composes documented primitives. Microsoft does not document an atomic guarantee for the whole suspend/continue/detach/resume sequence. Only the coordinator's real Windows native canary can establish this exact source/OS/compiler/profile observation. Portable tests, source inspection, and PowerShell parsing cannot establish it.

## Fixed native matrix and bounds

There are 34 closed cases: nine positive launches; three wrong-hash/different-file-object/different-image refusals; three file/ancestor/hardlink-alias replacement controls; six stops from creation through the one resume; nine explicit refusal seams before event/image-handle/duplicate/query/suspend/continue/detach/postcondition/resume; deadline, output-limit and crash controls; and debugger-owner-thread interruption.

Replacement controls use separate fresh qualification staging. The file pin remains open while a file, ancestor or hardlink alias rename is attempted. Only a fixed sharing/access denial, or replacement followed by actual FileID and digest mismatch refusal, is acceptable. The guard never treats path text as identity, and neither result qualifies the namespace. Moved or replaced owned staging files are retained privately, not rolled back across possibly changed names. Baseline binaries are never mutated.

The `fail-*` cases are intentional fail-closed seams before their named operation. They prove refusal ordering and cleanup from those phases, not that every possible Windows API failure has been independently induced. A genuine unexpected API result still refuses. Owner interruption ends the actual creating debugger thread with its first event pending and the default debugger kill policy intact; the observer retains the newly created process handle and requires its signaled exit with no markers. It does not prove outer-controller loss after successful detach.

The first event waits at most one second. Barriers observe 25 ms each. Normal target completion allows 1.5 seconds, the deadline control 500 ms, native output stops above 256 KiB, and final drained output must remain at most 1 MiB per pipe. Cleanup uses bounded owned-event draining (64 events, two seconds) and a further one-second signaled-process wait, with independent target/control attempts and no resume during cleanup. A complete case must finish within ten seconds, have EOF on both pipes, zero owned handle residue, no observed handle-count increase, and a conclusively stopped owned target/control. The Node driver caps each controller receipt at 64 KiB and twelve seconds. Missing exit, unknown stop, cap, unexpected phase/count/marker, missing compiler, or interruption produces no upload qualification. The waiting fixture has an eight-second self-deadline; that fallback does not establish observed cleanup after controller loss. Flooding writes can block if their pipe owner disappears, so detached owner-loss remains explicitly unqualified.

## Fixed failure visibility

The driver's stderr identifies only fixed phase/case/category/compiler fields, `tool=none|vswhere|compiler|linker` and a closed condition. Existing conditions remain accepted; the canary adds `nested-command-unavailable`, `unresolved-command-unavailable` and `command-probe-failure`. Optional module observations contain only `inbox/core=present|absent|unknown`, `autoload=all|qualified|none|unknown` and `direct=imported|not-imported|unknown`. Every field is revalidated immediately before formatting. A malformed field, extra key, unsupported cross-field combination or unknown case collapses to fixed unexpected output. Pin failures can name their current fixed case; host/build failures cannot. These observations are not a root-cause diagnosis or a successful qualification receipt.

The build catch selects its category from fixed stage variables, never exception text. Its complete diagnostic wire is one line: `OWNED_IMAGE_BUILD`, protocol `3`, category, code, source-kind, line, tool role and condition, separated by tabs. Older schemas or a missing role/condition are rejected rather than treated as current evidence. This diagnostic-only version change leaves the successful qualification receipt protocol, grammar and artifact guard exact. Build categories remain `host`, `path`, `existing-build`, `missing-msvc`, `tool-signature`, `compiler-version`, `source`, `compile`, `build-cap`, `source-changed`, `binary`, `report` and `unexpected`. Optional codes remain `C####` or `LNK####`, with a nonzero first digit. Source kinds remain `probe`, `shared`, `fixture`, `fixture-dll` or `none`; known source line numbers remain 1-4096. Linker or source-unknown diagnostics use `none`/0. Compiler fields are allowed only for the `compile` build category. Unknown or unprojectable compiler output becomes `none`/`none`/0.

A non-`none` tool role and rejection condition are valid only with `phase=build`, `case=none`, `category=tool-signature` and empty compiler fields. That signature category requires exactly `vswhere`, `compiler` or `linker` plus one of the closed non-`none` conditions; every other category requires both fields to be `none`. The build script assigns roles only at its existing verifier sites and clears the role/condition on success. No executable name, path, issuer, signer, raw certificate status, hash, error type or exception text becomes either field. The existing schema 3 fields/version and successful artifact grammar remain exact; only the condition allowlist gains the four branch labels.

`Get-OwnedImageSignatureCondition` retains the exact existing accepted status comparison, null-signer refusal, subject regex and status-first order. Its unexpected-property catch remains `classification-failure`. `Invoke-OwnedImageSignatureCondition` adds the imported-only canary described below, then uses the same `LiteralPath` argument and signature classifier. Parameter-binding and other invocation exceptions retain their existing fixed labels; command-resolution failures gain only the narrower attribution described below. No exception object, message, type name or parameter value is read into a diagnostic. Legacy broad failures remain accepted for retained evidence. The only success remains the original accepted status plus matching signer subject; no unsigned tool or different signer is accepted.

## Module-resolution canary and evidence boundary

The source selected for this task is `b34a10ea`: the workflow runs under `pwsh`, the Node bootstrap changes PATH without normalizing module variables, and the driver starts the fixed Windows PowerShell 5.1 executable through Node with its inherited environment. The build script sets no module path or autoload preference. Microsoft's [Windows PowerShell module-path contract](https://learn.microsoft.com/sr-cyrl-rs/PowerShell/module/microsoft.powershell.core/about/about_psmodulepath?view=powershell-5.1) describes a risk when PS7 launches WinPS through an intermediate process: PS7 paths can remain ahead of inbox paths and prevent loading a shared-name Windows module. The [preference contract](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_preference_variables?view=powershell-5.1#psmoduleautoloadingpreference) distinguishes all, module-qualified and disabled autoloading, with an absent preference meaning all. The source proves that this inheritance boundary exists, but not the actual host's values or historical cause. No explicit OS module import, module-path reset, profile enablement or broad autoload relaxation is justified or applied here.

Immediately before the existing signature query, the canary performs one exact `Get-Command` lookup restricted to Cmdlet and `-ListImported`. The [official lookup contract](https://learn.microsoft.com/ar-sa/powershell/module/microsoft.powershell.core/get-command?view=powershell-5.1) distinguishes imported-only lookup from ordinary exact-name discovery that can auto-import. No additional module search/import is introduced. A captured CommandInfo is invoked directly; a subsequent command-resolution exception is then `nested-command-unavailable`. If no imported command exists, the original name-based query still runs, retaining its existing autoload behavior; an exception there is `unresolved-command-unavailable`, which does not prove direct target absence versus an autoload/nested failure. A malformed or failed probe is `command-probe-failure`, with no signature query. Not-imported status alone never refuses a query that otherwise succeeds.

Path flags compare bounded current-process `PSModulePath` entries with the current WinPS `$PSHOME/Modules` and the documented default `ProgramFiles/PowerShell/7/Modules`. They use case-insensitive, slash-normalized lexical equality with trailing separators removed, not filesystem search or alias/provenance validation. The core flag describes only that default PS7 location; it cannot exclude custom PS7 paths. There are at most 32768 characters and 128 entries; uninspectable/capped observations become explicit unknowns. The autoload flag reads only the current engine preference through SessionState, never profiles or user/registry configuration. No raw environment, path, module name, command name, error, type, certificate or status value is output.

On a signature failure only, the existing BUILD row may be followed by exactly one fixed row: `OWNED_IMAGE_MODULE`, version `1`, inbox flag, default-core flag, autoload enum and direct-command enum. Total diagnostic input stays at most 512 bytes. The new decoder accepts only the legacy one-row form or this exact two-row form, with no free text or additional rows. New nested/unresolved/probe conditions require respectively imported/not-imported/unknown direct evidence and cannot be formatted without that coherent row. Malformed metadata collapses to the existing fixed unexpected result. Successful receipts and their guard are unchanged; the optional row is never made an upload artifact.

PS7 synthetic tests verify the lexical flags, imported-only lookup arguments, known-object dispatch, unresolved fallback, malformed-probe refusal and closed projection. A FunctionInfo is used only as a synthetic CommandInfo interface stand-in; it is not proof of a real WinPS CmdletInfo, inbox module contents, module-path values or native host cause. The next exact-head native run belongs to the coordinator. Any eventual OS-only initialization proposal still requires that evidence and must preserve the signature predicate and trusted module boundary.
