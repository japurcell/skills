# Foundation qualification evidence

## Definition and trust boundary

`.github/workflows/software-factory-qualification.yml` runs on relevant package/workflow/test-runner changes for `push` and `pull_request`, plus manual `workflow_dispatch`. A single `native-foundation` matrix job uses Ubuntu 24.04 x64, Windows 2025 x64 and macOS 15 arm64, `fail-fast: false`, and a 20-minute job limit. Each run retains uniquely named native artifacts for 14 days, including failure JSON/logs. Missing evidence is an upload error.

Permissions are only `contents: read`; checkout credentials are not persisted. There is no privileged pull-request trigger, reusable cache, provider authentication, account installer or desktop notification call. PR code is untrusted and executes on disposable hosted VMs without repository secrets. Node downloads happen only in the explicitly opted-in Actions bootstrap, never product startup. The manifest pins downloaded bytes; npm installs the committed lock with scripts disabled. Both Actions are immutable official release SHAs, verified 2026-10-21:

- [checkout v7.0.0](https://github.com/actions/checkout/releases/tag/v7.0.0): `9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0`.
- [upload-artifact v7.0.0](https://github.com/actions/upload-artifact/releases/tag/v7.0.0): `bbbca2ddaa5d8feaa63e36b76fdaad77386f024f`.

Prerequisites include runner-provided bootstrap Node with fetch support, HTTPS access to official Node/npm distribution, native tar extraction, Git, supported local persistent placement, Windows PowerShell/native volume APIs, and the existing POSIX Python resource fixture. Missing prerequisites produce a failed step. Exact downloaded Node 24.22.1, SQLite 3.53.4 and lockfile dependencies are checked before foundation tests. GitHub runner image metadata and actual bundled npm version are saved.

`bootstrap.json` records archive hash/native versions or the blocking error. `foundation.json` records every selected command/status/duration, image metadata and explicit foundation scope. Individual logs retain failures; `runtime.json` holds direct SQLite proof when that probe succeeds. The runner continues independent foundation checks after a test/build failure so other evidence survives, but any failed command makes the job fail. Dependency-install failure stops dependent checks.

Separately, the cancellation test's qualifier worker failed on a real `BEGIN IMMEDIATE` with SQLite errcode 5 after its 100 ms timeout, before reaching cancellation. Direct Windows storage proof passed with 80 concurrent rows, WAL/FULL/foreign keys, backup integrity, committed/uncommitted process-loss results, p95 commit 5.9677 ms and max 25.5193 ms. Preserve this partial evidence without promoting the failed job.

The repair changes the fixture to an owned temporary container containing `repository/`, an empty regular `gitconfig` and an empty `hooks/` directory. The Git-only paths stay outside the worktree and cleanup removes the entire container. This follows [Git configuration overrides](https://git-scm.com/docs/git-config) without writing user/global configuration. The qualifier retries only confirmed SQLite busy errors before a successful `BEGIN IMMEDIATE`, with a 5 second deadline; inserts/commits are never replayed and the separate 40 ms busy probe is unchanged. [SQLite result-code guidance](https://sqlite.org/rescode.html#busy) identifies contention at `BEGIN IMMEDIATE` as a safe point to retry acquisition.

Two real held-lock tests reproduced the 100 ms failure before the repair. After repair, release after 350 ms commits all 40 rows; an unreleased writer lock fails after about 5.16 seconds and commits zero rows. The complete local repair foundation passed both strict typechecks, build, fixtures 6/6, store/placement 29/29, separate placement 2/2, CI contracts 2/2, runtime 4/4 and direct SQLite JSON. A direct fixture inspection also verified the regular empty config, external empty hooks directory and full-container cleanup. Local macOS evidence is retained in `/tmp/factory-native-repair-local-evidence`; subsequent hosted run `39719540444` now supplies passing repaired Windows execution.

The parent integrated shared placement into the store and registered placement/CI contract coverage before the first hosted run. The original POSIX RLIMIT_FSIZE fixture is retained. Windows now selects a native shared WAL byte-range write lock after the committed-prefix barrier, using a separate owned PowerShell/C# process. The same assertions require actual recorder failure, blocked admission, one shutdown request, one fallback notice, the saved prefix and readable prior events. Native helper setup/cleanup errors fail the test; no platform is skipped. The helper has a ready handshake, bounded range/wait and explicit release before store close. Its PowerShell syntax and embedded C# compilation passed on macOS PowerShell; all 15 capture tests, including POSIX RLIMIT_FSIZE, passed locally after the change. The first hosted store tests failed at Git setup before this helper. The subsequent passing run exercised the helper and all unchanged recorder assertions on Windows. This establishes the native I/O-failure case, not disk-full parity. [Windows byte-range locks](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex) allow reads but deny writes for a shared range, including beyond EOF. [SQLite WAL](https://sqlite.org/wal.html) appends transaction records, but memory-mapped writes bypass byte locks, so documentation and syntax checks cannot establish native acceptance.

Parent integrated and pushed the reviewed repair; run `39719540444` passed all matrix jobs. No authenticated-provider workflow is created without configured credentials and a useful harmless bounded contract. Extend this foundation workflow to later supported suites as they land; T17 requires complete supported acceptance.
