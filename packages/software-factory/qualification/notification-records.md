# Initial notification record qualification

Status: T12b1 source and deterministic public invocation proof on macOS arm64, 2026-10-22. No real desktop notifier was invoked. T12b2 owns preferences, acknowledgments, reminders and UI metadata. T15 must supply a trusted installed sender binding; T17 owns visible desktop delivery qualification.

An issue is a finalized invocation with a non-success outcome, unknown cleanup, or at least one complete saved request capture. A saved request causes `CommandRunner.drain()` to throw, so an ordinary successful invocation has no initial issue and follows its existing atomic finalization and claim release. For a non-success outcome, `src/lifecycle.ts` first commits the ordinary final invocation summary while retaining the existing worktree owner claim. `src/notifications.ts` then reserves one `initial` delivery identity, `<invocationId>:initial`, with state `unknown` and reason `submission_unconfirmed`. The native submission, when a trusted sender is injected, occurs outside the SQLite transaction. The result updates the same record to `submitted`, `failed`, `timed_out`, or `unknown`; a complete-cleanup claim is released only after that write settles. This excludes maintenance during a live send without a second lock service. A failed or uncertain claim release leaves the exact claim for explicit owner recovery and cannot rewrite the saved execution outcome or delivery state. `submitted` means command/API acceptance only; every record states `visibleDelivery: false`. The title and body contain only bounded issue categories and counts, not question text, diagnostics, captured output, or secrets. The existing native sender performs its own secret filtering before a process argument is formed.

With no installed binding, a development invocation records `failed` with `unbound_sender` and performs no desktop operation. A sender rejection or a five-second nonsettling sender records `unknown` because submission or cleanup cannot be disproved. A native `timed_out` result remains `timed_out` when its cleanup is confirmed. No notification path changes the saved workflow outcome, question capture, cleanup fact, or CLI exit status. Saved metadata is returned by ordinary `invoke` and `history` output and persists across reopening the store. Success without an issue stays quiet.

The reservation has a uniqueness constraint on `(invocation_id,kind)`. A second request for the same identity returns the saved record without calling a sender. If reservation commit is uncertain, no send follows. If submission or the result update is uncertain, the pre-send `unknown` record remains. Startup never scans or replays notification records. An invocation that crashes before reservation has no later automatic notice.

Schema version is now 5. `openRepositoryStore` checks `PRAGMA user_version` before configuration and refuses older stores without mutation. T16 must provide an explicit, reviewed forward migration. From version 4 to 5, add `notification_deliveries(id TEXT PRIMARY KEY, invocation_id TEXT NOT NULL REFERENCES invocations(id), kind TEXT NOT NULL CHECK(kind='initial'), data TEXT NOT NULL CHECK(json_valid(data)), UNIQUE(invocation_id,kind))`, add `notification_invocation` on `invocation_id`, then set `user_version=5` in the same explicit migration transaction. Existing finalized invocations must not be backfilled into resend jobs or inferred as delivered. Earlier versions require their existing explicit transitions through version 4 before this step; no automatic migration is part of T12b1.
