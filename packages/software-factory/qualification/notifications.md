# Native notification sender qualification

The T12a sender is a best-effort one-shot submission. `submitted` means the native command returned success and all owned pipes closed before the deadline. It does not mean the desktop displayed a banner or a person saw it. `failed`, `timed_out`, and `unknown` retain fixed reason codes and independent `cleanup` evidence. No sender result changes the workflow exit status. Live desktop delivery tests are deferred to T17-desktop by the user's 2026-10-21 direction.

## Source and build contract

`src/native/notifications.ts` selects fixed commands, and its internal `src/native/notification-transport.ts` uses Node 24.22.1 `spawn` with `shell: false` and an absolute five-second maximum from the call through cleanup. The sender filters configured and environment secrets, validates title (256 UTF-8 bytes) and body (4096 UTF-8 bytes), and passes them only as positional data. Diagnostic text from a native command is classified and discarded, never returned or logged. macOS invokes `/usr/bin/osascript` with a fixed `on run argv` routine and the two text arguments after `--`. Linux invokes `/usr/bin/notify-send` with fixed `--app-name=Software Factory`, `--`, a plain summary, and an XML-escaped body because the desktop notification protocol permits body markup. No action or wait flag is used. If those exact commands or the desktop service are absent, the result is a fixed failure. The runtime does not install prerequisites.

Windows uses `native/windows-notify/main.cpp`, a C++17 C++/WinRT console executable built by `native/windows-notify/windows-notify.vcxproj`. On a qualified Windows host with Visual Studio 2022 C++ v143 tools and the Windows SDK including C++/WinRT headers, run:

```powershell
msbuild native/windows-notify/windows-notify.vcxproj /p:Configuration=Release /p:Platform=x64 /m:1
```

The expected artifact is `native/windows-notify/out/x64/windows-notify.exe`. The project links the Windows SDK `windowsapp.lib`, `runtimeobject.lib`, `shell32.lib`, `ole32.lib`, and `propsys.lib`. It has no Windows App SDK or .NET runtime dependency and does not fetch a package during build. ARM64 uses `/p:Platform=ARM64` and `out/ARM64/windows-notify.exe`; that target still needs native compilation proof. The helper is not built by the cross-platform TypeScript build. A missing compatible compiler or SDK is a failed prerequisite, not evidence of helper support.

T15 is not implemented. Until its trusted installation loader supplies a descriptor, the public sender fails closed on Windows with `registration_missing`. `DesktopNotification` carries only content, optional filtering secrets, and timeout. Its message cannot select a platform, executable, AUMID, install root, hash, or ownership token. The internal `WindowsNotificationInstallation` descriptor must come from the installer's persisted manifest, with `installRoot` (canonical, dedicated, access-controlled directory), `helperRelativePath` (exactly `windows-notify.exe`), `helperSha256` (SHA-256 of the packaged architecture-specific binary), `repositoryCommonDirectory` (the canonical Git common directory used to derive the AUMID), and `shortcutOwnerToken` (32 uppercase hexadecimal digits from 128 cryptographically random bits generated once by the installer). The sender resolves the root and helper, rejects links or changed paths, verifies the binary hash before launch, and derives the AUMID from `repositoryCommonDirectory`. T15 must keep the installation directory immutable to untrusted writers throughout verification and launch and must persist the descriptor outside notification messages. No arbitrary or test-only executable launcher is part of the public production message.

Under T15's explicit maintenance gate, the installer runs `windows-notify.exe install <AUMID> <shortcutOwnerToken>` for the current user. The helper creates `Software Factory <24 uppercase hex>.lnk` in that user's Start Menu Programs folder with target equal to the installed helper, argument `activated`, and matching AUMID. It first saves the link in a unique temporary directory, then publishes the final name with `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`. An existing link is never adopted from matching target, arguments, and AUMID alone. The adjacent `.lnk.owner` record is created exclusively after publication and contains the token plus the new link's volume, file index, and creation time. An existing link is accepted as this installation's link only when the record, file identity, token, and link contents all match. The installer must persist the exact descriptor and ownership token for update/uninstall. An update that changes executable path must remove the old shortcut through the old helper before installing the new one; failure leaves maintenance incomplete. Uninstall runs `windows-notify.exe remove <AUMID> <shortcutOwnerToken>` before removing the executable. Removal reads and rechecks both file identities and link contents, then deletes through verified file handles. An interrupted publication or record write can leave an unowned link or record; maintenance must report that conflict and require independent inspection and explicit recovery, never infer ownership or overwrite a preexisting collision. The `activated` command is a no-op local handler, and a toast subscribes to the required in-process `Activated` event only while the short-lived sender runs. There is no workflow action, background service, or post-exit click guarantee.

The sender calls `windows-notify.exe send <AUMID> <shortcutOwnerToken> <title> <body>`. The helper verifies its owned shortcut and record, checks `ToastNotifier.Setting()`, creates `ToastText02` XML through DOM text nodes, subscribes to a no-op activation callback, and calls `ToastNotificationManager.CreateToastNotifier(AUMID).Show(toast)`. Exit 0 means `Show` returned. Exit 2 means invalid arguments, 3 means missing owned registration, 4 means denied or conflicting ownership, and 5 means a native error. It emits no user text in diagnostics. The Node transport maps 3 to `registration_missing`, 4 to `denied`, and other nonzero exits to `sender_exit_nonzero`.

## Deterministic evidence and remaining gates

From `packages/software-factory`, run `npm run build`, `npm run typecheck`, and `node --test test/notification-senders.test.mjs` using the pinned Node 24.22.1 runtime. The focused test uses disposable real Node child executables. It checks exact fixed argv and filtering, data containing shell/XML syntax, rejection of a caller-selected Windows helper, missing executable and registration, unavailable service, denied delivery, nonzero exit, deadline termination, and an inherited pipe that makes cleanup unknown. It does not invoke any desktop notifier. On 2026-10-22, the pinned macOS arm64 runtime passed typecheck and build, then all 9 focused tests. The original 500/450 ms assertions on the two timeout scenarios remain intact. Windows native compilation, native shortcut race behavior, and all visible delivery remain unverified.

Windows compile-only qualification should run the `msbuild` command on a native Actions Windows x64 runner and archive compiler diagnostics. It must not run `install`, `send`, or `remove` against that runner's real Start Menu during this phase. A future native ownership harness should compile a separate test-only variant whose Programs path is injected from a fresh directory under `$env:RUNNER_TEMP`, with deterministic barriers immediately before publication and removal. The harness should prove: an identical preexisting link without a matching ownership record returns 4 and retains its file identity; a foreign link published at the final name while installation waits returns 4 and survives; a link or record replaced while removal waits returns 4 and survives; a missing link with an orphan record returns 4; a valid owned pair is removed by handle; and missing registration returns 3 without invoking Toast APIs. The test variant must disable the toast call and never ship in the production helper. T17-desktop later needs a disposable interactive desktop and explicit records of shortcut creation/removal, denied settings, actual visible delivery, XML-special text rendering, helper exit within five seconds, and click behavior after sender exit. macOS and Linux also need visible-delivery tests in suitable desktop sessions. Headless success establishes only command submission.
