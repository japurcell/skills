# Native notification sender qualification

The T12a sender is a best-effort one-shot submission. `submitted` means the native command returned success and all owned pipes closed before the deadline. It does not mean the desktop displayed a banner or a person saw it. `failed`, `timed_out`, and `unknown` retain fixed reason codes and independent `cleanup` evidence. No sender result changes the workflow exit status. Live desktop delivery tests are deferred to T17-desktop by the user's 2026-10-21 direction.

## Source and build contract

`src/native/notifications.ts` selects fixed commands, and its internal `src/native/notification-transport.ts` uses Node 24.22.1 `spawn` with `shell: false` and an absolute five-second maximum from the call through cleanup. The sender filters configured and environment secrets, validates title (256 UTF-8 bytes) and body (4096 UTF-8 bytes), and passes them only as positional data. Diagnostic text from a native command is classified and discarded, never returned or logged. macOS invokes `/usr/bin/osascript` with a fixed `on run argv` routine and the two text arguments after `--`. Linux invokes `/usr/bin/notify-send` with fixed `--app-name=Software Factory`, `--`, a plain summary, and an XML-escaped body because the desktop notification protocol permits body markup. No action or wait flag is used. If those exact commands or the desktop service are absent, the result is a fixed failure. The runtime does not install prerequisites.

Windows uses `native/windows-notify/main.cpp`, a C++17 C++/WinRT console executable built by `native/windows-notify/windows-notify.vcxproj`. On a qualified Windows host with Visual Studio 2022 C++ v143 tools and the Windows SDK including C++/WinRT headers, run:

```powershell
msbuild native/windows-notify/windows-notify.vcxproj /p:Configuration=Release /p:Platform=x64 /m:1
```

The expected artifact is `native/windows-notify/out/x64/windows-notify.exe`. The project links the Windows SDK `windowsapp.lib`, `runtimeobject.lib`, `shell32.lib`, `ole32.lib`, and `propsys.lib`. It has no Windows App SDK or .NET runtime dependency and does not fetch a package during build. ARM64 uses `/p:Platform=ARM64` and `out/ARM64/windows-notify.exe`; that target still needs native compilation proof. A release packager must include only the built executable for the selected architecture in its manifest with an integrity hash, then pass its absolute installed path to the sender. The helper is not built by the cross-platform TypeScript build. A missing compatible compiler or SDK is a failed prerequisite, not evidence of helper support.

The installer must derive `repositoryNotificationAppId(commonDirectory)` from the repository Git common directory and run the installed helper as `windows-notify.exe install <AUMID>` under its explicit maintenance gate. The helper creates `Software Factory <24 uppercase hex>.lnk` in the current user's Start Menu Programs folder, pointing only to that installed executable with `activated` as its argument and the same AUMID property. It refuses an existing shortcut whose target, argument, or AUMID differs. The manifest must record the exact executable and shortcut ownership for update/uninstall. An update that changes the executable path must remove the old shortcut through the old helper before installing the new one; failure leaves maintenance incomplete. Uninstall runs `windows-notify.exe remove <AUMID>` before removing the executable. Removal refuses a changed shortcut and never deletes unrelated files. The `activated` command is a no-op local handler, and a toast subscribes to the required in-process `Activated` event only while the short-lived sender runs. There is no workflow action, background service, or post-exit click guarantee.

The sender calls `windows-notify.exe send <AUMID> <title> <body>`. The helper verifies its owned shortcut, checks `ToastNotifier.Setting()`, creates `ToastText02` XML through DOM text nodes, subscribes to a no-op activation callback, and calls `ToastNotificationManager.CreateToastNotifier(AUMID).Show(toast)`. Exit 0 means `Show` returned. Exit 2 means invalid arguments, 3 means missing owned shortcut, 4 means denied or conflicting ownership, and 5 means a native error. It emits no user text in diagnostics. The Node transport maps 3 to `service_unavailable`, 4 to `denied`, and other nonzero exits to `sender_exit_nonzero`.

## Deterministic evidence and remaining gates

From `packages/software-factory`, run `npm run build`, `npm run typecheck`, and `node --test test/notification-senders.test.mjs` using the pinned Node 24.22.1 runtime. The focused test uses disposable real Node child executables. It checks exact fixed argv and filtering, data containing shell/XML syntax, missing executable, unavailable service, denied delivery, nonzero exit, deadline termination, and an inherited pipe that makes cleanup unknown. It does not invoke any desktop notifier. On 2026-10-22, the pinned macOS arm64 runtime passed typecheck and build, then all 8 focused tests in 510 ms. The original 500/450 ms assertions on the two timeout scenarios remain intact. Windows native compilation and all visible delivery remain unverified.

Windows compile-only qualification should run the `msbuild` command on a native Actions Windows x64 runner and archive compiler diagnostics. It must not run `install`, `send`, or `remove` against that runner's real Start Menu during this phase. T17-desktop later needs a disposable interactive desktop and explicit records of shortcut creation/removal, denied settings, actual visible delivery, XML-special text rendering, helper exit within five seconds, and click behavior after sender exit. macOS and Linux also need visible-delivery tests in suitable desktop sessions. Headless success establishes only command submission.
