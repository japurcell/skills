# Native notification sender qualification

The T12a sender is a best-effort one-shot submission. `submitted` means the native command returned success and all owned pipes closed before the deadline. It does not mean the desktop displayed a banner or a person saw it. `failed`, `timed_out`, and `unknown` retain fixed reason codes and independent `cleanup` evidence. No sender result changes the workflow exit status. Live desktop delivery tests are deferred to T17-desktop by the user's 2026-10-21 direction.

## Source and build contract

`src/native/notifications.ts` selects fixed commands, and its internal `src/native/notification-transport.ts` uses Node 24.22.1 `spawn` with `shell: false` and an absolute five-second maximum from the call through cleanup. The sender filters configured secrets and environment values of at least four characters whose variable names contain `SECRET`, `TOKEN`, `PASSWORD`, or `API_KEY`, regardless of case. It cannot discover arbitrary unknown secrets. It validates title (256 UTF-8 bytes) and body (4096 UTF-8 bytes), and passes them only as positional data. Diagnostic text from a native command is classified and discarded, never returned or logged. macOS invokes `/usr/bin/osascript` with a fixed `on run argv` routine and the two text arguments after `--`. Linux invokes `/usr/bin/notify-send` with fixed `--app-name=Software Factory`, `--`, a plain summary, and an XML-escaped body because the desktop notification protocol permits body markup. No action or wait flag is used. If those exact commands or the desktop service are absent, the result is a fixed failure. The runtime does not install prerequisites.

Windows uses `native/windows-notify/main.cpp` and shared `native/windows-notify/registration-core.hpp`, a C++17 C++/WinRT console executable built by `native/windows-notify/windows-notify.vcxproj`. On a qualified Windows host with Visual Studio 2022 C++ v143 tools and the Windows SDK including C++/WinRT headers, run:

```powershell
msbuild native/windows-notify/windows-notify.vcxproj /p:Configuration=Release /p:Platform=x64 /m:1
```

The expected artifact is `native/windows-notify/out/x64/windows-notify.exe`. The project links the Windows SDK `windowsapp.lib`, `runtimeobject.lib`, `shell32.lib`, `ole32.lib`, and `propsys.lib`. It has no Windows App SDK or .NET runtime dependency and does not fetch a package during build. ARM64 uses `/p:Platform=ARM64` and `out/ARM64/windows-notify.exe`; that target still needs native compilation proof. The helper is not built by the cross-platform TypeScript build. A missing compatible compiler or SDK is a failed prerequisite, not evidence of helper support.

T15 is not implemented. Until its trusted installation loader supplies a descriptor, the public sender fails closed on Windows with `registration_missing`. `DesktopNotification` carries only content, optional filtering secrets, and timeout. Its message cannot select a platform, executable, AUMID, install root, hash, or ownership token. The internal `WindowsNotificationInstallation` descriptor must come from the installer's persisted manifest, with `installRoot` (canonical, dedicated, access-controlled directory), `helperRelativePath` (exactly `windows-notify.exe`), `helperSha256` (SHA-256 of the packaged architecture-specific binary), `repositoryCommonDirectory` (the canonical Git common directory used to derive the AUMID), and `shortcutOwnerToken` (32 uppercase hexadecimal digits from 128 cryptographically random bits generated once by the installer). The sender resolves the root and helper, rejects links or changed paths, verifies the binary hash before launch, and derives the AUMID from `repositoryCommonDirectory`. T15 must keep the installation directory immutable to untrusted writers throughout verification and launch and must persist the descriptor outside notification messages. No arbitrary or test-only executable launcher is part of the public production message.

Under T15's explicit maintenance gate, the installer runs `windows-notify.exe install <AUMID> <shortcutOwnerToken>` for the current user. The helper creates `Software Factory <24 uppercase hex>.lnk` in that user's Start Menu Programs folder with target equal to the installed helper, argument `activated`, and matching AUMID. It serializes the shell link to an in-memory COM stream, creates the file exclusively in a unique temporary directory, and holds the created handle through semantic checks and publication. It checks that the temporary name still refers to the created file, verifies target, arguments, and AUMID from the held handle, then publishes that handle with `FileRenameInfo` and replacement disabled. It verifies the published name, file identity, and link contents before creating the adjacent `.lnk.owner` record. The held handle denies in-place writes; a rename and replacement at the temporary name returns conflict without deleting or adopting the replacement. The record contains the token plus the new link's volume, file index, and creation time. An existing link is never adopted from matching target, arguments, and AUMID alone. It is accepted as this installation's link only when the record, file identity, token, and link contents all match. The installer must persist the exact descriptor and ownership token for update/uninstall. An update that changes executable path must remove the old shortcut through the old helper before installing the new one; failure leaves maintenance incomplete. Uninstall runs `windows-notify.exe remove <AUMID> <shortcutOwnerToken>` before removing the executable. Removal reads and rechecks both file identities and link contents, then deletes through verified file handles. An interrupted publication or record write can leave an unowned link or record; maintenance must report that conflict and require independent inspection and explicit recovery, never infer ownership or overwrite a preexisting collision. The `activated` command is a no-op local handler, and a toast subscribes to the required in-process `Activated` event only while the short-lived sender runs. There is no workflow action, background service, or post-exit click guarantee.

The sender calls `windows-notify.exe send <AUMID> <shortcutOwnerToken> <title> <body>`. The helper verifies its owned shortcut and record, checks `ToastNotifier.Setting()`, creates `ToastText02` XML through DOM text nodes, subscribes to a no-op activation callback, and calls `ToastNotificationManager.CreateToastNotifier(AUMID).Show(toast)`. Exit 0 means `Show` returned. Exit 2 means invalid arguments, 3 means missing owned registration, 4 means denied or conflicting ownership, and 5 means a native error. It emits no user text in diagnostics. The Node transport maps 3 to `registration_missing`, 4 to `denied`, and other nonzero exits to `sender_exit_nonzero`.

## Deterministic evidence and remaining gates

From `packages/software-factory`, run `npm run build`, `npm run typecheck`, `npm run test:notifications`, and `npm run test:store` using the pinned Node 24.22.1 runtime. The focused tests use disposable real Node child executables and a mocked, unresolved Windows file lookup. They check exact fixed argv and filtering, data containing shell/XML syntax, rejection of a caller-selected Windows helper, invalid public input, missing executable and registration, unavailable service, denied delivery, Windows fixed exit codes despite contradictory diagnostic wording, nonzero exit, deadline termination, an inherited pipe that makes cleanup unknown, and abandonment of a delayed preflight without a later launch. They do not invoke any desktop notifier. On 2026-10-22, the pinned macOS arm64 runtime passed build, typecheck, and all 13 notification tests after the hosted repair. Earlier qualification passed all 31 store tests. The original 500/450 ms assertions on the two timeout scenarios remain intact. The five-second deadline bounds asynchronous preflight completion and process cleanup while the event loop can run; it cannot interrupt a blocked synchronous OS call or a stalled scheduler. Windows native compilation, native shortcut race behavior, and all visible delivery remain unverified.

The separate `registration-tests.vcxproj` compiles `registration-tests.cpp` against the same registration source as production. Its executable requires one temp parent directory argument and creates a fresh child folder there. It has no toast call and never selects the real Start Menu path. On a native Actions Windows x64 runner, run these exact commands from `packages/software-factory`:

```powershell
msbuild native/windows-notify/windows-notify.vcxproj /p:Configuration=Release /p:Platform=x64 /m:1
msbuild native/windows-notify/registration-tests.vcxproj /p:Configuration=Release /p:Platform=x64 /m:1
& native/windows-notify/out/x64/windows-notify-registration-tests.exe $env:RUNNER_TEMP
```

The temp-only executable tests invalid and valid copied replacements after save, preservation of both foreign replacements and renamed originals, in-place write attempts while temporary and published handles are held, a foreign collision at publication, rename and replacement of a temporary link, an identical preexisting link without ownership, link and record replacement before removal, valid owned-pair removal, an orphan record, and missing registration without any Toast API call. These commands still need native Windows execution; compiler-only success cannot establish the race or ownership behavior. They must not invoke `windows-notify.exe install`, `send`, or `remove` against the runner's real Start Menu. T17-desktop later needs a disposable interactive desktop and explicit records of shortcut creation/removal, denied settings, actual visible delivery, XML-special text rendering, helper exit within five seconds, and click behavior after sender exit. macOS and Linux also need visible-delivery tests in suitable desktop sessions. Headless success establishes only command submission.

## Deterministic inherited-pipe setup repair

Independent registry review observed the original inherited-pipe case return timed_out/complete instead of unknown, while one rerun passed. The original fake helper had to start a second Node process before the transport's 150ms stop point; if startup consumed that allowance, no escaped pipe existed and complete cleanup was correct. This was a fixture setup assumption, not evidence that the runtime should relabel complete cleanup as unknown.

The pipe scenario now runs in isolated `test/notification-pipe.test.mjs` with Node's test-only module mocking flag. It prepares a real process and detached pipe holder, waits for the actual inherited-FD readiness acknowledgment, then substitutes that prepared ChildProcess only at the operating-system spawn boundary. The unchanged transport receives the same process/streams and its original 200ms lifetime begins. The original unknown result and less-than450ms assertion remain exact. A separate real-spawn case still covers startup, termination and pipe cleanup within250/500ms. The holder's700ms timer starts only when the measured scenario begins, then test teardown verifies its exit marker and native identity absence before removing its owned temporary directory. A disposable public transport probe with 200ms fake-helper startup reproduces the old unknown assertion failure as timed_out/complete (`/tmp/factory-notification-startup-red.log`). The repaired fixture includes that same200ms setup delay before readiness and still passes the unchanged measured lifetime assertions. The missing readiness protocol also failed before the fixture update and passed afterward. No production test switch, sender deadline or assertion was widened. Group dispatch runs all three no-desktop test files; visible delivery remains deferred.

## Native delegate definition link repair

Hosted Windows run `39807241491` at `02479d09` compiles the namespace repair, then fails at link with LNK2019 for the `winrt::Windows::Foundation::TypedEventHandler<ToastNotification, IInspectable>` constructor used by the existing in-process activation callback. The retained red is `/tmp/factory-notification-39807241491-failed.log`. `main.cpp` now explicitly includes `winrt/Windows.Foundation.h`, the namespace projection that defines the consumed delegate. The helper callback and behavior, ownership implementation, dependencies and build flags remain unchanged.

Microsoft's [C++/WinRT API consumption guidance](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/consume-apis) requires including the namespace header for consumed types. Its [linker troubleshooting guidance](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/troubleshooting) describes unresolved consumption definitions when the corresponding projection header is missing. This source-level diagnosis still requires a fresh native MSVC link and TEMP-only ownership run; no local macOS check claims to prove Windows compilation or visible notification delivery.
