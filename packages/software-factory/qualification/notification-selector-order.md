Independent review found that an aborted programmatic runner can remain open when a test worker handles SIGTERM and holds an interval. The maintained resistant-worker fixture failed red with `runner or test child retained an open pipe` at `/tmp/factory-notification-ordering-resistant-red.log`. The runner now executes the ordered Node API in an owned child process. Abort first requests an ordinary runner shutdown; after one second, the parent force-terminates that child's process group on POSIX or uses Windows `taskkill /PID ... /T /F` for its process tree. It waits for the child to close and returns failure on any cancellation. The synthetic test installs a SIGTERM handler in a running worker, sends both SIGTERM and SIGINT to separate harness runs, and requires exit 143/130 within two seconds, no queued test start, and no surviving worker PID. This tests termination through the same exported runner used by the notification selector.

This uses the [Node 24.22.1 `run()` options](https://nodejs.org/download/release/v24.22.1/docs/api/test.html#runoptions) and its [per-file and final summaries](https://nodejs.org/download/release/v24.22.1/docs/api/test.html#event-testsummary). Node documents that `test:start` and `test:pass` are buffered in declaration order while `test:dequeue` and `test:complete` reflect execution order, so TAP order alone is not scheduling proof. The [event lifecycle](https://nodejs.org/download/release/v24.22.1/docs/api/test.html#event-lifecycle) explains that distinction. Node [documents detached POSIX child process groups](https://nodejs.org/download/release/v24.22.1/docs/api/child_process.html#optionsdetached) and warns that [killing a child does not kill its descendants](https://nodejs.org/download/release/v24.22.1/docs/api/child_process.html#subprocesskillsignal). Microsoft [documents `taskkill /T` and `/F`](https://learn.microsoft.com/windows-server/administration/windows-commands/taskkill) for the Windows tree termination path.
