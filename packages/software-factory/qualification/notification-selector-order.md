## Native Windows cancellation follow-up

The native Windows foundation at source `b6af776feeab99dab3fb28859683811da0cbb2bd` ran the ordered-runner fixture and failed its resistant-worker case in 221.2611 ms: `null !== 143` after `child.kill('SIGTERM')`. Its retained evidence is `/tmp/factory-native-foundation-39863447743/software-factory-foundation-win32-x64-39863447743-1/fixtures.log` and `/tmp/factory-native-39863447743-failed.log`. The first four ordering and completeness cases passed on Windows. Other foundation failures report `startup Git probe cleanup unknown` in separately owned product paths.

The failure exposed an invalid test input on Windows. [Node v24.22.1 documents](https://github.com/nodejs/node/blob/v24.22.1/doc/api/child_process.md#subprocesskillsignal) that `subprocess.kill('SIGTERM')` and `subprocess.kill('SIGINT')` forcefully terminate the immediate Windows child without running its handlers. [Its process documentation](https://github.com/nodejs/node/blob/v24.22.1/doc/api/process.md#signal-events) likewise states that Windows has no POSIX signal delivery and these `process.kill()` calls terminate unconditionally. The old fixture expected the terminated harness's handler to abort `runOrderedTests`, so its null exit code did not exercise the runner's cancellation path or prove its worker tree closed.

The revised fixture retains both original signal-resistant worker scenarios on POSIX. On every platform it also starts that worker, then sends a control message to the fixture harness so the harness aborts the `AbortSignal` passed to the exported `runOrderedTests`. It requires the public runner to return failure, the one-second force deadline to close the runner within the original two-second outer deadline, no queued tail receipt, no surviving owned worker PID, and a surviving unrelated process. A separate Windows case checks the documented abrupt native `child.kill()` behavior for both SIGTERM and SIGINT, including that the child's handler was not invoked. These are distinct claims: a native Windows kill is not treated as cooperative cancellation. The production runner still requests abort through IPC and escalates with `taskkill /PID <runner> /T /F` after one second; the [Microsoft command contract](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill) says `/T` includes children and `/F` forcefully ends them. No runner implementation change was justified by the observed Windows failure.

Local pinned Node v24.22.1 on macOS: the focused ordered-runner suite passed 6/6 in 3.85 seconds after this change, with the POSIX signal case in 2.20 seconds and the public `AbortSignal` case in 1.10 seconds. The native Windows `AbortSignal` closure case and its `taskkill` escalation still require fresh Windows Actions execution on the integrated head. This local result is not Windows proof.
