# T15a release packaging qualification

T15a produces a reviewable directory and manifest. It does not install into a repository, download Node, publish a release, or claim native desktop delivery. The command requires an explicit JSON release selection and an absolute destination outside the source tree that does not yet exist. A matching complete destination may be verified and returned again. A changed or partial destination is preserved and refused for operator inspection.

Build with the pinned Node v24.22.1 and the locked development dependencies by explicitly running `npm run build` in the package, then run `node packages/software-factory/scripts/package-release.mjs --descriptor /absolute/selection.json --destination /absolute/new-bundle` from the repository root. `--source-root /absolute/package-root` is available for disposable qualification fixtures. The selected JSON has `version` (semantic version), `platform` (`darwin-arm64`, `linux-x64`, or `win32-x64`), and `node` with exact `version`, `url`, and `sha256` fields. Those Node values must match the pinned official release values in [`runtime-manifest.json`](runtime-manifest.json), sourced from the [Node v24.22.1 release checksums](https://nodejs.org/download/release/v24.22.1/SHASUMS256.txt). The command never guesses or downloads an asset. The caller must supply the intended release version and selected artifact facts.

The explicit build removes the previous local `node_modules/.factory-build-receipt.json` before compilation. It hashes the complete source, web, templates, package and lock files, TypeScript configuration, build and packaging scripts, installed compiler and type packages, and the running Node executable before compilation. After compilation and web copy, it requires the input snapshot to be unchanged and records the exact compiled output inventory and hashes. Packaging runs the current source release module using [Node's built-in TypeScript type stripping](https://nodejs.org/api/typescript.html), recalculates both sides of the receipt, and refuses missing, stale, extra, or changed output before creating a destination. It does not rebuild or install anything. This receipt proves local consistency against the observed build inputs; it is not an authenticated provenance statement from an independent builder. The selected external manifest digest remains the consumer trust binding. Concurrent writers to the source or toolchain during packaging are outside this local workflow's guarantee.

For `win32-x64`, the selection additionally requires `windowsHelper` with absolute `path`, exact `sha256`, and `qualificationRun: "39808257041"`. Packaging pins SHA256 `f46ba4a408f8618d5e186ce29cf47bdac3411b67356136d79da4a0ed0c35ec44`, the retained native x64 helper from that run, and verifies the selected binary before copying it. That run proved native compilation and temporary shortcut ownership tests. Visible delivery remains unverified. An ARM64 helper, a different hash, or an absent binary is refused until separately qualified and the pinned release contract is revised. macOS and Linux use the platform's existing system notification commands, so no helper binary is bundled for them. The Windows startup Git/TypeScript helper candidates remain unqualified and are not included.

The payload owns `dist/` compiled runtime plus web, `templates/`, a minimal ESM `package.json`, and the pinned Windows helper only on `win32-x64`. `dist/learning.js` is an ordinary importable runtime module for an explicit operator learning workflow. Templates use `@local/software-factory` only for TypeScript type imports; the release package does not install an authoring dependency environment. T15b/T16 must install and maintain that environment separately. No `node_modules` or development package metadata is copied into the payload.

`src/release.ts` exports the typed `ReleaseSelection`, `ReleaseManifest`, `packageRelease`, `validateReleaseSelection`, and `validateReleaseBundle` contract. The command prints `manifestSha256` in JSON. T15b must obtain that digest from its selected release descriptor and pass it as the required second argument to `validateReleaseBundle(absoluteBundleRoot, expectedManifestSha256)` before consuming any file. Validation checks the exact pinned Node/platform/helper facts, regular files, every file SHA256 and byte length, the complete schema-1 runtime inventory (every compiled JavaScript module, source map, and declaration, including `notifications.js`, `redaction.js`, and `workflow.d.ts`), web and templates, no unowned files or directories, no symlinks, safe portable paths, duplicates, and case-insensitive collisions. A future source module requires a deliberate update to the versioned inventory. Portable names follow the [Windows file naming rules](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file), including forbidden characters and superscript COM/LPT device names. The selected manifest digest is the external trust binding; a manifest inside the directory alone cannot authenticate itself.

The deterministic public command and validator tests use disposable source and destination trees. They cover complete sorted inventory, repeat verification, payload tamper and unowned content refusal, source symlinks, stale built web, missing or changed build receipts, source mutation during compilation, a self-consistent but incomplete consumer manifest, every Windows-reserved filename character and device name through the consumer validator on every host, source-packaging refusal for illegal names when the host filesystem can create them, manifest hash/traversal/duplicate refusal, exact version/platform/Node asset selection, missing/unqualified/changed Windows helper refusal, and --help execution from an actual built bundle.
