# Forward schema store qualification

This is the bounded T16a store operation. It does not publish an upgraded installation or mark a repository ready. The public `prepareForwardSchema(repository, selection, owner)` seam admits a sole typed upgrade claim, keeps the repository ready while the claim excludes other writers, then binds a verified consistent SQLite backup. `prepareMaintenanceHandoff` and `consumeMaintenanceHandoff` transfer the exact claim to a live staged controller and mark the repository incomplete. Each `advanceForwardSchema(handle)` call commits at most one fixed historical DDL transition with its checkpoint and event. The last call returns `v7` while the sole upgrade claim and incomplete repository remain. `inspectForwardSchema` is redacted and `resumeForwardSchema` requires matching original and target selection plus inspected operator clearance.

The supported database shapes are the actual v3, v4-base, v4-plus, v5, v6, and v7 `sqlite_schema` inventories frozen in `schema-forward.ts`. Normal `openRepositoryStore` still refuses old schemas without migration. The forward opener uses an existing-only `file:` URL with `mode=rw`, checks main-file identity and private mode, and refuses any bootstrap marker. The fixed schema signatures are tied to Node 24.22.1 and SQLite 3.53.4. Administrative claim, typed intent and start event commit before the backup; no domain row, DDL, installed file or authoring file changes before verified backup and staged handoff. The private backup helper runs in an owned foreground process group, uses SQLite's backup API from a separate read-only connection, and must exit with confirmed group closure. The operation keeps partial or uncertain backup targets rather than reusing them. An explicit prebind recovery rotates token and backup ID together, leaves the old evidence untouched, and creates a new absent target.

The backup lives under `factory/maintenance-backups/<operation-id>/<backup-id>/history.sqlite` with an operation-bound private receipt. The compact claim binds backup inode, full SHA-256, size, count digest, receipt identity and receipt SHA-256. Backup validation uses an immutable read-only SQLite connection so inspection does not create WAL sidecars. It checks full integrity and foreign keys, exact historical shape, repository and sole claim, and original release. A changed byte, new inode with identical bytes, link, extra entry, or changed receipt refuses before handoff and before every forward step.

Focused proof on pinned Node 24.22.1: `node --test test/forward-schema.test.mjs` passed 12/12, zero skips. Its disposable Git repositories use SQL captured from the historical source revisions, including linked run, worktree, invocation, operation, attempt, capture and capture-chunk rows. Six shape cases prove backup and one-step transitions to v7; the remaining cases cover admission collision, marker, unsupported/changed schema, linked store and WAL, bound backup and receipt tamper, exact token, known-live and wrong-selection recovery refusal, explicit partial-backup recovery, dashboard and runner exclusion, busy writer, corruption and foreign-key inconsistency. Existing controller 15/15, store 33/33, release 55/55, strict TypeScript and build also passed. The controlled stage and exit receipt prove the controller state contract, not a real installed upgrade or native Windows lifetime.

Windows forward writes are deliberately refused because private ACL and process-group closure are not qualified there. T16b must authenticate and bind an actual original installed runtime/ownership receipt, a new release and independent stage; publish the new files; validate the installed result; and atomically mark ready and release the claim. Historical v3-v6 SQL fixtures are store-transition evidence, not proof that an owned historical installation exists. Backup retention and cleanup are separate selected operations. No restore, downgrade, automatic replay, provider launch, notification send, or schema repair is performed here.
